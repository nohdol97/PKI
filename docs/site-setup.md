# 배포처 설정 안내

- 날짜: 2026-11-21 / 관련: [ownership.md](ownership.md), [ARCHITECTURE 9절 가정 표](ARCHITECTURE.md#9-가정-표), [ADR 0012](adr/0012-upstream-and-fork-ownership.md), 이슈 #37(R07)

이 문서는 제품을 실제 환경에 올리는 **배포처**가 따르는 안내다. 공용 저장소는 구조와 기본값만 갖고, 환경에 달린 값과 실행 검증은 배포처가 채운다. 이 문서에는 **실제 값을 적지 않는다.** 어떤 종류의 값이 필요한지만 적는다. 채운 값은 배포처 포크의 `site/config/`에만 두고 공용 저장소로 보내지 않는다([ownership.md 6절](ownership.md)).

낯선 말은 [ARCHITECTURE 0절](ARCHITECTURE.md#0-처음-나오는-말)에 풀이가 있다. `R02`·`R03`·`R04`는 배포처에서 실행하는 검증 작업(이슈 #11, #12, #13)이고 `A01`~`A22`는 아키텍처 문서의 가정 번호다.

## 1. 지금 상태

아래 설정 키는 V01(#16)이 구현한 이름이다(V01-T17이 구현과 맞췄다. 이름과 값의 형태는 잠정이며 바뀌면 이 문서를 함께 고친다). 검증 스크립트와 결과 기록 양식은 R02·R03·R04의 사외 준비물로 따로 들어온다.

**먼저 알아 둘 것**: 설치 파일로 묶은 실행본(배포 빌드)은 격리 검증을 통과해 목록에 등록된 CLI 조합만 실행한다. 공용 저장소의 목록은 비어 있으므로, S07을 끝내고 **다시 빌드하기 전**의 설치본은 Claude Code와 Codex CLI를 **전혀 실행하지 않는다.** 그동안 쓸 수 있는 LLM 경로는 API 키 Provider(S05)뿐이다.

## 2. 설정의 형태

값이 정해지는 때가 둘이다. **빌드할 때 정해지는 것**은 포크의 `site/config/`나 아래 표가 가리키는 코드에 두고 다시 빌드해야 바뀐다. 실행 중에 설정 화면이나 환경 변수로는 바꿀 수 없다. **실행 중 설정**은 앱의 설정 화면(설정 API)으로 바꾸며, 값은 데이터 디렉터리의 정본 DB(`settings` 표)에 남는다. 따로 읽는 설정 파일은 없다. 이름은 잠정이다.

### 빌드할 때 정해지는 것

| 자원(잠정 이름) | 필요한 값의 종류 | 공용 기본값 |
|---|---|---|
| 검증된 CLI 조합 목록(`providers/src/verified-cli-combinations.json`) | 격리 검증을 통과한 조합의 목록. 항목마다 `cli`(`claude-code` 또는 `codex`), `version`(**정확한 버전 하나**. 범위가 아니며 CLI가 알리는 문자열과 글자까지 같아야 한다), `os`(`win32`, `darwin`, `linux`), `profile`(인자 프로필의 이름. 목록에 넣는 것은 `claude-code/standard-2`처럼 `standard` 프로필이다), `model`(R02를 실행한 모델 이름 하나. 제품이 `--model`로 넘긴다. 비어 있거나 `-`로 시작하거나 공백이 들면 거부), `verifiedOn`(`YYYY-MM-DD`). 인자 프로필의 내용은 제품 코드(`providers/src/cli-profiles.ts`)에 고정되어 있고 여기서는 이름만 고른다. 제품 프로필이 어느 R02 프로필과 같은 인자인지는 그 파일에 적혀 있다(V01-T10). 그 R02 프로필의 결과로 이 이름을 적는다. 항목이 하나라도 틀리면 백엔드가 시작하지 않는다 | 빈 목록. 비어 있으면 배포 빌드는 CLI를 실행하지 않는다 |
| 빌드 종류 | 포크가 정하지 않는다. 설치 파일을 만드는 빌드는 언제나 배포 빌드다 | 배포 빌드 |
| 합성 목록 | 포크가 정하지 않는다. 공용 저장소의 합성 자료에서 만들어진다. 실제 수집기가 가져온 자료는 여기에 들어가지 않는다 | 공용 저장소의 합성 자료 |
| Embedding 모델의 revision과 파일 해시 | 포크가 다른 모델을 쓰기로 했을 때만 바꾼다. 바꾸면 홈의 내려받기 승인 문구(`apps/web/src/status-text.ts`의 `DOWNLOAD_APPROVAL`: 출처 호스트, 파일 수, 크기)도 함께 고친다. 사용자가 승인하는 내용이 그 문구이기 때문이다. 내려받기는 huggingface.co가 넘겨 주는 다른 호스트에서도 오므로 방화벽·프록시 허용 목록에 그 호스트까지 넣는다(S09) | 공용 저장소가 고정한 값 |
| 데이터 등급 목록 | 등급 이름의 목록(엄격하지 않은 것부터). 바꾸면 Broker의 등급 계산(`providers/src/broker.ts`의 `grade`)도 함께 바꾼다. 정책 버전에 들어가므로 바꾸면 모든 동의가 무효가 된다 | "합성"과 일반 등급 하나(`@pki/contracts`의 `DATA_CLASSES`) |
| 배포처 전송 규칙 | 규칙의 목록. 규칙마다 Provider, 작업 종류, 데이터 등급(각각 `*` 가능), 허용 또는 거부. 여기의 거부는 사용자의 동의로 뒤집히지 않고, 여기의 허용만으로는 동의를 대신하지 않는다. 구성 지점(`backend/src/composition.ts`의 `productEgress`)이 넘기는 값이며 설정 파일이나 설정 API로는 바꿀 수 없다. 하나라도 고치면 정책 버전이 바뀌어 모든 동의가 무효가 된다 | 빈 목록(`PUBLIC_SITE_RULES`). 사용자가 앱에서 등급을 골라 동의하면 그 Provider의 허용 규칙이 생긴다 |
| 묶을 Provider(`backend/src/composition.ts`의 `productProviders`) | 쓸 수 있게 둘 Provider 구현의 목록. CLI를 쓰지 않기로 했으면(S06) 여기서 CLI Provider 둘을 뺀다. 묶인 것만 설정 화면의 "기본 Provider"에 나오고, 설치되어 있지 않은 것은 "설치되어 있지 않음"으로 표시된다 | Claude Code, Codex CLI, OpenAI 호환 셋 |
| 접근 범위 정책 이름(`apps/desktop/src/layout.production.ts`의 `SCOPE_POLICY`) | 이 설치본이 쓸 접근 범위 규칙의 이름 하나: `default` 또는 `site`(S21). 규칙 자체는 이름이 아니라 코드(`backend/src/scope-policy.ts`)에 있다. 환경 변수 `PKI_SCOPE_POLICY`는 개발 실행에서만 듣고 설치본은 무시한다. 빈 이름이나 모르는 이름은 시작을 막는다(오타가 기본 규칙으로 조용히 떨어지지 않게 한다). 설정 화면에서 바꾸는 값이 아니다 | `default`(규칙 없음: 한 PC의 한 사용자). `site`는 공용 저장소에서 `배포처 후속` 알림과 함께 시작을 멈춘다 |
| 수집기 인스턴스(`backend/src/composition.ts`의 `productConnectors`) | 수집기 종류마다 인스턴스와 그 수집기가 요구하는 설정(S01~S04). 실행 중 설정이 아니며 설정 화면에서 더할 수 없다 | 종류마다 하나(`site-mail`, `site-messenger`, `site-wiki`), 모두 "미구현(배포처 후속)" |

### 실행 중 설정

"공용 기본값"은 배포처 값이 아니라 아무 설정 없이 로컬에서 도는 값이다.

| 설정(잠정 이름) | 필요한 값의 종류 | 공용 기본값 |
|---|---|---|
| `providers.openaiCompatible.baseUrl` | OpenAI 호환 API를 제공하는 **`https`** 주소 하나. 바꾸면 그 Provider에 대한 사용자의 동의가 무효가 된다 | 없음. 비어 있으면 이 Provider는 "미설정"이다 |
| `providers.openaiCompatible.model` | 그 엔드포인트에서 쓸 모델의 이름 | 없음 |
| API 키 | 설정 파일에 두지 않는다. 앱에서 입력하면 OS가 보호하는 키로 암호화되어 데이터 디렉터리의 `secrets.json`에 암호문으로만 남는다([ADR 0010](adr/0010-encryption-at-rest.md)). OS 보호를 쓸 수 없으면 저장되지 않고 그 Provider는 "사용 불가"다. 키는 입력할 때의 주소 호스트에 묶이므로 `baseUrl`의 호스트를 바꾸면 키를 다시 입력한다 | 없음 |
| `providers.default` | 연결 시험과 호출에 쓸 Provider 이름 하나(`claude-code`, `codex`, `openai-compatible`). 설정 화면의 "기본 Provider"가 이 값을 쓴다. 비어 있거나 묶이지 않은 이름이면 어느 Provider도 부르지 않으며, 설치된 CLI가 하나뿐이어도 저절로 고르지 않는다 | 없음 |
| `providers.cli.background` | `on` 또는 `off`(정확히 `on`일 때만 켬). 목록에 있는 조합의 백그라운드 자동 실행을 허용할지. 설정 화면의 "CLI 백그라운드 실행 허용"이 이 값을 쓴다. 가져오기 뒤의 추출도 백그라운드 실행이다. 홈의 Provider 행은 이 추출이 돌 수 있는지를 보이므로, 꺼져 있으면 목록에 있는 CLI도 "실행이 막힘(백그라운드 실행이 꺼져 있음)"으로 보인다(연결 시험은 사용자 호출이라 실행된다) | 끔 |

설정이 아닌 것:

- **Embedding 모델 준비**: 설정 값이 아니라 홈의 "Embedding 모델 준비"에서 보내는 준비 요청이다(`POST /api/embedding/prepare`. 로컬 팩 폴더의 절대 경로, 또는 확인 창에서 승인한 내려받기). 무엇을 준비했는지는 저장하지 않으므로 앱을 다시 켜면 "모델 없음"이고, 같은 요청이 설치된 파일을 네트워크 없이 해시 확인만으로 다시 올린다. 자동으로 내려받지 않는다(S09).
- **자동 업데이트 주소**: 아직 없다. 업데이트는 H02(#33)가 정하며 그때 이 표에 키를 더한다(S12).

## 배포처 설정 체크리스트

항목마다 무엇을 하는지, 어떤 종류의 값이 필요한지, 끝났다는 것을 무엇으로 확인하는지 적었다. 번호(`S01` 등)는 구현 spec의 비목표 항목과 일대일로 대응한다([V01](specs/2026-11-21-V01-vertical-skeleton.md) S01~S13, [V02](specs/2026-11-21-V02-vertical-slice.md) S14~S15, [I02-A](specs/2026-11-21-I02-document-normalization.md) S16~S17, [I01](specs/2026-11-21-I01-connector-sdk.md) S18, [I04](specs/2026-11-21-I04-invalidation.md) S21~S22).

### 수집

이 절과 아래 S18에서 말하는 `Connector` 규격은 SDK 규격 v2(`CONNECTOR_SDK_VERSION` = 2)이다. 수집기를 만드는 방법은 [connector-sdk.md](connector-sdk.md)에 있다.

- [ ] **S01 메일 수집기 구현.** `Connector` 규격을 구현해 `site-mail` 자리에 등록한다. 필요한 것: 메일 시스템에 접근하는 방법, 수집 범위(어느 편지함, 어느 기간). 확인: `packages/testkit`의 Connector 계약 테스트 통과, `site-mail` 실행 시 "미구현" 대신 변경분이 나온다.
- [ ] **S02 메신저 수집기 구현.** 같은 방식으로 `site-messenger`. 필요한 것: 메신저 시스템 접근 방법, 수집할 대화방의 범위, 스레드를 복원할 식별자. 확인: S01과 같다.
- [ ] **S03 Wiki 수집기 구현.** 같은 방식으로 `site-wiki`. 필요한 것: Wiki 시스템 접근 방법, 수집할 공간의 범위, 페이지 버전 정보. 확인: S01과 같다.
- [ ] **S04 수집기의 인증과 권한 매핑.** 각 수집기가 사용자 본인의 권한으로 인증하게 하고, 원본마다 access_scope(누가 볼 수 있는 자료인가)를 채운다. 수집기는 데이터 등급을 정하지 못한다. 등급은 제품이 access_scope에서 계산하며, 실제 수집기가 가져온 자료는 "합성"이 될 수 없다. 필요한 것: 인증 방식, 원본의 공개 범위를 알아내는 방법. 확인: 수집한 원본에 access_scope가 비어 있지 않고, 삭제되거나 권한이 철회된 원본에 대해 수집기가 그 사건을 낸다(제품은 그 원본의 내용을 지운다).
- [ ] **S18 실제 수집기로 SDK v2 계약 판정과 실제 동기화를 실행하고 기록.** 공용 저장소는 Connector 규격 v2를 지어낸 원 시스템(예시 수집기, 대본 수집기)으로만 증명했다. 실제 원 시스템을 상대로 규격을 지키는지는 포크의 수집기로만 확인할 수 있다. 수집기 작성법은 [connector-sdk.md](connector-sdk.md)다. 필요한 것: S01~S03 가운데 하나 이상의 실제 수집기, 그 시스템에서 합성 자료를 만들고 고치고 지울 수 있는 시험 계정(실제 업무 자료로 하지 않는다), 인스턴스 범위 파일(아래). 실행: ① 포크의 수집기 테스트에서 계약 묶음 `connectorContract`를 돌려 위반 코드가 하나도 없는 것을 확인한다(작성법 6장). 이 묶음은 지어낸 원 시스템으로 돌리므로 실제 확인은 ②③이다. ② 앱에서 그 인스턴스를 동기화한다(수동 동기화와 주기 동기화). ③ 아래 다섯 가지를 기록한다. 기록할 것: (가) 요청 한도: 원 시스템이 한도를 알리는 방식, 그것이 `ConnectorRateLimitError`의 `retryAfterMs`로 옮겨지는지, 동기화 결과에 `rate-limited`와 `retryAfterMs`가 남는지. (나) cursor 만료와 그 동안의 삭제: 만료를 `cursorExpired`로 알리는지, 재스캔 결과의 `rescanned`와 `deletionsMayBeMissed`, 만료된 동안 지워진 원본이 수집기의 `deletionsOnRescan` 선언대로 `delete`로 다시 알려지는지. (다) 대량 페이지: 한 번에 100개를 요청할 때의 소요 시간과 메모리, 한 번 읽는 데 가져갈 페이지 수의 상한 `maxPages`(기본 10,000쪽)가 모자라지 않는지, 첫 동기화가 제품의 작업 실행 시간 제한 `DEFAULT_RUN_TIMEOUT_MS`(기본 10분, 잠정)를 넘지 않는지. (라) `accessScope`와 `revision` 채우기: 레코드마다 비어 있지 않은 `accessScope`가 채워지는지, `revision`이 원 시스템에서 고칠 때마다 커지는지(정수 번호가 없으면 수정 시각의 밀리초). (마) 가져오기 인스턴스와 범위가 없는 원본의 등급 매핑: 가져온(`scope_claimed`) 원본과 `accessScope`가 없는 원본이 S08의 매핑에서 가장 엄격한 등급으로 가는지를 합성 자료로 확인한다.
  **인스턴스 범위 파일 `site/config/connector-scopes.json`.** 가져온 범위(사용자가 적은 값)가 인스턴스에 배포처가 정해 둔 범위보다 느슨한 등급을 얻지 못하게 하는 기준이다. 형식은 `{ "<인스턴스 ID>": ["범위", ...] | null }`이다. 범위는 비어 있지 않은 문자열이고 `null`은 알 수 없음이다. 이 파일은 빌드 자원이라 다시 빌드해야 바뀌고, 설정 API와 화면은 이 값을 쓰지도 보이지도 않는다. 공용 저장소는 이 파일을 갖지 않으며, 파일이 없거나 그 인스턴스가 없으면 알 수 없음이라 가장 엄격한 등급이다. 파일을 읽을 수 없거나 JSON 객체가 아니면 파일 전체를, 형식이 틀린 항목은 그 항목만 쓰지 않는다. 어느 경우에도 알 수 없음보다 넓어지지 않는다. 시작할 때 백엔드의 로그(표준 오류로 나간다. `providers/src/log.ts`)에 상태가 한 줄 남는다. 파일 없음은 `connector-scopes-absent`, 읽을 수 없음은 `connector-scopes-unreadable`, JSON 객체가 아님은 `connector-scopes-invalid`, 읽었지만 쓰지 않은 항목이 있음은 `connector-scopes-rejected`(그 수만 적힌다)다. 값은 정본의 `connector_instances.configured_scope`에 복사된다(시작할 때 모든 인스턴스 행, 인스턴스가 처음 등록될 때 그 행).
  **설치본에서 이 파일을 읽는 길은 만들지 않았다.** 지금 코드(`backend/src/connector-scopes.ts`)는 소스 트리의 `site/config/connector-scopes.json`을 모듈 위치 기준으로 읽으므로 소스에서 실행할 때만 효과가 있다. 묶은 설치본이 이 파일을 안에 묶는지 설치 자원으로 두는지는 정해지지 않았고, Windows 설치본에서 확인하지 않았다. 파일을 읽지 못하면 모든 인스턴스가 알 수 없음이라 닫힌 쪽이지만, 값을 채웠는데 설치본에서 효과가 없는 조용한 실패가 될 수 있다. **확인(설치본에서)**: 설치본을 시작해 ① 백엔드 로그에 위 네 코드 가운데 어느 것도 없는지 보고, ② 인스턴스를 한 번 동기화한 뒤 앱을 닫고 데이터 폴더의 정본 `pki.sqlite`를 읽기 전용으로 열어 `SELECT id, configured_scope FROM connector_instances`의 값이 파일의 값과 같은지 본다. 범위 값은 로그에 남지 않으므로 ②가 실제 증거이고, ①이 통과해도 ②가 `null`이면 읽히지 않은 것이다. 설치본에서 로그가 어디에 남는지도 확인하지 않았다. 확인한 결과(통과·실패)만 기록하고 범위 값은 공용 이슈에 올리지 않는다.

### LLM Provider와 외부 전송

- [ ] **S05 LLM Provider 구성.** 쓸 Provider를 고르고, OpenAI 호환 경로를 쓴다면 엔드포인트 주소와 모델 이름을 설정하고 키를 발급받아 앱에 입력한다. 필요한 것: 허용된 Provider의 목록, `https` 엔드포인트 주소, 모델 이름, 키 발급 절차. 확인: 앱의 설정 화면에서 그 Provider의 연결 시험이 성공한다(합성 자료 한 건의 구조화 응답이 스키마 검증을 통과, A06).
- [ ] **S06 구독 로그인 CLI 사용 허용 여부 확인.** 사용자의 구독 로그인으로 CLI를 제품이 호출해도 되는지를 벤더의 공식 조건과 배포처 정책으로 확인한다. "배포처에서 두 CLI를 쓸 수 있다"는 것은 지금까지 사용자의 진술뿐이고 문서 근거가 없다. 조사 문서는 벤더 문구를 "모호"로 판정했고 허용된다고 말하지 않는다([CLI Provider 조사 3절](research/2026-11-21-cli-provider-terms-and-isolation.md)). 필요한 것: 확인한 조건의 출처와 날짜. 확인: R02-C4에 허용 경로 또는 "미확인"이 기록된다. 허용되지 않으면 묶을 Provider(`productProviders`, 2절 빌드 표)에서 CLI를 빼고 S07을 하지 않는다(A01).
- [ ] **S07 CLI 격리 검증과 검증된 조합 등록.** R02의 절차대로 합성 악성 문서로 부정 테스트를 실행하고, 통과한 조합만 "검증된 CLI 조합 목록"에 넣은 뒤 **설치본을 다시 빌드**한다. 등록된 조합만 설치본에서 실행된다. 그 뒤 백그라운드 자동 실행을 켤지 따로 정한다. 필요한 것: 배포할 CLI의 정확한 버전, 검증한 OS, R02를 실행한 모델 이름(목록 항목의 `model`에 고정한다). R02의 `result.json`은 알려진 벤더 계열 밖의 모델 이름을 `h:<sha256 앞 12자>`로 적으므로, 목록의 `model`을 기록과 대조할 때는 그 이름의 해시를 비교한다. 확인: R02-C1~C3의 실행 기록. 등록하지 않은 버전으로는 설치본에서 사용자가 연결 시험을 눌러도 차단된다. 실행할 R02 프로필은 목록에 적을 제품 프로필과 같은 인자의 것이다. 그 대응은 `providers/src/cli-profiles.ts`의 `CLI_ARGUMENTS`가 프로필마다 `r02` 칸에 적는다(지금은 `claude-code/standard-2` → `claude-A-restricted-safe`, `codex/standard-2` → `codex-A-full`). R02의 판정은 그 실행의 **버전과 모델**에서만 유효하므로, R02에 `--model-claude`·`--model-codex`로 준 모델 이름을 목록 항목의 `model`에 그대로 적는다. 제품은 목록에 있는 조합을 그 모델로만 실행한다(`--model <model>`). R02는 제품이 찾는 것과 같은 실행 파일로 돌린다. Windows의 제품은 `.exe`만 찾으므로 npm이 까는 `.cmd`로 R02를 통과해도 제품은 그 CLI를 찾지 못한다(미검증). 프록시·사설 인증서 환경 변수(`HTTPS_PROXY`, `NO_PROXY`, `NODE_EXTRA_CA_CERTS` 등)는 제품이 CLI에 넘기지 않는다(잠정). R02를 `--pass-env`로 통과한 조합도 프록시가 필요하면 제품에서는 연결하지 못한다. **CLI가 버전을 올리면 그 CLI는 다시 막히므로**, 배포할 버전을 고정하고 버전을 올릴 때마다 다시 검증해 등록하고 빌드한다(A02~A05, A22).
- [ ] **S08 외부 전송 정책의 값.** 데이터 등급을 정하고 등급마다 어느 Provider에 보낼 수 있는지 규칙을 채운다. 필요한 것: 배포처의 데이터 분류 기준, 등급별 허용 Provider. 확인: 거부 규칙에 걸리는 합성 입력이 호출 없이 "전송 거부"로 남고, 사용자가 동의해도 그 거부가 유지되며, 허용 규칙에 걸리는 입력만 호출된다. **주의**: 규칙에는 목적지 칸이 없다. `openai-compatible`을 허용하면 사용자가 `providers.openaiCompatible.baseUrl`에 넣은 어느 `https` 호스트로 보내는 것이든 허용된다(사용자의 동의는 여전히 필요하다). 엔드포인트를 정해 두어야 한다면 `openai-compatible`을 거부하거나, 주소를 빌드 자원으로 바꾸거나, 규칙에 목적지 칸을 더한다(V01 spec "T08이 넘기는 것" 1항). **접근 범위를 등급으로 바꾸는 매핑(`ScopeGrading`)도 이 항목의 값이다.** 수집기가 채운 접근 범위는 Broker가 `ScopeGrading`(`providers/src/scope-grading.ts`)의 `grade`로 데이터 등급을 매긴다. 공용 기본(`publicScopeGrading`)은 모든 범위를 일반 등급 하나로 매긴다. 포크의 매핑은 **`strictest([])`와 `grade(null)`이 가장 엄격한 등급을 돌려주게** 해야 한다. 범위를 알 수 없는 원본(`null`), 인스턴스 범위(S18)가 없는 가져온 원본, 정책이 두 범위를 비교하지 못한 경우가 모두 `strictest([])`로 간다. Broker는 두 범위의 등급을 합칠 때 `strictest`의 답이 물어본 두 등급 가운데 하나인지 확인하고 아니면 요청을 거절한다(`scope-unjudged`). 매핑이 던지거나 허용된 등급(`SCOPE_CLASSES`) 밖의 값을 답해도 같다. **`synthetic`은 매핑이 낼 수 없는 등급이다**(합성 등급은 합성 목록과의 대조로만 붙는다). **자기 등급을 더하려면 한 곳만 바꾸어서는 안 된다.** `packages/contracts/src/provider.ts`의 `DATA_CLASSES`(덜 엄격한 쪽이 앞), `providers/src/scope-grading.ts`의 `SCOPE_CLASSES`, `providers/src/broker.ts`의 `asScopeClass`와 입력 전체를 합치는 `strictest(graded)`(지금은 합성이 아니면 일반으로 줄인다), 그 등급을 읽는 `providers/src/egress-policy.ts`의 전송 규칙과 `providers/src/execution-gate.ts`의 실행 조건, 그리고 포크의 `ScopeGrading`을 함께 바꾼다. 하나라도 빠지면 그 등급은 `scope-unjudged` 거절이 되거나 일반으로 줄어든다(닫힌 쪽이다). 매핑을 끼우는 자리는 `backend/src/composition.ts`의 `productCalls`가 쓰는 `publicScopeGrading`이다(설정 이름으로 고르는 장치는 없다). 포크의 매핑은 흉내(대역)로만 시험했다. 가져온 범위가 그 매핑에서 느슨해지지 않는지는 S18이 확인한다.

### Embedding

- [ ] **S09 Embedding 모델 반입.** 외부에서 내려받을 수 있는지 확인하고, 안 되면 모델 파일을 내부로 반입해 로컬 팩으로 둔다. 필요한 것: 외부 모델 저장소 접근 허용 여부, 반입한 파일을 둘 위치, 모델 라이선스 확인. 확인: 반입한 파일의 해시가 제품이 고정한 값과 맞아 앱의 embedding 상태가 "준비됨"이 되고, 합성 문장의 embedding 왕복이 통과한다. 속도와 메모리는 R03-C3의 기준으로 잰다(A11, A12).

### 설치와 운영

- [ ] **S10 Windows 11 설치본 검증.** 깨끗한 Windows 11에서 Node·Python·Docker·DB 서버를 따로 설치하지 않고 설치·실행·제거한다. 필요한 것: 깨끗한 Windows 11 시험 환경. 확인: R04-C1의 실행 기록(A07, A13, A18). 설치 파일의 입력은 Windows에서 `pnpm --filter @pki/desktop build`로 만든 `apps/desktop/dist/app/`이다(네이티브 모듈은 빌드한 PC의 것만 들어간다). Electron fuses는 패키저 설정에서 켠다. 목록은 [V01 spec "T15가 넘기는 것" 9항](specs/2026-11-21-V01-vertical-skeleton.md)(잠정).
- [ ] **S11 저장 데이터 보호 확인.** 제품을 쓸 PC에 OS 디스크 암호화가 적용되는지, 앱이 OS 자격 증명 저장소를 쓸 수 있는지, 앱의 데이터 디렉터리가 다른 PC로 따라다니지 않는 위치인지 확인한다. 필요한 것: PC 보안 정책의 해당 항목. 확인: 앱에 API 키를 저장했다가 재시작 뒤 다시 쓸 수 있고(로밍 프로필 동기화 뒤에도. ADR 0010 "지켜볼 것"), 그 키의 평문이 앱의 어떤 파일에도 남아 있지 않다(`secrets.json`에는 암호문만). **디스크 암호화가 확인되지 않은 PC에는 실제 업무 데이터를 넣지 않는다**([ADR 0010](adr/0010-encryption-at-rest.md), A16, A19).
- [ ] **S12 서명, 배포 채널, 업데이트.** 설치 파일과 그 안의 네이티브 모듈을 무엇으로 서명할지, 사용자에게 어떻게 배포할지, 업데이트를 어디서 받게 할지 정한다. 필요한 것: 서명 주체, 내부 배포 방법, 업데이트를 둘 주소(없으면 자동 업데이트를 끈다). 확인: R04-C3의 기록. 설치와 실행에서 Windows의 차단 동작을 관찰해 적는다. 자동 업데이트를 실제로 돌려 보는 확인은 R04의 기준에 없으며 H02(#33)에서 한다(A14, A15).
- [ ] **S13 엔진과 저장소의 실행 비교.** R03의 절차대로 엔진 후보와 저장소를 합성 입력으로 실행해 비교한다. 벡터 색인의 실제 구현 후보(sqlite-vec)가 Windows에서 로드되는지, 정본 SQLite가 갑작스러운 종료를 견디는지도 여기서 확인한다. Phase 1의 제품에는 벡터 색인 구현이 들어 있지 않다. 필요한 것: 실행 환경과 R05가 고정한 측정 기준. 확인: R03-C1~C4의 실행 기록. 결과로 [ADR 0002](adr/0002-authority-in-product-records.md), [0003](adr/0003-phase1-without-engine.md), [0004](adr/0004-embedded-storage.md), [0011](adr/0011-sidecar-language.md), [0013](adr/0013-failure-recovery.md)을 R07에서 확정하거나 고친다(A08, A09, A10, A20).

### 수직 흐름

- [ ] **S14 수직 흐름을 설치본과 실제 Provider로 실행.** V02의 흐름(합성 출처 3개 → 일정 위험 Insight → 근거 화면)을 Windows 설치본에서 실제 Provider로 실행한다. 가져오기 뒤의 추출은 백그라운드 실행이므로 Provider는 둘 중 하나여야 한다: API 키 Provider(S05), 또는 목록에 등록되어 있고(S07) 백그라운드 설정을 켠 CLI. 필요한 것: S10이 끝난 환경(R04의 설치 파일로 설치하고 데이터 폴더 `%LOCALAPPDATA%\PKI`가 빈 Windows 11), 기본 Provider로 고를 실제 Provider와 그 버전, Python 3.8 이상. 실행: [verification/v02-site-flow/RUNBOOK.md](../verification/v02-site-flow/RUNBOOK.md)의 순서대로 설정을 `v02-result\config.json`(gitignore됨)에 두고 `python verification\v02-site-flow\run.py preflight --config v02-result\config.json` → `prepare --config v02-result\config.json --out v02-result` → 사람이 화면 걸음(앱은 설치된 exe로만 켬, 가져오기, "추론" 표지, 근거 3개, 재입력, 재시작) → 앱을 닫고 `record --config v02-result\config.json --out v02-result --observed …`(관찰 다섯). 같은 커밋의 test double E2E 기록은 RUNBOOK 6절의 `summarize`로 짝짓는다. Provider가 test double이거나 Windows 설치본이 아니면 실행기는 `배포처 후속`으로 시작하는 알림을 내고 3으로 끝난다(V02-H2). 확인: `record`가 `V02-C4:site-flow PASS`를 내고, 붙이는 결과(결과 폴더 `v02-result`의 `result.md`)에 Provider 종류 `real`, Provider id와 버전, 앱 버전, 인용문 대조에서 버린 수(`dropped_quotes`)가 적힌다. 그 결과를 이슈 #17에 붙이고 `v02-result/raw/`는 붙이지 않는다(V02-C4, A21).

### 삭제와 접근 범위

이 절의 두 항목은 [I04 spec](specs/2026-11-21-I04-invalidation.md)의 배포처 후속 항목이다. 용어: **접근 범위(access_scope)**는 "원 시스템에서 누가 이 자료를 볼 수 있는가"를 나타내는 값이고, 수집기가 원본마다 채운다. **tombstone**은 "이 원본은 지웠다"는 내용 없는 표시이고, 지운 자료가 재수집이나 백업 복원으로 되살아나는 것을 막는다. **카나리**는 시험 자료에 일부러 넣는 흔적 없는 단어이며, 지운 뒤에 그 단어가 어느 파일에도 남지 않았는지 찾아 "정말 지워졌다"를 확인하는 데 쓴다.

- [ ] **S21 접근 범위 규칙(`ScopePolicy`)의 값과 구현.** 제품은 파생물(Insight, 연결 후보처럼 원본에서 만들어진 것)의 접근 범위를 저장하지 않고, 그것이 기댄 원본들(그 목록을 **계보**라 부른다)의 범위에서 그때그때 계산한다. 어떤 범위가 다른 범위보다 엄격한지, 서로 다른 범위의 자료를 한 항목이나 한 Insight로 묶어도 되는지, 어떤 용도(`display`, `search`, `notify`, `answer`)로 보여 줘도 되는지는 **규칙 하나**(`storage/src/derivatives.ts`의 `ScopePolicy`)가 정한다. 공용 기본 규칙(`storage/src/scope-policy.ts`)은 한 PC의 한 사용자를 전제로 아무것도 거부하지 않는다(묶기와 허용은 언제나 참). 배포처는 조직의 권한 모델에 맞는 규칙을 구현한다. 이 항목이 끝나기 전에는 `site` 규칙을 쓸 수 없고, 접근 범위가 다른 자료가 한 Insight에 섞일 수 있다. 필요한 것: 수집기(S04)가 채우는 범위 값의 형태(`string[]`, 모름은 `null`)와 그 값의 엄격함 순서, 묶어도 되는 조합, 용도별 허용 기준. **구현 방법**: ① 포크가 `ScopePolicy`의 네 함수를 구현한다. `compare(a, b)`는 `stricter`·`equal`·`looser`·`incomparable` 중 하나를 돌려주고(증명되지 않으면 `incomparable`), `strictest(scopes)`는 가장 엄격한 범위 **또는** 비교할 수 없는 범위들의 묶음(`{ incomparable }`)을 돌려주며, `combinable(scopes)`와 `allows(scopes, purpose)`는 참·거짓이다. 기본 규칙처럼 `null`(모름)은 어떤 값보다 엄격하게 둔다. 제품은 `combinable`·`allows`의 답이 **정확히 `true`가 아니면 거부**로 읽는다(`combinable`이 오류를 던져도 거부, `allows`가 오류를 던지면 그 읽기 호출이 실패해 행을 보이지 않는 쪽으로 닫는다). **규칙을 구현하는 쪽의 의무**: 제품은 파생물이 기댄 원본들의 서로 다른 범위를 **한 번의 호출에 통째로** 넘길 뿐 범위마다 따로 묻지 않는다. 그러므로 "그 가운데 하나라도 허용되지 않으면 전체를 거부한다"는 제품이 대신 해 주는 동작이 아니라 규칙이 지켜야 할 의무다. 합쳐진 자료가 가장 제한적인 원본보다 더 넓게 보이면 안 되기 때문이다. 계보가 빈 파생물은 범위 목록 `[]`로 두 함수에 오므로 `[]`를 어떻게 다룰지도 정해야 한다. ② `backend/src/scope-policy.ts`의 `productScopePolicy`에서 `site` 이름이 그 규칙을 돌려주게 한다(공용 저장소에서는 `미구현, 배포처 후속` 오류로 시작을 멈추는 자리다). ③ `apps/desktop/src/layout.production.ts`의 `SCOPE_POLICY`를 `site`로 바꾸고 **다시 빌드한다**. 이 값은 빌드할 때 정해지며(2절 빌드 표) 설치본은 환경 변수 `PKI_SCOPE_POLICY`를 무시한다. ④ 포크가 **읽기 경로를 더하면**(예: 배포처 전용 조회 API) 그 응답이 파생물을 내보내기 직전에 `backend/src/read-gate.ts`의 `createReadGate`를 거치게 한다. 지금 거치는 종류는 원본(`source`)·Insight(`insight`)·근거(`evidence`)이고, 사실·관계·항목을 내보내는 경로는 그 종류(`fact`, `relation`, `item`)로 거치게 한다. 그리고 `backend/src/boot.read-gate.test.ts`에 그 경로의 경우를 더한다. 그렇지 않으면 그 경로에는 이 규칙의 `allows`와 tombstone 가림이 적용되지 않는다. **비용 경고**: 규칙이 계속 거부하는 후보는 추출할 때마다 기록(`scope_policy_drops`)을 남기고, 원본의 접근 범위가 바뀔 때마다(좁아지든 넓어지든) 그런 기록이 있는 원본이 **모두 다시 추출**된다(원본마다 Provider 호출 한 번). 거부를 많이 내는 규칙은 범위가 바뀔 때 Provider 호출과 시간이 늘어난다. 다시 추출하는 도중 범위가 또 넓어지면 새 재추출은 등록되지 않고 다음 범위 변경 때까지 기다린다(그 재추출의 후보는 이전 범위로 골라졌다). 접근 범위 변경은 수집기의 범위 변경(`scope-change`)이나 JSONL 가져오기의 `revoke` 줄이 만들고, 내용을 지우지 않는 `scope-changed` 전파가 된다(삭제가 아니다). 한 추출에서 규칙이 거부하는 조합이 생기면 그 Insight 규칙 항목이 통째로 거부되어 그 추출의 Insight 재계산이 건너뛰어지고, 다음 변경(범위 변경의 재추출 포함)에서 맞춰진다. **외부 전송 등급과의 연결**: Broker는 원본의 접근 범위를 `scopeClass`(`providers/src/broker.ts`)에서 등급으로 바꾼다. 정책과 범위→등급 매핑 `ScopeGrading`(`providers/src/scope-grading.ts`, 공용 기본 `publicScopeGrading`은 모든 범위를 일반으로 매긴다)은 `BrokerDeps.scope`로 들어오고 `backend/src/composition.ts`의 `productCalls`가 잇는다. 가져온 범위(청구)는 인스턴스 범위와 정책의 `compare`로 견주어 그 범위의 등급보다 느슨해지지 않는다(I01-R15). 배포처는 S08에서 이 매핑을 끼운다. 매핑은 합성 등급을 낼 수 없고 허용된 등급(`SCOPE_CLASSES`)만 답해야 하며, 등급을 더하려면 바꿀 자리가 여럿이다(I01 spec "T06이 넘기는 것" 10③. 그 문구는 I01-T10의 몫). **확인**(두 가지가 서로 다른 장치를 본다): (가) `allows`: 합성 범위 쌍으로 포크가 쓴 규칙의 네 함수를 시험하는 자체 테스트(같은 범위, `null`, 비교할 수 없는 쌍, 거부되는 조합과 용도)가 통과하고, `SCOPE_POLICY`를 `site`로 둔 설치본이 알림 없이 시작하며, `allows`가 거부하는 범위의 합성 원본이 그 용도(예: `search`)의 검색·목록에서 사라지고 허용되는 원본은 그대로 보인다. 이 거부는 읽을 때의 판정이라 **기록을 남기지 않는다**(아래 수에 잡히지 않는다). (나) `combinable`: 묶을 수 없는 두 범위의 합성 원본에서 나온 후보나 Insight가 만들어지지 않고, 활동 화면의 "범위 정책으로 빠진 항목 N건"(`apps/web/src/job-text.ts`의 `invalidationText`, 상태 API `invalidations.scopePolicyDrops`)의 N이 오른다. 공용 저장소의 시험(`backend/src/scope-policy.test.ts`)은 기본 규칙과 `site` 자리의 거부만 증명한다. 배포처 규칙의 동작은 증명하지 않는다.
- [ ] **S22 설치본에서 실제 수집기의 삭제·권한 상실로 무효화와 파일 소거를 실행하고 기록.** 사용자가 원본을 지우거나(출처 삭제) 원 시스템에서 볼 권한을 잃으면(권한 상실) 제품은 tombstone을 쓰고, 그 원본에서 나온 사실·Insight·키워드 색인·엔진 투영을 지우고, 데이터 폴더의 파일에서도 내용이 사라지게 한다(`secure_delete`, 정리 작업). 공용 저장소는 이것을 합성 수집기와 개발 OS에서 증명했고, **실제 수집기가 내는 사건의 순서와 Windows 설치본의 파일 바이트는 증명하지 못했다.** 그것을 확인하는 것이 이 항목이다. 필요한 것: S01~S04 가운데 하나 이상의 실제 수집기, 그 시스템에서 합성 자료를 만들고 지우고 권한을 뺄 수 있는 시험 계정(실제 업무 자료로 하지 않는다), S10이 끝난 환경(R04 설치 파일로 설치하고 데이터 폴더 `%LOCALAPPDATA%\PKI`가 빈 Windows 11), Electron userData 폴더의 경로(실행기 설정의 `userDataDir`, 필수), 엔진·벡터 색인을 실제 구현으로 묶었다면 그 저장 위치(`extraScanDirs`). 실행: [verification/v02-site-flow/RUNBOOK.md](../verification/v02-site-flow/RUNBOOK.md) 8절의 순서대로 `python verification\v02-site-flow\run.py delete-scenario prepare|record`를 실행한다. `prepare`가 합성 카나리 세 개를 만들고(하나는 출처 삭제로, 하나는 권한 상실로 지우고 하나는 남겨 둘 원본에 넣는다), 사람이 수집기로 가져오기·삭제·권한 회수를 하고 앱을 닫은 뒤 `record`가 ① 정본 DB의 무효화 기록을 읽기 전용으로 세고(출처 삭제 1, 권한 상실 1, 화면 삭제 0이어야 한다) ② **세 곳의 모든 파일**에서 카나리를 찾고 ③ 키워드 색인의 단어 목록(SQLite `fts5vocab`, 읽기 전용)에 지운 카나리가 없는지 묻는다. **찾는 곳**: 데이터 폴더 `%LOCALAPPDATA%\PKI`(`-journal`·`-wal`·`-shm` 포함. 위치는 `storage/src/data-directory.ts`), Electron의 userData 폴더, 설정의 `extraScanDirs`. userData(Chromium 저장소: 캐시, Local Storage 등)는 **데이터 폴더 밖**이다. 데이터 폴더는 Electron의 userData와 일부러 따로 정했고(그 파일의 주석), `apps/desktop`은 userData 위치를 바꾸지 않으므로 Windows에서는 로밍 `%APPDATA%` 아래에 앱 이름으로 만들어진다. 이름은 패키지 이름 `pki-desktop`(`apps/desktop/build/build.ts`)에서 오지만 R04의 패키저가 다른 이름을 줄 수 있어 **설치본에서 확인된 값이 아니다.** 그래서 실행기는 경로를 추측하지 않고 설정의 `userDataDir`를 필수로 받으며 없으면 `preflight`가 설정 오류로 멈춘다. **찾지 않는 곳**: 이 세 곳 밖의 모든 것(OS 백업·볼륨 스냅샷, 임시 폴더, 크래시 덤프, 페이지 파일, Provider 쪽 보관은 S11, S05·S08에서 따로). 찾는 방식: 카나리 단어의 **끝 12글자**를 대소문자 구분 없이 ASCII, UTF-16LE, UTF-16BE로 찾는다. 끝만 찾는 까닭은 SQLite FTS5가 앞 단어와 앞부분이 같은 단어를 뒤쪽 조각만으로 저장하기 때문이다. 이것은 `@pki/testkit`의 `findCanaries`(`packages/testkit/src/canary-files.ts`: 쓴 그대로와 소문자만 찾는다)와 **다르다**. 읽을 수 없는 폴더나 파일이 하나라도 있으면(개수만 기록) 통과로 판정하지 않는다. 이 공용 저장소에는 실제 수집기가 없어 이 시나리오는 Windows 설치본이 아닌 곳에서 `배포처 후속`으로 시작하는 알림을 내고 0이 아닌 값으로 끝난다(`미구현, 배포처 후속`). 어떤 환경에서도 mock 실행을 검증으로 기록하지 않는다. 기록에는 OS, 앱 버전, 수집기 종류, 종류별 지운 수, 카나리 발견 수(파일 쪽과 색인 쪽, 둘 다 0이어야 한다), 읽을 수 없던 경로 수, 남겨 둔 원본의 카나리가 파일과 색인 양쪽에서 찾아졌는지(찾기가 카나리를 볼 수 있다는 증거)가 든다. **어떤 사건이 삭제인가**: 출처 삭제는 수집기의 `delete` 변경(JSONL 가져오기 `POST /api/imports`의 `delete` 줄)이고 tombstone 사유 `source-deleted`가 된다. 권한 상실은 `access-revoked` 변경(JSONL의 `access-revoked` 줄)이고 사유 `access-revoked`가 된다. 둘이 지우기를 일으킨다. 같은 JSONL의 `revoke` 줄은 내용을 그대로 두고 범위만 좁히는 범위 변경이므로 **삭제로 검증하지 않는다**(지운 수에 잡히지 않아 FAIL이 된다). 파일 수집기는 다시 가져올 때 빠진 줄을 삭제로 치지 않는다(`deletionsOnRescan: false`): 삭제는 명시한 줄이어야 한다. 실제 수집기가 이 사건을 어떤 순서로 내는지가 이 항목이 확인할 것이다. **알아 둘 것**: ① 지운 원본의 외부 식별자는 키 있는 해시로 바뀌어 남고 그 키는 정본 DB의 표(`identity_key`)에 있다. 시작할 때 키 행이 없는데 해시된 원본이 남아 있으면 시작을 거부한다(새 키를 몰래 만들지 않는다. `storage/src/identity.ts`). **그러나 정본 DB 파일 전체를 잃으면 그렇지 않다.** 그 설치본은 새 키로 빈 DB를 만들어 정상 시작하고 **지난 삭제를 모두 잊는다**: 지운 자료가 수집기에서 다시 오면 다시 들어온다. tombstone 장부(I04-T10)는 이 위험을 줄이려는 것이지만 아직 이 저장소에 합쳐지지 않았으므로 지금은 보호가 없다. 배포처는 정본 DB를 백업하고 복원하는 절차를 갖춰야 하며, 복원본이 삭제 이전 상태이면 지운 자료가 되살아난다. 장부가 합쳐지면 이 문단과 이 시나리오의 찾는 곳을 고친다(spec "T11이 넘기는 것"에 기록한 의무). ② tombstone 자체는 지우지 않고 남긴다(내용이 없고, 지우면 재수집이나 백업 복원이 지운 자료를 되살린다). 지운 원본의 모든 version은 그 tombstone이 덮으며 함께 지워진다. ③ 이 시나리오는 위 세 곳만 본다. 확인: `record`가 `I04-C3:delete-scenario PASS`를 내고, 붙이는 결과(결과 폴더 `v02-result`의 `result.md`)에 위 기록이 적힌다. 지운 카나리가 한 파일에서라도 찾아지면 `FAIL`이며 그 파일 종류(브라우저 저장소, 엔진 색인 등)를 배포처 안에서 찾아 공용 저장소에는 합성 재현만 알린다([ownership.md 5절](ownership.md)). userData에서 찾아지면 제품 결함이거나 H03의 기준에 넣을 항목이다(spec "남는 위험" 표).
