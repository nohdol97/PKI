# 배포처 설정 안내

- 날짜: 2026-11-21 / 관련: [ownership.md](ownership.md), [ARCHITECTURE 9절 가정 표](ARCHITECTURE.md#9-가정-표), [ADR 0012](adr/0012-upstream-and-fork-ownership.md), 이슈 #37(R07)

이 문서는 제품을 실제 환경에 올리는 **배포처**가 따르는 안내다. 공용 저장소는 구조와 기본값만 갖고, 환경에 달린 값과 실행 검증은 배포처가 채운다. 이 문서에는 **실제 값을 적지 않는다.** 어떤 종류의 값이 필요한지만 적는다. 채운 값은 배포처 포크의 `site/config/`에만 두고 공용 저장소로 보내지 않는다([ownership.md 6절](ownership.md)).

낯선 말은 [ARCHITECTURE 0절](ARCHITECTURE.md#0-처음-나오는-말)에 풀이가 있다. `R02`·`R03`·`R04`는 배포처에서 실행하는 검증 작업(이슈 #11, #12, #13)이고 `A01`~`A22`는 아키텍처 문서의 가정 번호다.

## 1. 지금 상태

아래 설정 키는 V01(#16)이 구현한 이름이다(V01-T17이 구현과 맞췄다. 이름과 값의 형태는 잠정이며 바뀌면 이 문서를 함께 고친다). 검증 스크립트와 결과 기록 양식은 R02·R03·R04의 사외 준비물로 따로 들어온다.

**먼저 알아 둘 것**: 설치 파일로 묶은 실행본(배포 빌드)은 격리 검증을 통과해 목록에 등록된 CLI 조합만 실행한다. 공용 저장소의 목록은 비어 있으므로, S07을 끝내고 **다시 빌드하기 전**의 설치본은 Claude Code와 Codex CLI를 **전혀 실행하지 않는다.** 그동안 쓸 수 있는 LLM 경로는 API 키 Provider(S05)뿐이다.

## 2. 설정의 형태

값이 정해지는 때가 둘이다. **빌드할 때 정해지는 것**은 포크의 `site/config/`나 아래 표가 가리키는 코드에 두고 다시 빌드해야 바뀐다. 실행 중에 설정 화면이나 환경 변수로는 바꿀 수 없다. **실행 중 설정**은 앱의 설정 화면(설정 API)으로 바꾸며, 값은 데이터 디렉터리의 정본 DB(`settings` 표)에 남는다. 따로 읽는 설정 파일은 없다. 이름은 잠정이다.

### 빌드할 때 정해지는 것

| 자원(잠정 이름) | 필요한 값의 종류 | 공용 기본값 |
|---|---|---|
| 검증된 CLI 조합 목록(`providers/src/verified-cli-combinations.json`) | 격리 검증을 통과한 조합의 목록. 항목마다 `cli`(`claude-code` 또는 `codex`), `version`(**정확한 버전 하나**. 범위가 아니며 CLI가 알리는 문자열과 글자까지 같아야 한다), `os`(`win32`, `darwin`, `linux`), `profile`(인자 프로필의 이름. 목록에 넣는 것은 `claude-code/standard-2`처럼 `standard` 프로필이다), `model`(R02를 실행한 모델 이름 하나. 제품이 `--model`로 넘긴다. 비어 있거나 `-`로 시작하거나 공백이 들면 거부), `verifiedOn`(`YYYY-MM-DD`). 인자 프로필의 내용은 제품 코드(`providers/src/cli-profiles.ts`)에 고정되어 있고 여기서는 이름만 고른다. 제품 프로필이 어느 R02 프로필과 같은 인자인지는 그 파일에 적혀 있다(V01-T10). 그 R02 프로필의 결과로 이 이름을 적는다. 항목이 하나라도 틀리면 백엔드가 시작하지 않는다 | 빈 목록. 비어 있으면 배포 빌드는 CLI를 실행하지 않는다 |
| 빌드 종류 | 포크가 정하지 않는다. 설치 파일을 만드는 빌드는 언제나 배포 빌드다 | 배포 빌드 |
| 합성 목록 | 포크가 정하지 않는다. 공용 저장소의 합성 자료에서 만들어진다. 실제 수집기가 가져온 자료는 여기에 들어가지 않는다 | 공용 저장소의 합성 자료 |
| Embedding 모델의 revision과 파일 해시 | 포크가 다른 모델을 쓰기로 했을 때만 바꾼다. 바꾸면 홈의 내려받기 승인 문구(`apps/web/src/status-text.ts`의 `DOWNLOAD_APPROVAL`: 출처 호스트, 파일 수, 크기)도 함께 고친다. 사용자가 승인하는 내용이 그 문구이기 때문이다. 내려받기는 huggingface.co가 넘겨 주는 다른 호스트에서도 오므로 방화벽·프록시 허용 목록에 그 호스트까지 넣는다(S09) | 공용 저장소가 고정한 값 |
| 데이터 등급 목록 | 등급 이름의 목록(엄격하지 않은 것부터). 바꾸면 Broker의 등급 계산(`providers/src/broker.ts`의 `grade`)도 함께 바꾼다. 정책 버전에 들어가므로 바꾸면 모든 동의가 무효가 된다 | "합성"과 일반 등급 하나(`@pki/contracts`의 `DATA_CLASSES`) |
| 배포처 전송 규칙 | 규칙의 목록. 규칙마다 Provider, 작업 종류, 데이터 등급(각각 `*` 가능), 허용 또는 거부. 여기의 거부는 사용자의 동의로 뒤집히지 않고, 여기의 허용만으로는 동의를 대신하지 않는다. 구성 지점(`backend/src/composition.ts`의 `productEgress`)이 넘기는 값이며 설정 파일이나 설정 API로는 바꿀 수 없다. 하나라도 고치면 정책 버전이 바뀌어 모든 동의가 무효가 된다 | 빈 목록(`PUBLIC_SITE_RULES`). 사용자가 앱에서 등급을 골라 동의하면 그 Provider의 허용 규칙이 생긴다 |
| 묶을 Provider(`backend/src/composition.ts`의 `productProviders`) | 쓸 수 있게 둘 Provider 구현의 목록. CLI를 쓰지 않기로 했으면(S06) 여기서 CLI Provider 둘을 뺀다. 묶인 것만 설정 화면의 "기본 Provider"에 나오고, 설치되어 있지 않은 것은 "설치되어 있지 않음"으로 표시된다 | Claude Code, Codex CLI, OpenAI 호환 셋 |
| 접근 범위 정책(포크 조립 패키지 `site/composition`의 등록 `registration`의 `scopePolicy` 필드) | 이 설치본이 쓸 접근 범위 규칙 하나(S21). 등록에 규칙을 넣으면 설치본은 언제나 그 규칙을 쓰고, 넣지 않으면 공용 기본 규칙을 쓴다. 이름으로 고르는 스위치는 없다: 설치본은 `--scope-policy` 인자도 환경 변수 `PKI_SCOPE_POLICY`도 받지 않고, 둘 다 개발 실행에서만 듣는다. 설정 화면에서 바꾸는 값이 아니다. 필드의 모양은 `backend/src/site-registration.ts`의 `SiteRegistration`이다 | 규칙을 등록하지 않으면 공용 기본 규칙(규칙 없음: 한 PC의 한 사용자). 개발 실행에서 이름 `site`를 주면 등록에 규칙이 없는 공용 저장소는 `배포처 후속` 알림과 함께 시작을 멈춘다 |
| 수집기 종류와 인스턴스(포크 등록 `registration`의 `connectorKinds`와 `connectorInstances`) | 종류마다 수집기를 새로 만드는 함수와 인스턴스, 그 수집기가 요구하는 설정(S01~S04). 포크가 `site/composition`의 등록에 적는다. 인스턴스는 그 등록이 등록한 종류(자리표시 이름을 대체한 것 포함)의 것만 만들 수 있다. 공용 종류의 이름은 등록되지 않고(그 항목만 빠진다), 공용 종류의 인스턴스나 공용 인스턴스의 ID를 적은 등록은 시작하지 못한다. 실행 중 설정이 아니며 설정 화면에서 더할 수 없다 | 등록이 없으면 `productConnectors`가 주는 것: 종류마다 하나(`site-mail`, `site-messenger`, `site-wiki`), 모두 "미구현(배포처 후속)" |
| 인스턴스 범위(포크 등록 `registration`의 `connectorScopes` 필드. 값은 `site/config/connector-scopes.json`) | 수집기 인스턴스마다의 접근 범위(S18). 포크의 등록이 그 파일을 정적으로 가져와 이 필드에 넘기고, 빌드가 백엔드 묶음에 넣는다. 파일은 `site/config/`에만 둔다(S30). 다시 빌드해야 바뀐다 | 없음. 등록에 값이 없으면 모든 인스턴스가 알 수 없음이고 가장 엄격한 등급이다 |

### 실행 중 설정

"공용 기본값"은 배포처 값이 아니라 아무 설정 없이 로컬에서 도는 값이다.

| 설정(잠정 이름) | 필요한 값의 종류 | 공용 기본값 |
|---|---|---|
| `providers.openaiCompatible.baseUrl` | OpenAI 호환 API를 제공하는 **`https`** 주소 하나. 바꾸면 그 Provider에 대한 사용자의 동의가 무효가 된다 | 없음. 비어 있으면 이 Provider는 "미설정"이다 |
| `providers.openaiCompatible.model` | 그 엔드포인트에서 쓸 모델의 이름 | 없음 |
| API 키 | 설정 파일에 두지 않는다. 앱에서 입력하면 OS가 보호하는 키로 암호화되어 데이터 디렉터리의 `secrets.json`에 암호문으로만 남는다([ADR 0010](adr/0010-encryption-at-rest.md)). OS 보호를 쓸 수 없으면 저장되지 않고 그 Provider는 "사용 불가"다. 키는 입력할 때의 주소 호스트에 묶이므로 `baseUrl`의 호스트를 바꾸면 키를 다시 입력한다 | 없음 |
| 수집기 자격 증명(수집기 인스턴스마다의 칸. 칸의 이름은 포크 등록의 인스턴스 정의 `credentials`에 적는다) | 수집기가 원 시스템에 낼 비밀 값(API 토큰, 앱 암호, 클라이언트 비밀 값) 한 줄, 8192자 이하. 설정 파일에 두지 않으며 등록의 `config`에도 적지 않는다. 앱의 출처 화면에서 입력하면 OS가 보호하는 키로 암호화되어 데이터 디렉터리의 `secrets.json`에 암호문으로만 남는다([ADR 0010](adr/0010-encryption-at-rest.md), [ADR 0019](adr/0019-connector-credentials.md)). OS 보호를 쓸 수 없으면 저장되지 않고 그 인스턴스는 `unavailable`(사유 `credential-store-unavailable`)이다. 값은 인스턴스의 종류와 ID에 묶이고 원 시스템의 주소에는 묶이지 않으므로, 인스턴스가 가리키는 원 시스템을 바꿀 때는 인스턴스 ID도 바꾸고 값을 다시 입력한다(S28). 여러 줄 값은 이 화면이 받지 않는다 | 없음. 칸을 선언한 인스턴스가 없으면 아무것도 필요 없다 |
| `providers.default` | 연결 시험과 호출에 쓸 Provider 이름 하나(`claude-code`, `codex`, `openai-compatible`). 설정 화면의 "기본 Provider"가 이 값을 쓴다. 비어 있거나 묶이지 않은 이름이면 어느 Provider도 부르지 않으며, 설치된 CLI가 하나뿐이어도 저절로 고르지 않는다 | 없음 |
| `providers.cli.background` | `on` 또는 `off`(정확히 `on`일 때만 켬). 목록에 있는 조합의 백그라운드 자동 실행을 허용할지. 설정 화면의 "CLI 백그라운드 실행 허용"이 이 값을 쓴다. 가져오기 뒤의 추출도 백그라운드 실행이다. 홈의 Provider 행은 이 추출이 돌 수 있는지를 보이므로, 꺼져 있으면 목록에 있는 CLI도 "실행이 막힘(백그라운드 실행이 꺼져 있음)"으로 보인다(연결 시험은 사용자 호출이라 실행된다) | 끔 |
| `jobs.maxConcurrent` | 백그라운드 작업을 전체에서 한 번에 몇 개까지 실행할지: **1에서 4까지의 정수**. 범위 밖이거나 정수가 아닌 값은 가장 가까운 허용 값이 아니라 기본값으로 읽는다. 작업을 집을 때마다 읽으므로 앱을 다시 켜지 않아도 적용된다. 이 값은 전체의 상한일 뿐이고, 묶음마다의 상한은 따로 있어 값을 올려도 추출(묶음 `knowledge`)·투영 제거와 재구축·정리·같은 수집기 인스턴스의 동기화는 묶음마다 한 번에 하나다(`storage/src/job-concurrency.ts`의 `JOB_GROUP_CAPS`). 배포처의 Provider 요청 한도(S20)와 PC의 성능에 맞춰 정한다. 설정 화면에는 없다(저장소의 설정 쓰기 경로로만 바뀐다) | 2 |
| `semantic.autoVerify` | `on` 또는 `off`(정확히 `on`일 때만 켬). 후보 사실·관계를 조건을 채우면 `verified`로 올리는 **자동 승격**을 켤지([S01 spec R9](specs/2026-11-22-S01-semantic-registry.md)): 인식 유형이 `explicit`이고, 서로 다른 원본 둘 이상의 현재 근거가 있고, 그 유형 정의가 `verified`이고, 값이 하나여야 하는 종류면 다른 값의 유효한 행이 없을 때만 올린다. confidence는 조건이 아니다. 켜도 이미 있는 행을 훑지 않고, 다음 추출과 다음 원본 변경(새 version·삭제·정리)이 닿는 행부터 판정한다. 올라간 행은 두 번째 원본이 사라지거나 다른 값이 생기면 올리기 전 상태로 돌아간다. 끄면(`off`) 새 승격은 하지 않지만, 이미 올라간 행이 위 조건을 잃으면 계속 되돌린다. 근거가 그대로인 행은 `verified`로 남는다. 설정을 한 번도 쓰지 않았으면 판정은 설정 한 줄만 읽고 아무것도 쓰지 않는다. 사용자가 승인·기각·이의·직접 추가한 행은 손대지 않는다. 설정 API `GET`·`POST /api/settings/semantic`(`{ "autoVerify": true }`)으로 바꾸며 설정 화면에는 아직 없다. **켜기 전에 S32로 틀린 승격이 얼마나 나오는지 잰다** | 끔 |
| `semantic.autoDispute` | `on` 또는 `off`(정확히 `on`일 때만 켬). 두 유효한 사실의 값이 한 슬롯에서 어긋나는 `CONTRADICTS` 줄이 **새로** 생길 때, 정책이 `verified` 사실에 `disputed`(이의)를 거는 **자동 이의**를 켤지([S02 spec R20](specs/2026-11-22-S02-entity-resolution-temporal-graph.md)). 사용자가 승인한 사실도 `disputed`까지만 가고 기각되거나 값이 바뀌지 않으며, 한 묶음의 서로 다른 항목에 있는 두 사실이나 `candidate` 사실에는 이의가 일어나지 않고 줄만 생긴다. 끄면 줄만 생기고 상태는 그대로다. 틀린 유효 기간은 사용자가 검증한 값에 이의를 붙이므로 **켜기 전에 S33으로 얼마나 나오는지 잰다** | 끔 |
| `wiki.summary` | `on` 또는 `off`(정확히 `on`일 때만 켬). 위키 페이지마다 **LLM 요약**을 만들지([K01 spec R12](specs/2026-11-23-K01-wiki-projection.md)). 켜면 요약이 지금 내용의 것이 아닌 페이지마다 요약 작업이 하나씩 생기고, 작업은 문서의 ID만 Broker에 넘긴다. 문서 본문이 Provider로 나가므로 동의·전송 정책·데이터 등급·실행 조건이 추출과 똑같이 적용되고, 어느 하나라도 막으면 작업은 `held`로 대기하며 다른 Provider로 넘어가지 않는다. 원본 version이 8개를 넘는 페이지와 `syntheses` 페이지는 요약하지 않는다. 설정 API `POST /api/settings/semantic`(`{ "autoVerify": false, "wikiSummary": true }`)으로 바꾸며 설정 화면에는 없다. **켜기 전에 요약의 품질과 비용을 잰다** | 끔 |
| `insight.interpret` | `on` 또는 `off`(정확히 `on`일 때만 켬). Insight마다 **LLM 해석**을 붙일지([P01 spec R7](specs/2026-11-23-P01-insight-discovery.md)). 켜면 활성 Insight(코드 규칙이 판정한 것)마다 해석 작업이 하나씩 생기고, 작업은 Insight의 근거 문서 ID와 두 항목·그 Insight의 ID만 Broker에 넘긴다. 문서 본문과 Insight의 줄(원본 값을 담은 문장)이 Provider로 나가므로 동의·전송 정책·데이터 등급·실행 조건이 추출과 똑같이 적용되고, 어느 하나라도 막으면 작업은 `held`로 대기하며 다른 Provider로 넘어가지 않는다. 해석은 이유 요약·영향·실행 가능성의 세 열에만 저장되고 코드가 쓴 내용은 바뀌지 않으며, 해석이 낸 `opportunity`는 부모 Insight의 근거를 그대로 가진 신뢰도 40 이하의 한 건이다. 원본 version이 8개를 넘는 Insight는 해석하지 않는다. 작업 종류별로 전송을 막는 배포처 규칙은 `insight-interpret`을 이름으로 적거나 `*`를 써야 이 작업을 덮는다. 설정 API `POST /api/settings/semantic`(`{ "autoVerify": false, "insightInterpret": true }`)과 설정 화면의 "Insight LLM 해석 사용" 체크박스로 바꾼다(요청에서 빠지면 그대로, 켜면 작업 실행기를 깨운다). **켜기 전에 해석의 품질과 호출 비용을 잰다** | 끔 |
| `reflection.refine` | `on` 또는 `off`(정확히 `on`일 때만 켬). 점검 결과 가운데 열린 `synonym`·`missing-link` 발견마다 **LLM 의견**을 붙일지([K02 spec R16·R17](specs/2026-11-23-K02-reflection-consolidation.md)). 켜면 주간 재검토가 끝난 뒤 그런 발견마다(한 번에 20건까지) 작업이 하나씩 생기고, 작업은 발견의 근거 문서 ID와 두 항목의 ID만 Broker에 넘긴다. 문서 본문이 Provider로 나가므로 동의·전송 정책·데이터 등급·실행 조건이 추출과 똑같이 적용되고, 어느 하나라도 막으면 작업은 `held`로 대기하며 다른 Provider로 넘어가지 않는다. 의견은 판정(같음·관련·무관)과 원문에서 정확히 한 번 찾은 인용문의 위치뿐이며, 인용문을 못 찾으면 버린다. 발견의 상태와 지식 행은 바뀌지 않고 화면에 "LLM 의견"으로 보인다. 같은 발견을 같은 근거로 다시 묻지 않고, 원본 version이 8개를 넘는 발견은 묻지 않는다. **켜는 API·화면은 아직 없다**(저장소의 설정 쓰기 경로로만 바뀐다). **켜기 전에 전송되는 원본의 등급과 호출 비용을 잰다** | 끔 |

설정이 아닌 것:

- **Embedding 모델 준비**: 설정 값이 아니라 홈의 "Embedding 모델 준비"에서 보내는 준비 요청이다(`POST /api/embedding/prepare`. 로컬 팩 폴더의 절대 경로, 또는 확인 창에서 승인한 내려받기). 무엇을 준비했는지는 저장하지 않으므로 앱을 다시 켜면 "모델 없음"이고, 같은 요청이 설치된 파일을 네트워크 없이 해시 확인만으로 다시 올린다. 자동으로 내려받지 않는다(S09).
- **자동 업데이트 주소**: 아직 없다. 업데이트는 H02(#33)가 정하며 그때 이 표에 키를 더한다(S12).

### 수집

이 절과 아래 S18에서 말하는 `Connector` 규격은 SDK 규격 v2(`CONNECTOR_SDK_VERSION` = 2)이다. 수집기를 만드는 방법은 [connector-sdk.md](connector-sdk.md)에 있다.

- [ ] **S01 메일 수집기 구현.** `Connector` 규격을 구현해 `site-mail` 자리에 등록한다. 필요한 것: 메일 시스템에 접근하는 방법, 수집 범위(어느 편지함, 어느 기간). 확인: `packages/testkit`의 Connector 계약 테스트 통과, `site-mail` 실행 시 "미구현" 대신 변경분이 나온다. 메일의 첨부는 이 수집기가 낸다: 메일 첨부의 이름·형식·크기와 근거 위치를 레코드에 싣는다(이슈 #19 I02-C1; 레코드의 자리는 이슈 #122, [spec](specs/2026-11-23-I02-attachment-metadata.md)).
- [ ] **S02 메신저 수집기 구현.** 같은 방식으로 `site-messenger`. 필요한 것: 메신저 시스템 접근 방법, 수집할 대화방의 범위, 스레드를 복원할 식별자. 확인: S01과 같다.
- [ ] **S03 Wiki 수집기 구현.** 같은 방식으로 `site-wiki`. 필요한 것: Wiki 시스템 접근 방법, 수집할 공간의 범위, 페이지 버전 정보. 확인: S01과 같다.
- [ ] **S04 수집기의 인증과 권한 매핑.** 각 수집기가 사용자 본인의 권한으로 인증하게 하고, 원본마다 access_scope(누가 볼 수 있는 자료인가)를 채운다. 수집기는 데이터 등급을 정하지 못한다. 등급은 제품이 access_scope에서 계산하며, 실제 수집기가 가져온 자료는 "합성"이 될 수 없다. 필요한 것: 인증 방식(비밀 값이 필요하면 인스턴스 정의의 `credentials`에 칸을 선언한다. S28, [connector-sdk.md](connector-sdk.md) 8장), 원본의 공개 범위를 알아내는 방법. 확인: 수집한 원본에 access_scope가 비어 있지 않고, 삭제되거나 권한이 철회된 원본에 대해 수집기가 그 사건을 낸다(제품은 그 원본의 내용을 지운다).
- [ ] **S18 실제 수집기로 SDK v2 계약 판정과 실제 동기화를 실행하고 기록.** 공용 저장소는 Connector 규격 v2를 지어낸 원 시스템(예시 수집기, 대본 수집기)으로만 증명했다. 실제 원 시스템을 상대로 규격을 지키는지는 포크의 수집기로만 확인할 수 있다. 수집기 작성법은 [connector-sdk.md](connector-sdk.md)다. 필요한 것: S01~S03 가운데 하나 이상의 실제 수집기, 그 시스템에서 합성 자료를 만들고 고치고 지울 수 있는 시험 계정(실제 업무 자료로 하지 않는다), 인스턴스 범위 파일(아래). 실행: ① 포크의 수집기 테스트에서 계약 묶음 `connectorContract`를 돌려 위반 코드가 하나도 없는 것을 확인한다(작성법 6장). 이 묶음은 지어낸 원 시스템으로 돌리므로 실제 확인은 ②③이다. ② 앱에서 그 인스턴스를 동기화한다(수동 동기화와 주기 동기화). ③ 아래 다섯 가지를 기록한다. 기록할 것: (가) 요청 한도: 원 시스템이 한도를 알리는 방식, 그것이 `ConnectorRateLimitError`의 `retryAfterMs`로 옮겨지는지, 동기화 결과에 `rate-limited`와 `retryAfterMs`가 남는지. (나) cursor 만료와 그 동안의 삭제: 만료를 `cursorExpired`로 알리는지, 재스캔 결과의 `rescanned`와 `deletionsMayBeMissed`, 만료된 동안 지워진 원본이 수집기의 `deletionsOnRescan` 선언대로 `delete`로 다시 알려지는지. (다) 대량 페이지: 한 번에 100개를 요청할 때의 소요 시간과 메모리, 한 번 읽는 데 가져갈 페이지 수의 상한 `maxPages`(기본 10,000쪽)가 모자라지 않는지, 첫 동기화가 제품의 작업 실행 시간 제한 `DEFAULT_RUN_TIMEOUT_MS`(기본 10분, 잠정)를 넘지 않는지. (라) `accessScope`와 `revision` 채우기: 레코드마다 비어 있지 않은 `accessScope`가 채워지는지, `revision`이 원 시스템에서 고칠 때마다 커지는지(정수 번호가 없으면 수정 시각의 밀리초). (마) 가져오기 인스턴스와 범위가 없는 원본의 등급 매핑: 가져온(`scope_claimed`) 원본과 `accessScope`가 없는 원본이 S08의 매핑에서 가장 엄격한 등급으로 가는지를 합성 자료로 확인한다.
  **인스턴스 범위 파일 `site/config/connector-scopes.json`.** 가져온 범위(사용자가 적은 값)가 인스턴스에 배포처가 정해 둔 범위보다 느슨한 등급을 얻지 못하게 하는 기준이다. 형식은 `{ "<인스턴스 ID>": ["범위", ...] | null }`이다. 범위는 비어 있지 않은 문자열이고 `null`은 알 수 없음이다. 이 파일은 포크의 등록이 빌드할 때 묶는다(`SiteRegistration.connectorScopes`, 방법은 S30). 다시 빌드해야 바뀌고, 설정 API와 화면은 이 값을 쓰지도 보이지도 않는다. 공용 저장소는 이 파일을 갖지 않으며, 등록에 값이 없거나 그 인스턴스가 없으면 알 수 없음이라 가장 엄격한 등급이다. 실행 중에 만들어지는 가져오기 인스턴스(I02-B의 `jsonl-file:…`)에는 범위 파일로 범위를 적을 수 없고, 그런 인스턴스는 알 수 없음(닫힌 쪽)이다. 값이 JSON 객체가 아니면 값 전체를, 형식이 틀린 항목은 그 항목만 쓰지 않는다. 어느 경우에도 알 수 없음보다 넓어지지 않는다. 시작할 때 백엔드의 로그(표준 오류로 나간다. `providers/src/log.ts`)에 상태가 한 줄 남는다. 등록에 값이 없음은 `connector-scopes-absent`, 값이 객체가 아님은 `connector-scopes-invalid`, 객체이지만 범위가 있는 항목이 하나도 없음은 `connector-scopes-empty`, 범위가 있는 항목이 하나 이상임은 `connector-scopes-bound`(그 수만 적힌다)이고, 쓰지 않은 항목이 있으면 `connector-scopes-rejected`(그 수만 적힌다)가 한 줄 더 남는다. 범위 값과 인스턴스 ID는 로그에 없다. 값은 정본의 `connector_instances.configured_scope`에 복사된다(시작할 때 모든 인스턴스 행, 인스턴스가 처음 등록될 때 그 행).
  **설치본에서의 확인은 S31이다.** 이 값이 설치본의 정본까지 복사되었는지는 로그가 아니라 정본을 읽어 확인하며, 공용 저장소는 그것을 Windows 설치본에서 확인하지 못했다.

- [ ] **S05 LLM Provider 구성.** 쓸 Provider를 고르고, OpenAI 호환 경로를 쓴다면 엔드포인트 주소와 모델 이름을 설정하고 키를 발급받아 앱에 입력한다. 필요한 것: 허용된 Provider의 목록, `https` 엔드포인트 주소, 모델 이름, 키 발급 절차. 확인: 앱의 설정 화면에서 그 Provider의 연결 시험이 성공한다(합성 자료 한 건의 구조화 응답이 스키마 검증을 통과, A06).
- [ ] **S06 구독 로그인 CLI 사용 허용 여부 확인.** 사용자의 구독 로그인으로 CLI를 제품이 호출해도 되는지를 벤더의 공식 조건과 배포처 정책으로 확인한다. "배포처에서 두 CLI를 쓸 수 있다"는 것은 지금까지 사용자의 진술뿐이고 문서 근거가 없다. 조사 문서는 벤더 문구를 "모호"로 판정했고 허용된다고 말하지 않는다([CLI Provider 조사 3절](research/2026-11-21-cli-provider-terms-and-isolation.md)). 필요한 것: 확인한 조건의 출처와 날짜. 확인: R02-C4에 허용 경로 또는 "미확인"이 기록된다. 허용되지 않으면 묶을 Provider(`productProviders`, 2절 빌드 표)에서 CLI를 빼고 S07을 하지 않는다(A01).
- [ ] **S07 CLI 격리 검증과 검증된 조합 등록.** R02의 절차대로 합성 악성 문서로 부정 테스트를 실행하고, 통과한 조합만 "검증된 CLI 조합 목록"에 넣은 뒤 **설치본을 다시 빌드**한다. 등록된 조합만 설치본에서 실행된다. 그 뒤 백그라운드 자동 실행을 켤지 따로 정한다. 필요한 것: 배포할 CLI의 정확한 버전, 검증한 OS, R02를 실행한 모델 이름(목록 항목의 `model`에 고정한다). R02의 `result.json`은 알려진 벤더 계열 밖의 모델 이름을 `h:<sha256 앞 12자>`로 적으므로, 목록의 `model`을 기록과 대조할 때는 그 이름의 해시를 비교한다. 확인: R02-C1~C3의 실행 기록. 등록하지 않은 버전으로는 설치본에서 사용자가 연결 시험을 눌러도 차단된다. 실행할 R02 프로필은 목록에 적을 제품 프로필과 같은 인자의 것이다. 그 대응은 `providers/src/cli-profiles.ts`의 `CLI_ARGUMENTS`가 프로필마다 `r02` 칸에 적는다(지금은 `claude-code/standard-2` → `claude-A-restricted-safe`, `codex/standard-2` → `codex-A-full`). R02의 판정은 그 실행의 **버전과 모델**에서만 유효하므로, R02에 `--model-claude`·`--model-codex`로 준 모델 이름을 목록 항목의 `model`에 그대로 적는다. 제품은 목록에 있는 조합을 그 모델로만 실행한다(`--model <model>`). R02는 제품이 찾는 것과 같은 실행 파일로 돌린다. Windows의 제품은 `.exe`만 찾으므로 npm이 까는 `.cmd`로 R02를 통과해도 제품은 그 CLI를 찾지 못한다(미검증). 프록시·사설 인증서 환경 변수(`HTTPS_PROXY`, `NO_PROXY`, `NODE_EXTRA_CA_CERTS` 등)는 제품이 CLI에 넘기지 않는다(잠정). R02를 `--pass-env`로 통과한 조합도 프록시가 필요하면 제품에서는 연결하지 못한다. **CLI가 버전을 올리면 그 CLI는 다시 막히므로**, 배포할 버전을 고정하고 버전을 올릴 때마다 다시 검증해 등록하고 빌드한다(A02~A05, A22).
- [ ] **S08 외부 전송 정책의 값.** 데이터 등급을 정하고 등급마다 어느 Provider에 보낼 수 있는지 규칙을 채운다. 필요한 것: 배포처의 데이터 분류 기준, 등급별 허용 Provider. 확인: 거부 규칙에 걸리는 합성 입력이 호출 없이 "전송 거부"로 남고, 사용자가 동의해도 그 거부가 유지되며, 허용 규칙에 걸리는 입력만 호출된다. **주의**: 규칙에는 목적지 칸이 없다. `openai-compatible`을 허용하면 사용자가 `providers.openaiCompatible.baseUrl`에 넣은 어느 `https` 호스트로 보내는 것이든 허용된다(사용자의 동의는 여전히 필요하다). 엔드포인트를 정해 두어야 한다면 `openai-compatible`을 거부하거나, 주소를 빌드 자원으로 바꾸거나, 규칙에 목적지 칸을 더한다(V01 spec "T08이 넘기는 것" 1항). **접근 범위를 등급으로 바꾸는 매핑(`ScopeGrading`)도 이 항목의 값이다.** 수집기가 채운 접근 범위는 Broker가 `ScopeGrading`(`providers/src/scope-grading.ts`)의 `grade`로 데이터 등급을 매긴다. 공용 기본(`publicScopeGrading`)은 모든 범위를 일반 등급 하나로 매긴다. 포크의 매핑은 **`strictest([])`와 `grade(null)`이 가장 엄격한 등급을 돌려주게** 해야 한다. 수집기가 낸 원본은 범위가 `null`(알 수 없음)이어도 `grade(null)`로 등급을 매긴다. **가져온(청구한) 원본**은 달라서, 그 범위나 인스턴스 범위(S18)가 `null`인 경우와 정책이 두 범위를 비교하지 못한 경우가 `strictest([])`로 간다. Broker는 두 범위의 등급을 합칠 때 `strictest`의 답이 물어본 두 등급 가운데 하나인지 확인하고 아니면 요청을 거절한다(`scope-unjudged`). 매핑이 던지거나 허용된 등급(`SCOPE_CLASSES`) 밖의 값을 답해도 같다. **`synthetic`은 매핑이 낼 수 없는 등급이다**(합성 등급은 합성 목록과의 대조로만 붙는다). **자기 등급을 더하려면 한 곳만 바꾸어서는 안 된다.** `packages/contracts/src/provider.ts`의 `DATA_CLASSES`(덜 엄격한 쪽이 앞), `providers/src/scope-grading.ts`의 `SCOPE_CLASSES`, `providers/src/broker.ts`의 `asScopeClass`와 입력 전체를 합치는 `strictest(graded)`(지금은 합성이 아니면 일반으로 줄인다), 그 등급을 읽는 `providers/src/egress-policy.ts`의 전송 규칙과 `providers/src/execution-gate.ts`의 실행 조건, 그리고 포크의 `ScopeGrading`을 함께 바꾼다. 하나라도 빠지면 그 등급은 `scope-unjudged` 거절이 되거나 일반으로 줄어든다(닫힌 쪽이다). 매핑을 끼우는 자리는 포크 등록(`registration`)의 `scopeGrading` 필드다(`backend/src/site-registration.ts`의 `SiteRegistration`). 넣으면 Broker가 그 매핑을 쓰고(빌드 종류와 무관하다. Broker를 만드는 `backend/src/composition.ts`의 `productCalls`가 받는다), 넣지 않으면 `publicScopeGrading`이다. 등록 검사(`checkSiteRegistration`)는 매핑이 `grade(null)`, `grade([])`, `strictest([])`에 가장 엄격한 등급을 답하고 허용된 등급(`SCOPE_CLASSES`) 안에서만 답하는지 묻는다(`scope-grading-invalid`). 이 검사는 등록 검사 테스트에서만 돌고 시작할 때는 하지 않으므로, 포크의 `registration.test.ts`가 반드시 돌려야 한다. 포크의 매핑은 흉내(대역)로만 시험했다. 가져온 범위가 그 매핑에서 느슨해지지 않는지는 S18이 확인한다.

### Embedding

- [ ] **S09 Embedding 모델 반입.** 외부에서 내려받을 수 있는지 확인하고, 안 되면 모델 파일을 내부로 반입해 로컬 팩으로 둔다. 필요한 것: 외부 모델 저장소 접근 허용 여부, 반입한 파일을 둘 위치, 모델 라이선스 확인. 확인: 반입한 파일의 해시가 제품이 고정한 값과 맞아 앱의 embedding 상태가 "준비됨"이 되고, 합성 문장의 embedding 왕복이 통과한다. 속도와 메모리는 R03-C3의 기준으로 잰다(A11, A12).

### 설치와 운영

- [ ] **S10 Windows 11 설치본 검증.** 깨끗한 Windows 11에서 Node·Python·Docker·DB 서버를 따로 설치하지 않고 설치·실행·제거한다. 필요한 것: 깨끗한 Windows 11 시험 환경. 확인: R04-C1의 실행 기록(A07, A13, A18). 설치 파일의 입력은 Windows에서 `pnpm --filter @pki/desktop build`로 만든 `apps/desktop/dist/app/`이다(네이티브 모듈은 빌드한 PC의 것만 들어간다). Electron fuses는 패키저 설정에서 켠다. 목록은 [V01 spec "T15가 넘기는 것" 9항](specs/2026-11-21-V01-vertical-skeleton.md)(잠정).
- [ ] **S11 저장 데이터 보호 확인.** 제품을 쓸 PC에 OS 디스크 암호화가 적용되는지, 앱이 OS 자격 증명 저장소를 쓸 수 있는지, 앱의 데이터 디렉터리가 다른 PC로 따라다니지 않는 위치인지 확인한다. 필요한 것: PC 보안 정책의 해당 항목. 확인: 앱에 API 키를 저장했다가 재시작 뒤 다시 쓸 수 있고(로밍 프로필 동기화 뒤에도. ADR 0010 "지켜볼 것"), 그 키의 평문이 앱의 어떤 파일에도 남아 있지 않다(`secrets.json`에는 암호문만). **디스크 암호화가 확인되지 않은 PC에는 실제 업무 데이터를 넣지 않는다**([ADR 0010](adr/0010-encryption-at-rest.md), A16, A19).
- [ ] **S12 서명, 배포 채널, 업데이트.** 설치 파일과 그 안의 네이티브 모듈을 무엇으로 서명할지, 사용자에게 어떻게 배포할지, 업데이트를 어디서 받게 할지 정한다. 필요한 것: 서명 주체, 내부 배포 방법, 업데이트를 둘 주소(없으면 자동 업데이트를 끈다). 확인: R04-C3의 기록. 설치와 실행에서 Windows의 차단 동작을 관찰해 적는다. 자동 업데이트를 실제로 돌려 보는 확인은 R04의 기준에 없으며 H02(#33)에서 한다(A14, A15).
- [ ] **S13 엔진과 저장소의 실행 비교.** R03의 절차대로 엔진 후보와 저장소를 합성 입력으로 실행해 비교한다. 벡터 색인의 실제 구현 후보(sqlite-vec)가 Windows에서 로드되는지, 정본 SQLite가 갑작스러운 종료를 견디는지도 여기서 확인한다. Phase 1의 제품에는 벡터 색인 구현이 들어 있지 않다. 필요한 것: 실행 환경과 R05가 고정한 측정 기준. 확인: R03-C1~C4의 실행 기록. 결과로 [ADR 0002](adr/0002-authority-in-product-records.md), [0003](adr/0003-phase1-without-engine.md), [0004](adr/0004-embedded-storage.md), [0011](adr/0011-sidecar-language.md), [0013](adr/0013-failure-recovery.md)을 R07에서 확정하거나 고친다(A08, A09, A10, A20).

### 수직 흐름

- [ ] **S14 수직 흐름을 설치본과 실제 Provider로 실행.** V02의 흐름(합성 출처 3개 → 일정 위험 Insight → 근거 화면)을 Windows 설치본에서 실제 Provider로 실행한다. 가져오기 뒤의 추출은 백그라운드 실행이므로 Provider는 둘 중 하나여야 한다: API 키 Provider(S05), 또는 목록에 등록되어 있고(S07) 백그라운드 설정을 켠 CLI. 필요한 것: S10이 끝난 환경(R04의 설치 파일로 설치하고 데이터 폴더 `%LOCALAPPDATA%\PKI`가 빈 Windows 11), 기본 Provider로 고를 실제 Provider와 그 버전, Python 3.8 이상. 실행: [verification/v02-site-flow/RUNBOOK.md](../verification/v02-site-flow/RUNBOOK.md)의 순서대로 설정을 `v02-result\config.json`(gitignore됨)에 두고 `python verification\v02-site-flow\run.py preflight --config v02-result\config.json` → `prepare --config v02-result\config.json --out v02-result` → 사람이 화면 걸음(앱은 설치된 exe로만 켬, 가져오기, "추론" 표지, 근거 3개, 재입력, 재시작) → 앱을 닫고 `record --config v02-result\config.json --out v02-result --observed …`(관찰 다섯). 같은 커밋의 test double E2E 기록은 RUNBOOK 6절의 `summarize`로 짝짓는다. Provider가 test double이거나 Windows 설치본이 아니면 실행기는 `배포처 후속`으로 시작하는 알림을 내고 3으로 끝난다(V02-H2). 확인: `record`가 `V02-C4:site-flow PASS`를 내고, 붙이는 결과(결과 폴더 `v02-result`의 `result.md`)에 Provider 종류 `real`, Provider id와 버전, 앱 버전, 인용문 대조에서 버린 수(`dropped_quotes`)가 적힌다. 그 결과를 이슈 #17에 붙이고 `v02-result/raw/`는 붙이지 않는다(V02-C4, A21).
- [ ] **S15 실제 수집 데이터에서의 품질 확인.** 실제 수집기로 가져온 자료에서 추출과 Insight가 쓸 만한지 배포처 안에서 확인한다. 필요한 것: S01~S04와 S11이 끝난 환경. 확인: 결과는 배포처 안에만 남긴다. 공용 저장소에는 범용 문제만 합성 재현 형태로 알린다([ownership.md 5절](ownership.md)).

### 문서 가져오기

- [ ] **S16 문서 파서 의존성의 npm 미러 설치 확인.** 문서 정규화 패키지(`@pki/document-normalize`)의 의존성(unpdf, mammoth, read-excel-file, parse5, mdast-util-from-markdown, csv-parse, yauzl, fflate, @xmldom/xmldom, iconv-lite와 그 전이 의존성)을 배포처의 npm 미러에서 설치한다. 필요한 것: 미러 주소와 그 미러가 가진 패키지의 범위(위 패키지가 전부 있는지), 설치를 막는 정책(설치 스크립트 차단 등). 확인: 저장소의 `pnpm-lock.yaml`로 `pnpm install --frozen-lockfile`이 미러에서 끝까지 성공하고, 빠진 패키지가 있으면 그 이름을 기록한다. 이 의존성은 모두 설치 스크립트와 네이티브 모듈이 없는 npm 레지스트리 패키지이며(I02-A spec R21), 미러가 막는 패키지가 있으면 [ADR 0015](adr/0015-document-parsing-stack.md)의 해당 행을 고친다.
- [ ] **S17 실제 업무 문서로 형식별 정규화 결과 확인.** 배포처의 실제 문서 폴더(PDF, Word, Excel, HTML, Markdown, TXT, CSV, JSON을 섞어서)에 조사 실행기 `pnpm --filter @pki/document-normalize survey <폴더>`를 실행한다. 이 실행기는 형식별 성공 수, 오류 종류별 수, 한계 코드별 수, 인코딩별 수만 JSON으로 출력하며 파일 이름과 글은 출력하지 않는다. 이 저장소 안의 폴더로는 실행되지 않는다(`배포처 후속` 알림). 필요한 것: 실제 문서 폴더(문서 보안(DRM)으로 감싼 파일이 일부 든 것), 설치본(Electron)에서의 실행 방법. 확인: ① 오류 종류별 수가 설명되는 범위인지 본다. 특히 DRM으로 감싼 파일이 `corrupt`·`format-mismatch`로 알려지는지(깨진 글이 성공으로 나오지 않는지) 확인한다. ② EUC-KR(CP949) 문서가 `euc-kr` 인코딩으로 풀리는지, 이 확인을 **설치본 안의 Node(Electron 45.4.1의 Node 24.22.3)에서도** 한다. EUC-KR은 `iconv-lite`로 풀기 때문에 Electron의 ICU 구성에 기대지 않지만 설치본에서 실제로 보기 전에는 확인된 것이 아니다. ③ 한계 코드 수가 한도 기본값(`DEFAULT_LIMITS`)이 실제 문서에서 너무 빡빡한지 보는 근거가 된다. 결과는 배포처 안에만 남기고 공용 저장소에는 범용 문제만 합성 재현 형태로 알린다([ownership.md 5절](ownership.md)). 폴더 감시와 가져오기 화면은 I02-B(#19)가 맡으며 이 항목의 범위가 아니다.

### 로컬 파일과 폴더

- [ ] **S23 Windows 11 설치본에서 로컬 파일 수집 검증 실행기를 돌리고 기록.** 공용 저장소는 로컬 파일·폴더 가져오기를 macOS에서만 시험했고 Windows 동작을 확인된 것으로 적지 않는다. 설치된 앱을 밖에서 보는 실행기 `python verification\local-files\run.py`(`prepare`, 사람이 설치본에서 폴더를 승인하고 [RUNBOOK](../verification/local-files/RUNBOOK.md)의 순서를 따른 뒤 앱을 닫고 `record`)가 시나리오를 만들고 결과(통과·실패·판정 불가), OS, 앱 버전, 파일 시스템 종류만 JSON으로 기록한다. 파일 이름과 글은 기록하지 않는다. 시나리오: W1 NTFS에서 이름 바꾸기·이동·바꿔치기 저장 뒤 파일 번호의 유지와 재사용, W2 위치 안의 junction·디렉터리 symlink와 훑는 도중 마지막 이름의 symlink 바꿔치기, W3 클라우드 동기화 폴더의 "온라인 전용" 파일을 읽을 때의 내려받기, W4 UNC 경로(거부)와 드라이브 문자에 붙인 네트워크 드라이브, W5 260자 넘는 경로·끝이 점이나 공백인 이름·예약 이름, W6 감시의 잇단 저장·폴더 통째 이동·절전과 최대 절전 복귀 뒤 상태, W7 대소문자만 다른 이름 바꾸기와 한글 이름의 NFC·NFD, W8 Office가 연 채 잠근 파일과 `~$` 파일, W9 설치본에서의 정규화 작업자와 두 재현 입력, W10 선택 창·"폴더에서 보기"·외장 디스크 뽑기와 다시 꽂기, W11 데이터 디렉터리와 userData를 다른 표기(대소문자, 8.3 짧은 이름, `\\?\` 접두사, junction)로 승인 시도, W12 NTFS·exFAT·ReFS에서 `lstat`과 `fstat`의 `(dev, ino)`. 필요한 것: 깨끗한 Windows 11 시험 환경과 설치본, 빈 폴더. 확인: 실행기의 JSON 기록과 항목별 판정(공용 저장소가 이 항목을 확인된 것으로 적지 않는다. 설치본이 없거나 Windows가 아니면 실행기는 `배포처 후속` 알림을 내고 종료 값 3으로 끝난다).
- [ ] **S24 실제 업무 폴더의 규모로 한도와 주기의 값을 정함.** 값은 위 「실행 중 설정」 아래 「로컬 자료 한도(`localFiles.*`)」의 키다: 위치당 파일 수, 정규화 시간과 메모리 상한, 안정화 시간, 훑기 주기(Activity 화면의 `connector-sync` 주기), 철회 묶음 크기. 필요한 것: 실제 업무 폴더의 규모(파일 수, 가장 큰 파일, 깊이)와 PC 사양. 확인: 정한 값으로 큰 폴더를 승인해 훑기가 `limit-exceeded` 없이 끝나고 정규화가 시간·메모리 상한 안에 끝난다. 이 항목은 값을 정하는 일이라 실행할 제품 경로가 없다.
- [ ] **S25 네트워크 공유와 클라우드 동기화 폴더를 승인 위치로 허용할지 정하고, 허용한다면 구현·검증.** 지금 제품은 UNC 경로를 사유 `network-location`(문구 "미구현, 배포처 후속")으로 거부하고, 드라이브 문자에 붙은 네트워크 드라이브와 클라우드 폴더의 자리 표시 파일은 경로만으로 알 수 없다(S23 W3·W4). 로컬 파일(범위 "알 수 없음")의 등급 매핑을 S08에서 함께 정한다. 필요한 것: 배포처의 공유·동기화 폴더 정책과 데이터 등급 기준. 확인: 허용하지 않으면 거부 문구가 그대로 보인다. 허용한다면 구현과 함께 감시·삭제·잠금 동작을 실행해 기록한다.

### 큐와 스케줄러

이 절의 두 항목은 [I03 spec](specs/2026-11-21-I03-persistent-queue.md)의 배포처 후속 항목이다. 용어: **임대**는 실행기가 작업을 기한이 있는 권리로 집는 것이고, 기한이 지나면 다른 실행이 다시 집을 수 있다. **slot**은 주기의 예정 시각 하나이고, 놓친 slot을 작업 하나로 합치는 것을 **합치기**라 부른다. **호출 예산**은 Provider에 보내는 호출을 시간창(1시간)마다 세어 막는 상한이다.

- [ ] **S19 Windows 11 설치본에서 강제 종료·절전·최대 절전·시계 변경·시간대 변경 시나리오를 실행하고 기록.** 제품은 작업을 정본 SQLite에 두고, 끊긴 작업을 임대 기한이 지난 뒤 다시 집고, 놓친 주기를 작업 하나로 합치고, 시계가 뒤로 가도 작업이 막히지 않게 한다. 공용 저장소는 이것을 개발 OS의 자식 프로세스 강제 종료와 가짜 시계로 증명했고, **실제 Windows 절전·최대 절전에서 깨어난 뒤의 합치기와 임대 처리, 실행 중 시간대 변경, Windows에서의 프로세스 강제 종료는 증명하지 못했다**(I03 spec 가정 I03-A1·A2·A4·A5, ARCHITECTURE 9절 A23·A24·A26·A27). 그것을 확인하는 것이 이 항목이다. 필요한 것: S10이 끝난 환경(R04 설치 파일로 설치한 Windows 11), 실제 Provider가 설정된 설치본(S05 또는 S07, 추출이 실제로 돌아야 한다), 합성 원본 셋, **하루보다 짧은 주기 하나**(절전·최대 절전·시계 앞당김 시나리오의 전제. 공용 제품의 `site-*` 수집기는 `not-implemented`라 기본 주기는 정리 매일 03:00뿐이므로, S01~S04의 실제 수집기가 만드는 1시간 동기화 주기를 쓰거나 활동 화면에서 정리 주기를 10분으로 바꿔 쓴다. 설치본에서 그 변경이 되는지는 확인하지 못했으며, 되지 않으면 이 세 시나리오는 수집기를 갖출 때까지 실행할 수 없는 **배포처 후속**이다), 최대 절전이 켜진 PC(`powercfg /a`), 시계와 시간대를 바꿀 수 있는 권한. 실행: [verification/v02-site-flow/RUNBOOK.md](../verification/v02-site-flow/RUNBOOK.md) 9절의 순서대로 시나리오 여섯(`kill`, `sleep`, `hibernate`, `clock-forward`, `clock-back`, `timezone`)을 하나씩 `python verification\v02-site-flow\run.py queue-scenario prepare|record --scenario <이름>`으로 실행한다. 사람이 설치된 앱에서 가져오기·강제 종료·절전·시계 변경을 하고 앱을 닫은 뒤, `record`가 정본 DB의 작업 표를 읽기 전용으로 읽어 ① 성공한 추출 작업 수(효과 행)가 가져온 합성 원본 수와 같은지 ② 포기한 작업과 끝나지 않은 작업이 없는지 ③ 시나리오의 흔적(`kill`은 시도 2 이상으로 끝난 작업, 절전·최대 절전·시계 앞당김은 **한 작업으로 합쳐진 slot**: 점검이 예정이 지난 slot 여럿을 보고 작업 하나만 등록한 경우의 나머지 slot 수이며, 작업 행에 저장되지 않아 `prepare` 때의 주기별 다음 예정 시각·주기 길이와 그 뒤 등록된 작업들의 slot 간격에서 다시 계산하며, 절전·최대 절전은 수동 확인 기록의 시간대와 겹치는 간격만 센다. 앱이 꺼져 있던 동안 시작 점검이 합친 것은 증거가 아니므로 `prepare`는 다음 예정이 이미 지난 주기가 있으면 거부한다. 잠정)이 있는지를 판정한다. 같은 원본 버전·같은 주기 slot의 작업이 둘이 되는 것은 정본의 작업 표 키가 막으므로 이 실행이 증명하지 않는다(그 결과의 한 번 남음은 개발 쪽 시험 I03-C1이 증명한다). 기록에는 OS, 앱 버전, 시나리오, 사람이 관찰한 상태 전이(관찰 단어), 효과 행 수, 합쳐진 slot 수가 든다(시도 2 이상으로 끝난 작업 수도 함께 적히나 보통 재시도도 세므로 강제 종료의 유일한 증거는 아니다). **절전과 최대 절전은 실행기가 PC를 재울 수 없고 재웠는지 볼 수도 없으므로** 사람이 재우기 전에 수동 확인 기록 `sleep-confirmation.json`(재운 시각, 깨운 시각)을 적고, 그 기록이 없거나 이 실행과 맞지 않으면 실행기는 `배포처 후속`으로 시작하는 알림을 내고 0이 아닌 값으로 끝난다. Windows 설치본이 아닌 환경에서도 같다(이 공용 저장소의 개발 PC에서 `미구현, 배포처 후속`). 어떤 환경에서도 가짜 시계 결과를 실제 절전의 결과로 기록하지 않는다. **틀렸을 때 고칠 곳**: 절전에서 깨어나도 타이머가 서지 않으면(A23) 쉘의 전원 이벤트(Electron `powerMonitor`의 resume)를 백엔드에 전달해 점검을 깨운다. 시간 제한이 절전 중에 지난 것으로 보여 호출이 취소되지 않으면(A24) 깨어남을 알아챈 뒤 진행 중 호출을 모두 취소하고 재시도로 돌린다. 시간대를 바꾸어도 프로세스가 새 시간대를 못 따르면(A27) 매일·매주 주기는 다음 재시작부터 새 시간대를 따른다고 화면에 알린다. 전원 차단과 정본 SQLite 자체의 갑작스러운 종료 내성은 이 항목이 아니라 A20(S13)의 몫이다. 결과는 이슈 #20(I03)에 남기고 여섯 시나리오를 모두 실행하기 전에는 끝났다고 적지 않는다.
- [ ] **S20 배포처 Provider의 요금·한도와 실제 수집기에 맞춰 호출 예산과 수집 주기의 값을 정함.** 제품의 기본값은 합성 자료와 개발 환경을 위한 값이다: Broker의 시간창 호출 예산 **1시간에 60회**(`providers/src/broker.ts`의 `DEFAULT_LIMITS`, `callBudget`), 작업 한 번이 Broker에 보낼 수 있는 요청 수 **2**(`backend/src/job-broker.ts`의 `DEFAULT_MAX_REQUESTS`), 작업의 시도 상한 **5**(`storage/src/jobs.ts`의 `DEFAULT_MAX_ATTEMPTS`), 끝나지 않은 작업의 전체 상한 **1000**(`backend/src/scheduler.ts`의 `OPEN_JOB_CAP`), 전체 동시 실행 **2**(실행 중 설정 `jobs.maxConcurrent`, 2절), 사용할 수 있는 수집기 인스턴스마다 동기화 **1시간**과 정리 **매일 03:00**. 배포처 Provider의 요금과 요청 한도, 실제 수집기가 한 번에 끌어오는 양과 허용하는 호출 빈도는 이 값과 다를 수 있다. 예산이 너무 작으면 작업이 "예산 소진"으로 다음 시간창까지 미뤄지고, 너무 크면 Provider의 한도를 넘어 429 같은 응답으로 시도가 낭비된다. 필요한 것: 배포처 Provider의 요청 한도와 요금(S05, S07), 그 한도에 닿았을 때 Provider가 돌려주는 응답의 형태와 값, 실제 수집기(S01~S04)의 호출 허용 빈도와 한 번에 가져오는 양, 사용자가 자리에 없을 때 도는 작업의 하루 호출 수 추정. 하는 일: ① 호출 예산은 포크가 Broker를 만들 때(`backend/src/composition.ts`의 `createBroker`) `limits`로 넘겨 정한다. 값을 바꾸는 API나 설정 화면은 없다. ② 수집 주기는 활동 화면 또는 주기 API(`/api/schedules/change`)로 10분·1시간·매일·매주 가운데에서 고르고, 전체 동시 실행은 `jobs.maxConcurrent`로 정한다. ③ 값을 정한 뒤 수집기를 하루 이상 돌려 작업 API `/api/jobs`의 응답을 본다(읽기 전용이며 코드·ID·수만 있다): `budget`의 사용량과 상한이 창을 넘지 않는지, `backlog`의 끝나지 않은 작업 수가 상한의 90%(경고) 아래인지, `schedules`의 합쳐진 수·건너뛴 수·멈춤 사유가 예상 범위인지, 포기한 작업이 쌓이지 않는지. 확인: 한 시간 창의 호출 수가 Provider의 한도 아래이고, 합성 자료로 수집기를 돌린 하루 동안 `dead_letter`가 없고 `backlog.warning`이 거짓이다. 이 확인은 실제 업무 자료 없이 합성 자료로 한다. 결과(값과 근거)는 배포처 안에만 남기고, 범용으로 고칠 만한 문제만 합성 재현 형태로 알린다([ownership.md 5절](ownership.md)). 주기·예산의 값은 [ownership.md](ownership.md)의 "설정 값" 칸에 든다.

### 삭제와 접근 범위

이 절의 두 항목은 [I04 spec](specs/2026-11-21-I04-invalidation.md)의 배포처 후속 항목이다. 용어: **접근 범위(access_scope)**는 "원 시스템에서 누가 이 자료를 볼 수 있는가"를 나타내는 값이고, 수집기가 원본마다 채운다. **tombstone**은 "이 원본은 지웠다"는 내용 없는 표시이고, 지운 자료가 재수집이나 백업 복원으로 되살아나는 것을 막는다. **카나리**는 시험 자료에 일부러 넣는 흔적 없는 단어이며, 지운 뒤에 그 단어가 어느 파일에도 남지 않았는지 찾아 "정말 지워졌다"를 확인하는 데 쓴다.

- [ ] **S21 접근 범위 규칙(`ScopePolicy`)의 값과 구현.** 제품은 파생물(Insight, 연결 후보처럼 원본에서 만들어진 것)의 접근 범위를 저장하지 않고, 그것이 기댄 원본들(그 목록을 **계보**라 부른다)의 범위에서 그때그때 계산한다. 어떤 범위가 다른 범위보다 엄격한지, 서로 다른 범위의 자료를 한 항목이나 한 Insight로 묶어도 되는지, 어떤 용도(`display`, `search`, `notify`, `answer`)로 보여 줘도 되는지는 **규칙 하나**(`storage/src/derivatives.ts`의 `ScopePolicy`)가 정한다. 공용 기본 규칙(`storage/src/scope-policy.ts`)은 한 PC의 한 사용자를 전제로 아무것도 거부하지 않는다(묶기와 허용은 언제나 참). 배포처는 조직의 권한 모델에 맞는 규칙을 구현한다. 이 항목이 끝나기 전에는 포크의 규칙을 쓸 수 없고, 접근 범위가 다른 자료가 한 Insight에 섞일 수 있다. 필요한 것: 수집기(S04)가 채우는 범위 값의 형태(`string[]`, 모름은 `null`)와 그 값의 엄격함 순서, 묶어도 되는 조합, 용도별 허용 기준. **구현 방법**: ① 포크가 `ScopePolicy`의 네 함수를 구현한다. `compare(a, b)`는 `stricter`·`equal`·`looser`·`incomparable` 중 하나를 돌려주고(증명되지 않으면 `incomparable`), `strictest(scopes)`는 가장 엄격한 범위 **또는** 비교할 수 없는 범위들의 묶음(`{ incomparable }`)을 돌려주며, `combinable(scopes)`와 `allows(scopes, purpose)`는 참·거짓이다. 기본 규칙처럼 `null`(모름)은 어떤 값보다 엄격하게 둔다. 제품은 `combinable`·`allows`의 답이 **정확히 `true`가 아니면 거부**로 읽는다(`combinable`이 오류를 던져도 거부, `allows`가 오류를 던지면 그 읽기 호출이 실패해 행을 보이지 않는 쪽으로 닫는다). **규칙을 구현하는 쪽의 의무**: 제품은 파생물이 기댄 원본들의 서로 다른 범위를 **한 번의 호출에 통째로** 넘길 뿐 범위마다 따로 묻지 않는다. 그러므로 "그 가운데 하나라도 허용되지 않으면 전체를 거부한다"는 제품이 대신 해 주는 동작이 아니라 규칙이 지켜야 할 의무다. 합쳐진 자료가 가장 제한적인 원본보다 더 넓게 보이면 안 되기 때문이다. 계보가 빈 파생물은 범위 목록 `[]`로 두 함수에 오므로 `[]`를 어떻게 다룰지도 정해야 한다. ② 포크 등록(`registration`)의 `scopePolicy` 필드에 그 규칙을 넣는다(`backend/src/site-registration.ts`의 `SiteRegistration`). 이름 없이 시작한 설치본은 등록의 규칙을 쓴다(`backend/src/scope-policy.ts`의 `productScopePolicy`가 이름과 등록으로 정한다). ③ **다시 빌드한다.** 설치본은 이름을 받지 않으므로(`--scope-policy` 인자가 없고 환경 변수 `PKI_SCOPE_POLICY`는 개발 실행에서만 듣는다) 등록의 규칙이 언제나 쓰이고, 설치본을 `default`로 돌리는 스위치는 없다. 규칙은 빌드할 때 정해지며(2절 빌드 표) 설정 화면에서 바꿀 수 없다. ④ 포크가 **읽기 경로를 더하면**(예: 배포처 전용 조회 API) 그 응답이 파생물을 내보내기 직전에 `backend/src/read-gate.ts`의 `createReadGate`를 거치게 한다. 지금 거치는 종류는 원본(`source`)·Insight(`insight`)·근거(`evidence`)이고, 사실·관계·항목을 내보내는 경로는 그 종류(`fact`, `relation`, `item`)로 거치게 한다. 그리고 `backend/src/boot.read-gate.test.ts`에 그 경로의 경우를 더한다. 그렇지 않으면 그 경로에는 이 규칙의 `allows`와 tombstone 가림이 적용되지 않는다. **비용 경고**: 규칙이 계속 거부하는 후보는 추출할 때마다 기록(`scope_policy_drops`)을 남기고, 원본의 접근 범위가 바뀔 때마다(좁아지든 넓어지든) 그런 기록이 있는 원본이 **모두 다시 추출**된다(원본마다 Provider 호출 한 번). 거부를 많이 내는 규칙은 범위가 바뀔 때 Provider 호출과 시간이 늘어난다. 다시 추출하는 도중 범위가 또 넓어지면 새 재추출은 등록되지 않고 다음 범위 변경 때까지 기다린다(그 재추출의 후보는 이전 범위로 골라졌다). 접근 범위 변경은 수집기의 범위 변경(`scope-change`)이나 JSONL 가져오기의 `revoke` 줄이 만들고, 내용을 지우지 않는 `scope-changed` 전파가 된다(삭제가 아니다). 한 추출에서 규칙이 거부하는 조합이 생기면 그 Insight 규칙 항목이 통째로 거부되어 그 추출의 Insight 재계산이 건너뛰어지고, 다음 변경(범위 변경의 재추출 포함)에서 맞춰진다. **외부 전송 등급과의 연결**: Broker는 원본의 접근 범위를 `scopeClass`(`providers/src/broker.ts`)에서 등급으로 바꾼다. 정책과 범위→등급 매핑 `ScopeGrading`(`providers/src/scope-grading.ts`, 공용 기본 `publicScopeGrading`은 모든 범위를 일반으로 매긴다)은 `BrokerDeps.scope`로 들어오고 `backend/src/composition.ts`의 `productCalls`가 잇는다. 가져온 범위(청구)는 인스턴스 범위와 정책의 `compare`로 견주어 그 범위의 등급보다 느슨해지지 않는다(I01-R15). 배포처는 S08에서 이 매핑을 끼운다. 매핑은 합성 등급을 낼 수 없고 허용된 등급(`SCOPE_CLASSES`)만 답해야 하며, 등급을 더하려면 바꿀 자리가 여럿이다(I01 spec "T06이 넘기는 것" 10③. 그 문구는 I01-T10의 몫). **확인**(두 가지가 서로 다른 장치를 본다): (가) `allows`: 합성 범위 쌍으로 포크가 쓴 규칙의 네 함수를 시험하는 자체 테스트(같은 범위, `null`, 비교할 수 없는 쌍, 거부되는 조합과 용도)가 통과하고, 등록에 규칙을 넣은 설치본이 알림 없이 시작하며, `allows`가 거부하는 범위의 합성 원본이 그 용도(예: `search`)의 검색·목록에서 사라지고 허용되는 원본은 그대로 보인다. 이 거부는 읽을 때의 판정이라 **기록을 남기지 않는다**(아래 수에 잡히지 않는다). (나) `combinable`: 묶을 수 없는 두 범위의 합성 원본에서 나온 후보나 Insight가 만들어지지 않고, 활동 화면의 "범위 정책으로 빠진 항목 N건"(`apps/web/src/job-text.ts`의 `invalidationText`, 상태 API `invalidations.scopePolicyDrops`)의 N이 오른다. 공용 저장소의 시험(`backend/src/scope-policy.test.ts`)은 기본 규칙과, 이름과 등록에 따라 어느 규칙이 쓰이는지(여섯 경우)만 증명한다. 배포처 규칙의 동작은 증명하지 않는다.
- [ ] **S22 설치본에서 실제 수집기의 삭제·권한 상실로 무효화와 파일 소거를 실행하고 기록.** 사용자가 원본을 지우거나(출처 삭제) 원 시스템에서 볼 권한을 잃으면(권한 상실) 제품은 tombstone을 쓰고, 그 원본에서 나온 사실·Insight·키워드 색인·엔진 투영을 지우고, 데이터 폴더의 파일에서도 내용이 사라지게 한다(`secure_delete`, 정리 작업). 공용 저장소는 이것을 합성 수집기와 개발 OS에서 증명했고, **실제 수집기가 내는 사건의 순서와 Windows 설치본의 파일 바이트는 증명하지 못했다.** 그것을 확인하는 것이 이 항목이다. 필요한 것: S01~S04 가운데 하나 이상의 실제 수집기, 그 시스템에서 합성 자료를 만들고 지우고 권한을 뺄 수 있는 시험 계정(실제 업무 자료로 하지 않는다), S10이 끝난 환경(R04 설치 파일로 설치하고 데이터 폴더 `%LOCALAPPDATA%\PKI`가 빈 Windows 11), Electron userData 폴더의 경로(실행기 설정의 `userDataDir`, 필수), 엔진·벡터 색인을 실제 구현으로 묶었다면 그 저장 위치(`extraScanDirs`). 실행: [verification/v02-site-flow/RUNBOOK.md](../verification/v02-site-flow/RUNBOOK.md) 8절의 순서대로 `python verification\v02-site-flow\run.py delete-scenario prepare|record`를 실행한다. `prepare`가 합성 카나리 세 개를 만들고(하나는 출처 삭제로, 하나는 권한 상실로 지우고 하나는 남겨 둘 원본에 넣는다), 사람이 수집기로 가져오기·삭제·권한 회수를 하고 앱을 닫은 뒤 `record`가 ① 정본 DB의 무효화 기록을 읽기 전용으로 세고(출처 삭제 1, 권한 상실 1, 화면 삭제 0이어야 한다) ② **세 곳의 모든 파일**에서 카나리를 찾고 ③ 키워드 색인의 단어 목록(SQLite `fts5vocab`, 읽기 전용)에 지운 카나리가 없는지 묻는다. **찾는 곳**: 데이터 폴더 `%LOCALAPPDATA%\PKI`(`-journal`·`-wal`·`-shm` 포함. 위치는 `storage/src/data-directory.ts`), Electron의 userData 폴더, 설정의 `extraScanDirs`. userData(Chromium 저장소: 캐시, Local Storage 등)는 **데이터 폴더 밖**이다. 데이터 폴더는 Electron의 userData와 일부러 따로 정했고(그 파일의 주석), `apps/desktop`은 userData 위치를 바꾸지 않으므로 Windows에서는 로밍 `%APPDATA%` 아래에 앱 이름으로 만들어진다. 이름은 패키지 이름 `pki-desktop`(`apps/desktop/build/build.ts`)에서 오지만 R04의 패키저가 다른 이름을 줄 수 있어 **설치본에서 확인된 값이 아니다.** 그래서 실행기는 경로를 추측하지 않고 설정의 `userDataDir`를 필수로 받으며 없으면 `preflight`가 설정 오류로 멈춘다. **찾지 않는 곳**: 이 세 곳 밖의 모든 것(OS 백업·볼륨 스냅샷, 임시 폴더, 크래시 덤프, 페이지 파일, Provider 쪽 보관은 S11, S05·S08에서 따로). 찾는 방식: 카나리 단어의 **끝 12글자**를 대소문자 구분 없이 ASCII, UTF-16LE, UTF-16BE로 찾는다. 끝만 찾는 까닭은 SQLite FTS5가 앞 단어와 앞부분이 같은 단어를 뒤쪽 조각만으로 저장하기 때문이다. 이것은 `@pki/testkit`의 `findCanaries`(`packages/testkit/src/canary-files.ts`: 쓴 그대로와 소문자만 찾는다)와 **다르다**. 읽을 수 없는 폴더나 파일이 하나라도 있으면(개수만 기록) 통과로 판정하지 않는다. 이 공용 저장소에는 실제 수집기가 없어 이 시나리오는 Windows 설치본이 아닌 곳에서 `배포처 후속`으로 시작하는 알림을 내고 0이 아닌 값으로 끝난다(`미구현, 배포처 후속`). 어떤 환경에서도 mock 실행을 검증으로 기록하지 않는다. 기록에는 OS, 앱 버전, 수집기 종류, 종류별 지운 수, 카나리 발견 수(파일 쪽과 색인 쪽, 둘 다 0이어야 한다), 읽을 수 없던 경로 수, 남겨 둔 원본의 카나리가 파일과 색인 양쪽에서 찾아졌는지(찾기가 카나리를 볼 수 있다는 증거)가 든다. **어떤 사건이 삭제인가**: 출처 삭제는 수집기의 `delete` 변경(JSONL 가져오기 `POST /api/imports`의 `delete` 줄)이고 tombstone 사유 `source-deleted`가 된다. 권한 상실은 `access-revoked` 변경(JSONL의 `access-revoked` 줄)이고 사유 `access-revoked`가 된다. 둘이 지우기를 일으킨다. 같은 JSONL의 `revoke` 줄은 내용을 그대로 두고 범위만 좁히는 범위 변경이므로 **삭제로 검증하지 않는다**(지운 수에 잡히지 않아 FAIL이 된다). 파일 수집기는 다시 가져올 때 빠진 줄을 삭제로 치지 않는다(`deletionsOnRescan: false`): 삭제는 명시한 줄이어야 한다. 실제 수집기가 이 사건을 어떤 순서로 내는지가 이 항목이 확인할 것이다. **알아 둘 것**: ① 지운 원본의 외부 식별자는 키 있는 해시로 바뀌어 남고 그 키는 정본 DB의 표(`identity_key`)에 있다. 시작할 때 키 행이 없는데 해시된 원본이 남아 있으면 시작을 거부한다(새 키를 몰래 만들지 않는다. `storage/src/identity.ts`). **정본 DB 파일 전체를 잃어도 같은 데이터 폴더의 tombstone 장부(`tombstone-ledger.jsonl`, I04-T10)가 남아 있으면** 새 DB가 장부 머리의 키를 받아들이고 장부의 줄을 다시 적용해 지난 삭제가 유지된다(오래된 백업으로 DB만 되돌려도 장부가 그 뒤의 삭제를 시작 때 다시 적용한다). **DB와 장부를 둘 다 잃으면** 새 키로 빈 DB를 만들어 정상 시작하고 지난 삭제를 모두 잊으며, 지운 자료가 수집기에서 다시 오면 다시 들어온다. 장부만 잃으면 앱이 새 장부를 만들고 "백업 뒤의 삭제는 다시 수집해야 반영됨"을 화면에 알린다. 장부는 백업 대상이 아니고 복원이 덮어쓰지 않으며, 배포처는 정본 DB 백업을 갖추되 장부 파일도 데이터 폴더와 함께 지키는 절차(H01)를 정해야 한다. **이 장부 파일(`tombstone-ledger*.jsonl`, 옆으로 치운 이름과 `.tmp` 포함)도 위 "찾는 곳" 안에 있어 찾기 대상이며 카나리 발견 수는 0이어야 한다**(장부가 데이터 폴더 밖에 놓이면 `extraScanDirs`에 넣는다). 장부 줄에는 원본의 글이 없고 키 있는 해시, 연결 인스턴스 ID와 종류, 숫자·사유·시각만 있다. ② tombstone 자체는 지우지 않고 남긴다(내용이 없고, 지우면 재수집이나 백업 복원이 지운 자료를 되살린다). 지운 원본의 모든 version은 그 tombstone이 덮으며 함께 지워진다. ③ 이 시나리오는 위 세 곳만 본다. 확인: `record`가 `I04-C3:delete-scenario PASS`를 내고, 붙이는 결과(결과 폴더 `v02-result`의 `result.md`)에 위 기록이 적힌다. 지운 카나리가 한 파일에서라도 찾아지면 `FAIL`이며 그 파일 종류(브라우저 저장소, 엔진 색인 등)를 배포처 안에서 찾아 공용 저장소에는 합성 재현만 알린다([ownership.md 5절](ownership.md)). userData에서 찾아지면 제품 결함이거나 H03의 기준에 넣을 항목이다(spec "남는 위험" 표).

### 포크의 조립과 설치본

이 절의 두 항목은 [I05 spec](specs/2026-11-22-I05-site-connector-registration.md)의 배포처 후속 항목이다. 용어: **조립 패키지**는 포크가 `site/composition/`에 두는 작은 패키지이고, 그 안의 **등록**(`SiteRegistration`) 하나에 수집기 종류와 만드는 함수, 인스턴스, 등급 매핑, 접근 범위 정책이 들어간다. 방법은 [connector-sdk.md](connector-sdk.md) 7장에, 이렇게 정한 이유는 [ADR 0018](adr/0018-fork-registration-at-build-time.md)에 있다.

- [ ] **S26 포크의 조립 패키지(`site/composition/`)를 만들고 수집기, 인스턴스, 등급 매핑, 접근 범위 정책을 등록하고 기록.** 공용 저장소는 이 장치를 예시 패키지(`packages/site-example/`)와 포크 모양으로 꾸민 버리는 작업 트리에서 한 번 돌려 본 것으로만 증명했다. 실제 수집기와 실제 의존성으로 포크가 `site/`만 더해 제품에 끼워지는지는 포크에서만 확인할 수 있다. 필요한 것: S01~S04 가운데 하나 이상의 수집기 패키지(`site/connectors/<이름>/`, 패키지 이름은 `@pki-site/`로 시작), 그 수집기의 계약 묶음 통과(`connectorContract`. 문서의 절차이고 빌드가 강제하지 않는다), 등록할 인스턴스의 설정. 하는 일: ① connector-sdk.md 7장대로 조립 패키지를 만든다(이름 `@pki-site/composition`, 등록 하나, 진입점 둘, 등록 검사 테스트. `tsconfig.json`은 예시를 그대로 복사하지 않는다). ② `pnpm install`, `pnpm lint && pnpm typecheck && pnpm test`, `pnpm --filter @pki-site/composition site-check <종류>`를 실행한다. ③ 공용 변경을 한 번 받아 오고 `git status --porcelain`으로 `site/` 밖에서 달라지거나 충돌한 추적 파일을 센다. 확인: 등록 검사 테스트가 빈 목록을 돌려주고, `site-check`가 등록한 종류마다 `미구현`이나 `unsupported-sdk-version`이 아닌 결과(`<종류>: ok`, 또는 빈 설정으로는 초기화할 수 없는 수집기가 내는 자기 설정 오류의 문구)를 알리고, `pnpm lint && pnpm typecheck && pnpm test`가 공용 테스트 파일을 고치지 않은 채 통과하고, 공용 변경을 받아 온 뒤 `site/` 밖의 충돌이 `pnpm-lock.yaml` 하나뿐이다(수집기 의존성에 설치 스크립트가 있으면 `pnpm-workspace.yaml`의 `allowBuilds`에 더한 `false` 줄도 함께 기록한다). `pnpm-lock.yaml`이 충돌하면 공용 쪽 내용을 취하고 `pnpm install`을 다시 실행한다. 주의: 공용의 빌드 검사는 네이티브 모듈이나 설치 스크립트가 정말 필요한 의존성을 지원하지 않는다. 그런 의존성이 필요하면 [ownership.md 5절](ownership.md)의 방법으로 공용에 알린다. 결과(명령, 종료 코드, 통과 수)는 배포처 안에만 남긴다.
- [ ] **S27 포크의 빌드를 Windows 11 설치본으로 만들어 등록한 수집기가 목록에 나오고 동기화되는지, 멈추는 수집기를 넣었을 때 앱이 제한 시간 안에 켜지는지 실행하고 기록.** 공용 저장소는 예시 수집기를 묶은 산출물을 macOS에서 묶어 보고 그 모듈 목록을 검사했다. 설치본이 Windows에서 켜지는지, 수집기의 의존성이 그곳에서 동작하는지는 확인하지 못했다. 빌드의 네이티브 모듈 검사는 빌드한 컴퓨터에 설치된 패키지만 보므로 그 통과는 Windows 동작의 증거가 아니다. 필요한 것: S26이 끝난 포크, R04의 설치 파일을 만드는 절차(S10), 합성 자료를 내는 시험 계정이나 지어낸 원 시스템. 하는 일: ① `pnpm --filter @pki/desktop build`로 만든 설치본을 Windows 11에 설치해 켠다. ② 등록한 수집기가 수집기 목록에 `ready`로 나오고 동기화하면 합성 자료가 원본으로 저장되는지 본다. ③ `initialize`가 비동기로 끝나지 않는 인스턴스를 하나 더 등록한 빌드로 켜서 앱이 제한 시간(`INITIALIZE_TIMEOUT_MS`, 잠정 10초) 안에 시작하고 그 인스턴스만 `unavailable`인지 본다. 동기 코드로 멈추는 수집기는 이 제한이 끊지 못하므로 일부러 넣지 않고, 수집기 코드 검토로 확인한다. ④ 배포처에서 10초가 알맞은지 재서 값을 기록하고, 맞지 않으면 [ownership.md 5절](ownership.md)의 방법으로 공용에 알린다(값은 공용 `backend/src/connectors.ts`의 `INITIALIZE_TIMEOUT_MS`이고 포크가 고치는 파일이 아니다). 확인: ②와 ③이 모두 맞다. 결과는 배포처 안에만 남기고, 범용으로 고칠 만한 문제만 합성 재현 형태로 알린다([ownership.md 5절](ownership.md)).

### 수집기 자격 증명

이 절의 두 항목은 [I06 spec](specs/2026-11-22-I06-connector-credentials.md)의 배포처 후속 항목이다. 용어: **칸**(slot)은 한 인스턴스가 필요로 하는 자격 증명 하나에 붙인 짧은 이름(예: `token`)이고 값이 아니라 자리의 이름이다. **접근자**는 수집기가 `initialize`의 둘째 인자로 받아 칸의 값을 읽는 작은 객체이며 읽을 때마다 저장소에서 가져온다. **변경 알림**은 화면이 값을 저장하거나 지운 뒤 백엔드에 알리는 호출이다. 방법은 [connector-sdk.md](connector-sdk.md) 8장에, 이렇게 정한 이유는 [ADR 0019](adr/0019-connector-credentials.md)에 있다. 수집기의 인증 방식을 고르는 일은 S04가, 앱이 OS 보호 저장소를 쓸 수 있는지의 확인은 S11이 이미 갖고 있으므로 다시 세지 않는다.

- [ ] **S28 실제 수집기의 자격 증명 칸을 선언하고 Windows 11 설치본에서 값을 넣어 동기화, 거부, 누출 없음, 저장소 불가를 실행하고 기록.** 공용 저장소는 이 길을 암호화 대역과 메모리 비밀 값 저장소, 지어낸 원 시스템으로 증명했고(macOS), 포크 모양으로 꾸민 버리는 작업 트리에서 공용 예시 수집기로 칸의 선언과 계약 묶음을 한 번 돌려 보았다. **Windows의 OS 보호(DPAPI)가 설치본에서 실제로 어떻게 동작하는지와 실제 원 시스템에서의 동작은 증명하지 못했다.** 그것을 확인하는 것이 이 항목이다. 필요한 것: S01~S04 가운데 하나 이상의 실제 수집기와 그 인증 방식(S04), 그 시스템의 시험 계정이 낸 자격 증명(실제 업무 자료로 하지 않는다), R04의 설치 파일을 만드는 절차(S10)와 깨끗한 Windows 11, 앱이 OS 보호 저장소를 쓸 수 있음(S11). 하는 일: ① 수집기가 필요한 자격 증명마다 칸 이름을 정해 포크 등록의 인스턴스 정의에 `credentials`로 선언하고, 수집기가 `initialize`의 접근자로 읽게 하며, 수집기의 계약 시험 시나리오에 `credentials`(지어낸 값)와 `rejected`(거부하는 지어낸 원 시스템)를 더해 위반 없이 통과시킨다(8장). ② `pnpm lint && pnpm typecheck && pnpm test`와 `pnpm --filter @pki-site/composition site-check <종류>`를 실행한다. `site-check`는 빈 설정으로 초기화하므로 칸을 읽기 전에 설정을 검사하는 수집기는 자기 설정 오류의 문구로 1로 끝나고, 읽는 것이 먼저인 수집기는 `<종류>: ok (credential-required)`와 0으로 끝난다. ③ 설치본을 Windows 11에 설치해 켜고 출처 화면에서 값을 넣어 다음을 실행한다. 확인: (가) 값을 넣으면 그 인스턴스가 `ready`가 되고 동기화된다. (나) 틀린 값을 넣으면 사유 `credential-rejected`("자격 증명이 거부됨")로 멈추고 값을 고쳐 넣으면 풀린다. (다) 데이터 폴더 `%LOCALAPPDATA%\PKI`의 모든 파일(`secrets.json`, 정본 DB와 `-wal`·`-shm`, 삭제 장부)과 설치본의 로그에 그 값이 원래 글, base64, 주소용 글(percent-encoding) 어느 모양으로도 없다. 설치본에서 로그가 어디에 남는지는 확인된 적이 없으므로 로그의 위치를 먼저 확인해 기록한다. (라) Windows의 OS 보호를 쓸 수 없는 계정에서는 값이 저장되지 않고 인스턴스가 "저장소를 쓸 수 없음"(`credential-store-unavailable`)으로 보인다. 그런 계정을 어떻게 만드는지는 배포처가 정한다. (마) 인스턴스가 가리키는 원 시스템의 주소를 바꿀 때는 인스턴스 ID도 바꾼다는 규칙을 포크의 등록이 지키는지 본다. 주소와 ID를 함께 바꾸면 그 인스턴스는 `credential-missing`이 되고 값을 다시 넣게 된다. 이 화면에서 넣는 값은 한 줄, 8192자 이하이고 여러 줄 값(PEM, JSON 키)은 받지 않는다. 원 시스템이 여러 줄 값을 요구하면 그 사실을 기록하고 [ownership.md 5절](ownership.md)의 방법으로 공용에 알린다. 이 화면에 남은 한계(코드가 넣은 값의 줄바꿈은 알 수 없다)는 connector-sdk.md 8장에 있다. 기록할 것: 결과(통과·실패·판정 불가)와 환경의 일반 정보(OS 버전, 앱 버전). 값과 계정 정보는 기록하지 않는다. 결과는 배포처 안에만 남기고, 범용으로 고칠 만한 문제만 합성 재현 형태로 알린다([ownership.md 5절](ownership.md)).
- [ ] **S29 실제 수집기와 그 의존성이 실제 원 시스템의 응답에서도 자격 증명을 레코드, 오류 문구, 자기 로그에 남기지 않는지 확인하고, 원 시스템의 만료와 잠금 정책을 기록.** 공용 저장소의 계약 묶음은 지어낸 원 시스템에서 값이 레코드, 건강 답, 오류, `console`과 표준 출력·오류에 나타나는지만 본다. 수집기가 파일이나 다른 통로로 쓴 것, 둘로 나눠 쓴 글, 16진수, `Basic` 머리말의 base64, 한 바퀴보다 늦게 도는 타이머가 쓴 글은 보지 못하고, 수집기의 의존성(HTTP 클라이언트 등)이 실제 응답에서 값을 남기는지는 알 수 없다. 제품은 값을 들고 있지 않아 수집기가 돌려준 레코드를 값과 견줄 수도 없다. 필요한 것: S28이 끝난 포크와 시험 계정, 수집기와 의존성의 로그 설정. 하는 일: ① 실제 원 시스템에서 수집을 돌린 뒤 수집기와 그 의존성이 남긴 레코드의 본문과 `metadata`, 던진 오류의 문구, 로그와 파일에 값이 없는지 찾는다(값의 세 모양과 `Authorization` 머리말에 실리는 모양을 함께 찾는다). ② 원 시스템이 자격 증명을 거부할 때 수집기가 `ConnectorCredentialError`를 던지는지(그 밖의 오류나 `healthCheck`의 다른 사유로 알리면 제품은 거부인지 알 수 없고 같은 값으로 한 시간마다 다시 시도한다), 일시 장애는 `ConnectorError`(`retryable: true`)로 알리는지 본다. ③ 원 시스템의 만료 주기와 계정 잠금 정책, 만료되었을 때 사용자가 값을 다시 넣는 절차를 적는다. 제품은 거부된 값을 한 시간마다 다시 시도하지 않고 변경 알림에는 30초에 한 번, 앱을 켤 때 한 번 시도하므로 그 횟수가 잠금 정책 안에 드는지 본다. ④ 원 시스템이 새 토큰을 내어 주며 옛 토큰을 버리는 방식(회전하는 토큰)이면 수집기가 값을 되쓸 길이 없다. 그 사실을 [ownership.md 5절](ownership.md)의 방법으로 공용 저장소에 알린다. 확인: 값이 어디에도 없고, 거부가 `ConnectorCredentialError`로 알려지며, 잠금 정책과 다시 시도 횟수가 맞다. 기록할 것: 결과와 원 시스템의 정책의 일반 요약(주소, 계정, 값은 적지 않는다). 결과는 배포처 안에만 남긴다.

### 인스턴스 범위의 묶음과 설치본 확인

이 절의 두 항목은 [I07 spec](specs/2026-11-22-I07-installed-scopes-file.md)의 배포처 후속 항목이다. 용어: **인스턴스 범위**는 배포처가 수집기 인스턴스마다 정해 둔 접근 범위이고, 사용자가 가져오기에서 적어 낸 범위가 이 범위보다 느슨한 등급을 얻지 못하게 하는 기준이다. **범위 파일**은 포크가 그 값을 적는 `site/config/connector-scopes.json`이다. **묶는다**는 빌드할 때 값을 실행본의 코드 묶음 안에 넣는 것이다. 방법은 [connector-sdk.md](connector-sdk.md) 7장의 "인스턴스 범위 파일"에, 이렇게 정한 이유는 [ADR 0020](adr/0020-installed-scopes-in-registration.md)에 있다.

- [ ] **S30 포크가 인스턴스 범위 파일을 채우고 등록에 묶어 기록.** 공용 저장소는 이 길을 예시 패키지와 포크 모양으로 꾸민 버리는 작업 트리에서 한 번 돌려 본 것으로만 증명했다(macOS). 실제 인스턴스 ID와 범위 값은 포크에서만 정할 수 있다. 필요한 것: S18의 수집기와 그 인스턴스의 ID, 인스턴스마다 정할 접근 범위. 하는 일: ① `site/config/connector-scopes.json`을 `{ "<인스턴스 ID>": ["범위", ...] }` 형식으로 채운다(예시의 값 `pki-example-scope`를 남기지 않는다). ② 조립 패키지의 `src/registration.ts`가 그 파일을 `import connectorScopes from "../../config/connector-scopes.json" with { type: "json" };`로 가져와 등록의 `connectorScopes`로 넘기게 한다. ③ `pnpm --filter @pki-site/composition site-check --scopes`와 `pnpm --filter @pki/desktop build`를 실행한다. 확인: `site-check --scopes`가 0으로 끝나고, 빌드가 통과하며, 빌드 보고서(`apps/desktop/dist` 폴더의 `build-report.json`)의 `connectorScopes`의 상태가 `bound`다. 기록할 것: 이 세 결과(범위 값과 인스턴스 ID는 기록하지 않는다). 실행 중에 만들어지는 가져오기 인스턴스(I02-B의 `jsonl-file:…`)는 ID를 미리 알 수 없어 범위 파일에 적을 수 없다. 적을 수 있는 인스턴스가 하나도 없으면 범위 파일을 두지 않고 그 사실을 기록한다(이때 `site-check --scopes`는 0이 아니고 보고서는 `absent`다). 빌드가 멈추면 오류의 문구가 이유를 알린다: `scopes-file-misplaced`(범위 파일이 `site/config/`가 아닌 자리에 있다), `scopes-file-unbound`(파일은 있는데 등록이 가져오지 않았다), `scopes-file-invalid`(형식이 틀렸다), `scopes-file-placeholder`(예시의 값이 그대로다).
- [ ] **S31 포크의 빌드를 Windows 11 설치본으로 만들어 검증 실행기의 `scopes-check`를 실행하고, 정본에 복사된 인스턴스 범위가 범위 파일의 값과 같다는 판정을 기록.** 공용 저장소는 값이 등록에서 정본까지 가는 것을 예시 등록과 지어낸 값으로 한 번 확인했다(macOS). 설치본에서의 실행은 하지 않았고, 설치본에서 백엔드 로그가 어디에 남는지도 확인하지 못했다. 그래서 확인은 로그가 아니라 정본을 읽는다. 필요한 것: S30이 끝나 보고서가 `bound`인 포크, 설치 파일을 만드는 절차(S10)와 깨끗한 Windows 11, 범위가 있는 인스턴스를 하나 이상 적은 범위 파일. 하는 일: ① 포크의 빌드로 만든 설치본을 설치해 켠다. ② 범위 파일이 이름 댄 인스턴스를 한 번 동기화하거나 가져와 그 인스턴스가 정본에 생기게 하고, 앱을 닫는다. ③ 검증 실행기의 `scopes-check`를 실행한다: `python verification\v02-site-flow\run.py scopes-check --config v02-result\config.json --expected site\config\connector-scopes.json --out v02-result`(절차는 `verification/v02-site-flow/RUNBOOK.md` 13절). 실행기를 쓸 수 없으면 정본 `pki.sqlite`를 읽기 전용으로 열어 `SELECT id, configured_scope FROM connector_instances`의 값을 범위 파일의 값과 손으로 견준다. 확인: 범위가 있는 인스턴스마다 정본의 `configured_scope`가 범위 파일의 값과 같다. 정본에는 정렬하고 중복을 없앤 값이 저장되므로 파일의 값도 정렬해서 견준다. 정본의 값이 `null`이면 읽히지 않은 것이다. 파일의 항목이 모두 `null`이면 읽혔어도 `null`이라 아무것도 증명하지 못하니 범위가 있는 항목을 하나 이상 두고 보고, 인스턴스가 정본에 아직 없으면 그것도 아무것도 증명하지 못한다. 이 확인이 증명하는 것은 값이 정본까지 복사되었다는 데까지이고, Broker가 그 값을 쓰는지는 공용 저장소의 시험이 본다. 기록할 것: 확인한 결과(통과·실패·판정 불가)와 견준 수. 범위 값과 인스턴스 ID는 공용 이슈에 올리지 않는다. 판정은 `PASS`·`FAIL`·`INCONCLUSIVE`이고, 결과 파일 `scopes-check-result.json`에는 OS, 앱 버전, 판정, 견준 수·같은 수·다른 수·정본에 없는 수만 담긴다(범위 값과 인스턴스 ID는 담기지 않는다).

### Semantic 등록부의 실측과 자동 승격

이 절의 한 항목은 [S01 spec](specs/2026-11-22-S01-semantic-registry.md)의 배포처 후속 항목이다. 용어: **표기**는 한 항목의 다른 글자(동의어·약어·다른 언어의 이름)이고 사실의 종류 `alias.*`로 쌓인다. **정의**는 항목이나 유형의 뜻풀이이고 사실의 종류 `definition`이다. **자동 승격**은 후보(`candidate`) 사실·관계가 조건을 채우면 사용자 대신 정책이 `verified`로 올리는 것이고, **정책이 올린 행**은 그렇게 올라간 행이다. 왜 기본이 꺼져 있고 켜면 무엇이 달라지는지(승격된 표기는 다른 원본의 연결 후보를 찾는 데 쓰이고, 그 이름이 Provider로 나간다)는 [ADR 0021](adr/0021-semantic-registry-on-existing-rows.md) 결정 3·4에 있고, 설정은 위 「실행 중 설정」의 `semantic.autoVerify` 줄이다.

- [ ] **S32 설치본과 실제 Provider로 표기·정의 추출을 실행하고, 자동 승격을 켤지 정해 기록.** 공용 저장소는 표기·정의 추출과 자동 승격을 test double Provider와 합성 자료로만 시험했다(macOS). 실제 Provider가 표기와 정의를 인용문 그대로 돌려주는지, 실제 자료에서 조건을 채운 승격이 얼마나 틀리는지는 확인하지 못했다. 필요한 것: 설치 파일을 만드는 절차(S10)와 깨끗한 Windows 11, 실제 Provider(S05·S07), 추출할 실제 자료(S01~S04의 수집기나 문서 폴더), 저장 데이터 보호 확인(S11). 하는 일: ① `semantic.autoVerify`를 한 번도 쓰지 않은 채로 실제 자료의 표기와 정의를 추출하고 앱을 닫은 뒤, 검증 실행기의 `semantic-scenario record --phase off`를 실행한다. ② `POST /api/settings/semantic`으로 `{ "autoVerify": true }`를 보내 자동 승격을 켜고, 추출이나 원본 변경이 행에 닿게 한 뒤(켜도 이미 있는 행을 훑지 않는다) 정책이 올린 행을 API로 확인해 틀린 것에 이의나 기각을 낸다. 앱을 닫고 `semantic-scenario record --phase on`을 실행한다. ③ 두 측정을 견주어 자동 승격을 켤지 정한다. 이 실행기(`semantic-scenario preflight|record`, [RUNBOOK](../verification/v02-site-flow/RUNBOOK.md) 10절)를 Windows 설치본과 실제 Provider가 아닌 환경에서 실행하면 `배포처 후속`으로 시작하는 알림을 내고 0이 아닌 값(3)으로 끝난다. 확인: 실행기가 0으로 끝나고 `--out`에 `semantic-counts.off.json`과 `semantic-counts.on.json`이 쓰인다. 이 파일은 측정이고 통과·실패 판정이 아니다. 수는 변경 이력의 줄이 아니라 지금 상태의 행을 센다(올렸다 되돌리고 다시 올린 행은 한 번이다). 내용 해시가 다른 거의 같은 글 두 원본은 두 원본으로 세므로, 그 둘이 만든 승격이 틀렸는지가 이 측정이 보려는 것이다. 기록할 것: 표기(`alias.*` 종류별)와 정의의 상태별 수, 자동 승격을 켰을 때 조건을 채워 올라간 수와 그 가운데 사용자가 틀렸다고 본 수, 켤지 정한 결과. 글·값·항목 이름은 기록하지 않는다. 공용 이슈에는 숫자만 올린다. 켜는 것은 릴리스 단계이고 이 항목의 기록이 그 근거다([ADR 0021](adr/0021-semantic-registry-on-existing-rows.md) 결정 3).

### 개체 해소와 자동 이의

이 절의 한 항목은 [S02 spec](specs/2026-11-22-S02-entity-resolution-temporal-graph.md)의 배포처 후속 항목이다. 용어: **합치기 후보**는 식별자·조직·프로젝트·이웃·시간 같은 결정론 신호로 같은 개체일 수 있다고 본 두 항목의 쌍(유사도 점수는 없고 합치는 것은 사용자뿐)이고, **합치기 줄**은 사용자가 두 항목을 합친 기록 하나(항목은 그대로 두고 한 쪽이 다른 쪽의 구성원이 된다)다. **구분 표시**는 두 항목이 다르다는 표시이고, **자동 이의**는 위 「실행 중 설정」의 `semantic.autoDispute`가 켜졌을 때 정책이 새 모순에 거는 이의다. 이렇게 정한 이유는 [ADR 0022](adr/0022-entity-resolution-and-conflicts.md)에 있다.

- [ ] **S33 설치본과 실제 Provider로 넓힌 유형의 추출과 합치기 후보를 실행하고, 자동 이의를 켤지 정해 기록.** 공용 저장소는 이 추출과 후보, 자동 이의를 test double Provider와 합성 자료로만 시험했다(macOS). 후보가 실제 자료에서 얼마나 맞는지, 실제 Provider가 준 유효 기간이 얼마나 틀리는지는 확인하지 못했다. 필요한 것: 설치 파일을 만드는 절차(S10)와 깨끗한 Windows 11, 실제 Provider(S05·S07), 추출할 실제 자료(S01~S04의 수집기나 문서 폴더), 저장 데이터 보호 확인(S11). 하는 일: ① `semantic.autoDispute`를 한 번도 쓰지 않은 채로 실제 자료를 추출하고 합치기 후보를 훑어 받아들이거나 물리친 뒤 앱을 닫고, 검증 실행기의 `entity-scenario record --phase off`를 실행한다. ② `semantic.autoDispute`를 `on`으로 쓰고(설정 화면은 아직 없다) 다음 추출이 행에 닿게 한 뒤(켜도 이미 있는 행을 훑지 않는다) 충돌 목록(`GET /api/conflicts`)에서 정책이 이의를 건 사실을 확인해 틀린 것을 되돌린다. 앱을 닫고 `entity-scenario record --phase on`을 실행한다. ③ 두 측정을 견주어 자동 이의를 켤지 정한다. 이 실행기(`entity-scenario preflight|record`, [RUNBOOK](../verification/v02-site-flow/RUNBOOK.md) 11절)를 Windows 설치본과 실제 Provider가 아닌 환경에서 실행하면 `배포처 후속`으로 시작하는 알림을 내고 0이 아닌 값(3)으로 끝난다. 확인: 실행기가 0으로 끝나고 `--out`에 `entity-counts.off.json`과 `entity-counts.on.json`이 쓰인다. 이 파일은 측정이고 통과·실패 판정이 아니다. 수는 변경 이력의 줄이 아니라 지금 상태의 행을 센다. 기록할 것: 항목 유형별 수, 합치기 후보의 수, 합치기 줄의 수(적용 중과 쉬는 중)와 구분 표시의 수(남긴 쪽별: 사용자, `link-check`=`links_refused`), 유효 구간이 붙은 사실의 수와 그 가운데 사용자가 구간을 고친 수, 자동 이의를 켰을 때의 이의 수, 켤지 정한 결과. 합치기 줄이 후보에서 왔는지 사용자가 직접 골랐는지는 저장되지 않아 "후보 가운데 받아들인 수"는 따로 적을 수 없다. 글·값·항목 이름은 기록하지 않는다. 결과는 이슈 #23(S02)에 남기고 공용 이슈에는 숫자만 올린다. 켜는 것은 릴리스 단계이고 이 항목의 기록이 그 근거다([ADR 0022](adr/0022-entity-resolution-and-conflicts.md)).

### 분석 의미의 실측과 프로파일

이 절의 한 항목은 [S03 spec](specs/2026-11-22-S03-analytical-semantic.md)의 배포처 후속 항목이다. 용어: **표 프로파일**은 가져온 CSV·XLSX에서 머리 행과 열 이름, 행 수를 읽어 Dataset 항목과 표 행을 만드는 일이고, **데이터 검사**는 사용자가 적은 Grain(행을 구별하는 열)과 계산 기준이 실제 표와 맞는지 세어 보는 일이다. 제품은 값을 계산하지 않는다. 왜 프로파일이 꺼진 채로 나가는지는 [ADR 0023](adr/0023-analytical-semantic-rows-and-data-checks.md) 결정 5에 있고, 설정 두 개는 아래 표에 적는다(「실행 중 설정」 표에는 아직 없다. 그 표의 키 목록을 대조하는 시험이 `providers/` 안에 있어, 두 키를 그 표로 옮기는 일은 그 시험에 두 줄을 더하는 것과 함께 한다).

| 키 | 뜻 | 기본값 |
|---|---|---|
| `analytical.profile` | `on` 또는 `off`(정확히 `on`일 때만 켬). 가져온 표 원본(CSV·XLSX)에서 머리 행과 열 이름을 읽어 Dataset 항목·표 행·열 사실을 만드는 **표 프로파일**을 켤지([S03 spec R6](specs/2026-11-22-S03-analytical-semantic.md), [ADR 0023](adr/0023-analytical-semantic-rows-and-data-checks.md) 결정 5). 켜면 이미 있는 표 원본마다 프로파일 작업이 쌓이고, 켜기 전에 가져온 표는 그때 함께 훑는다. 모든 표에서 머리 행을 짐작하는 규칙이라 표가 아닌 자료를 표로 잡을 수 있으므로 **켜기 전에 S34로 얼마나 나오는지 잰다**. 설정 API `POST /api/settings/analytical`(`{ "profile": true, "maxCells": 200000 }`)으로 바꾸며 설정 화면에는 없다 | 끔 |
| `analytical.maxCells` | 표 하나의 칸 수(열 수 × (자료 행 수 + 머리 행 1))의 상한인 양의 정수. 넘는 표는 표로 만들지 않는다. 범위 밖이거나 정수가 아닌 값은 기본값으로 읽는다. 배포처의 실제 표 크기와 PC의 성능에 맞춰 S34로 정한다. 설정 API는 `analytical.profile`과 같다 | 200000 |

- [ ] **S34 설치본과 실제 Provider로 표 자료의 분석 의미 추출·Dataset 프로파일·데이터 검사를 실행하고, 프로파일을 켤지와 한도 값을 정해 기록.** 공용 저장소는 이 경로를 합성 표 파일, test double Provider, 개발 OS(macOS)로만 시험했다. 실제 스프레드시트에서 표가 아닌 것을 표로 잡는 비율과 큰 시트에서 걸리는 시간은 재지 못했다. 필요한 것: 설치 파일을 만드는 절차(S10)와 깨끗한 Windows 11, 실제 Provider(S05·S07), 실제 표 자료(S01~S04의 수집기나 문서 폴더에 든 CSV·XLSX)와 그 표를 설명하는 문서, 저장 데이터 보호 확인(S11). 하는 일: ① 설치된 exe로 `POST /api/settings/analytical`에 `{ "profile": true, "maxCells": 200000 }`을 보내 `analytical.profile`을 켜고(설정 화면은 없다. 두 키 모두 필수이며, 한도를 따로 정하지 않았으면 기본값 200000을 보낸다) 표 자료와 설명 문서를 추출한 뒤 `GET /api/analytical`로 목록을 보며 맞지 않는 표와 행을 되돌리고 앱을 닫는다. ② 검증 실행기의 `analytical-scenario record`를 실행한다. 이 실행기(`analytical-scenario preflight|record`, [RUNBOOK](../verification/v02-site-flow/RUNBOOK.md) 12절)를 Windows 설치본과 실제 Provider가 아닌 환경에서 실행하면 `배포처 후속`으로 시작하는 알림을 내고 종료 값 3으로 끝나며 아무것도 쓰지 않는다. ③ 숫자를 보고 `analytical.profile`을 켤지와 `analytical.maxCells`의 값을 정한다. 확인: `preflight`가 `preflight ok`로 끝나고 `record`가 `analytical-counts.json`을 쓴다. 파일에는 표 원본·표 행의 수, 표가 없는 표 원본의 수, 사용자가 물리친 Dataset의 수, 분석용 항목·사실의 종류별 수, 검사 이름별 통과·실패 수, 가장 큰 표의 행 수와 프로파일·검사 작업 시간이 들어간다(글은 없다). 기록할 것: 이 숫자들(글, 값, 항목 이름은 기록하지 않는다)과 정한 값. **표로 보지 않은 사유별 수는 제품이 사유를 저장하지 않아 기록되지 않고, 시간은 작업이 큐에서 기다린 시간을 포함한 상한이다.** 이 실행기는 Windows에서 돌려 본 적이 없다. 결과는 이슈 #24(S03)에 남긴다.

### Wiki 투영의 실측

이 절의 한 항목은 [K01 spec](specs/2026-11-23-K01-wiki-projection.md)의 배포처 후속 항목이다. 용어: **Wiki 페이지**는 정본의 항목 묶음 하나(또는 Insight 하나)에 대해 사실·관계와 그 근거를 모아 놓은 사본이고, 언제든 정본에서 다시 만들 수 있다. **계보**는 그 페이지가 어느 원본 version에서 나왔는지의 목록이고, 페이지를 보여도 되는지는 이 계보의 접근 범위로 읽을 때마다 정한다. **다시 만들기**는 화면의 "위키" 아래 버튼으로 모든 페이지를 다시 쓰게 하는 것이다.

- [ ] **S35 배포처 범위 정책을 건 채로 Wiki를 열어 보고, 요약 전송 정책과 호출 예산을 확인하고, 실제 규모에서 만드는 시간을 재어 기록.** 공용 저장소는 Wiki를 합성 자료와 개발 OS에서만 시험했고(macOS), 범위 정책은 한 범위를 거부하는 시험용 정책으로만 걸어 보았다. 필요한 것: S21의 범위 정책(`ScopePolicy`)을 단 설치본, 실제 수집기로 쌓은 자료(S01~S04), 요약을 켜 볼 때는 실제 Provider와 그 전송 정책(S05~S07). 하는 일: ① 배포처 범위 정책을 건 채로 "위키"를 열어, 허용되지 않은 범위 원본의 주장·요약·backlink가 페이지와 목록에 나오지 않는지 본다(합성 시험의 K01-C3b ②를 실제 정책으로 되풀이하는 것이다). 서로 다른 범위를 한 페이지에 묶는 것을 정책이 거부하는 경우, 쓰기는 그 정책을 묻지 않으므로 저장된 페이지에는 그 조합이 있을 수 있고 읽을 때만 걸러진다는 점을 함께 본다. ② 요약 기능(K01-T2)이 들어와 `wiki.summary`를 켜기 전에, 요약에 실리는 원본의 등급이 배포처 전송 정책에서 허용되는지, 요약 호출이 추출의 호출 예산(S20)을 밀어내지 않는지 잰다. ③ 실제 규모의 정본에서 첫 만들기와 바뀐 것만 다시 만드는 증분 만들기의 시간을 잰다(만들기는 매번 모든 대상을 훑고 한 번에 쓰는 페이지에는 500쪽 상한이 있어, 그 이음은 공용 저장소에서 시험하지 않았다). 확인: 정책이 거부한 범위의 원본에서만 나온 페이지는 목록에도 없고 열면 없는 페이지와 같은 답이며, 정책이 허용한 범위의 페이지는 그대로 열린다. 기록할 것: 만든 페이지 수, 첫 만들기와 증분 만들기의 시간, 상한에 걸려 여러 번에 나눠 만든 횟수, 정책으로 가려진 페이지 수. 글·페이지 제목·메모는 기록하지 않는다. 공용 이슈에는 숫자만 올린다.

### 피드백 학습의 실측

이 절의 한 항목은 [P03 spec](specs/2026-11-23-P03-feedback-learning.md)의 배포처 후속 항목이다. 용어: **선호 신호**는 어떤 Insight나 항목에 사용자가 준 "유용함·중요함·관련 없음" 같은 선호 피드백을 숫자 하나(-100~100)와 숨김·알림 억제 표시 둘로 줄인 값이고, **유형 단계**는 그 대상에 직접 준 피드백이 없을 때 같은 유형의 다른 Insight에 달린 피드백으로 가중을 미루어 정하는 단계다. 아래 설정은 저장소 설정 하나뿐이고 API·화면이 없어 `settings` 테이블에 직접 쓴다.

| 키 | 뜻 | 기본값 |
|---|---|---|
| `feedback.learned` | `on` 또는 `off`(정확히 `on`일 때만 켬). 켜면 사용자가 누르지 않은 Insight의 순위를 같은 유형의 피드백으로 움직이는 유형 단계가 값을 낸다. 직접 준 선호, 항목에 준 선호, "관련 없음"·"이미 알고 있음"의 숨김과 알림 억제는 이 설정과 무관하게 늘 적용된다. 켜면 항목에 준 선호가 그 항목이 근거인 원본의 검색 순위도 조금(최대 ±10%) 움직인다(X01-R19) | 끔 |

- [ ] **S36 실제 사용 기록으로 개인화 전후 지표를 잰 뒤 `feedback.learned`를 켤지 정하고, 배포처 범위 정책을 건 채로 "최근 피드백"을 열어 확인해 기록.** 공용 저장소는 피드백 학습을 합성 자료와 개발 OS(macOS)로만 시험했고, 개인화가 실제로 쓸모 있는 순서를 만드는지는 확인하지 못했다. 필요한 것: 피드백을 쌓을 실제 사용 기간과 실제 수집기로 쌓은 자료(S01~S04), S21의 범위 정책(`ScopePolicy`)을 단 설치본. 하는 일: ① 한 주기 이상 홈의 Insight에 피드백을 주며 쓰고, 피드백을 주지 않은 Insight를 대상으로 [EVALUATION](EVALUATION.md) 2.2절의 두 지표(상위 3건 관련 비율, 관련 있음 평균 순위)를 선호 신호 없이와 `feedback.learned`를 켠 채로 각각 잰다. ② 켠 쪽이 나쁘지 않을 때만 `feedback.learned`를 `on`으로 쓴다(켜는 것은 릴리스 단계다). ③ 배포처 범위 정책을 건 채로 홈 아래 "최근 피드백"을 열어, 허용되지 않은 범위의 Insight·항목·사실·관계에 준 피드백이 목록에 나오지 않고 그 대상에 대한 기록·취소가 없는 대상과 같은 `not-found`로 답하는지 본다. 확인: 정책이 거부한 범위의 대상이 목록에 없고, 허용된 범위의 대상은 그대로 나온다. 기록할 것: 피드백 줄의 종류별 수, 두 지표의 값, `feedback.learned`를 켤지 정한 결과, 정책으로 가려진 줄의 수. 글·Insight 요약·항목 이름은 기록하지 않는다. 공용 이슈에는 숫자만 올린다.

### 질문의 실측

이 절의 항목은 [X01 spec](specs/2026-11-23-X01-retrieval-qa.md)의 배포처 후속 항목이다(번호는 이 문서가 합쳐질 때의 다음 번호이며, 병렬 브랜치가 같은 번호를 쓰면 나중에 합치는 쪽이 옮긴다). 용어: **질문**은 화면의 "질문"에서 말로 묻는 것이고, **전략**은 질문에 맞는 원본을 찾는 한 가지 방법(키워드, 벡터, 그래프 등)이다. **인용**은 답의 문장 하나가 기대는 원본 version과 그 안의 글자 위치이고, 코드가 원문에서 인용문을 정확히 한 번 찾은 문장만 화면에 나간다. 질문과 답은 저장하지 않으므로 아래에 쓰는 설정 키는 없다. 기본으로 켜는 전략은 코드 상수 하나이고 근거는 [ADR 0025](adr/0025-retrieval-strategies.md)다.

- [ ] **S37 실제 Provider로 질문해 인용문이 원문과 맞는 비율, 답 시간, 호출 예산을 재고 Citation Accuracy를 채점해 기록.** 공용 저장소는 답을 합성 자료와 test double Provider로만 시험했고(인용문은 문서 본문을 그대로 베끼는 대역이다), 실제 Provider의 인용문이 원문과 맞는지는 재지 못했다. 필요한 것: 실제 Provider(S05~S07)와 그 전송 동의, 실제 수집기로 쌓은 자료(S01~S04), [EVALUATION](EVALUATION.md)의 Citation Accuracy 기준. 하는 일: ① "질문"에서 실제 자료에 대한 질문 여러 개를 "답 받기"를 켠 채 묻는다. ② 문장마다 인용문이 원본에 있는 글인지 사람이 확인해, 확인되어 나온 문장의 수와 버려진 문장의 수(`done`의 버린 수)를 센다. ③ 질문 하나의 답이 나오기까지 걸린 시간과, 이 호출이 추출의 호출 예산(S20)을 밀어내는지 본다. 확인: 화면에 나온 문장의 인용문이 모두 원본에 있고, 버려진 문장은 화면에 나오지 않는다. 기록할 것: 질문 수, 나온 문장 수, 버린 문장 수, 인용이 맞은 비율, 답 시간의 분포, 예산이 밀렸는지. 질문·답·인용문·제목은 기록하지 않는다. 공용 이슈에는 숫자만 올린다.
- [ ] **S38 배포처 범위 정책을 건 채로 질문해 허용되지 않은 범위의 원본이 적중·답·Provider 요청에 나오지 않는지 확인하고, 질문 글의 전송 등급을 정해 기록.** 공용 저장소는 범위 정책을 한 범위를 거부하는 시험용 정책으로만 걸어 보았다. 필요한 것: S21의 범위 정책(`ScopePolicy`)을 단 설치본, 허용 범위와 거부 범위의 원본이 섞인 실제 자료, 실제 Provider와 그 전송 정책(S05~S07). 하는 일: ① 거부 범위의 원본에만 있는 낱말로 질문해 적중 목록, 답, 호출 기록(Activity)에 그 원본의 제목·글·번호가 나오지 않는지, 보이는 원본의 적중 수와 순서가 거부 범위가 없을 때와 같은지 본다. ② 정책이 `search`는 허용하고 `answer`만 거부하는 범위를 만들어, 적중에는 나오고 Provider 요청에는 들어가지 않는지 본다. ③ 질문 글은 출처 없는 글이라 Broker가 가장 엄격한 등급으로 매긴다(X01-D10). 배포처 전송 정책이 이 등급을 어떻게 판정하는지 정하고, 질문이 막히면 그 이유가 화면에 "답을 만들 수 없음"으로 나오는지 본다. 확인: 거부된 범위의 원본은 어디에도 나오지 않고 허용된 범위는 그대로 나온다. 기록할 것: 확인한 범위 정책의 종류 수, 질문 등급의 판정 결과. 글·제목은 기록하지 않는다.
- [ ] **S39 실제 벡터 구현이 들어온 뒤 `vector` 전략과 `search` 경로를 실제 구현으로 확인해 기록.** 공용 저장소는 벡터 색인을 규격과 메모리 구현으로만 두었고, X01은 찾는 쪽(`search`)만 불러 구현이 없으면 "사용 불가"를 알린다(문서 임베딩과 `upsert`는 R07 뒤의 벡터 구현 작업의 몫이다). 필요한 것: R07이 고른 벡터 구현이 묶인 설치본, 준비된 로컬 임베딩 모델 팩(S08~S09). 구현이 아직 없으면 이 항목은 "해당 없음(벡터 구현 없음)"으로 닫고 이유를 적는다. 하는 일: ① 서버 옵션 `askStrategies`에 `vector`를 더해 같은 질문을 묻고 `route`에서 `vector`가 `used`로 나오는지, 모델이나 색인이 없을 때는 `unavailable`과 이유가 나오고 다른 전략의 결과가 몰래 바뀌어 들어오지 않는지 본다. ② 원본을 삭제한 뒤 그 원본이 벡터 적중에도 나오지 않는지 본다. 확인: 위 둘. 기록할 것: 구현의 이름과 버전, 확인 결과.
- [ ] **S40 실제 추출과 코퍼스 T1에서 다섯 구성을 다시 재서 기본 전략 목록을 확정하거나 고치고, 봉인 eval을 한 번 돌려 기록.** 공용 저장소의 측정은 방해 문서 없는 코퍼스 T0와, 지식을 정답 라벨에서 심은 "상한"뿐이라 ADR 0025의 기본 켬 목록(키워드·메타데이터·합치기)은 잠정이다. 필요한 것: 실제 Provider로 한 추출(S05~S07), 코퍼스 T1([EVALUATION](EVALUATION.md)), 준비된 로컬 모델 팩(벡터 구성용), `backend/src/retrieval-ablation.ts`와 `eval/scorer`. 하는 일: ① 실제 추출을 거친 지식 위에서 다섯 구성(키워드 / +벡터 / +그래프 / +항목·시간 / +Wiki)을 dev 분할로 다시 재어 Recall@5·Precision@5·MRR을 구한다. ② EVALUATION 3절의 유지 조건으로 전략마다 켤지를 판정해 코드의 기본 목록 상수와 ADR 0025를 함께 고친다(둘이 어긋나면 대조 시험이 실패한다). ③ 최종 구성에 봉인된 eval 분할을 **한 번만** 돌린다. 확인: ADR과 기본 목록 상수가 같고 결과 파일이 `eval/results/`에 있다. 기록할 것: 구성별 세 지표, 재지 못한 구성과 이유, 판정. 원본의 글은 기록하지 않는다. 결과는 이슈 #30(X01)에 남긴다.
- [ ] **S41 Windows 11 설치본(Electron)에서 "질문" 화면이 단계별로 채워지고 취소가 되는지, 한 줄씩 오는 응답(NDJSON)이 쉘 안에서 끊기지 않는지 확인해 기록.** 공용 저장소는 화면을 브라우저(macOS, Chromium)에서만 시험했고 Electron 전용 시험은 없다. 필요한 것: 설치 파일을 만드는 절차(S10)와 깨끗한 Windows 11, 실제 Provider(S05~S07). 하는 일: ① 설치본에서 "질문"을 열어 묻고, 고른 길 → 적중 → 답 대기 표시 → 문장과 인용문 순서로 채워지는지 본다(응답이 모여서 한꺼번에 오면 중간 단계가 보이지 않는다). ② 답을 기다리는 동안 "취소"를 눌러 화면이 멈추고 "취소했습니다" 안내가 나오며, 이어서 호출 기록의 그 호출이 취소로 남는지 본다. ③ 화면 보안 설정(CSP)이 이 응답을 막지 않는지 본다. 확인: 위 셋. 기록할 것: 환경(Windows·Electron 버전)과 각 확인의 통과 여부. 질문·답은 기록하지 않는다.

### 탐색 화면의 확인

이 절의 항목은 [X02 spec](specs/2026-11-23-X02-explore-ux.md)의 배포처 후속 항목이다(번호는 이 문서가 합쳐질 때의 다음 번호이며, 병렬 브랜치가 같은 번호를 쓰면 나중에 합치는 쪽이 옮긴다). 용어: **탐색**은 항목 하나를 이름으로 찾아 이웃 관계·시간순 사실·근거 원본을 보는 화면이고, **지식 검토**는 후보를 승인·기각하고 충돌을 검토하는 화면이다. 두 화면은 아무것도 저장하지 않는다.

- [ ] **S42 배포처 범위 정책을 건 채로 "탐색"과 "지식 검토"를 열어, 허용되지 않은 범위의 항목·원본이 목록·이웃·근거에 나오지 않는지 확인해 기록.** 공용 저장소는 범위 정책을 한 범위를 거부하는 시험용 정책으로만 걸어 보았다(`backend/src/explore-gate.test.ts`). 필요한 것: S21의 범위 정책(`ScopePolicy`)을 단 설치본, 허용 범위와 거부 범위의 원본이 섞인 실제 수집기 자료. 하는 일: ① "탐색"에서 거부 범위의 원본에만 있는 항목 이름으로 찾아 목록에 나오지 않는지, 보이는 항목의 순서와 "더 보기"가 거부 범위가 없을 때와 같은지 본다. ② 허용된 항목의 이웃·타임라인·근거 보기에 거부 범위의 항목, 관계, 원본의 제목·글이 나오지 않는지 본다. ③ "지식 검토"의 목록과 충돌 쌍에 같은 것이 나오지 않는지 본다. ④ 실제 수집기 자료에서 두 화면이 읽을 만한지(이름·값 표시, 이웃 수) 눈으로 본다. 확인: 위 넷. 기록할 것: 확인한 범위 정책의 종류 수, 화면에서 읽기 어려웠던 점. 항목 이름·원본의 글은 기록하지 않는다.
### 백업·복원의 실측

- [ ] **S43 설치본에서 백업 → 삭제 → 복원 → 다시 시작을 실행해 지운 내용이 데이터 폴더의 파일 바이트에 없는지 기록하고, 백업 폴더가 회사 정책상 허용된 위치인지 정함.** 공용 저장소는 백업·복원([H01](specs/2026-11-23-H01-backup-restore.md))을 합성 자료와 개발 OS(macOS)로만 시험했고, Windows 설치본의 이름 바꾸기·되돌림, 실제 크기에서의 시간, 열린 파일 옆의 동작은 확인하지 못했다. 필요한 것: S10이 끝난 Windows 11 설치본, 합성 원본 둘 이상, 백업을 둘 폴더. 실행: 설정의 "백업·복원"에서 폴더를 정하고 암호구로 백업을 만든다 → 원본 하나를 지우고 전송 동의를 거둔다 → 그 백업을 살펴본 뒤 복원하고 앱을 다시 시작한다. 확인: ① 지운 원본의 카나리가 데이터 폴더 `%LOCALAPPDATA%\PKI`의 모든 파일(`-journal` 포함)에 없다(S22와 같은 방식) ② `pki.sqlite.before-restore`와 `restore\` 폴더가 남지 않는다 ③ 마무리 전에 시작이 실패하게 했을 때(예: 장부 줄을 적용하지 못하는 상태) 이전 데이터로 뜨고 설정에 실패 코드가 보인다 ④ 백업 파일 크기와 백업·준비·적용 시간 ⑤ `safeStorage`의 비밀 값이 복원 뒤에도 읽힌다(백업에는 없고 복원이 덮지 않는다). 백업 폴더(`backup.folder`)가 회사 정책상 허용된 위치인지도 여기서 정한다. 기록: OS, 앱 버전, 위 다섯 항목의 결과, 지난 `restore.last`의 수. 결과는 이슈 #32에 남긴다.

### 점검(재검토)의 실측

이 절의 한 항목은 [K02 spec](specs/2026-11-23-K02-reflection-consolidation.md)의 배포처 후속 항목이다. 용어: **점검 발견**은 규칙이 "고쳐 볼 만하다"고 알리는 후보이며 지식이 아니고, 받아들이거나 닫는 것은 사용자다. **오탐**은 사용자가 닫은 발견, **미탐**은 사용자가 "놓친 것"으로 알린 것이다. **LLM 의견**은 발견 하나에 Provider가 붙이는 판정(같음·관련·무관)이다.

- [ ] **S43 실제 자료에서 점검 규칙의 오탐·미탐을 모으고, 배포처 범위 정책을 건 채로 "점검"을 열어 보고, LLM 의견을 켜기 전에 전송 정책과 호출 예산을 확인하고, 실제 규모에서 재검토 시간을 재어 기록.** 공용 저장소는 점검을 합성 자료와 개발 OS(macOS)에서만 시험했고, 범위 정책은 한 범위를 거부하는 시험용 정책으로만 걸어 보았으며, LLM 의견은 test double Provider로만 시험했다. 필요한 것: 실제 수집기로 쌓은 자료(S01~S04), S21의 범위 정책(`ScopePolicy`)을 단 설치본, 의견을 켜 볼 때는 실제 Provider와 그 전송 정책(S05~S07). 하는 일: ① 점검을 한 주기 이상 돌리며 규칙별 오탐·미탐 수("점검" 화면의 규칙별 수)를 모아 문턱(K02-D5·R6의 상한과 `missing-link`의 원본 2개·5쌍)을 정한다. ② 배포처 범위 정책을 건 채로 "점검"을 열어, 허용되지 않은 범위 원본에 기댄 발견이 목록과 수에 나오지 않는지 본다(합성 시험의 K02-C3b ③을 실제 정책으로 되풀이하는 것이다). ③ `reflection.refine`을 켜기 전에, 의견에 실리는 원본의 등급이 배포처 전송 정책에서 허용되는지, 호출 예산(S20)이 추출을 밀어내지 않는지 잰다. 켜는 API·화면이 없어 저장소의 설정 쓰기 경로로 `on`을 쓴다. ④ 실제 규모의 정본에서 정본을 바꾸는 가져오기에 dirty 트리거가 더하는 시간과, 재검토 한 번의 시간(일간·주간)을 잰다. 확인: 정책이 거부한 범위의 원본에서만 나온 발견은 목록에도 수에도 없고 결정 요청은 없는 발견과 같은 답이며, 의견이 켜진 뒤 동의·전송 정책이 막으면 의견 작업은 `held`로 남고 발견은 의견 없이 그대로 보인다. 기록할 것: 규칙별 열림·받아들임·오탐·미탐 수, 재검토 한 번의 시간과 본 묶음 수, 가져오기 시간의 증가, 의견 호출 수. 글·항목 이름은 기록하지 않는다. 공용 이슈에는 숫자만 올린다.

### 알림과 OS 통로의 실측

이 절의 한 항목은 [P02 spec](specs/2026-11-23-P02-notifications-digest-timeline.md)의 배포처 후속 항목이다. 용어: **피드**는 앱 안의 알림 목록이고 OS 권한과 무관하게 항상 쌓인다. **OS 알림**은 Electron 쉘만 띄우는, 건수만 적힌 고정 문구의 토스트다. **조용한 시간**은 OS 알림만 미루는 시간대다.

| 키 | 뜻 | 기본값 |
|---|---|---|
| `notifications.os` | `on` 또는 `off`(정확히 `off`일 때만 끔). 끄면 OS 통로만 `unavailable`로 끝나고 피드는 그대로 쌓인다. 알림 화면의 "알림 설정"과 `POST /api/settings/notifications`로 바꾼다 | 켬 |
| `notifications.quietHours` | `{"enabled":true,"start":"22:00","end":"08:00"}` 꼴의 JSON. 이 시간대에는 OS 알림을 띄우지 않고 쌓아 두었다가 끝나면 건수 하나로 보낸다. 시각은 실행하는 PC의 시간대다. 값이 틀리면 기본값으로 읽는다 | 22:00~08:00, 켬 |
| `notifications.snoozeUntil` | 이 시각(ISO)까지 모든 OS 알림을 보류한다. 비어 있거나 틀리면 일시 중지가 없다 | 없음 |

작업 `notify`의 세 주기(`scan` 10분마다, `daily` 매일 09:00, `weekly` 월요일 09:10)는 활동 화면의 주기 목록에서 끄거나 바꾼다.

- [ ] **S44 Windows 11 설치본에서 OS 알림과 트레이를 확인하고, 배포처 범위 정책이 용도 `notify`에 답하는 값을 정하고, 실제 자료로 한 주 이상 돌려 문턱과 시각을 정해 기록.** 공용 저장소는 알림을 합성 자료와 개발 OS(macOS)에서, 쉘 쪽은 가짜 Electron 객체의 단위 시험으로만 확인했고 실제 토스트는 한 번도 띄우지 않았다. 필요한 것: 설치 파일을 만드는 절차(S10)와 깨끗한 Windows 11, S21의 범위 정책(`ScopePolicy`)을 단 설치본, 실제 수집기로 쌓은 자료(S01~S04)와 Insight가 생길 만큼의 사용 기간. 하는 일: ① 설치본에서 즉시 알림 하나를 만들어(문턱 이상의 Insight) 토스트가 뜨는지, 잠금 화면과 알림 센터에 "확인할 변경이 N건 있습니다" 꼴의 건수 문구만 보이는지(Insight의 이름·문장이 없는지), 트레이 아이콘의 툴팁이 읽지 않은 수인지 본다. 앱 ID(AppUserModelID)가 없을 때 토스트가 뜨지 않거나 보낸 곳 이름이 이상하게 나오면 설치본 작업(S10·H02)에 넘긴다. ② 집중 지원(방해 금지)을 켰을 때와 Windows 설정에서 이 앱의 알림 권한을 끈 때 피드는 그대로 쌓이고 오류가 나지 않는지 본다. 권한을 끈 채로 `show`가 실패를 알리는지는 확인한 적이 없고, 알리지 않으면 그 줄의 OS 통로 상태가 `handed`로 남는다(재시작해도 다시 보내지 않는다). ③ 배포처 범위 정책을 건 채로 허용되지 않은 범위 원본에 기댄 Insight가 피드·요약·OS 알림의 건수에 들지 않는지 본다(합성 시험의 P02-C3b ②를 실제 정책으로 되풀이하는 것이다). 정책이 용도 `notify`에 무엇을 답하는지(허용·거부)를 정해 적는다. ④ 한 주 이상 돌려 하루 즉시 알림의 수와 요약의 크기를 재고 문턱(점수 70)과 시각(요약 09:00, 조용한 시간)을 정한다. 확인: ① 토스트에 건수 문구만 있고 ② 피드의 줄이 그대로이며 ③ 거부된 범위의 Insight가 어느 건수에도 없다. 기록할 것: 하루 즉시 알림 수의 분포, 요약 줄 수, 정한 문턱과 시각, 정책의 답, 확인한 결과. 글·Insight 요약·원본 이름은 기록하지 않는다. 배포처가 메일·메신저로 알림을 보내려면 별도 spec과 사용자 승인이 먼저다. 이 저장소에는 그 통로가 없다.
