# 배포처 설정 안내

- 날짜: 2026-11-21 / 관련: [ownership.md](ownership.md), [ARCHITECTURE 9절 가정 표](ARCHITECTURE.md#9-가정-표), [ADR 0012](adr/0012-upstream-and-fork-ownership.md), 이슈 #37(R07)

이 문서는 제품을 실제 환경에 올리는 **배포처**가 따르는 안내다. 공용 저장소는 구조와 기본값만 갖고, 환경에 달린 값과 실행 검증은 배포처가 채운다. 이 문서에는 **실제 값을 적지 않는다.** 어떤 종류의 값이 필요한지만 적는다. 채운 값은 배포처 포크의 `site/config/`에만 두고 공용 저장소로 보내지 않는다([ownership.md 6절](ownership.md)).

낯선 말은 [ARCHITECTURE 0절](ARCHITECTURE.md#0-처음-나오는-말)에 풀이가 있다. `R02`·`R03`·`R04`는 배포처에서 실행하는 검증 작업(이슈 #11, #12, #13)이고 `A01`~`A19`는 아키텍처 문서의 가정 번호다.

## 1. 지금 상태

제품 코드는 아직 없다. 아래 설정 키와 절차는 V01(#16)에서 구현하면서 확정하며, 그때 이 문서를 실제 이름으로 고친다. 검증 스크립트와 결과 기록 양식은 R02·R03·R04의 사외 준비물로 따로 들어온다.

**먼저 알아 둘 것**: 설치 파일로 묶은 실행본(배포 빌드)은 격리 검증을 통과해 목록에 등록된 CLI 조합만 실행한다. 공용 저장소의 목록은 비어 있으므로, S07을 끝내기 전의 설치본은 Claude Code와 Codex CLI를 **전혀 실행하지 않는다.** 그동안 쓸 수 있는 LLM 경로는 API 키 Provider(S05)뿐이다.

## 2. 설정의 형태

키 이름은 잠정이다. "공용 기본값"은 배포처 값이 아니라 아무 설정 없이 로컬에서 도는 값이다.

| 설정(잠정 이름) | 필요한 값의 종류 | 공용 기본값 |
|---|---|---|
| `providers.enabled` | 쓸 수 있게 둘 Provider 이름의 목록 | 전부. 설치되어 있지 않은 것은 "없음"으로 표시된다 |
| `providers.openaiCompatible.baseUrl` | OpenAI 호환 API를 제공하는 HTTPS 주소 하나 | 없음. 비어 있으면 이 Provider는 "미설정"이다 |
| `providers.openaiCompatible.model` | 그 엔드포인트에서 쓸 모델의 이름 | 없음 |
| API 키 | 설정 파일에 두지 않는다. 앱의 설정 화면에서 입력하면 OS 자격 증명 저장소에 들어간다 | 없음 |
| `providers.cli.verifiedProfiles` | 격리 검증을 통과한 조합의 목록. 항목마다 CLI 이름, 버전 범위, 인자 프로필 이름, 검증한 날짜 | 빈 목록. 비어 있으면 배포 빌드는 CLI를 실행하지 않는다 |
| `providers.cli.background` | 켬 또는 끔. 목록에 있는 조합의 백그라운드 자동 실행을 허용할지 | 끔 |
| `egress.classes` | 데이터 등급 이름의 목록(엄격한 순서) | "합성"과 일반 등급 하나 |
| `egress.rules` | 규칙의 목록. 규칙마다 Provider, 작업 종류, 데이터 등급, 허용 또는 거부 | 빈 목록(전부 거부). 사용자가 앱에서 동의하면 그 Provider의 허용 규칙이 생긴다 |
| `embedding.modelSource` | "내려받기" 또는 "로컬 팩"과 그 폴더 위치 | 내려받기(사용자 승인 뒤) |
| `update.feedUrl` | 업데이트를 받아 올 HTTPS 주소 | 없음(자동 업데이트 끔) |
| `connectors` | 수집기 인스턴스의 목록. 항목마다 종류, 인스턴스 이름, 그 수집기가 요구하는 설정 | 빈 목록 |

배포 빌드인지 개발 모드인지는 설정이 아니다. 빌드할 때 정해지며 이 표의 어떤 값으로도 바꿀 수 없다.

## 배포처 설정 체크리스트

항목마다 무엇을 하는지, 어떤 종류의 값이 필요한지, 끝났다는 것을 무엇으로 확인하는지 적었다. 번호(`S01` 등)는 구현 spec의 비목표 항목과 일대일로 대응한다([V01](specs/2026-11-21-V01-vertical-skeleton.md) S01~S13, [V02](specs/2026-11-21-V02-vertical-slice.md) S14~S15).

### 수집

- [ ] **S01 메일 수집기 구현.** `Connector` 규격을 구현해 `site-mail` 자리에 등록한다. 필요한 것: 메일 시스템에 접근하는 방법, 수집 범위(어느 편지함, 어느 기간). 확인: `packages/testkit`의 Connector 계약 테스트 통과, `site-mail` 실행 시 "미구현" 대신 변경분이 나온다.
- [ ] **S02 메신저 수집기 구현.** 같은 방식으로 `site-messenger`. 필요한 것: 메신저 시스템 접근 방법, 수집할 대화방의 범위, 스레드를 복원할 식별자. 확인: S01과 같다.
- [ ] **S03 Wiki 수집기 구현.** 같은 방식으로 `site-wiki`. 필요한 것: Wiki 시스템 접근 방법, 수집할 공간의 범위, 페이지 버전 정보. 확인: S01과 같다.
- [ ] **S04 수집기의 인증과 권한 매핑.** 각 수집기가 사용자 본인의 권한으로 인증하게 하고, 원본마다 access_scope(누가 볼 수 있는 자료인가)를 채운다. 실제 수집기는 "합성" 등급을 붙이지 않는다. 필요한 것: 인증 방식, 원본의 공개 범위를 알아내는 방법. 확인: 수집한 원본에 access_scope가 비어 있지 않고, 권한이 철회된 원본에 대해 수집기가 `access-revoked` 사건을 낸다.

### LLM Provider와 외부 전송

- [ ] **S05 LLM Provider 구성.** 쓸 Provider를 고르고, OpenAI 호환 경로를 쓴다면 엔드포인트 주소와 모델 이름을 설정하고 키를 발급받아 앱에 입력한다. 필요한 것: 허용된 Provider의 목록, 엔드포인트 주소, 모델 이름, 키 발급 절차. 확인: 앱의 설정 화면에서 그 Provider의 상태가 "사용 가능"이고 합성 입력 한 건의 구조화 응답이 스키마 검증을 통과한다(A06).
- [ ] **S06 구독 로그인 CLI 사용 허용 여부 확인.** 사용자의 구독 로그인으로 CLI를 제품이 호출해도 되는지를 벤더의 공식 조건과 배포처 정책으로 확인한다. 조사 문서는 벤더 문구를 "모호"로 판정했고 허용된다고 말하지 않는다([CLI Provider 조사 3절](research/2026-11-21-cli-provider-terms-and-isolation.md)). 필요한 것: 확인한 조건의 출처와 날짜. 확인: R02-C4에 허용 경로 또는 "미확인"이 기록된다. 허용되지 않으면 `providers.enabled`에서 CLI를 빼고 S07을 하지 않는다(A01).
- [ ] **S07 CLI 격리 검증과 검증된 조합 등록.** R02의 절차대로 합성 악성 문서로 부정 테스트를 실행하고, 통과한 CLI 버전과 인자 프로필만 `providers.cli.verifiedProfiles`에 넣는다. 등록된 조합만 설치본에서 실행된다. 그 뒤 백그라운드 자동 실행을 켤지 따로 정한다. 필요한 것: 배포할 CLI의 고정 버전. 확인: R02-C1~C3의 실행 기록. 등록하지 않은 버전으로는 설치본에서 사용자가 눌러도 호출이 차단된다. CLI 버전을 올리면 다시 검증해 등록한다(A02~A05).
- [ ] **S08 외부 전송 정책의 값.** 데이터 등급을 정하고 등급마다 어느 Provider에 보낼 수 있는지 규칙을 채운다. 필요한 것: 배포처의 데이터 분류 기준, 등급별 허용 Provider. 확인: 거부 규칙에 걸리는 합성 입력이 호출 없이 "전송 거부"로 남고, 허용 규칙에 걸리는 입력만 호출된다.

### Embedding

- [ ] **S09 Embedding 모델 반입.** 외부에서 내려받을 수 있는지 확인하고, 안 되면 모델 파일을 내부로 반입해 로컬 팩으로 둔다. 필요한 것: 외부 모델 저장소 접근 허용 여부, 반입한 파일을 둘 위치, 모델 라이선스 확인. 확인: 앱에서 embedding 상태가 "준비됨"이고 합성 문장의 embedding 왕복이 통과한다. 속도와 메모리는 R03-C3의 기준으로 잰다(A11, A12).

### 설치와 운영

- [ ] **S10 Windows 11 설치본 검증.** 깨끗한 Windows 11에서 Node·Python·Docker·DB 서버를 따로 설치하지 않고 설치·실행·제거한다. 필요한 것: 깨끗한 Windows 11 시험 환경. 확인: R04-C1의 실행 기록(A07, A13, A18).
- [ ] **S11 저장 데이터 보호 확인.** 제품을 쓸 PC에 OS 디스크 암호화가 적용되는지, 앱이 OS 자격 증명 저장소를 쓸 수 있는지 확인한다. 필요한 것: PC 보안 정책의 해당 항목. 확인: 앱에 API 키를 저장했다가 재시작 뒤 다시 쓸 수 있다. **디스크 암호화가 확인되지 않은 PC에는 실제 업무 데이터를 넣지 않는다**([ADR 0010](adr/0010-encryption-at-rest.md), A16, A19).
- [ ] **S12 서명, 배포 채널, 업데이트.** 설치 파일과 그 안의 네이티브 모듈을 무엇으로 서명할지, 사용자에게 어떻게 배포할지, 업데이트를 어디서 받게 할지 정한다. 필요한 것: 서명 주체, 내부 배포 방법, 업데이트를 둘 주소(없으면 자동 업데이트를 끈다). 확인: R04-C3의 기록. 설치와 실행에서 Windows의 차단 동작을 관찰해 적는다(A14, A15).
- [ ] **S13 엔진과 저장소의 실행 비교.** R03의 절차대로 엔진 후보와 저장소를 합성 입력으로 실행해 비교한다. 벡터 색인의 실제 구현 후보(sqlite-vec)가 Windows에서 로드되는지도 여기서 확인한다. Phase 1의 제품에는 벡터 색인 구현이 들어 있지 않다. 필요한 것: 실행 환경과 R05가 고정한 측정 기준. 확인: R03-C1~C4의 실행 기록. 결과로 [ADR 0002](adr/0002-authority-in-product-records.md), [0003](adr/0003-phase1-without-engine.md), [0004](adr/0004-embedded-storage.md), [0011](adr/0011-sidecar-language.md)을 R07에서 확정하거나 고친다(A08, A09, A10, A17).

### 수직 흐름

- [ ] **S14 수직 흐름을 설치본과 실제 Provider로 실행.** V02의 흐름(합성 출처 3개 → 일정 위험 Insight → 근거 화면)을 Windows 설치본에서 실제 Provider로 실행한다. 필요한 것: S10이 끝난 환경과, API 키 Provider(S05) 또는 등록된 CLI 조합(S07) 가운데 하나. 확인: V02의 배포처 검증 실행기가 통과하고, 결과 기록에 Provider 종류가 "실제"로 적힌다(V02-C4).
- [ ] **S15 실제 수집 데이터에서의 품질 확인.** 실제 수집기로 가져온 자료에서 추출과 Insight가 쓸 만한지 배포처 안에서 확인한다. 필요한 것: S01~S04와 S11이 끝난 환경. 확인: 결과는 배포처 안에만 남긴다. 공용 저장소에는 범용 문제만 합성 재현 형태로 알린다([ownership.md 5절](ownership.md)).

## 3. 결과를 어디에 남기는가

- R02·R03·R04의 실행 기록은 각 이슈(#11, #12, #13)에 남기고, R07(#37)에서 가정 표와 하나씩 대조한다.
- 공용 이슈에 올릴 수 있는 것은 합성 입력의 결과와 환경의 일반 정보뿐이다. 주소, 계정, 업무 데이터는 올리지 않는다.
- 실행하지 못한 항목은 "미검증"으로 남긴다. 이 저장소의 문서는 실행하지 않은 것을 통과로 적지 않는다.
