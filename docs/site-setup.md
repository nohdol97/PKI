# 배포처 설정 안내

- 날짜: 2026-11-21 / 관련: [ownership.md](ownership.md), [ARCHITECTURE 9절 가정 표](ARCHITECTURE.md#9-가정-표), [ADR 0012](adr/0012-upstream-and-fork-ownership.md), 이슈 #37(R07)

이 문서는 제품을 실제 환경에 올리는 **배포처**가 따르는 안내다. 공용 저장소는 구조와 기본값만 갖고, 환경에 달린 값과 실행 검증은 배포처가 채운다. 이 문서에는 **실제 값을 적지 않는다.** 어떤 종류의 값이 필요한지만 적는다. 채운 값은 배포처 포크의 `site/config/`에만 두고 공용 저장소로 보내지 않는다([ownership.md 6절](ownership.md)).

낯선 말은 [ARCHITECTURE 0절](ARCHITECTURE.md#0-처음-나오는-말)에 풀이가 있다. `R02`·`R03`·`R04`는 배포처에서 실행하는 검증 작업(이슈 #11, #12, #13)이고 `A01`~`A22`는 아키텍처 문서의 가정 번호다.

## 1. 지금 상태

제품 코드는 아직 없다. 아래 설정 키와 절차는 V01(#16)에서 구현하면서 확정하며, 그때 이 문서를 실제 이름으로 고친다. 검증 스크립트와 결과 기록 양식은 R02·R03·R04의 사외 준비물로 따로 들어온다.

**먼저 알아 둘 것**: 설치 파일로 묶은 실행본(배포 빌드)은 격리 검증을 통과해 목록에 등록된 CLI 조합만 실행한다. 공용 저장소의 목록은 비어 있으므로, S07을 끝내고 **다시 빌드하기 전**의 설치본은 Claude Code와 Codex CLI를 **전혀 실행하지 않는다.** 그동안 쓸 수 있는 LLM 경로는 API 키 Provider(S05)뿐이다.

## 2. 설정의 형태

값이 정해지는 때가 둘이다. **빌드할 때 정해지는 것**은 포크의 `site/config/`에 두고 다시 빌드해야 바뀐다. 실행 중에 설정 화면이나 설정 파일, 환경 변수로는 바꿀 수 없다. **실행 중 설정**은 앱의 설정으로 바꾼다. 이름은 잠정이다.

### 빌드할 때 정해지는 것

| 자원(잠정 이름) | 필요한 값의 종류 | 공용 기본값 |
|---|---|---|
| 검증된 CLI 조합 목록(`providers/src/verified-cli-combinations.json`) | 격리 검증을 통과한 조합의 목록. 항목마다 `cli`(`claude-code` 또는 `codex`), `version`(**정확한 버전 하나**. 범위가 아니며 CLI가 알리는 문자열과 글자까지 같아야 한다), `os`(`win32`, `darwin`, `linux`), `profile`(인자 프로필의 이름. 목록에 넣는 것은 `claude-code/standard-2`처럼 `standard` 프로필이다), `model`(R02를 실행한 모델 이름 하나. 제품이 `--model`로 넘긴다. 비어 있거나 `-`로 시작하거나 공백이 들면 거부), `verifiedOn`(`YYYY-MM-DD`). 인자 프로필의 내용은 제품 코드(`providers/src/cli-profiles.ts`)에 고정되어 있고 여기서는 이름만 고른다. 제품 프로필이 어느 R02 프로필과 같은 인자인지는 그 파일에 적혀 있다(V01-T10). 그 R02 프로필의 결과로 이 이름을 적는다. 항목이 하나라도 틀리면 백엔드가 시작하지 않는다 | 빈 목록. 비어 있으면 배포 빌드는 CLI를 실행하지 않는다 |
| 빌드 종류 | 포크가 정하지 않는다. 설치 파일을 만드는 빌드는 언제나 배포 빌드다 | 배포 빌드 |
| 합성 목록 | 포크가 정하지 않는다. 공용 저장소의 합성 자료에서 만들어진다. 실제 수집기가 가져온 자료는 여기에 들어가지 않는다 | 공용 저장소의 합성 자료 |
| Embedding 모델의 revision과 파일 해시 | 포크가 다른 모델을 쓰기로 했을 때만 바꾼다 | 공용 저장소가 고정한 값 |
| 데이터 등급 목록 | 등급 이름의 목록(엄격하지 않은 것부터). 바꾸면 Broker의 등급 계산(`providers/src/broker.ts`의 `grade`)도 함께 바꾼다. 정책 버전에 들어가므로 바꾸면 모든 동의가 무효가 된다 | "합성"과 일반 등급 하나(`@pki/contracts`의 `DATA_CLASSES`) |
| 배포처 전송 규칙 | 규칙의 목록. 규칙마다 Provider, 작업 종류, 데이터 등급(각각 `*` 가능), 허용 또는 거부. 여기의 거부는 사용자의 동의로 뒤집히지 않고, 여기의 허용만으로는 동의를 대신하지 않는다. 구성 지점(`backend/src/composition.ts`의 `productEgress`)이 넘기는 값이며 설정 파일이나 설정 API로는 바꿀 수 없다. 하나라도 고치면 정책 버전이 바뀌어 모든 동의가 무효가 된다 | 빈 목록(`PUBLIC_SITE_RULES`). 사용자가 앱에서 등급을 골라 동의하면 그 Provider의 허용 규칙이 생긴다 |

### 실행 중 설정

"공용 기본값"은 배포처 값이 아니라 아무 설정 없이 로컬에서 도는 값이다.

| 설정(잠정 이름) | 필요한 값의 종류 | 공용 기본값 |
|---|---|---|
| `providers.enabled` | 쓸 수 있게 둘 Provider 이름의 목록 | 전부. 설치되어 있지 않은 것은 "없음"으로 표시된다 |
| `providers.openaiCompatible.baseUrl` | OpenAI 호환 API를 제공하는 **`https`** 주소 하나. 바꾸면 그 Provider에 대한 사용자의 동의가 무효가 된다 | 없음. 비어 있으면 이 Provider는 "미설정"이다 |
| `providers.openaiCompatible.model` | 그 엔드포인트에서 쓸 모델의 이름 | 없음 |
| API 키 | 설정 파일에 두지 않는다. 앱에서 입력하면 OS가 보호하는 키로 암호화되어 데이터 디렉터리의 `secrets.json`에 암호문으로만 남는다([ADR 0010](adr/0010-encryption-at-rest.md)). OS 보호를 쓸 수 없으면 저장되지 않고 그 Provider는 "사용 불가"다. 키는 입력할 때의 주소 호스트에 묶이므로 `baseUrl`의 호스트를 바꾸면 키를 다시 입력한다 | 없음 |
| `providers.default` | 연결 시험과 호출에 쓸 Provider 이름 하나(`claude-code`, `codex`, `openai-compatible`). 설정 화면의 "기본 Provider"가 이 값을 쓴다. 비어 있거나 묶이지 않은 이름이면 어느 Provider도 부르지 않으며, 설치된 CLI가 하나뿐이어도 저절로 고르지 않는다 | 없음 |
| `providers.cli.background` | `on` 또는 `off`(정확히 `on`일 때만 켬). 목록에 있는 조합의 백그라운드 자동 실행을 허용할지. 설정 화면의 "CLI 백그라운드 실행 허용"이 이 값을 쓴다. 가져오기 뒤의 추출도 백그라운드 실행이다 | 끔 |
| `embedding.modelSource` | "로컬 팩"과 그 폴더 위치, 또는 "내려받기" | 정해지지 않음. 사용자가 고르기 전의 상태는 "모델 없음"이며 자동으로 내려받지 않는다 |
| `update.feedUrl` | 업데이트를 받아 올 `https` 주소 | 없음(자동 업데이트 끔) |
| `connectors` | 수집기 인스턴스의 목록. 항목마다 종류, 인스턴스 이름, 그 수집기가 요구하는 설정 | 빈 목록 |

## 배포처 설정 체크리스트

항목마다 무엇을 하는지, 어떤 종류의 값이 필요한지, 끝났다는 것을 무엇으로 확인하는지 적었다. 번호(`S01` 등)는 구현 spec의 비목표 항목과 일대일로 대응한다([V01](specs/2026-11-21-V01-vertical-skeleton.md) S01~S13, [V02](specs/2026-11-21-V02-vertical-slice.md) S14~S15, [I02-A](specs/2026-11-21-I02-document-normalization.md) S16~S17).

### 수집

- [ ] **S01 메일 수집기 구현.** `Connector` 규격을 구현해 `site-mail` 자리에 등록한다. 필요한 것: 메일 시스템에 접근하는 방법, 수집 범위(어느 편지함, 어느 기간). 확인: `packages/testkit`의 Connector 계약 테스트 통과, `site-mail` 실행 시 "미구현" 대신 변경분이 나온다.
- [ ] **S02 메신저 수집기 구현.** 같은 방식으로 `site-messenger`. 필요한 것: 메신저 시스템 접근 방법, 수집할 대화방의 범위, 스레드를 복원할 식별자. 확인: S01과 같다.
- [ ] **S03 Wiki 수집기 구현.** 같은 방식으로 `site-wiki`. 필요한 것: Wiki 시스템 접근 방법, 수집할 공간의 범위, 페이지 버전 정보. 확인: S01과 같다.
- [ ] **S04 수집기의 인증과 권한 매핑.** 각 수집기가 사용자 본인의 권한으로 인증하게 하고, 원본마다 access_scope(누가 볼 수 있는 자료인가)를 채운다. 수집기는 데이터 등급을 정하지 못한다. 등급은 제품이 access_scope에서 계산하며, 실제 수집기가 가져온 자료는 "합성"이 될 수 없다. 필요한 것: 인증 방식, 원본의 공개 범위를 알아내는 방법. 확인: 수집한 원본에 access_scope가 비어 있지 않고, 삭제되거나 권한이 철회된 원본에 대해 수집기가 그 사건을 낸다(제품은 그 원본의 내용을 지운다).

### LLM Provider와 외부 전송

- [ ] **S05 LLM Provider 구성.** 쓸 Provider를 고르고, OpenAI 호환 경로를 쓴다면 엔드포인트 주소와 모델 이름을 설정하고 키를 발급받아 앱에 입력한다. 필요한 것: 허용된 Provider의 목록, `https` 엔드포인트 주소, 모델 이름, 키 발급 절차. 확인: 앱의 설정 화면에서 그 Provider의 연결 시험이 성공한다(합성 자료 한 건의 구조화 응답이 스키마 검증을 통과, A06).
- [ ] **S06 구독 로그인 CLI 사용 허용 여부 확인.** 사용자의 구독 로그인으로 CLI를 제품이 호출해도 되는지를 벤더의 공식 조건과 배포처 정책으로 확인한다. "배포처에서 두 CLI를 쓸 수 있다"는 것은 지금까지 사용자의 진술뿐이고 문서 근거가 없다. 조사 문서는 벤더 문구를 "모호"로 판정했고 허용된다고 말하지 않는다([CLI Provider 조사 3절](research/2026-11-21-cli-provider-terms-and-isolation.md)). 필요한 것: 확인한 조건의 출처와 날짜. 확인: R02-C4에 허용 경로 또는 "미확인"이 기록된다. 허용되지 않으면 `providers.enabled`에서 CLI를 빼고 S07을 하지 않는다(A01).
- [ ] **S07 CLI 격리 검증과 검증된 조합 등록.** R02의 절차대로 합성 악성 문서로 부정 테스트를 실행하고, 통과한 조합만 "검증된 CLI 조합 목록"에 넣은 뒤 **설치본을 다시 빌드**한다. 등록된 조합만 설치본에서 실행된다. 그 뒤 백그라운드 자동 실행을 켤지 따로 정한다. 필요한 것: 배포할 CLI의 정확한 버전, 검증한 OS. 확인: R02-C1~C3의 실행 기록. 등록하지 않은 버전으로는 설치본에서 사용자가 연결 시험을 눌러도 차단된다. 실행할 R02 프로필은 목록에 적을 제품 프로필과 같은 인자의 것이다. 그 대응은 `providers/src/cli-profiles.ts`의 `CLI_ARGUMENTS`가 프로필마다 `r02` 칸에 적는다(지금은 `claude-code/standard-2` → `claude-A-restricted-safe`, `codex/standard-2` → `codex-A-full`). R02의 판정은 그 실행의 **버전과 모델**에서만 유효하므로, R02에 `--model-claude`·`--model-codex`로 준 모델 이름을 목록 항목의 `model`에 그대로 적는다. 제품은 목록에 있는 조합을 그 모델로만 실행한다(`--model <model>`). R02는 제품이 찾는 것과 같은 실행 파일로 돌린다. Windows의 제품은 `.exe`만 찾으므로 npm이 까는 `.cmd`로 R02를 통과해도 제품은 그 CLI를 찾지 못한다(미검증). 프록시·사설 인증서 환경 변수(`HTTPS_PROXY`, `NO_PROXY`, `NODE_EXTRA_CA_CERTS` 등)는 제품이 CLI에 넘기지 않는다(잠정). R02를 `--pass-env`로 통과한 조합도 프록시가 필요하면 제품에서는 연결하지 못한다. **CLI가 버전을 올리면 그 CLI는 다시 막히므로**, 배포할 버전을 고정하고 버전을 올릴 때마다 다시 검증해 등록하고 빌드한다(A02~A05, A22).
- [ ] **S08 외부 전송 정책의 값.** 데이터 등급을 정하고 등급마다 어느 Provider에 보낼 수 있는지 규칙을 채운다. 필요한 것: 배포처의 데이터 분류 기준, 등급별 허용 Provider. 확인: 거부 규칙에 걸리는 합성 입력이 호출 없이 "전송 거부"로 남고, 사용자가 동의해도 그 거부가 유지되며, 허용 규칙에 걸리는 입력만 호출된다. **주의**: 규칙에는 목적지 칸이 없다. `openai-compatible`을 허용하면 사용자가 `providers.openaiCompatible.baseUrl`에 넣은 어느 `https` 호스트로 보내는 것이든 허용된다(사용자의 동의는 여전히 필요하다). 엔드포인트를 정해 두어야 한다면 `openai-compatible`을 거부하거나, 주소를 빌드 자원으로 바꾸거나, 규칙에 목적지 칸을 더한다(V01 spec "T08이 넘기는 것" 1항).

### Embedding

- [ ] **S09 Embedding 모델 반입.** 외부에서 내려받을 수 있는지 확인하고, 안 되면 모델 파일을 내부로 반입해 로컬 팩으로 둔다. 필요한 것: 외부 모델 저장소 접근 허용 여부, 반입한 파일을 둘 위치, 모델 라이선스 확인. 확인: 반입한 파일의 해시가 제품이 고정한 값과 맞아 앱의 embedding 상태가 "준비됨"이 되고, 합성 문장의 embedding 왕복이 통과한다. 속도와 메모리는 R03-C3의 기준으로 잰다(A11, A12).

### 설치와 운영

- [ ] **S10 Windows 11 설치본 검증.** 깨끗한 Windows 11에서 Node·Python·Docker·DB 서버를 따로 설치하지 않고 설치·실행·제거한다. 필요한 것: 깨끗한 Windows 11 시험 환경. 확인: R04-C1의 실행 기록(A07, A13, A18).
- [ ] **S11 저장 데이터 보호 확인.** 제품을 쓸 PC에 OS 디스크 암호화가 적용되는지, 앱이 OS 자격 증명 저장소를 쓸 수 있는지, 앱의 데이터 디렉터리가 다른 PC로 따라다니지 않는 위치인지 확인한다. 필요한 것: PC 보안 정책의 해당 항목. 확인: 앱에 API 키를 저장했다가 재시작 뒤 다시 쓸 수 있고(로밍 프로필 동기화 뒤에도. ADR 0010 "지켜볼 것"), 그 키의 평문이 앱의 어떤 파일에도 남아 있지 않다(`secrets.json`에는 암호문만). **디스크 암호화가 확인되지 않은 PC에는 실제 업무 데이터를 넣지 않는다**([ADR 0010](adr/0010-encryption-at-rest.md), A16, A19).
- [ ] **S12 서명, 배포 채널, 업데이트.** 설치 파일과 그 안의 네이티브 모듈을 무엇으로 서명할지, 사용자에게 어떻게 배포할지, 업데이트를 어디서 받게 할지 정한다. 필요한 것: 서명 주체, 내부 배포 방법, 업데이트를 둘 주소(없으면 자동 업데이트를 끈다). 확인: R04-C3의 기록. 설치와 실행에서 Windows의 차단 동작을 관찰해 적는다. 자동 업데이트를 실제로 돌려 보는 확인은 R04의 기준에 없으며 H02(#33)에서 한다(A14, A15).
- [ ] **S13 엔진과 저장소의 실행 비교.** R03의 절차대로 엔진 후보와 저장소를 합성 입력으로 실행해 비교한다. 벡터 색인의 실제 구현 후보(sqlite-vec)가 Windows에서 로드되는지, 정본 SQLite가 갑작스러운 종료를 견디는지도 여기서 확인한다. Phase 1의 제품에는 벡터 색인 구현이 들어 있지 않다. 필요한 것: 실행 환경과 R05가 고정한 측정 기준. 확인: R03-C1~C4의 실행 기록. 결과로 [ADR 0002](adr/0002-authority-in-product-records.md), [0003](adr/0003-phase1-without-engine.md), [0004](adr/0004-embedded-storage.md), [0011](adr/0011-sidecar-language.md), [0013](adr/0013-failure-recovery.md)을 R07에서 확정하거나 고친다(A08, A09, A10, A20).

### 수직 흐름

- [ ] **S14 수직 흐름을 설치본과 실제 Provider로 실행.** V02의 흐름(합성 출처 3개 → 일정 위험 Insight → 근거 화면)을 Windows 설치본에서 실제 Provider로 실행한다. 가져오기 뒤의 추출은 백그라운드 실행이므로 Provider는 둘 중 하나여야 한다: API 키 Provider(S05), 또는 목록에 등록되어 있고(S07) 백그라운드 설정을 켠 CLI. 필요한 것: S10이 끝난 환경. 확인: V02의 배포처 검증 실행기가 통과하고, 결과 기록에 Provider 종류가 "실제"로, 그리고 근거 인용문 대조에서 버려진 수가 적힌다(V02-C4, A21).
- [ ] **S15 실제 수집 데이터에서의 품질 확인.** 실제 수집기로 가져온 자료에서 추출과 Insight가 쓸 만한지 배포처 안에서 확인한다. 필요한 것: S01~S04와 S11이 끝난 환경. 확인: 결과는 배포처 안에만 남긴다. 공용 저장소에는 범용 문제만 합성 재현 형태로 알린다([ownership.md 5절](ownership.md)).

### 문서 가져오기

- [ ] **S16 문서 파서 의존성의 npm 미러 설치 확인.** 문서 정규화 패키지(`@pki/document-normalize`)의 의존성(unpdf, mammoth, read-excel-file, parse5, mdast-util-from-markdown, csv-parse, yauzl, fflate, @xmldom/xmldom, iconv-lite와 그 전이 의존성)을 배포처의 npm 미러에서 설치한다. 필요한 것: 미러 주소와 그 미러가 가진 패키지의 범위(위 패키지가 전부 있는지), 설치를 막는 정책(설치 스크립트 차단 등). 확인: 저장소의 `pnpm-lock.yaml`로 `pnpm install --frozen-lockfile`이 미러에서 끝까지 성공하고, 빠진 패키지가 있으면 그 이름을 기록한다. 이 의존성은 모두 설치 스크립트와 네이티브 모듈이 없는 npm 레지스트리 패키지이며(I02-A spec R21), 미러가 막는 패키지가 있으면 [ADR 0015](adr/0015-document-parsing-stack.md)의 해당 행을 고친다.
- [ ] **S17 실제 업무 문서로 형식별 정규화 결과 확인.** 배포처의 실제 문서 폴더(PDF, Word, Excel, HTML, Markdown, TXT, CSV, JSON을 섞어서)에 조사 실행기 `pnpm --filter @pki/document-normalize survey <폴더>`를 실행한다. 이 실행기는 형식별 성공 수, 오류 종류별 수, 한계 코드별 수, 인코딩별 수만 JSON으로 출력하며 파일 이름과 글은 출력하지 않는다. 이 저장소 안의 폴더로는 실행되지 않는다(`배포처 후속` 알림). 필요한 것: 실제 문서 폴더(문서 보안(DRM)으로 감싼 파일이 일부 든 것), 설치본(Electron)에서의 실행 방법. 확인: ① 오류 종류별 수가 설명되는 범위인지 본다. 특히 DRM으로 감싼 파일이 `corrupt`·`format-mismatch`로 알려지는지(깨진 글이 성공으로 나오지 않는지) 확인한다. ② EUC-KR(CP949) 문서가 `euc-kr` 인코딩으로 풀리는지, 이 확인을 **설치본 안의 Node(Electron 45.4.1의 Node 24.22.3)에서도** 한다. EUC-KR은 `iconv-lite`로 풀기 때문에 Electron의 ICU 구성에 기대지 않지만 설치본에서 실제로 보기 전에는 확인된 것이 아니다. ③ 한계 코드 수가 한도 기본값(`DEFAULT_LIMITS`)이 실제 문서에서 너무 빡빡한지 보는 근거가 된다. 결과는 배포처 안에만 남기고 공용 저장소에는 범용 문제만 합성 재현 형태로 알린다([ownership.md 5절](ownership.md)). 폴더 감시와 가져오기 화면은 I02-B(#19)가 맡으며 이 항목의 범위가 아니다.

## 3. 결과를 어디에 남기는가

- R02·R03·R04의 실행 기록은 각 이슈(#11, #12, #13)에 남기고, R07(#37)에서 가정 표와 하나씩 대조한다.
- 공용 이슈에 올릴 수 있는 것은 합성 입력의 결과와 환경의 일반 정보뿐이다. 주소, 계정, 업무 데이터는 올리지 않는다.
- 실행하지 못한 항목은 "미검증"으로 남긴다. 이 저장소의 문서는 실행하지 않은 것을 통과로 적지 않는다.
