# 소유 경계 — 공용 저장소와 배포처 포크

- 날짜: 2026-11-21 / 관련: [ADR 0012](adr/0012-upstream-and-fork-ownership.md), [site-setup.md](site-setup.md), 이슈 #1 "공용 제품과 배포처 포크의 책임"

이 문서는 누가 무엇을 만들고 고치는지를 정한다. **공용 저장소**는 이 저장소(범용 제품)이고, **배포처 포크**는 제품을 실제 환경에 맞춰 쓰려는 곳이 이 저장소를 복제해 만든 자기 저장소다. 낯선 말은 [ARCHITECTURE 0절](ARCHITECTURE.md#0-처음-나오는-말)에 풀이가 있다.

## 1. 누가 무엇을 갖는가

| 공용 저장소 | 배포처 포크 |
|---|---|
| 범용 제품 기능 전체: 지식 파이프라인, Insight, 화면, 설치·운영 | 실제 메일·메신저·Wiki 수집기 |
| Connector 규격, 계약 테스트, JSONL·파일 import, 테스트 Connector | 사내 인증·권한 API 연동, access_scope 매핑 |
| Provider 어댑터(Claude Code, Codex, OpenAI 호환), Broker, 전송 정책의 형태와 기본 거부 | 허용 Provider 목록, 엔드포인트 주소·모델·키, 데이터 등급별 전송 규칙의 값 |
| Embedding 계약과 기본 구현, 로컬 팩 가져오기 기능 | 모델 파일 반입 경로와 승인 |
| 패키징 구성의 뼈대 | 서명, 배포 채널, 업데이트를 받아 올 주소 |
| 합성 데이터와 품질 평가 | 배포처 실행 검증(R02, R03, R04)과 그 결과 |
| 설정의 **형태**(어떤 키가 있고 어떤 종류의 값이 들어가는가) | 설정의 **값** |

판정이 애매하면 한 문장으로 가른다: **"배포처에 이미 있는 것을 봐야 정할 수 있는가?"** 그렇다면 포크의 일이다.

## 2. 포크가 구현해야 하는 규격

규격은 `packages/contracts`에, 그 규격을 지키는지 확인하는 계약 테스트는 `packages/testkit`에 있다(둘 다 V01에서 만든다). 포크의 구현은 계약 테스트를 통과해야 한다.

| 규격 | 포크가 하는 일 | 필수 여부 |
|---|---|---|
| `Connector` ([ARCHITECTURE 5.5절](ARCHITECTURE.md), 규격 v2) | 수집기마다 하나씩 구현. 변경분 조회, 삭제·권한 철회 사건, 범위 변경 사건(`scope-change`), cursor 만료 처리, access_scope·revision·namespace 채우기, `deletionsOnRescan` 선언, 자격 증명이 필요하면 칸의 선언과 접근자로 읽기. 공용의 `@pki/connector-sdk`를 쓸 수 있다 | 실제 수집을 하려면 필수 |
| `LLMProvider` (5.1절) | 배포처의 모델 엔드포인트가 OpenAI 호환이 아닐 때만 구현 | 조건부 |
| `EmbeddingProvider` (5.2절) | 배포처가 다른 모델·런타임을 써야 할 때만 구현 | 조건부 |
| `KnowledgeEngine`, `VectorIndex` (5.3~5.4절) | 포크가 구현하지 않는다. 엔진과 저장소 선택은 공용의 결정이다 | 해당 없음 |
| 설정 파일 | [site-setup.md](site-setup.md)의 형태에 맞춰 값을 채운다 | 필수 |

공용 저장소에는 실제 수집기 자리에 `site-mail`, `site-messenger`, `site-wiki`라는 이름의 **미구현 표시용 구현**이 있다. 실행하면 `미구현, 배포처 후속`을 알리고 실패한다. 포크는 같은 이름으로 실제 구현을 등록해 이것을 대체한다.

Connector를 구현하는 방법(규격, 받아들이는 규칙, 오류와 재시도, 계약 테스트 돌리는 법, 예시 수집기)은 [connector-sdk.md](connector-sdk.md)에 있다.

## 3. 포크의 코드는 어디에 두는가

포크 전용 코드와 설정은 **`site/` 디렉터리 안에만** 둔다.

```text
site/
├── README.md        공용 저장소가 갖는 유일한 파일(이 자리의 용도 안내)
├── composition/     포크: 조립 패키지(등록 객체 하나와 진입점 둘. 수집기를 제품에 끼운다)
├── connectors/      포크: 실제 수집기
├── providers/       포크: 필요할 때만
└── config/          포크: 설정 값(인스턴스 범위 `connector-scopes.json` 포함)
```

공용 저장소는 `site/` 아래에 안내문 말고는 아무것도 만들지 않고, 포크는 `site/` 밖의 파일을 고치지 않는 것을 원칙으로 한다. 두 쪽이 같은 파일을 고치지 않으므로 공용의 변경을 받아 갈 때 충돌이 나지 않는다. `site/` 밖을 고쳐야만 하는 일이 생기면 그것은 규격에 빈 곳이 있다는 신호다. 고치지 말고 5절의 방법으로 공용에 알린다.

**현재의 예외.** 규칙은 위와 같다. 포크는 수집기, 인스턴스, 등급 매핑, 접근 범위 정책을 `site/composition/`의 등록에 적어 제품에 끼우고, 이를 위해 공용의 `backend/src/composition.ts`나 `backend/package.json`을 고치지 않는다. 방법은 [connector-sdk.md](connector-sdk.md) 7장에, 이렇게 정한 이유는 [ADR 0018](adr/0018-fork-registration-at-build-time.md)에 있다. 그래도 `site/` 밖에서 달라지는 추적 파일이 아직 있다.

- `pnpm-lock.yaml`: `pnpm install`이 다시 쓴 변경만(포크 패키지의 항목과 그 외부 의존성). 손으로 고치지 않는다. 공용 변경을 받아 충돌하면 공용 쪽 내용을 취하고 `pnpm install`을 다시 실행한다.
- `pnpm-workspace.yaml`의 `allowBuilds`: 설치 스크립트가 있는 포크 의존성을 위해 더한 `false` 줄뿐이다(스크립트를 돌리지 않는다는 뜻이다). `packages:` 목록은 포함하지 않는다. 스크립트가 정말 필요한 의존성은 지원하지 않으며 5절의 방법으로 공용에 알린다.
- 아직 메우지 못한 빌드 값: 배포처 전송 규칙·묶을 Provider·검증된 CLI 조합 목록·데이터 등급 목록. 각각 정책 판단이 따로 필요해 등록 객체로 옮기지 않았고, 포크가 공용 파일을 고쳐야 하는 값이다([site-setup.md](site-setup.md) 2절의 "빌드할 때 정해지는 것" 표).

`site/config/connector-scopes.json`은 수집기 인스턴스마다의 접근 범위를 두는 파일이고, 가져온 범위가 인스턴스에 정해 둔 범위보다 느슨한 등급을 얻지 못하게 하는 기준이다([site-setup.md](site-setup.md) S18). 이 파일은 포크의 등록(`connectorScopes`)에 묶어야 쓰이고, 포크의 빌드가 그 값을 백엔드 묶음에 넣는다. 파일은 `site/config/connector-scopes.json`에만 둔다(다른 자리나 이름이면 빌드가 멈추거나 판정을 벗어난다. 방법은 [connector-sdk.md](connector-sdk.md) 7장). 공용 저장소의 import 검사(수집기 경로가 허용 목록 밖의 패키지나 네트워크를 쓰지 못하게 하는 검사)는 `site/`를 보지 않으므로, 포크의 수집기는 `site/connectors/`에서 자기 시스템의 클라이언트를 쓸 수 있다.

수집기가 원 시스템에 낼 자격 증명은 `site/`에 두지 않는다. 포크는 필요한 칸의 이름을 등록의 인스턴스 정의(`credentials`)에 선언하고 수집기가 `initialize`의 접근자로 읽게 할 뿐이고, 값은 앱의 출처 화면에서 사용자가 넣어 OS가 보호하는 저장소에만 남는다. 값을 넣는 화면과 저장소는 공용 저장소의 것이라 포크는 화면을 고치지 않는다. 방법은 [connector-sdk.md](connector-sdk.md) 8장에, 이렇게 정한 이유는 [ADR 0019](adr/0019-connector-credentials.md)에 있다.

`site/connectors/`에 둔 수집기를 계약 테스트로 확인하는 방법은 [connector-sdk.md](connector-sdk.md) 6장에, 제품에 연결하는 방법은 7장에 있다.

## 4. 변경이 흐르는 방향

**기본 방향은 공용 → 포크 하나뿐이다.**

1. 공용 저장소의 `main`에 변경이 들어온다.
2. 포크가 그 변경을 받아 온다.
3. 포크가 계약 테스트와 자기 수집기 테스트를 돌린다.
4. 규격의 버전이 올랐으면 포크가 `site/` 안의 구현을 맞춘다.

포크의 변경을 공용으로 되돌려 보내는 흐름은 **두지 않는다.** 되돌리는 길을 열어 두면 배포처의 내용이 공개 저장소로 새는 길도 함께 열리기 때문이다.

## 5. 포크에서 범용 문제를 발견했을 때

포크의 commit이나 diff를 공용으로 가져오지 않는다. 대신:

1. 문제를 배포처 맥락 없이 다시 적는다. 합성 데이터로 재현되는 형태여야 한다.
2. 공용 저장소에 그 설명으로 이슈를 만든다.
3. 공용 저장소에서 **처음부터 다시 작성해** 고친다.
4. 포크가 그 수정을 4절의 흐름으로 받아 간다.

## 6. 공용 저장소로 절대 넘어오면 안 되는 것

이슈, PR, commit 메시지, 테스트 데이터, 화면 캡처, 로그 어디에도 넣지 않는다.

- 배포처의 주소: 호스트 이름, 내부 URL, 내부 서비스·앱 이름
- 계정과 자격 증명: 사용자 ID, 조직·팀 이름, API 키, 토큰, 인증서
- 실제 업무 데이터와 그것을 가공해 만든 테스트 데이터
- 현장 정책의 값: 허용 모델 목록, 데이터 등급 이름과 규칙, 보안 설정
- 실제 수집기의 코드와 그 수집기가 부르는 내부 API의 모양
- 배포처에서 실행한 결과 가운데 위 항목이 드러나는 부분

배포처 실행 결과를 공용 이슈에 남길 때 올릴 수 있는 것은 **합성 입력에 대한 결과와 환경의 일반 정보**(OS 버전, CLI 버전, 통과·실패)뿐이다(이슈 #37 R07-C1).

## 7. 규격이 바뀔 때

- 규격에는 버전이 있다(`Connector`의 `schemaVersion` 등).
- 호환이 깨지는 변경은 공용 저장소의 ADR과 변경 기록에 남기고, 포크가 옮겨 갈 방법을 함께 적는다.
- 계약 테스트는 규격과 같은 PR에서 바뀐다. 포크는 계약 테스트의 실패로 변경을 알아챈다.
