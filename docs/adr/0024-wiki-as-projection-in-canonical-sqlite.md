# ADR 0024: Wiki는 정본 SQLite 안의 투영이고 OSS는 들이지 않는다 — 삭제는 같은 트랜잭션에서, 낡음은 Wiki 자신의 입력 순번으로, 사용자 편집은 읽을 때 겹친다

- 날짜: 2026-11-23 / 상태: **잠정 — 배포처 검증 대기**(실제 규모에서의 만들기 시간과 범위 정책을 건 읽기는 배포처 S35에서 잰다)
- 관련: [K01 spec](../specs/2026-11-23-K01-wiki-projection.md)(K01-R1~R17, 잠정 결정 K01-D1~D10), 이슈 #25, [ADR 0002](0002-authority-in-product-records.md)(정본은 제품의 기록, Wiki는 투영), [ADR 0013](0013-failure-recovery.md), [I04 spec](../specs/2026-11-21-I04-invalidation.md)(등록표의 Wiki 줄, 실행 위치를 이 ADR이 고친다), [OSS_EVALUATION](../OSS_EVALUATION.md)

## 맥락

ADR 0002는 Wiki를 정본의 투영으로 정했지만 어디에 어떻게 둘지는 비워 두었다. R01은 LLM Wiki 후보(llm-wiki-compiler, sage-wiki)를 "보류"하고 K01에서 다시 보기로 했다. 두 후보 모두 자기 페이지 파일을 정본처럼 다루고, 원본 삭제가 파생 페이지까지 번지는지와 시간 유효성은 실행으로 확인된 적이 없다. I04는 파생물 종류의 등록표에 "Wiki 페이지: 실행 위치 projection"을 적어 두었다. 투영은 보통 커밋 뒤 작업이 지운다(엔진·벡터 투영).

## 결정

1. **Wiki OSS를 들이지 않는다(K01-D1).** 같은 구조(종류별 페이지, index, log)를 제품이 만든다. 후보를 실행해 본 것은 아니고, 위의 이유와 아래 2번 때문이다. 읽기 API 뒤에서 만들기만 어댑터로 바꿀 수 있게 정본·읽기 문·편집 레이어는 그대로 둔다.
2. **페이지는 정본 SQLite 안의 테이블이다(K01-D2).** `wiki_pages`, `wiki_page_lineage`, `wiki_links`, `wiki_log`, `wiki_edits`, `wiki_state` 여섯 개(스키마 v27). 본문은 구조화된 JSON이고 문장으로 풀어 쓰는 일은 화면이 한다. 같은 정본 상태에서는 같은 바이트가 나온다. Wiki의 글은 어떤 경우에도 근거가 되지 않는다.
3. **파생물 종류 `wiki-page`의 실행 위치는 `canonical`이다(K01-D3, I04 등록표를 고친다).** 페이지가 정본과 같은 파일에 있으므로 tombstone과 지난 version 정리의 트랜잭션 안에서 처리할 수 있다. 그 원본만이 채우던 페이지는 계보·링크와 함께 지우고, 다른 원본도 채우던 페이지는 영향받은 키를 정본의 남은 상태로 다시 그려 같은 트랜잭션에서 덮어 쓴다. 층은 `projection` 그대로다. 커밋 뒤 작업으로 두면 지운 내용이 남는 구간이 생긴다.
4. **낡음은 Wiki 자신의 입력 순번으로 판정한다(K01-D4).** 페이지가 읽는 테이블의 트리거가 `wiki_state`의 입력 순번을 올린다. knowledge revision은 항목·사실·관계·유형 정의만 따라가 근거·충돌·묶음·Insight·삭제를 놓치고, 그 뜻을 넓히면 S03의 검사 현재성이 흔들리므로 기록과 동일성 시험에만 쓴다.
5. **만들기는 작업 `wiki-build` 하나이고 Provider를 부르지 않는다.** 모든 대상을 훑어 내용 해시가 달라진 페이지만 한 트랜잭션에 쓴다(한 번에 500쪽, 강제 다시 만들기는 상한 밖). `wiki-build`는 원본 version에 묶이지 않는 fence 없는 종류다. 쓰기에서는 결합 정책을 묻지 않고(거부하면 재추출을 부르는 기록이 남는다) 보여도 되는지를 읽을 때 계보에서 정한다.
6. **사용자 편집은 메모와 숨김 둘이고 `wiki_edits`에 두며 읽을 때 겹친다(K01-D7).** 다시 만들기가 이 테이블을 쓰지 않으므로 편집을 잃을 길이 없다. 숨김은 그 사실·관계와 함께 지워지고, 메모는 사용자가 쓴 글이라 페이지가 없어져도 남는다.
7. **LLM 요약은 선택 기능이고 Broker만 지난다.** 기본 OFF이고 별도 작업(K01-T2)으로 들어온다. 허용되지 않으면 결정적 페이지만 보인다.

## 기각한 대안

- **llm-wiki-compiler 도입**: 페이지 파일이 두 번째 정본이 되고, 삭제 연쇄·시간 유효성·Electron 번들 호환이 확인되지 않았다.
- **저장하지 않고 읽을 때마다 만들기**: 변경 이력과 요약을 둘 곳이 없고 backlink를 매번 전부 계산한다.
- **삭제를 커밋 뒤 작업으로(엔진·벡터 투영과 같은 길)**: 같은 파일이라 같은 트랜잭션에서 처리할 수 있는데, 일부러 지운 내용이 남는 구간을 만들게 된다.
- **knowledge revision의 뜻을 넓혀 낡음을 판정하기**: 다른 소비자(S03 검사 현재성)의 기준이 흔들린다.
- **편집을 페이지에 직접 쓰기**: 다시 만들 때 합치는 규칙이 필요하고 틀리면 편집을 잃는다.

## 결과

- 마이그레이션 v27은 테이블 여섯과 입력 테이블의 트리거를 더하기만 한다. 새 작업 종류 `wiki-build`, 새 파생물 종류 `wiki-page`, API 네 경로(`GET /api/wiki`, `POST /api/wiki/page`·`edit`·`rebuild`)가 생긴다.
- I04 등록표의 Wiki 줄이 `projection`에서 `canonical`로 바뀌었고, 그 spec의 변경 이력에 적었다.
- 알려진 한계: 500쪽 상한을 넘을 때 다음 실행이 잇는 반복은 시험하지 않았다. 범위 정책이 서로 다른 범위의 묶음을 거부하는 것은 읽을 때만 적용된다(저장된 페이지에는 그 조합이 있을 수 있다). 모든 대상을 매번 훑으므로 항목 수만 개에서의 시간은 재지 않았다. 셋 다 배포처 S35와 K01 spec의 미해결 질문에 있다.
- 되돌리려면: 종류의 `storage`를 `projection`으로 바꾸고 `projection-remove` 포트를 단다(3번). 만들기만 OSS 어댑터로 바꾼다(1번).
