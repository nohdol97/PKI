# ADR 0011: 사이드카 언어 — Python, Go 단일 바이너리, 또는 없음

- 날짜: 2026-11-21 / 상태: **미결**(R03 실행 결과가 있어야 정할 수 있다. R07에서 결정)
- 관련: 원 설계 2절 "Simplicity First"·15절, [OSS_EVALUATION 4.6절·6절 2번](../OSS_EVALUATION.md), 이슈 #12(R03), #13(R04)

## 질문

제3자 지식 엔진을 꽂을 때 그 엔진은 앱 본체 옆의 보조 프로세스(사이드카)로 돈다. 어떤 언어의 런타임을 설치 파일에 넣을 것인가. 선택지는 셋이다.

| 선택지 | 해당 후보 | 조사에서 알려진 것 |
|---|---|---|
| Python 사이드카 | LightRAG, cognee | 런타임을 번들해야 한다. 기본 번들 방식은 python-build-standalone(4.8절). Python 후보 모두 최근에 Windows 파일 잠금·네이티브 확장 버그가 있었다(2.4절). cognee에는 패키지된 Windows 호스트에서 로컬 서버가 죽는 열린 이슈가 있다(#6808) |
| Go 단일 바이너리 | sage-wiki, cortexdb | Python 번들과 torch 문제를 피한다. Windows release 산출물은 파일 이름으로 존재만 확인했다. 둘 다 성숙도 위험이 있다(3.1절, 5.1절) |
| 사이드카 없음 | — | Phase 1의 현재 상태([ADR 0003](0003-phase1-without-engine.md)). 엔진의 일이 필요해지면 유지할 수 없다 |

원 설계는 "Python 기반 오픈소스를 재사용하는 것이 Node.js에서 동일 기능을 직접 개발하는 것보다 효율적이라면 Python Sidecar를 허용"하되 "최종 설치 파일에 필요한 런타임과 의존성이 포함되어야 한다"고 한다.

## 결정 기준

아래 순서로 판정한다. 앞의 기준에서 떨어진 선택지는 뒤의 기준으로 되살리지 않는다.

1. **엔진이 R03을 통과했는가.** 통과한 엔진이 속한 언어만 후보다(R03-C1, R03-C2).
2. **깨끗한 Windows 11에서 번들된 채로 도는가.** 별도 설치 없이 설치·실행·제거되는가(R04-C2).
3. **라이선스.** 런타임, 전이 의존성, 번들 도구가 [ADR 0009](0009-license.md)를 통과하는가.
4. **수명 주기.** 쉘이 사이드카를 시작·종료하고, 죽었을 때 다시 띄우고, 고아 프로세스를 남기지 않는가.
5. **크기와 유휴 자원.** 설치 파일 크기, 유휴 CPU·메모리(R04-C3). 수치 기준은 R05가 먼저 고정한다.
6. **유지보수 위험.** 버전 변동 속도, 기여자 수, Windows 이슈 대응.

둘 이상이 남으면 런타임이 가벼운 쪽을 고른다. 하나도 남지 않으면 "사이드카 없음"을 유지하고 엔진 대안 조사로 돌아간다. 자체 엔진 개발로 가지 않는다(이슈 #15 R06-C4).

## 지금 정해 둔 것

- 사이드카는 `KnowledgeEngine` 어댑터 뒤에서만 쓴다. 사이드카와 말하는 방식(로컬 프로세스 간 통신)은 어댑터 구현 안에 숨는다.
- 문서 파싱용 Docling은 torch 기반이라 Python 사이드카를 강제한다. 그래서 핵심 의존성이 아니라 선택적 "문서 처리" 사이드카로 본다(4.7절 7번). 그 결정은 Phase 2(I02)에서 따로 한다.
- Phase 1은 이 결정을 기다리지 않는다.
