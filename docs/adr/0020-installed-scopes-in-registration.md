# ADR 0020: 포크의 인스턴스 범위는 등록이 빌드할 때 묶어 설치본에 싣는다

- 날짜: 2026-11-23 / 상태: **잠정 — 배포처 검증 대기**(Windows 설치본에서 값이 정본까지 가는지는 S31, 실제 포크에서 이 길이 서는지는 S30에서 확인한다. 번호는 머지 순서로 조정한 잠정이다)
- 관련: [I07 spec](../specs/2026-11-22-I07-installed-scopes-file.md)(I07-R1~R16, "대안과 기각 사유", "남는 위험"), 이슈 #115, [ADR 0012](0012-upstream-and-fork-ownership.md), [ADR 0018](0018-fork-registration-at-build-time.md), [ownership.md 3절](../ownership.md), [connector-sdk.md 7장](../connector-sdk.md), [site-setup.md](../site-setup.md)의 S18·S30·S31

## 맥락

배포처는 수집기 인스턴스마다 접근 범위(인스턴스 범위)를 정해 둔다. 사용자가 가져오기에서 적어 낸 범위가 이 범위보다 느슨한 등급을 얻지 못하게 하는 기준이다. 값은 포크의 `site/config/connector-scopes.json`에 적고, 값을 알 수 없으면 가장 엄격한 등급이 된다(닫힌 쪽).

I01-T06은 이 파일을 백엔드 모듈이 **자기 위치 기준의 상대 경로**로 읽게 했다. 소스에서 실행할 때는 저장소 루트의 `site/config/`가 읽히지만, 설치본에서는 세 가지가 비어 있었다. 빌드가 그 파일을 싣지 않았고, 묶은 뒤의 같은 상대 경로는 앱 폴더의 바깥 아무도 고르지 않은 자리를 가리켰으며(그 자리에 놓인 미끼 파일이 실제로 읽혔다. I07-T01의 측정 1), 파일이 없어도 닫힌 쪽이라 조용했다. 배포처는 값을 채웠는데 설치본에서는 쓰이지 않는 상태를 로그 한 줄 말고는 알 길이 없었다.

그 사이 [ADR 0018](0018-fork-registration-at-build-time.md)이 포크의 값이 제품에 들어오는 길을 **빌드할 때 등록 객체 하나**(`SiteRegistration`)로 모았다. 이 결정은 인스턴스 범위도 그 길을 타게 한다.

## 결정

1. **값은 등록의 `connectorScopes` 필드로 들어온다.** 타입은 `unknown`이다(범위 파일의 내용은 형식을 믿지 않고 읽을 때 검사한다). 포크의 `site/composition/src/registration.ts`가 범위 파일을 정적 `import`(`with { type: "json" }`)로 가져와 이 필드에 그대로 넘긴다. 정적이라서 빌드 도구가 그 파일을 백엔드 묶음에 넣는다. 공용 등록 `publicSite`는 이 필드를 갖지 않는다.
2. **실행본은 파일을 읽지 않고 등록이 준 값만 쓴다.** 환경 변수, 명령줄 인자, 현재 폴더, 데이터 폴더, 설치 폴더에 놓인 파일로 인스턴스 범위를 바꿀 길이 없다. 값은 띄운 백엔드마다 표 하나로 갖고, 시작할 때의 전체 복사, 동기화와 가져오기가 인스턴스를 처음 등록할 때의 복사, 삭제 장부의 재적용이 그 표 하나를 건네받는다. 전역 값은 없다.
3. **해석은 닫힌 쪽이다.** 값이 객체가 아니면 전체를, 형식이 틀린 항목은 그 항목만 쓰지 않는다. 어떤 경우에도 인스턴스가 알 수 없음보다 넓어지지 않는다(`bindConnectorScopes`).
4. **시작할 때마다 상태 한 줄이 남는다.** `connector-scopes-absent`, `connector-scopes-invalid`, `connector-scopes-empty`, `connector-scopes-bound` 가운데 정확히 하나가 남고, 쓰지 않은 항목이 있으면 `connector-scopes-rejected`가 한 줄 더 남는다. 값이 모두 쓰인 시작에도 `bound` 줄이 남는다. 줄이 없어도 통과하는 확인은 거짓 통과를 만들기 때문이다. 범위 값과 인스턴스 ID는 로그에 싣지 않는다.
5. **범위 파일의 자리는 고정이고, 빌드가 판정한다.** 공용 진입점과 포크의 조립 패키지 진입점은 `site/config/connector-scopes.json`만 허용한다. 판정(`apps/desktop/build/scopes-check.ts`)은 포크의 코드를 실행하지 않고 묶은 진입점, 백엔드 묶음의 모듈 목록, 허용된 자리의 파일만 본다. 끝은 일곱이다: 통과 셋(`absent`, `empty`, `bound`)과 실패 넷(`scopes-file-misplaced`, `scopes-file-unbound`, `scopes-file-invalid`, `scopes-file-placeholder`). 실패는 빌드를 멈춘다. 빌드는 범위 파일을 앱 폴더에 복사하지 않고, 상태와 두 수(항목 수, 범위가 있는 항목 수)를 빌드 보고서에 적는다.
6. **모듈 경계 규칙에 예외 하나를 둔다.** 조립 패키지의 `src/registration.ts`가 저장소 루트의 `site/config/connector-scopes.json`을 상대 경로의 정적 `import` 선언으로 가져오는 것만 `pki/module-boundary`가 허용한다. 가져오는 쪽, 대상, 형태가 모두 맞아야 하고, 하나라도 다르면 지금처럼 막는다.
7. **등록 검사와 `site-check`가 같은 값을 알린다.** `checkSiteRegistration`이 `connector-scopes-field-invalid`와 `connector-scopes-entry-invalid`를 더한다(검사에서만 나오고 시작은 닫힌 쪽으로 계속된다). `site-check --scopes`는 종류 대신 등록의 인스턴스 범위 상태를 알리고, 필드가 없거나 틀렸거나 예시 값 그대로거나 범위가 있는 항목이 없으면 0이 아닌 값으로 끝난다.
8. **설치본에서의 확인은 정본을 읽는다.** 설치본에서 로그가 어디에 남는지는 확인된 적이 없으므로, 확인은 로그가 아니라 정본의 `connector_instances.configured_scope`가 범위 파일의 값과 같은지를 본다(site-setup S31). 그 절차를 검증 실행기의 `scopes-check`로 만드는 일은 I07-T05의 몫이고 이 ADR 시점에는 아직 없다.

## 기각한 대안

| 대안 | 기각 이유 |
|---|---|
| **(가) 빌드가 파일을 앱 폴더에 복사하고 실행본이 고정 경로에서 읽음.** 이슈의 처음 과제 문장이었다 | 걱정이 생기는 단계(복사, 설치 파일을 만드는 도구의 누락, 실행 중 읽기)를 하나도 없애지 못한 채 검사만 더한다. 설치 폴더에 코드와 따로 놓인 글 파일이 등급을 좌우하게 되고, 코드 서명이나 묶음 무결성 검사가 생겨도 따로 놓인 자원은 그 대상이 아닐 수 있다. "묶음 안의 경로를 실행 중에 읽을 수 있는가"는 설치 형식마다 확인해야 한다 |
| **(다) 둘 다** | (가)의 길이 그대로 남고 두 값이 다를 때의 규칙이 더 필요하다. 길이 둘이다 |
| **데이터 폴더의 파일에서 읽음** | 데이터 폴더는 사용자가 쓸 수 있다. 가져오는 사용자가 자기 청구의 기준을 스스로 정하게 된다 |
| **환경 변수나 인자로 경로를 받음** | 이슈가 명시적으로 막은 것이다. 설치본은 지금도 모르는 인자를 거부한다 |
| **빌드가 포크의 등록을 실행해 상태를 물음** | 빌드 과정에서 포크의 코드가 돈다. 파일과 모듈 목록만 보는 판정으로 충분하다 |
| **모듈 경계 규칙의 거부를 포크의 `// eslint-disable-next-line pki/module-boundary` 한 줄로 품** | 포크의 코드에서 경계 규칙을 끄는 것이 정해진 절차가 된다. 공용 시험은 포크의 주석을 볼 수 없어 무엇이 꺼졌는지 붙잡지 못한다. 규칙 안의 좁은 예외는 공용 시험이 그 폭을 붙잡는다 |
| **범위 파일을 조립 패키지 안으로 옮겨 규칙을 피함** | 고정한 자리(결정 5)와 부딪친다. 그 자리는 `scopes-file-misplaced`다 |
| **모듈 경계 규칙이 모든 `.json` 가져오기나 `site/config/` 전체를 허용** | 필요한 것은 가져오기 하나다. 넓게 풀면 포크의 다른 파일이나 공용 코드가 `site/config/`에 닿는 길이 열리고, 값이 들어오는 자리가 등록 하나라는 전제가 흐려진다 |
| **등록 검사와 따로 둔 함수로 범위를 검사** | 포크가 검사 하나를 더 불러야 하고 잊으면 조용하다. 이미 부르는 검사에 행을 더하는 쪽이 조용한 미적용을 줄인다 |

## 결과

- 포크가 하는 일은 `site/config/connector-scopes.json`을 채우고 `registration.ts`가 그것을 가져와 `connectorScopes`로 넘기게 하는 것이다. 순서는 [connector-sdk.md 7장](../connector-sdk.md), 체크리스트는 [site-setup.md](../site-setup.md)의 S30·S31이다.
- 공용 빌드의 산출물에는 범위 파일도 그 값도 없다. 어느 빌드든 앱 폴더에 `connector-scopes.json`이라는 이름의 파일이 없다. 포크의 빌드에서는 값이 백엔드 묶음 안에만 있다.
- 브라우저 개발용 백엔드(`backend/src/dev.ts`)는 등록을 받지 않으므로 포크에서도 인스턴스 범위가 모두 알 수 없음이다. 지금까지는 소스 트리의 파일을 읽었으므로 이 동작이 바뀐다.
- 남는 위험(자세한 표는 I07 spec의 "남는 위험"):
  - 인스턴스 ID를 잘못 적은 항목은 드러나지 않는다. 형식은 맞고 아무 인스턴스에도 닿지 않아, 의도한 인스턴스는 알 수 없음으로 남는다. S31이 정본의 값과 견줄 때 그 인스턴스의 행이 없거나 값이 `NULL`이어서 드러난다.
  - 가져온 값을 다른 곳에는 쓰면서 `connectorScopes`에는 넘기지 않은 등록은 빌드가 잡지 못한다(가져오고 어디에도 쓰지 않으면 `scopes-file-unbound`로 잡힌다). `site-check --scopes`와 시작 로그가 드러낸다.
  - `node_modules/` 아래의 JSON이나 이름을 바꾼 파일은 빌드 판정이 보지 못한다. 문서는 범위 파일을 이 자리와 이 이름으로만 두라고 적는다.
  - `import` 줄에서 `with { type: "json" }`를 빠뜨린 포크는 타입 검사와 시험이 통과하고 Node의 소스 실행이 실패한다. 묶기는 재지 않았다.
  - 실행 중에 만들어지는 가져오기 인스턴스(`jsonl-file:…`)는 ID를 미리 알 수 없어 범위 파일에 적을 수 없고, 알 수 없음(닫힌 쪽)이다.
  - 묶음 파일 자체를 고치는 일은 코드를 고치는 일과 같고 막지 않는다(H03 #34의 범위).
  - 예시 값 판정(`scopes-file-placeholder`)은 실수를 잡는 장치다. 포크가 다른 지어낸 값을 채운 것은 알아보지 못한다.
- 이 결정이 선 근거는 macOS에서 돌린 시험과 포크 모양을 흉내 낸 버리는 작업 트리의 예행이다. Windows 설치본, 실제 포크, `references`가 있는 실제 포크의 `tsconfig.json`, 설치본에서의 로그 위치는 확인하지 못했다.

## 되돌리거나 다시 볼 조건

- 빌드한 묶음이 값을 실제로 싣지 못하는 설치 형식이 드러나면(Windows 설치본에서 정본의 값이 범위 파일과 다른 경우가 S31에서 반복되면) (가)를 다시 본다. 이때 고칠 곳은 I07 spec의 "(가)로 되돌리려면"에 적혀 있다.
- 인스턴스 ID를 미리 알 수 없는 인스턴스에도 범위를 정해야 하는 요구가 생기면(접두사나 종류 단위의 기본값) 범위 파일의 형식을 바꾸는 일이므로 별도의 결정으로 다룬다.
- 묶음 도구가 JSON 모듈을 모듈 목록에 저장소 경로로 내지 않게 되면 빌드 판정의 입력("모듈 목록")을 다른 표지로 바꾼다(I07 spec의 가정 B4).
