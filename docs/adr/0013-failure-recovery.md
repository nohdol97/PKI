# ADR 0013: 저장소 사이의 실패 복구 — 정본 먼저, fence와 tombstone, 투영은 재구축

- 날짜: 2026-11-21 / 상태: **잠정 — 배포처 검증 대기**
- 관련: 이슈 #1 설계 분석 1~2번, 이슈 #15 R06-C2, 이슈 #18 I01-C2, [ARCHITECTURE 6~7절](../ARCHITECTURE.md), [ADR 0002](0002-authority-in-product-records.md), 가정 A20

## 맥락

정본 SQLite, 벡터 색인, (나중의) 엔진 저장소와 Wiki는 서로 다른 저장소다. 한 트랜잭션으로 묶을 수 없으므로 중간에 꺼지면 어긋난다. 또 추출은 느린 작업이라 그 사이 원본이 수정되거나 삭제될 수 있고, 늦게 끝난 결과가 지운 데이터를 되살릴 수 있다. 원 설계 20절은 원본 삭제 시 파생 지식 갱신과 재시작 뒤 안전한 재개를 요구한다. 이슈 #18의 I01-C2는 "Evidence는 immutable source version과 span…을 가리킨다"고 정해 두었다.

## 결정

1. **정본을 먼저, 한 트랜잭션으로 쓴다.** 원본 저장과 작업 등록, 지식 기록은 각각 한 트랜잭션이다. cursor는 원본을 저장한 뒤에 확정한다.
2. **원본의 version은 바뀌지 않는다.** 한번 저장된 version의 내용은 삭제될 때까지 그대로이고, 근거는 자기가 나온 version을 계속 가리킨다. 새 version이 와도 이전 version을 가리키던 근거를 떼어 내지 않는다. 그 근거는 "지난 근거"가 될 뿐이다.
3. **version fence.** 작업은 시작할 때 본 원본 version을 들고 다니고, 결과를 쓰는 트랜잭션 안에서 그 version이 여전히 최신인지 확인한다. 아니면 결과를 버린다.
4. **tombstone.** 삭제와 권한 철회는 표식으로 남긴다. 표식에는 원본의 식별자, **덮는 version**(그 이하의 모든 제품 version을 덮는다. version이 저장된 적 없는 원본은 0), 삭제 때의 출처 revision, 시각, 사유만 있고 **내용은 없다.** 결과 쓰기, 재수집, 투영 갱신, 검색 결과 반환에서 확인한다([I04 spec](../specs/2026-11-21-I04-invalidation.md) I04-R9).
   - **덮는 범위.** 덮인 version 번호는 다시 쓰지 않는다. 모든 version이 지워져도 다음 version은 덮는 version + 1이다.
   - **사유.** 출처가 지움(`source-deleted`), 권한을 잃음(`access-revoked`), 사용자가 지움(`user-deleted`). 같은 덮는 version에서는 사용자의 삭제가 출처 사유를 덮어쓰고 그 반대는 없다. 그 밖에는 더 큰 덮는 version만 표식을 옮긴다.
   - **해제.** 사용자만 표식을 해제할 수 있다. 지운 내용은 돌아오지 않고, 그 뒤의 도착을 막지 않을 뿐이다. 해제 뒤 새 version이 오기 전에 다시 삭제하면 그 사유로 다시 쓴다.
   - **도착 판정은 I01에 있다.** 해제되지 않은 표식 위로 원본이 돌아올 수 있는지는 revision의 순서로 정하고(표식의 revision보다 큰 revision), 해제 뒤에는 보통의 도착 규칙을 따른다([I01 spec](../specs/2026-11-21-I01-connector-sdk.md)).
   - 변경 순번은 새 표식과 덮는 version이 바뀔 때만 오른다. 사유 변경과 해제는 내용을 바꾸지 않는다.
5. **삭제는 지우는 것이다.** tombstone을 쓰는 같은 트랜잭션에서 그 원본의 **모든 version**의 본문, 그 version들을 가리키는 근거와 인용문(지난 근거 포함), 키워드 색인의 행을 지우고, 근거가 하나도 남지 않은 지식을 지운다. 근거가 version에 붙어 남아 있으므로, 예전 version에만 있던 값도 이 경로로 찾아 지울 수 있다. 지운 자리가 파일에 남지 않게 한다.
6. **변경 순번.** 원본에 변경(새 version 저장, 삭제, 권한 철회)이 생길 때마다 정확히 1씩 오르는 번호를 같은 트랜잭션에서 올린다. 추출로 지식이 생기는 것만으로는 오르지 않는다.
7. **투영 동기화(Phase 1): 통지와 변경 순번 비교.** 정본을 쓴 뒤 엔진과 벡터 규격에 변경을 통지하고 그 변경 순번을 함께 넘긴다. 투영은 자기가 반영한 마지막 순번을 기억한다. 시작할 때 그 번호가 정본과 다르면 투영을 비우고 정본에서 다시 만든다. 같으면 아무것도 하지 않는다. 기준 번호가 통지할 변경에서만 오르므로, 깨끗이 끝냈다가 다시 켠 경우에는 재구축이 일어나지 않는다. 이 보장은 반영 순번을 기억하는 투영에 대한 것이다. 기억할 상태가 없는 null 구현은 언제나 `null`을 돌려주므로 켤 때마다 재구축을 받지만, 그 재구축은 아무 일도 하지 않는다(ARCHITECTURE 5.3절).
8. **outbox(나중).** 재구축 비용이 커지면 투영에 반영할 변경을 정본을 고친 트랜잭션 안에 목록으로 적고 순서대로 처리한다. 벡터에 실제 지식을 색인하는 작업에서 넣는다. Phase 1에는 넣지 않는다.
9. **작업 임대.** 실행기는 작업을 기한이 있는 임대로 집는다. 재시작하면 기한이 지난 작업을 다시 집는다. 같은 작업이 두 번 실행되어도 fence와 중복 키 때문에 결과는 한 번만 반영된다. Phase 1의 실행기는 작업을 한 번에 하나씩 처리한다.

구현 시점: 작업 테이블은 V01의 스키마 v1(Broker가 호출 종류를 판정하는 데 필요하다). 변경 순번, fence, tombstone, 삭제, 통지와 비교, 작업 임대는 V02. Phase 1의 키워드 색인은 정본과 같은 트랜잭션으로 갱신된다. knowledge revision(지식이 바뀔 때 오르는 번호)은 지식 자체를 색인하는 투영이 생길 때 그 투영의 기준 번호로 쓰며, Phase 1에는 그것을 읽는 투영이 없다.

## 기각한 대안

| 대안 | 기각 이유 |
|---|---|
| 저장소 여러 개에 차례로 쓰고 실패 시 되돌림 | 되돌리는 도중에 꺼지면 어긋난 채 남는다 |
| 투영을 먼저 쓰고 정본을 나중에 | 정본에 없는 내용이 검색에 나온다 |
| 삭제 시 행을 그냥 지움(tombstone 없음) | 진행 중이던 작업이나 재수집이 같은 원본을 되살린다 |
| 삭제 시 숨기기만 하고 내용은 남김 | 원 설계 17절 "원본 삭제와 파생 지식 삭제 동기화"에 어긋난다. 조사가 엔진을 걸러 낸 기준(OSS_EVALUATION 1절 탈락 조건 ③)을 제품이 스스로 못 지키게 된다 |
| 새 version이 오면 이전 version의 근거를 떼어 냄 | superseded가 된 행이 값은 갖고 있으면서 어느 원본에서 왔는지는 잃는다. 나중에 그 원본을 지워도 그 행을 찾지 못해 값이 남는다. I01-C2와도 어긋난다 |
| 투영의 기준 번호로 knowledge revision을 씀 | 추출만 해도 번호가 오르는데 엔진에는 통지가 가지 않는다. 엔진이 늘 뒤처진 것으로 보여 켤 때마다 재구축한다 |
| Phase 1부터 outbox | Phase 1의 투영은 null 구현과 빈 구현이라 재구축 비용이 0이다. 통지와 비교로 충분하다 |
| 엔진의 삭제 기능에만 의존 | 후보들의 삭제 동작이 실행으로 확인되지 않았다([OSS_EVALUATION 2.1절·7절](../OSS_EVALUATION.md)) |

## 결과

- 투영은 언제든 정본보다 잠깐 늦을 수 있다. 검색 결과는 반환 직전에 tombstone을 확인해 삭제된 원본을 걸러 낸다.
- 이전 version의 본문은 원본이 삭제될 때까지 저장소에 남는다(문서 버전 관리). 이전 version은 tombstone이 덮을 때 함께 지워지거나, 사용자가 원본 하나의 이전 version 지우기를 할 때 지워진다(I04-R10, 선택 작업 I04-T12). 자동으로 정리하지 않는다.
- 재구축 비용은 코퍼스 크기에 비례하며 측정하지 않았다.
- tombstone은 지우지 않는다(내용이 없고 작으며, 지우면 재수집과 백업 복원이 지운 데이터를 되살린다. I04-R10). 삭제한 원본의 내용은 복원하지 않는다. 사용자는 표식을 해제해 그 원본이 다시 수집되게 할 수 있을 뿐이다(I04-R9).
- 갑작스러운 종료와 읽기·쓰기의 동시 진행에서 SQLite 파일이 실제로 견디는지는 확인하지 못했다(A20). R03-C4의 실행 확인 대상이다.
