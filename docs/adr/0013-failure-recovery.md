# ADR 0013: 저장소 사이의 실패 복구 — 정본 먼저, fence와 tombstone, 투영은 재구축

- 날짜: 2026-11-21 / 상태: **잠정 — 배포처 검증 대기**
- 관련: 이슈 #1 설계 분석 1~2번, 이슈 #15 R06-C2, [ARCHITECTURE 6~7절](../ARCHITECTURE.md), [ADR 0002](0002-authority-in-product-records.md), 가정 A20

## 맥락

정본 SQLite, 벡터 색인, (나중의) 엔진 저장소와 Wiki는 서로 다른 저장소다. 한 트랜잭션으로 묶을 수 없으므로 중간에 꺼지면 어긋난다. 또 추출은 느린 작업이라 그 사이 원본이 수정되거나 삭제될 수 있고, 늦게 끝난 결과가 지운 데이터를 되살릴 수 있다. 원 설계 20절은 원본 삭제 시 파생 지식 갱신과 재시작 뒤 안전한 재개를 요구한다.

## 결정

1. **정본을 먼저, 한 트랜잭션으로 쓴다.** 원본 저장과 작업 등록, 지식 기록과 revision 증가는 각각 한 트랜잭션이다. cursor는 원본을 저장한 뒤에 확정한다.
2. **version fence.** 작업은 시작할 때 본 원본 version을 들고 다니고, 결과를 쓰는 트랜잭션 안에서 그 version이 여전히 최신인지 확인한다. 아니면 결과를 버린다.
3. **tombstone.** 삭제와 권한 철회는 표식으로 남긴다. 표식에는 원본의 식별자, 그때까지의 version 번호, 시각, 사유만 있고 **내용은 없다.** 결과 쓰기, 재수집, 투영 갱신, 검색 결과 반환에서 확인한다. 표식의 version 이하인 원본은 다시 들어오지 못한다.
4. **삭제는 지우는 것이다.** tombstone을 쓰는 같은 트랜잭션에서 그 원본의 모든 version의 본문, 그 원본을 가리키는 근거와 인용문, 키워드 색인의 행을 지우고, 근거가 0이 된 지식을 지운다. 지운 자리가 파일에 남지 않게 한다.
5. **투영 동기화(Phase 1): 통지와 revision 비교.** 정본을 쓴 뒤 엔진과 벡터 규격에 변경을 통지하고 그 변경의 knowledge revision을 함께 넘긴다. 투영은 자기가 반영한 revision을 기억한다. 시작할 때 그 번호가 정본과 다르면 투영을 비우고 정본에서 다시 만든다.
6. **outbox(나중).** 재구축 비용이 커지면 투영에 반영할 변경을 정본을 고친 트랜잭션 안에 목록으로 적고 순서대로 처리한다. 벡터에 실제 지식을 색인하는 작업에서 넣는다. Phase 1에는 넣지 않는다.
7. **작업 임대.** 실행기는 작업을 기한이 있는 임대로 집는다. 재시작하면 기한이 지난 작업을 다시 집는다. 같은 작업이 두 번 실행되어도 fence와 중복 키 때문에 결과는 한 번만 반영된다. Phase 1의 실행기는 작업을 한 번에 하나씩 처리한다.

구현 시점: knowledge revision, fence, tombstone, 삭제, 통지와 비교, 작업 임대는 V02. Phase 1의 키워드 색인은 정본과 같은 트랜잭션으로 갱신된다.

## 기각한 대안

| 대안 | 기각 이유 |
|---|---|
| 저장소 여러 개에 차례로 쓰고 실패 시 되돌림 | 되돌리는 도중에 꺼지면 어긋난 채 남는다 |
| 투영을 먼저 쓰고 정본을 나중에 | 정본에 없는 내용이 검색에 나온다 |
| 삭제 시 행을 그냥 지움(tombstone 없음) | 진행 중이던 작업이나 재수집이 같은 원본을 되살린다 |
| 삭제 시 숨기기만 하고 내용은 남김 | 원 설계 17절 "원본 삭제와 파생 지식 삭제 동기화"에 어긋난다. 조사가 엔진을 걸러 낸 기준(OSS_EVALUATION 1절 탈락 조건 ③)을 제품이 스스로 못 지키게 된다 |
| Phase 1부터 outbox | Phase 1의 투영은 null 구현과 빈 구현이라 재구축 비용이 0이다. 통지와 비교로 충분하다 |
| 엔진의 삭제 기능에만 의존 | 후보들의 삭제 동작이 실행으로 확인되지 않았다([OSS_EVALUATION 2.1절·7절](../OSS_EVALUATION.md)) |

## 결과

- 투영은 언제든 정본보다 잠깐 늦을 수 있다. 검색 결과는 반환 직전에 tombstone을 확인해 삭제된 원본을 걸러 낸다.
- 재구축 비용은 코퍼스 크기에 비례하며 측정하지 않았다.
- tombstone을 언제 지워도 되는지(보존 기간)와 삭제한 원본의 복원은 Phase 2(I04)에서 정한다.
- 갑작스러운 종료와 읽기·쓰기의 동시 진행에서 SQLite 파일이 실제로 견디는지는 확인하지 못했다(A20). R03-C4의 실행 확인 대상이다.
