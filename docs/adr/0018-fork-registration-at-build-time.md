# ADR 0018: 배포처 수집기는 빌드할 때 진입점 주입으로 등록한다

- 날짜: 2026-11-23 / 상태: **잠정 — 배포처 검증 대기**(실제 포크에서 이 방식이 서는지는 S26, Windows 설치본에서의 동작은 S27에서 확인한다)
- 관련: [I05 spec](../specs/2026-11-22-I05-site-connector-registration.md)(I05-R1~R25, "대안과 기각 사유", "신뢰 경계와 남는 위험"), 이슈 #113, [ADR 0012](0012-upstream-and-fork-ownership.md), [ADR 0016](0016-connector-sdk-v2.md), [ownership.md 3절](../ownership.md), [connector-sdk.md 7장](../connector-sdk.md), [site-setup.md](../site-setup.md)의 S26·S27

## 맥락

[ADR 0012](0012-upstream-and-fork-ownership.md)는 포크가 `site/` 안만 고친다고 정했다. 두 쪽이 같은 파일을 고치지 않아야 포크가 공용의 변경을 받아 갈 때 충돌이 나지 않기 때문이다. 그런데 수집기를 `site/` 안에 두고도 제품에 연결할 방법이 없었다. 포크는 수집기 종류 표(`backend/src/composition.ts`), 워크스페이스 목록, `backend/package.json`, 접근 범위 정책 이름(`apps/desktop/src/layout.production.ts`)을 고쳐야 했다.

시작 동작에도 빈 곳이 있었다. 수집기 하나의 `initialize`가 끝나지 않으면 앱이 켜지지 않았고, 만드는 함수가 던지거나 인스턴스가 모르는 종류를 적으면 시작이 중단됐다. 한 시간마다의 재점검은 실패했던 같은 객체의 `initialize`를 다시 불렀는데, 규격 v2는 그렇게 불러도 안전하다고 약속한 적이 없다.

포크의 코드는 가져온 내용이나 수집기가 돌려주는 값과 달리 **포크 소유자가 검토해 넣는 코드**다. 그러나 같은 프로세스에서 같은 권한으로 돌므로, 이 장치는 "포크의 코드를 어떻게 싣는가"와 "실린 코드가 잘못 동작해도 제품이 켜지는가"를 함께 정해야 했다.

## 결정

1. **결합은 빌드할 때의 정적 `import`다.** 포크는 `site/composition/`에 조립 패키지(`@pki-site/composition`)를 두고, 그 안의 등록 객체(`SiteRegistration`) 하나와 진입점 둘이 공용 백엔드의 함수(`runShell`, `runSiteCheck`)를 자기 등록으로 부른다. 공용 진입점은 같은 함수를 빈 등록(`publicSite`)으로 부른다. 빌드와 소스 실행은 `site/composition/package.json`이 있으면 `site/composition/src/shell.ts`를 고르고 없으면 `backend/src/shell.ts`를 고른다(`backendEntry`). 실행본은 디스크에서 코드를 찾아 읽어 들이지 않는다.
2. **등록은 바탕 묶음 위에 합쳐진다.** 필드는 모두 선택이다: `connectorKinds`(종류 → 만드는 함수), `connectorInstances`, `scopeGrading`, `scopePolicy`(그리고 I07이 더한 `connectorScopes`). 등록은 바탕을 바꾸거나 지우지 못하고 종류와 인스턴스를 더하거나 자리표시 이름을 같은 이름으로 대체할 수 있을 뿐이다.
3. **공용 종류는 등록할 수 없고, 등록은 사이트 종류의 인스턴스만 만든다.** 공용 종류의 목록은 상수 하나(`PUBLIC_CONNECTOR_KINDS`)에서 온다. 공용 종류는 제품이 따로 지키는 약속(사용자의 경로 승인, 합성 등급)을 갖기 때문이다. 공용 종류나 공용 인스턴스 ID를 쓰는 인스턴스(`instance-kind-reserved`, `instance-id-reserved`)는 **시작을 멈춘다.** 그 밖의 위반은 그 항목만 빠지고 시작은 계속된다. `checkSiteRegistration`이 위반을 코드의 목록으로 돌려주고, 포크는 자기 등록이 빈 목록을 돌려준다는 테스트를 둔다.
4. **시작할 때 `initialize`는 10초(`INITIALIZE_TIMEOUT_MS`)까지만 기다린다.** 만드는 함수의 예외, `initialize`의 예외, 시간 초과, 모르는 종류 모두 그 인스턴스만 `unavailable`이 되고 시작은 계속된다. 제한을 넘겨 끝난 결과는 버린다. 이 제한은 비동기로 기다리는 시간만 잰다.
5. **재점검은 만드는 함수를 다시 불러 새 객체를 만든다.** 제품은 한 객체의 `initialize`를 한 번만 부른다. 규격에 취소와 닫기가 없으므로 버려진 객체는 닫히지 않는다. 쌓이는 수에 끝을 두려고 60초를 넘겨 끝난 재점검이 연달아 3번이면 그 인스턴스의 재점검을 그만둔다.
6. **접근 범위 정책은 등록이 정한다.** 배포 빌드는 정책의 이름을 넘기지 않으므로, 정책을 등록한 포크의 설치본은 언제나 그 정책을 쓰고 설치본을 공용 기본 정책으로 돌리는 스위치는 없다. 등록의 등급 매핑은 빌드 종류와 무관하게 Broker가 쓴다.
7. **워크스페이스와 이름.** `pnpm-workspace.yaml`의 `packages:`에 `site/composition`과 `site/connectors/*`를 공용 저장소가 미리 둔다(폴더가 없어도 설치가 통과한다). 포크 패키지의 이름은 `@pki-site/`로 시작한다. 모듈 경계 규칙이 이 이름으로 포크의 것을 알아보고, 포크의 패키지가 `backend/src`나 `@pki/backend`의 하위 경로를 가져오는 일과 수집기 구현을 `registration.ts` 밖에서 가져오는 일을 막는다. 공용 패키지는 `@pki-site/*`를 가져오지 못한다.
8. **`site/` 밖에서 달라지는 추적 파일은 `pnpm-lock.yaml`이다.** 도구가 다시 만든 변경만 받아들이고, 충돌하면 공용 쪽을 취하고 `pnpm install`을 다시 실행한다. 설치 스크립트가 있는 의존성이면 `pnpm-workspace.yaml`의 `allowBuilds`에 `false` 줄이 하나 더해진다. 스크립트가 정말 필요한 의존성과 네이티브 실행 모듈은 지원하지 않는다.
9. **포크의 코드는 믿는 코드이고 가두지 않는다.** 등록 검사는 실수를 잡는 무결성 검사이고, 시간 제한과 인스턴스 단위 실패는 가용성 장치다. 어느 것도 격리가 아니다. 수집기가 돌려주는 값은 여전히 믿지 않는 자료다.
10. **공용의 `pnpm lint`·`pnpm typecheck`·`pnpm test`는 포크 모양에서도 통과한다.** `site/`가 있느냐로 결과가 달라지는 코드는 저장소 루트를 인자로 받고, 그 시험은 임시 폴더를 루트로 쓴다. 포크는 공용의 테스트 파일을 고치지 않고 `pnpm test`를 돌린다. **`pnpm e2e`도 포크 모양에서 통과한다.** 예행에서 공용 e2e 다섯이 포크 모양에서 실패했고 I05-T06이 두 모양에서 참이 되게 고쳤다(`v02-flow`는 포크 모양에서도 공용 이중을 시험한다). `pnpm lint`는 루트의 `eslint.config.js` 하나만 쓴다(`-c`).

## 기각한 대안

| 대안 | 기각 이유 |
|---|---|
| **실행 중 로더.** 시작할 때 폴더를 훑어 수집기를 동적으로 읽어 들임 | 실행본이 디스크의 코드를 실행하게 된다. 설치 폴더나 데이터 폴더에 파일을 쓸 수 있는 누구든 정본과 비밀 값 통로를 가진 백엔드 안에서 코드를 돌릴 수 있다. 산출물 검사(V01-T15)는 묶음에 남은 모듈 목록으로 판정하는데 나중에 읽히는 코드는 그 목록에 없고, 수집기의 의존성도 묶이지 않는다. ADR 0012가 기각한 것은 소유 구조이지 실행 중 로더 자체가 아니므로, 이 기각은 위 이유에 따른 이 결정이다 |
| **생성된 등록표.** 도구가 `site/connectors/`를 훑어 `import` 목록 파일을 만들어 줌 | 타입 검사 프로젝트는 참조에 적힌 패키지만 가져올 수 있어서 만든 파일이 포크 패키지를 가져오려면 `tsconfig`와 의존성까지 함께 만들어야 한다. 설치 훅, 낡음 검사, 추적되지 않는 파일이 타입 검사의 입력이 되는 일이 따라온다. 결과는 같고 장치만 많다 |
| **해석 별칭.** `#site` 같은 이름을 포크 파일이 있으면 그리로, 없으면 공용 기본으로 풀기 | Node 소스 실행, 테스트 러너, 타입 검사, 번들러 넷이 각자 설정을 가져야 하고, 넷이 어긋나면 테스트는 통과하고 산출물만 틀린다 |
| **공용이 `site/`에 씨앗 파일을 두고 포크가 고침** | ADR 0012의 "안내문만 둔다"와 어긋나고, 두 쪽이 같은 파일을 만지게 된다. 그 파일을 고정하는 공용 테스트는 포크에서 실패한다 |
| **`site/`를 별도 워크스페이스로**(자기 lockfile) | lockfile 충돌은 없어지지만 설치가 둘이 되고, 공용 패키지를 `link:`로 물어야 하며, Node와 pnpm 고정 값이 두 곳에 생긴다 |
| **규격이 `initialize` 재호출 안전을 약속** | 모든 포크 수집기가 반쯤 초기화된 상태를 스스로 되돌려야 하고, 계약 묶음은 실제 부분 실패를 흉내 낼 수 없어 약속을 증명하지 못한다. 새 객체를 만드는 쪽은 만드는 함수가 이미 인자 없는 함수이고 계약 묶음이 이미 새 객체를 여러 번 만든다 |
| **시작할 때 기다리지 않고 전부 뒤에서 초기화** | 시작 직후의 일들(기본 주기 만들기, 준비된 인스턴스의 보류 풀기)이 "시작이 끝나면 상태가 정해져 있다"에 기대고 있어 고칠 곳이 넓다 |
| **등록이 공용 종류의 인스턴스도 만들 수 있게 함** | 공용 종류는 사용자의 경로 승인이나 합성 등급 같은 자기 보호를 갖는다. 등록으로 그 인스턴스를 만들면 보호를 모두 건너뛴다 |
| **공용 `site-check`가 포크 패키지 이름을 적어 둠** | "공용 코드에 `@pki-site/`가 없다"와 부딪친다. 이름을 포크의 `package.json`에서 읽으면 둘 다 지켜진다 |

## 결과

- 포크가 하는 일은 `site/` 안에 파일을 더하는 것이다. 순서와 명령은 [connector-sdk.md 7장](../connector-sdk.md), 체크리스트는 [site-setup.md](../site-setup.md)의 S26·S27이다.
- 공용 저장소의 빌드 산출물은 달라지지 않고, 포크의 빌드에는 등록한 수집기가 들어가고 테스트 코드는 들어가지 않는다.
- 남는 위험(자세한 표는 I05 spec의 "신뢰 경계와 남는 위험"):
  - 동기 코드로 멈추는 수집기와 포크 모듈을 읽는 도중의 예외는 막지 못한다. 포크의 검토와 S27이 맡는다.
  - 제한을 넘긴 초기화가 뒤에서 계속 돌고 버려진 객체는 닫히지 않는다. 규격에 닫기를 더하는 일은 규격 v3의 몫이다.
  - 린트가 보지 않는 길이 있다: `tsconfig`의 `paths` 별칭, 심볼릭 링크, `createRequire(...)`, 계산된 이름의 `import()`, `package.json`의 `imports`(`#이름`). 네이티브 모듈 검사는 계산된 이름으로 불러오고 JS 코드로 내려가는 패키지를 놓치고, 빌드하는 OS에 설치된 패키지만 본다.
- 예행에서 `pnpm test`는 포크 모양에서 통과했고 `pnpm e2e`는 공용 시험 다섯이 실패했다. I05-T06이 고친 뒤 같은 모양의 예행에서 `pnpm e2e`가 통과했다.
- 이 결정이 선 근거는 포크 모양을 흉내 낸 버리는 작업 트리의 한 번의 예행이다(I05 spec의 "I05-T05가 넘기는 것"). 실제 포크의 의존성 조합, Windows, 설치본에서의 실행은 확인하지 못했고 S26·S27이 맡는다.

## 되돌리거나 다시 볼 조건

- 다시 빌드하지 않고 수집기를 설치해야 한다는 요구가 생기면 실행 중 로더를 다시 본다. 지금은 비목표다.
- 배포처가 검토하지 않은 수집기를 실어야 하면 수집기를 다른 프로세스나 작업자로 옮기는 구조 변경을 정한다(동기 멈춤과 모듈 최상위 예외는 같은 프로세스에서는 막을 수 없다).
- 공용 종류의 인스턴스를 배포처가 미리 설정해야 하는 요구가 생기면 그 종류의 spec이 승인 절차와 함께 길을 연다.
- `pnpm-lock.yaml` 충돌이 `pnpm install`로 고쳐지지 않는 일이 S26에서 드러나면 `site/`를 별도 워크스페이스로 두는 쪽을 다시 본다.
