# ADR 0019: 수집기 자격 증명은 V01의 비밀 값 저장소에 두고 접근자로 건넨다

- 날짜: 2026-11-23 / 상태: **잠정 — 배포처 검증 대기**(Windows 설치본에서 OS 보호가 값을 실제로 지키는지와 실제 원 시스템의 거부·잠금 동작은 S28과 S29에서 확인한다. 번호는 머지 순서로 조정한 잠정이다)
- 관련: [I06 spec](../specs/2026-11-22-I06-connector-credentials.md)(I06-R1~R25, "대안과 기각 사유", "잠정 결정과 가정", I06-R19의 남는 위험 표), 이슈 #114, [ADR 0010](0010-encryption-at-rest.md), [ADR 0016](0016-connector-sdk-v2.md), [ADR 0018](0018-fork-registration-at-build-time.md), [ownership.md 3절](../ownership.md), [connector-sdk.md 8장](../connector-sdk.md), [site-setup.md](../site-setup.md)의 S28·S29
- 후속: 웹 로그인이 인증인 원 시스템(세션 쿠키, 회전하는 토큰)의 길은 [ADR 0027](0027-session-credentials-interactive-login.md)이 잇는다. 결정 8의 "값이 지나는 길은 둘뿐"에 세션 칸에 한해 "수집기 → 백엔드 → 셸의 저장소"가 더해지고, 「되돌리거나 다시 볼 조건」 1의 `write`가 그 칸에만 생겼다. 이 ADR의 나머지 결정(고정 값 칸, 사유, 재시도 상한, 누출 없음)은 그대로다.

## 맥락

실제 메일·메신저·Wiki 수집기는 원 시스템에 접근하려면 토큰이나 암호가 있어야 한다. 그런데 수집기가 제품에서 받는 것은 `initialize(config)`의 설정 하나였고, 그 값을 보관해 건네는 길이 없었다. [connector-sdk.md](../connector-sdk.md) 8장은 "자격 증명은 OS 자격 증명 저장소에 두고 레코드·설정 파일·로그에 넣지 않는다"는 **규칙**만 적었고 수단은 "포크가 정해야 한다"고 적어 두었다.

수단이 없으면 포크가 고를 수 있는 길은 셋인데 모두 나쁘다. 값을 등록의 `config`에 적으면 값이 저장소의 코드에 남고 제품이 기본 주기를 정할 때 읽는 값이라 다른 코드로 흘러간다. 수집기가 OS 보관함을 직접 부르려면 네이티브 모듈이 필요한데 [ADR 0018](0018-fork-registration-at-build-time.md)이 정한 길은 포크의 네이티브 모듈을 지원하지 않는다. 포크가 입력 화면을 따로 만들면 `site/` 밖의 화면을 고치게 되어 [ownership.md 3절](../ownership.md)의 규칙을 어긴다.

한편 V01은 이미 비밀 값 저장소를 갖고 있다([ADR 0010](0010-encryption-at-rest.md)). Electron 셸이 값을 `safeStorage`로 암호화해 두고, 백엔드는 쓸 때마다 셸에 물어 받으며, 화면은 저장·확인·삭제만 할 수 있고 되읽지 못한다. 상태 쪽에도 빈 곳이 있었다. 자격 증명이 없거나 만료된 인스턴스는 초기화 실패와 구별되지 않았고, 동기화 도중의 거부는 재시도를 다 쓰고 포기한 작업이 되었다.

## 결정

1. **수집기의 자격 증명은 V01의 비밀 값 저장소에만 둔다.** 새 저장소나 OS 보관함용 네이티브 모듈을 만들지 않는다. 저장, 암호화, 파일 형식, "OS 보호를 쓸 수 없으면 아무것도 저장하지 않는다"는 규칙은 ADR 0010 그대로다. 한 칸의 저장 이름은 `connector.<32자리 16진수>.<칸>`이고 16진수는 종류, 줄바꿈 한 글자, 인스턴스 ID를 이은 글의 SHA-256 앞 32자리다(`connectorCredentialName`, `isConnectorCredentialSecret`). 종류를 함께 넣어 같은 ID가 다른 종류로 다시 쓰여도 옛 종류의 값이 건네지지 않게 한다. **저장 이름은 `config`(원 시스템의 주소)를 묶지 않는다.** 주소를 바꾼 빌드에서 옛 값이 새 주소로 건네지는 것은 포크의 규칙(원 시스템을 바꾸면 인스턴스 ID도 바꾼다)으로 막는다. 셸은 백엔드의 읽기와 존재 확인에 Provider 키의 이름과 수집기 자격 증명의 이름에만 답하고, Provider 키를 정리하는 요청은 수집기 자격 증명을 지우지 않는다.
2. **규격에는 선택 항목으로만 더하고 버전은 2 그대로다.** `initialize(config, context?)`의 둘째 인자 `ConnectorContext`, 읽기 하나뿐인 `ConnectorCredentials`, 인자가 없고 문구가 고정인 `ConnectorCredentialError`(고정 문구 상수 `CONNECTOR_CREDENTIAL_MESSAGE`), `healthCheck`가 거부를 알리는 상수 `HEALTH_REASON_CREDENTIAL_REJECTED`다. 인자 하나만 받는 기존 구현은 고치지 않아도 타입 검사와 실행이 그대로다. 제품은 `initialize`를 부를 때 **언제나** `context`를 넘기고, 이 길이 들어오기 전의 제품은 넘기지 않으므로 자격 증명을 쓰는 수집기는 `context`가 없으면 `ConnectorCredentialError`로 끝낸다. 오류를 알아보는 방식(`isConnectorCredentialError`)은 `instanceof`와 고정된 이름·문구 쌍 **둘 다**다. 포크의 번들이 `@pki/contracts`를 한 벌 더 싣더라도 거부가 읽히게 하려는 것이다. 계약 묶음이 쓰는 대본 수집기의 `onInitialize`(`@pki/testkit`)도 공개 표면이다.
3. **값은 접근자로 건넨다.** 값을 설정에 합치거나 통째로 넘기지 않는다. 접근자는 `read(칸)`을 부를 때마다 저장소에서 읽고 제품은 값을 기억하지 않는다. 선언하지 않은 칸, 없음, 쓸 수 없음, 3초 안에 오지 않은 답은 모두 같은 고정 오류로 거부하고 그 오류에는 칸 이름도 저장 이름도 싣지 않는다. 제품이 버린 객체(시간 제한을 넘긴 시도, 실패한 재점검, 새 객체로 바뀐 것)의 접근자는 끊긴다. 수집기 객체를 만들고 초기화하는 한 곳(`openConnector`)이 접근자를 만들며, 만들기 전에 선언한 칸이 모두 있는지 먼저 묻는다.
4. **칸은 인스턴스 정의의 `credentials`로 선언한다.** 종류의 `manifest`가 아니라 인스턴스가 선언해 같은 종류의 두 인스턴스가 다른 칸을 가질 수 있다. 이름은 `^[a-z][a-z0-9-]{0,15}$`, 한 인스턴스 안에서 서로 달라야 하고 많아야 8개(`MAX_CREDENTIAL_SLOTS`)다. 어기면 등록 검사가 새 코드 `instance-credentials-invalid`를 돌려주고 시작할 때는 그 인스턴스만 빠진다.
5. **거부는 수집기가 알리고, 사유는 저장소가 한 답으로 정한다.** 원 시스템이 자격 증명을 받아 주지 않으면 수집기가 `initialize`나 `getChanges`에서 `ConnectorCredentialError`를 던지거나 `healthCheck`가 상수를 답한다. 만료와 거부는 한 사유다(저장소가 만료 시각을 모르고 사용자가 할 일이 같다). 제품은 수집기의 말이 아니라 존재 확인을 다시 물은 저장소의 답으로 사유를 정한다: `credential-store-unavailable`, `credential-missing`, `credential-unreadable`, `credential-rejected`. 칸을 선언하지 않은 인스턴스의 거부는 넣을 값이 없으므로 사유 없는 `unavailable`이다. 동기화 도중의 거부는 새 멈춤 코드 `credential-unusable`이 되어 작업이 시도를 쓰지 않고 `held`가 된다(재시도하지 않는다).
6. **거부된 값은 한 시간마다 다시 시도하지 않는다.** `credential-rejected`인 인스턴스는 한 시간마다의 재점검이 건너뛴다. 다시 시도되는 때는 변경 알림(`CREDENTIAL_RETRY_MIN_MS`, 잠정 30초에 한 번, 첫 알림은 곧바로)과 앱을 켤 때 한 번이다. 거부되었다는 사실은 저장하지 않는다. 같은 값으로 원 시스템을 되풀이해 두드려 계정이 잠기는 것을 피하기 위해서다.
7. **변경 알림에 의한 다시 만들기를 [ADR 0018](0018-fork-registration-at-build-time.md)의 새 객체 재점검에 더한다.** 화면이 값을 저장하거나 지운 뒤 `POST /api/connectors/credentials-changed`(`{ connectorId }`, 값 없음)를 부르면 백엔드는 그 인스턴스를 새 객체로 다시 만든다. `ready`인 인스턴스도 다시 만든다(옛 값으로 돌던 객체가 새 값을 읽게 할 다른 길이 없다). 재점검과 같은 자리 하나를 써서 끝나지 않은 객체가 인스턴스마다 둘을 넘지 않게 한다.
8. **값은 화면에서 셸로 곧장 가고 백엔드의 API를 지나지 않는다.** 저장과 삭제는 Provider 키와 같은 preload 함수를 쓰고 함수를 더하지 않는다. 값이 지나는 길은 둘뿐이다. "화면 입력 → 셸의 저장소"와 "셸 → 백엔드 프로세스 → 수집기"다. 화면은 값을 되읽지 못하고, 이 화면에서 넣는 자격 증명은 한 줄, 8192자 이하다(줄바꿈이 든 값과 긴 값은 자르지 않고 거부한다). 여러 줄 값은 받지 않는다.
9. **누출 없음은 시험이 찾을 수 있는 모양으로 적는다.** 값(원래 글, base64, percent-encoding)은 데이터 폴더의 모든 파일, 설정 파일, 제품의 로그와 표준 출력·오류, 모든 API 응답, 동기화 결과와 작업, `site-check`의 출력에 남지 않는다. 수집기가 값을 오류의 문구에 일부러 실어도 같다. 백엔드를 띄워 값이 든 자료를 지나가게 한 뒤 훑는 시험이 이것을 붙잡고, 계약 묶음은 수집기가 값을 레코드, 건강 답, 오류, 로그에 싣는 것을 코드 넷으로, 거부를 오류로 알리지 않는 것을 코드 하나로 잡는다.
10. **인스턴스가 등록에서 빠져도 값을 지우지 않는다.** 자동으로 지우면 공용 진입점이나 수집기를 뺀 빌드로 같은 데이터 폴더를 한 번 띄우는 것만으로 모든 값이 사라진다. 남은 값은 어느 수집기에도 건네지지 않고, 같은 종류와 ID의 인스턴스가 다시 등록될 때만 다시 쓰인다.

## 기각한 대안

| 대안 | 기각 이유 |
|---|---|
| **값을 `config`에 합쳐 넘김** | `config`는 모양을 모르는 값이라 합칠 자리를 정할 수 없고, 제품이 기본 주기를 정할 때 읽는 값이라 값이 다른 코드로 흘러간다. "설정에 비밀 값을 넣지 않는다"는 규칙과도 어긋난다 |
| **만드는 함수의 인자로 넘김** | 쓸 수 있는 방법이다. 계약 묶음과 `site-check`이 모두 `initialize`를 기준으로 수집기를 판정하고, 이슈의 과제가 "`initialize`에 넘기는 규격"이며, 만드는 함수는 I05가 등록 계약으로 막 정한 타입이라서 고르지 않았다 |
| **값을 통째로 넘김(칸 → 값의 표)** | 관리 모듈이 값을 변수로 쥐게 되고 수집기가 나중에 다시 읽을 길이 없다. 접근자는 제품이 값을 들지 않게 하고 끊을 수 있다 |
| **수집기가 OS 보관함을 직접 부름** | 네이티브 모듈이 필요하다. 값을 넣는 화면이 없어 포크가 화면을 고쳐야 하고, 제품이 "없음"과 "거부"를 구별할 수 없다 |
| **만료를 저장소의 메타데이터로 판정(사용자가 만료일을 함께 입력)** | 저장소는 만료를 모르고 사용자가 넣은 날짜는 원 시스템의 사실과 어긋날 수 있다. 철회는 날짜로 알 수 없다. 원 시스템의 답이 유일한 사실이다 |
| **없어진 인스턴스의 값을 시작할 때 자동 삭제** | 수집기를 뺀 빌드로 한 번 띄우면 모든 값이 사라지고 값은 다시 발급받기 어려울 수 있다 |
| **값 입력을 포크 전용 수단으로(포크의 화면이나 명령줄 도구)** | 포크가 `site/` 밖의 화면을 고쳐야 하고, 명령줄 도구는 셸의 저장소(Electron의 암호화)에 닿을 수 없다 |
| **규격 버전을 3으로 올림** | 깨지는 변경이 아니다. 올리면 모든 수집기가 `unsupported-sdk-version`이 되어 옮겨 갈 일이 생긴다 |
| **셸이 저장 사실을 백엔드에 직접 알림** | 부모 채널의 메시지 종류가 하나 늘고 셸이 수집기 인스턴스를 알아야 한다. 화면의 알림이 빠져도 잘못된 값이 쓰이지는 않고 늦게 반영될 뿐이다 |
| **거부된 인스턴스도 한 시간마다 재점검** | 틀린 값으로 원 시스템을 계속 두드린다. 계정 잠금으로 이어질 수 있다. 일시적인 인증 서버 장애는 수집기가 `ConnectorError`(재시도 가능)로 알려야 한다 |
| **저장 이름에 `config`(주소)를 묶음** | 제품이 어느 필드가 주소인지 모르고, `config` 전체를 해시하면 주기 같은 무관한 값을 고칠 때마다 값을 다시 넣어야 한다. 저장 이름의 규칙은 되돌리기 어려워 S28 ⑤에서 포크의 규칙만으로 부족하다고 알려 오면 다시 본다 |
| **변경 알림의 다시 만들기를 재점검과 따로 돌림(자리가 둘)** | 한 인스턴스의 끝나지 않은 객체가 셋이 되어 I05가 정한 한도를 넓히고, 같은 인스턴스에 두 새 객체의 결과가 다투게 된다 |
| **읽히지 않는 값을 `credential-rejected`나 `credential-store-unavailable`에 묶음** | 앞의 것은 한 시간 재점검을 꺼서 OS의 키가 돌아와도 풀리지 않고, 뒤의 것은 사용자가 할 일(지우고 다시 넣는다)을 가린다 |

## 결과

- 포크가 하는 일은 필요한 칸의 이름을 등록의 인스턴스에 선언하고 수집기가 접근자로 읽게 하는 것이다. 값은 사용자가 공용 제품의 출처 화면에서 넣으므로 포크는 `site/` 밖의 화면을 고치지 않는다. 순서는 [connector-sdk.md 8장](../connector-sdk.md), 체크리스트는 [site-setup.md](../site-setup.md)의 S28·S29다.
- 제품은 값을 들고 있지 않다. 수집기가 값을 어디에 쓰는지는 제품이 알 수 없다. 포크의 수집기는 백엔드와 같은 프로세스에서 같은 권한으로 도는 믿는 코드이므로 칸 단위의 제한은 실수를 잡는 장치이지 격리가 아니다.
- 이 화면에서 넣는 자격 증명은 한 줄, 8192자 이하다. 여러 줄 값(PEM, JSON 키)은 받지 않는다. 끌어 놓기와 설정 화면의 틈은 #162에서 닫혔다. 남은 한계는 코드가 넣은 값의 줄바꿈을 화면이 알 수 없다는 것 하나다.
- 남는 위험(자세한 표는 I06 spec의 I06-R19와 connector-sdk.md 8장):
  - 수집기가 값을 레코드, 자기 로그, 파일에 쓰는 것은 제품이 막지 못한다. 계약 묶음의 코드 넷과 S29가 맡고, 계약 묶음은 둘로 나눠 쓴 글, 16진수, `Basic` base64, 패딩이 어긋난 base64, 처리되지 않은 약속 거부, 한 바퀴보다 늦게 도는 타이머가 쓴 글을 재지 않는다.
  - 주소만 바꾸고 인스턴스 ID를 그대로 둔 빌드는 옛 값을 새 주소로 건넨다. 포크의 규칙과 S28 ⑤가 맡는다.
  - 수집기가 거부를 `ConnectorCredentialError`로 알리지 않으면 제품은 그것이 거부인지 알 수 없고 한 시간마다 같은 값으로 다시 시도한다. 계약 묶음의 `credential-rejection-unsignalled`와 S29가 맡는다.
  - 초기화가 60초 가까이 걸리는 수집기는 값을 바꿀 때마다 길어야 한 시간 `unavailable`이 된다.
  - 알림을 쉬지 않고 보내는 호출자는 거부된 값이 한 시간에 120번쯤까지 시도되게 할 수 있다. 알림은 세션 토큰을 가진 화면만 보낼 수 있다.
  - 화면(렌더러)이 깨지면 수집기 자격 증명을 바꿔 넣거나 지울 수 있다. 읽지는 못한다.
- 값을 되쓰는 길이 없다. 원 시스템이 새 토큰을 내어 주며 옛 토큰을 버리는 방식이면 사용자가 값을 다시 넣어야 한다.
- 이 결정이 선 근거는 암호화 대역과 메모리 비밀 값 저장소를 쓴 시험, 지어낸 원 시스템, 그리고 포크 모양으로 꾸민 버리는 작업 트리에서 공용 예시 수집기로 칸의 선언과 계약 묶음을 한 번 돌려 본 예행(macOS)이다. **Windows 설치본, 실제 OS 보호(DPAPI)의 동작, 실제 수집기와 그 의존성, 실제 원 시스템의 거부·만료·잠금 정책은 확인하지 못했다.**

## 되돌리거나 다시 볼 조건

- S29에서 원 시스템이 회전하는 토큰을 쓴다고 알려 오면 접근자에 `write`를 더하는 것을 다시 본다. 수집기가 준 값을 저장소에 쓰는 것은 방향이 반대인 새 통로라 크기 제한, 덮어쓰기 실패, 두 객체가 동시에 쓰는 경우를 함께 정해야 한다.
- S28 ⑤에서 포크의 규칙만으로 옛 값이 새 주소로 건네지는 일을 막지 못한다고 알려 오면 인스턴스 정의에 "묶을 글"의 선택 필드를 더한다. 저장 이름의 규칙을 옮기는 단계가 필요하다.
- S28·S29에서 잠금 정책이 엄한 원 시스템이 확인되면 거부되었다는 사실을 다시 시작 뒤에도 기억하는 것을 다시 본다.
- S28에서 `credential-unreadable`이 값을 다시 넣지 않고도 풀리는 일이 흔하면 늦은 답과 읽을 수 없음을 구별한다(저장소의 읽기 답에 종류 하나를 더하는 V01의 계약 변경이 필요하다).
- 원 시스템이 여러 줄 값(PEM)이나 8192자를 넘는 값을 요구하면 입력 화면과 저장소의 값 한도를 함께 다시 본다.
- 배포처가 값의 폐기를 요구하면 쓰이지 않는 자격 증명을 정리하는 화면을 다시 본다. 셸이 이름을 세어 주는 함수가 하나 더 필요하다.
