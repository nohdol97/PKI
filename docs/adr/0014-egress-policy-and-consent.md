# ADR 0014: 외부 전송 정책과 동의

- 날짜: 2026-11-21 / 상태: **확정**(정책의 모양. 등급과 규칙의 값은 배포처가 정한다)
- 관련: 원 설계 17절, 이슈 #1 설계 분석 5번, 이슈 #15 R06-C3, [ARCHITECTURE 3.1절·5.1절·5.2절·8절](../ARCHITECTURE.md), [ADR 0005](0005-llm-providers.md)

## 맥락

원 설계 17절: "Claude Code와 Codex가 로컬에서 실행되더라도 실제 추론 요청은 외부 서버로 전송될 수 있다", "승인되지 않은 업무 데이터는 외부 Provider로 전송하지 않는다". 이슈 #1은 원문뿐 아니라 요약·embedding 입력·그래프 경로·관련 문맥 같은 파생 데이터에도 원본의 접근 범위와 전송 정책이 따라가야 한다고 정했다.

## 결정

**데이터 등급과 나가는 글**

- 모든 원본은 접근 범위(access_scope)를 갖고, 여기서 **데이터 등급**이 정해진다. 여러 원본이 섞인 입력의 등급은 그중 가장 엄격한 값이다. 요약, 추출 결과, 관련 문맥도 자기가 나온 원본의 등급을 물려받는다. 연결 후보로 보여 주는 기존 항목의 이름은 그 항목의 근거가 된 원본의 등급을 물려받는다. 그 원본들은 Broker가 **파생물 등록부의 계보**(`lineage`)로 찾는다(I04-R16): 부르는 코드는 파생물의 ID만 넘기고, 각 원본의 등급을 계산해 가장 엄격한 것을 쓴다. 계보가 비어 있으면 합성으로 보지 않고 일반 등급이며, 등록부가 모르는 종류의 ID를 넘기면 요청을 거부한다.
- **access_scope 사이의 비교**(어느 쪽이 더 엄격한가, 한 항목·한 Insight로 묶어도 되는가, 용도별 허용)는 `ScopePolicy` 하나가 정한다(ARCHITECTURE 5.6절). 파생물의 범위는 계보의 원본들에서 계산하며 모르는 범위(`null`)는 가장 엄격하다. 공용 기본 구현은 아무것도 거부하지 않고, 배포처 구현(`scopePolicy: "site"`)은 공용 저장소에서 `미구현, 배포처 후속`으로 시작을 멈춘다. 정책이 오류를 내면 거부로 닫는다. 가져오기로 들어온 범위(사용자가 적은 값)가 수집기 인스턴스의 범위보다 느슨해질 수 없다는 규칙은 I01-R15가 정하며 이 비교를 쓴다.
- 등급은 **Broker가 정본에서 계산한다.** 요청, Connector, 가져온 레코드가 적어 보낸 등급을 쓰지 않는다.
- **Broker는 등급을 계산한 바로 그 원본의 글을 정본에서 직접 꺼내 보낸다.** 부르는 쪽이 건넨 글은 Provider에 가지 않는다. 지시문은 코드의 상수다. Provider에 보내는 원본의 필드는 제목과 본문뿐이다.
- "합성" 등급은 원본의 제목과 본문을 묶은 해시가 빌드할 때 만든 합성 목록에 있을 때만 붙는다.

**정책 버전**

- 정책 버전은 사람이 매기는 번호가 아니라 **지금 적용되는 규칙 전체(배포처 규칙, 등급 목록)에서 계산한 값**이다. 규칙을 하나라도 고치면 값이 달라진다. 그래서 규칙을 바꾸고도 예전 동의가 살아 있는 일이 생기지 않는다.

**동의**

- 동의는 **Provider, 목적지, 정책 버전** 세 가지에 묶인다. 목적지는 HTTP Provider의 경우 엔드포인트의 호스트이고, CLI Provider의 경우 "그 CLI가 정하는 벤더 서비스"다. 셋 중 하나라도 바뀌면(엔드포인트 주소를 고쳤다, 배포처 규칙이 바뀌었다) 그 동의는 무효이고 다시 받아야 한다.
- 동의 화면은 어떤 등급의 데이터가 어디로 나가는지 보여 주고, 사용자는 **허용할 등급을 고른다.** 아무것도 고르지 않은 상태가 기본이다.
- CLI Provider도 "외부 전송"이라고 표시하고 "로컬 추론"이라고 부르지 않는다.

**규칙과 판정**

- 전송 규칙은 `(Provider, 작업 종류, 데이터 등급) → 허용 또는 거부`의 목록이다. 규칙은 두 곳에서 온다: 배포처가 설정으로 둔 규칙, 그리고 사용자의 동의에서 생긴 허용 규칙(그 Provider, 사용자가 고른 등급, 모든 작업 종류).
- **거부가 우선**하고, 맞는 규칙이 없으면 거부다. 배포처의 거부 규칙은 사용자의 동의로 뒤집을 수 없다.
- 공용 저장소의 기본은 **외부 전송 전부 거부**다.
- 판정은 **호출 직전마다** Broker가 두 단계로 한다: ① 그 Provider·목적지·정책 버전에 유효한 동의가 있는가 ② 규칙이 이 작업 종류와 등급을 허용하는가. 동의를 철회하거나 정책이 바뀌면 대기 중이던 작업도 다음 판정에서 막힌다.
- 거부되면 호출하지 않고 작업을 보류로 둔다. **다른 Provider로 몰래 넘어가지 않는다.**

**전송 경로**

- HTTP Provider의 주소는 `https`여야 한다. `http`는 loopback 주소에 한해 개발 빌드와 테스트 빌드에서만 받는다.
- 호출 이력에는 Provider, 목적지, 작업 종류, 등급, 정책 버전, 결과, 걸린 시간만 남기고 본문은 남기지 않는다.

**Embedding**

- Embedding 구현은 자기가 `'local'`인지 `'external'`인지 밝힌다([ADR 0006](0006-embedding.md)). **외부 서비스를 부르는 구현의 입력은 이 정책의 대상이다.** LLM 호출과 같은 동의와 규칙 판정을 지난다. 공용 저장소의 구현은 로컬 계산이라 판정 대상이 아니다.
- 모델 파일을 내려받는 일은 업무 데이터가 나가는 것은 아니지만 네트워크 접근이므로 사용자 승인을 거친다.

## 기각한 대안

| 대안 | 기각 이유 |
|---|---|
| 앱 전체에 대한 한 번의 동의 | Provider마다 데이터가 가는 곳이 다르다. 원 설계가 요구한 "전송 범위 제어"가 되지 않는다 |
| Provider 이름에만 묶인 동의 | 동의한 뒤 엔드포인트 주소를 바꾸면 다른 곳으로 데이터가 간다 |
| 정책 버전을 사람이 올리는 번호로 | 규칙을 고치고 번호를 올리지 않으면 예전 동의가 그대로 통한다 |
| 원문에만 정책 적용 | 요약과 관련 문맥으로 같은 내용이 나간다 |
| Embedding을 정책에서 통째로 제외 | 포크가 외부 embedding 서비스를 넣으면 원문이 정책 없이 나간다. 이슈 #1이 embedding 입력을 명시했다 |
| 거부 시 허용된 다른 Provider로 자동 전환 | 사용자가 모르는 곳으로 데이터가 간다. 프로젝트 규칙이 조용한 대체를 금지한다 |

## 결과

- 등급의 종류와 각 등급에 허용할 Provider는 배포처가 정한다([site-setup.md](../site-setup.md) S08). 공용 저장소는 규칙의 형태, "합성"과 일반 등급 하나, 기본 거부만 갖는다.
- 배포처가 규칙을 고치면 모든 사용자의 동의가 무효가 되어 다시 받아야 한다.
- 여러 원본을 종합하는 작업은 가장 엄격한 원본 하나 때문에 통째로 막힐 수 있다. 막힌 이유를 화면에 보인다.
- 질의응답과 알림 직전의 재검사는 그 기능이 생기는 Phase(X01, P02)에서 같은 Broker 판정을 쓴다.
