# ADR 0027: 대화형 로그인 세션은 셸의 로그인 창이 얻어 같은 저장소 칸에 두고, 회전값은 수집기가 세션 칸에만 되쓴다

- 날짜: 2026-11-26 / 상태: **잠정 — 배포처 검증 대기**(초안. 실제 IdP, Windows 설치본의 로그인 창과 쿠키 읽기, 실제 세션의 회전·만료·잠금 정책은 S49에서 확인한다)
- 관련: [I06S spec](../specs/2026-11-26-I06S-session-credentials.md)(I06S-R1~R15, D1~D10), 이슈 #362, [ADR 0019](0019-connector-credentials.md)(이 ADR이 잇는 결정, 「되돌리거나 다시 볼 조건」 1), [ADR 0010](0010-encryption-at-rest.md), [ADR 0018](0018-fork-registration-at-build-time.md), [connector-sdk.md 8장](../connector-sdk.md), [site-setup.md](../site-setup.md) S29·S49

## 맥락

ADR 0019는 자격 증명을 "사용자가 화면에 넣는 한 줄 값, 수집기는 읽기만"으로 정했다. 원 시스템의 인증이 대화형 웹 로그인(IdP에 로그인해 받는 세션 쿠키)이면 셋 다 맞지 않는다. 사용자는 세션 값을 볼 수 없어 넣을 수 없고, 수집기는 얻은 값과 회전한 새 토큰을 저장할 수 없으며, 만료의 할 일은 "값을 고친다"가 아니라 "다시 로그인한다"다. ADR 0019는 회전하는 토큰이 알려지면 접근자에 `write`를 더하는 것을 다시 보기로 했다(재검토 조건 1). 포크의 코드는 백엔드에만 실리므로(ADR 0018) 창을 여는 기계는 포크가 만들 수 없다.

## 결정

1. **로그인 창은 제품 화면의 단추가 열고, 창은 셸이 띄운다.** 화면은 preload `openLogin(connectorId)`에 인스턴스 ID만 건넨다. 셸은 백엔드에 그 인스턴스의 로그인 설명을 묻는다(`login-request` → `login`). 설명(`startUrl`, `doneUrlPrefix`, 쿠키 이름, 세션 칸)은 포크 등록의 인스턴스 정의 `login`에 있다. 수집기는 창을 요청하지 않는다.
2. **창은 어댑터 `LoginHost` 뒤에 둔다.** 공용은 Electron 구현(preload 없음, `sandbox`, 로그인마다 새 비영속 partition, `http(s)` 밖 이동·다운로드·권한·새 창 거부)과 시험용 가짜 구현을 싣는다. 사이트마다 다른 것은 설명뿐이다.
3. **세션 값은 칸 하나의 한 줄 JSON** `{"cookies":{…}}`이고, 셸 main 프로세스가 곧장 ADR 0010의 같은 저장소에 쓴다. 화면과 백엔드 API를 지나지 않는다. 화면에는 값이 없는 결과 코드만 간다. 쿠키 밖에 세션을 두는 원 시스템은 미구현, 배포처 후속이다.
4. **회전값은 수집기가 `context.credentials.write(slot, value)`로 되쓴다.** 쓸 수 있는 칸은 `login.slot` 하나이고, 끊긴 접근자·다른 칸·한 줄이 아니거나 8192자를 넘는 값·저장 불가는 `ConnectorCredentialError`로 거부한다. 백엔드는 셸에 `secret-request` 모드 `write`로 쓰고, 셸은 수집기 자격 증명 이름만 받는다. 쓰기는 다시 만들기를 일으키지 않는다.
5. **새 사유 `login-required`.** 세션 칸이 있는 인스턴스의 빈 세션과 원 시스템의 거부는 `credential-missing`·`credential-rejected` 대신 이것이고 사용자 할 일은 "로그인 창을 다시 연다"다. 재시도 상한은 `credential-rejected`와 같다(한 시간 재점검 건너뜀, 알림 30초 간격, 앱을 켤 때 한 번). 제품은 로그인 창을 스스로 열지 않는다.
6. **규격 버전은 2 그대로.** `write`와 `login`은 선택 항목이다. `write`를 쓰는 수집기는 그것이 없으면 `ConnectorCredentialError`로 끝낸다.
7. **계약 묶음에 코드 둘.** 쓴 값이 돌려준 것·던진 것·건강 답·출력에 있으면 `rotated-credential-leaked`, 쓴 값으로 초기화한 새 객체가 거부되면 `session-not-persisted`. 예시는 지어낸 원 시스템 `rotating-session-notes`다.
8. **누출 없음(ADR 0019 결정 9)은 쓰기 길에도 같다.** 백엔드를 띄워 쓴 표식 값이 지나간 뒤 같은 곳들을 훑는 시험이 붙잡는다.

## 기각한 대안

| 대안 | 기각 이유 |
|---|---|
| **수집기가 로그인 창을 요청(`context.requestLogin()`)** | 세션이 없으면 객체를 만들지 않으므로 요청할 객체가 없다. 백엔드 → 셸 → 화면의 알림 통로가 새로 필요하고, 로그인은 어차피 사용자가 해야 한다 |
| **화면이 설명(주소)을 셸에 건넴** | 깨진 렌더러가 아무 주소로 창을 열고 그 쿠키를 아무 칸에 쓰게 된다. 설명은 백엔드의 등록에만 있으면 된다 |
| **포크가 셸에 로그인 코드를 더함** | ADR 0012·0018: 포크는 `site/` 밖을 고치지 않고, 포크 코드는 셸에 실리지 않는다 |
| **세션을 칸 여럿(쿠키마다 칸 하나)으로** | 칸 상한 8과 칸 이름 규칙에 쿠키 이름이 묶이고, 로그인 하나의 결과가 여러 번의 쓰기로 쪼개져 반만 저장될 수 있다 |
| **값을 화면 입력란에 붙여 넣게 함(개발자 도구에서 쿠키 복사)** | 사용자에게 httpOnly 쿠키를 꺼내게 하는 일이고 회전되면 곧 무효다. ADR 0019의 "포크 전용 수단" 기각과 같은 이유로 공용 규격 안의 자리가 필요하다 |
| **세션을 백엔드 메모리에만 둠** | 앱을 켤 때마다 다시 로그인해야 한다. #362가 짚은 문제 그대로다 |
| **수집기가 모든 칸에 쓸 수 있음** | 고정 값(API 키)을 수집기 실수로 덮는다. 칸 제한은 격리가 아니라 실수를 잡는 장치다(ADR 0019 결과) |
| **`credential-rejected`를 그대로 쓰고 안내 문장만 바꿈** | 같은 사유에 두 할 일이 붙어 화면이 단추를 고를 수 없다 |
| **`ConnectorLoginRequiredError`를 새로 둠** | 오류 종류와 알리지 않음 위반 코드가 하나씩 는다. 세션 칸의 유무로 가를 수 있다. 고정 칸이 틀려도 "로그인"으로 보이는 한계는 S49에서 다시 본다 |
| **만료를 미리 알고 자동으로 다시 로그인·갱신** | 만료는 원 시스템의 답이 유일한 사실이다(ADR 0019 기각 표). 자동 재로그인은 잠금 방지(결정 6)를 깬다 |
| **규격 버전을 3으로 올림** | 깨지는 변경이 아니다(ADR 0019와 같은 이유) |

## 결과

- 포크가 하는 일은 인스턴스 정의에 세션 칸과 `login` 설명을 적고, 수집기가 세션 칸을 읽고 회전값을 `write`로 되쓰게 하는 것이다. 화면과 셸은 고치지 않는다.
- 값이 지나는 길이 셋이 된다: "화면 입력 → 셸의 저장소", "셸 → 백엔드 → 수집기", 그리고 "수집기 → 백엔드 → 셸의 저장소(세션 칸만)". 로그인 창이 얻은 값은 셸 안에서 저장소로 간다.
- 남는 위험: 새 로그인 직후 알림 전의 밀리초 틈에 옛 객체가 회전값으로 새 세션을 덮을 수 있다. 세션 칸과 고정 칸을 함께 둔 인스턴스는 고정 칸이 틀려도 `login-required`로 보인다. 창 안 IdP 페이지의 행동은 포크의 주소 검토가 맡는다.
- 근거는 가짜 `LoginHost`, 메모리 저장소, 지어낸 원 시스템의 시험이다. **Electron 로그인 창의 실제 동작, Windows 설치본, 실제 IdP와 세션 정책은 확인하지 못했다(S49).**

## 되돌리거나 다시 볼 조건

- S49에서 쿠키 밖(localStorage, 응답 본문)에 세션을 두거나 팝업 로그인을 쓰는 원 시스템이 알려지면 설명에 잡는 종류를 더한다.
- 세션 값이 8192자를 넘는 원 시스템이 알려지면 저장소의 값 한도를 다시 본다.
- 고정 칸 거부가 `login-required`로 보이는 것이 실제로 문제가 되면 로그인 필요 전용 오류를 더한다.
- 수집기가 만료 직전에 사용자를 불러야 하는 원 시스템이면 수집기 요청형 로그인(기각한 첫 대안)을 다시 본다.
