# ADR 0017: 로컬 파일은 사본 없이 승인한 자리에서 읽고, 정규화는 백엔드 밖에서 돈다

- 날짜: 2026-11-23 / 상태: **잠정 — 배포처 검증 대기**(Windows에서의 경로 경계와 정규화 호스트는 S23 W1~W12에서 확인한다)
- 관련: [I02-B spec](../specs/2026-11-22-I02-local-file-import.md)(I02B-R2~R10, R22~R25, R32~R34, R46~R48), 이슈 #19·#116, [ADR 0002](0002-authority-in-product-records.md), [ADR 0013](0013-failure-recovery.md), [ADR 0015](0015-document-parsing-stack.md), [ARCHITECTURE.md](../ARCHITECTURE.md)의 4절·9절, [site-setup.md](../site-setup.md)의 S23~S25

## 맥락

사용자 자료는 파일과 폴더에도 있다. 이 자료를 제품에 넣으려면 네 가지를 정해야 했다. 읽은 파일의 사본을 제품이 갖는가, "어느 파일을 어떤 정체로 알렸는가"를 적은 색인을 어디에 두는가, 믿을 수 없는 파일을 푸는 파서를 어디서 돌리는가, 사용자가 승인하지 않은 곳을 읽지 못하게 하는 경계가 무엇을 막는가. 앞의 둘은 [ADR 0002](0002-authority-in-product-records.md)(정본은 제품의 기록)와 [ADR 0013](0013-failure-recovery.md)(정본 먼저, 투영은 재구축)의 말을 그대로 따르면 되는지, 뒤의 둘은 새로 정해야 하는지의 문제였다.

## 결정

1. **사본을 두지 않는다.** 제품은 승인한 폴더나 파일을 그 자리에서 읽기만 한다. 원본 파일의 사본을 데이터 디렉터리에 두지 않는다. 사본이 있으면 사용자가 원래 파일을 지워도 제품에 남아, "출처에서 지우면 제품에서도 지워진다"는 약속이 깨진다. 그래서 파일 하나를 가져오는 것도 한 번 복사하고 잊는 것이 아니라 파일 하나짜리 승인 위치다. 고치거나 지우면 폴더 안의 파일과 똑같이 따라간다(I02B-R3, R32).
2. **색인은 정본 안의 "원본 정체" 기록이며 파생물 종류가 아니다.** 어느 경로의 파일이 어느 무작위 파일 ID로 어떤 크기·시각·내용 해시·revision으로 알려졌는지는 정본 SQLite의 표(`local_file_entries`)에 둔다. 색인은 원본이 생기기 전에 적히고 삭제 뒤에도 행이 남으므로 지우고 다시 만드는 투영이 아니다. 그래서 파생물 등록부의 종류가 아니라 `원본` 분류이고, tombstone이 생기면 트리거가 그 행의 경로와 내용을 비운다(I02B-R33, I04-R3).
3. **정규화는 백엔드 밖의 호스트 프로세스에서 돈다.** 파서는 시간과 메모리를 묶지 않으므로 작은 파일 하나가 백엔드를 멈출 수 있다. 정규화는 호스트 프로세스에서 돌고(호스트 안에서는 작업자 하나가 힙 한도를 받는다), 호스트는 작업 사이에 다시 쓰이고 죽으면 다시 뜬다. 시간 초과와 메모리 초과는 그 파일만 건너뛴 사유가 된다. 힙 한도가 프로세스 전체를 중단시킬 수 있다는 측정 때문에 같은 프로세스의 작업자만으로는 부족했다(I02B-R22~R25).
4. **경로 경계는 닫는 쪽이고, 보장의 범위는 I02B-R46~R48이다.** 판정할 수 없으면 "안쪽이다, 같은 것이 아니다"로 보고 건너뛰거나 승인을 거부하며 사유를 보인다. 실제 경로는 OS에게 묻고(`fs.realpath.native`), 파일은 이름으로 본 것과 연 핸들이 같은 정체일 때만 읽는다. 플랫폼의 API로 지킬 수 없는 보장은 지킨다고 적지 않는다. JSONL 파일 위치(#116)도 같은 경계로 연다(I02B-R41).

## 기각한 대안

| 대안 | 기각한 까닭 |
|---|---|
| 가져올 때 사본을 데이터 디렉터리에 둔다 | 원본이 지워져도 사본이 남아 삭제가 닿지 않는다. 사용자가 지운 내용이 제품에 남는다 |
| 색인을 파생물 종류로 등록한다 | 파생물은 원본에서 다시 만들 수 있어야 하는데 색인은 원본보다 먼저 적히고, 삭제 뒤에도 행이 있어야 같은 파일이 새 원본이 되는 것을 막는다 |
| 정규화를 백엔드의 작업자 스레드에서만 돌린다 | 힙 한도로 작업자가 죽을 때 프로세스 전체가 중단된 사례를 쟀다(I02-B spec의 가정 G19) |
| 경로를 문자열 앞부분 비교로 판정한다 | `/data/a`와 `/data/ab`를 가르지 못하고 대소문자·짧은 이름·junction을 놓친다 |

## 결과와 남는 위험

- 파일이 이동하거나 이름이 바뀌면 내용 해시로 같은 원본을 잇는다. 옮기면서 고친 파일은 삭제와 새 원본이 된다(안전한 쪽).
- 외장 디스크를 뽑아도 읽지 못하는 위치의 삭제는 알리지 않는다. 같은 자리에 다른 디스크가 꽂히면 저절로 이어지지 않고 사용자가 "다시 연결"을 한다.
- Windows에서의 파일 정체(`dev`, `ino`), junction, 짧은 이름, 설치본의 호스트는 이 저장소에서 확인하지 못했다. 공용 저장소의 문서는 그것을 확인된 것으로 적지 않으며(I02B-R45) 배포처가 S23의 실행기로 확인한다.
- 네트워크 공유와 클라우드 동기화 폴더는 승인하지 않는다(사유 `network-location`). 허용 여부는 S25에서 배포처가 정한다.
