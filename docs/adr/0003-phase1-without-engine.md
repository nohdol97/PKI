# ADR 0003: Phase 1은 제3자 지식 엔진 없이, 어댑터와 null 구현으로

- 날짜: 2026-11-21 / 상태: **잠정 — 배포처 검증 대기**
- 관련: 원 설계 2절·19절, [ARCHITECTURE 3.2절·5.3절](../ARCHITECTURE.md), [OSS_EVALUATION 5.1절](../OSS_EVALUATION.md), 가정 A10

## 맥락

엔진 후보 3개(LightRAG, cognee, sage-wiki)는 모두 "보류"이고 실행 확인은 배포처에서만 할 수 있다(OSS_EVALUATION 5.1절, 7절). 한편 원 설계 19절은 Phase 1에서 "전체 기반 시스템을 먼저 구축하느라 핵심 제품 검증이 지연되지 않도록 한다"고 한다. 엔진 선정을 기다리면 Phase 1이 멈춘다.

## 결정

- Phase 1의 처리 경로에는 제3자 지식 엔진이 없다.
- 추출은 LLM Provider의 구조화 출력을 받아 제품의 정본 기록에 쓴다. 날짜, 상태, 의존 관계, 중복 검사는 결정론 코드가 한다(원 설계 10절).
- `KnowledgeEngine` 어댑터 규격과 계약 테스트, 아무것도 하지 않는 null 구현, 테스트용 메모리 구현을 V01에서 만든다. 엔진 후보는 배포처 검증 뒤 이 자리에 꽂는다.

**범위 제한(이 선을 넘으면 멈추고 ADR을 다시 쓴다).**

1. 원본 하나당 구조화 출력 호출은 1회, 형식 오류 재시도는 1회까지다.
2. 문서를 chunk로 나누지 않는다. 한 번에 넣을 수 없는 크기의 원본은 "보류"로 남긴다.
3. 기존 항목과의 연결 후보는 이름·식별자의 정확 일치로만 찾는다. 유사도 점수나 군집을 코드로 계산하지 않는다.
4. 관계 조회는 정해진 질의의 한두 단계 조인까지다. 일반 그래프 탐색을 만들지 않는다.
5. Wiki 합성, 기억 통합, 벡터 색인 알고리즘을 만들지 않는다.

## 위험

이 방식은 **얇은 엔진을 직접 만드는 쪽으로 번질 수 있다.** 추출 품질이 모자랄 때 보충 추출을 한 번 더 넣고, 개체가 안 합쳐질 때 유사도 비교를 넣는 식으로 조금씩 넓어진다. 그러면 원 설계 2절("독자적으로 다시 구현하지 않는 것을 원칙")과 이슈 #15의 R06-C4("자체 엔진 재개발을 기본 대안으로 삼지 않는다")를 어긴다.

방지 장치는 둘이다. 위의 범위 제한 다섯 줄을 V02 spec의 요구사항으로 옮겨 리뷰가 대조하게 하고, R07에서 이 ADR을 실행 결과와 함께 다시 검토한다.

## 기각한 대안

| 대안 | 기각 이유 |
|---|---|
| 엔진 선정까지 Phase 1을 미룸 | 사용자가 실행 검증을 배포처로 옮기면서 개발을 잠정 ADR로 시작하기로 정했다(이슈 #1 진행 로그 2026-11-21) |
| 실행해 보지 않은 엔진을 지금 하나 골라 넣음 | Windows 실행, 라이선스 전체, 삭제 동작이 미검증이다. 틀리면 Phase 1 전체를 다시 한다 |
| 어댑터 없이 추출 코드를 파이프라인에 직접 엮음 | 엔진을 꽂을 때 상위 코드를 고쳐야 한다. V01-C7에 어긋난다 |

## 결과

- Phase 1의 추출 품질은 Provider 모델과 지시문에만 달려 있다. 품질 수치는 R05 기준이 고정된 뒤에 잰다.
- R03에서 통과한 엔진이 나오면 어댑터에 꽂고, 위 범위 제한에 묶여 있던 기능(보충 추출, 개체 해소, 관련 문맥 검색)을 엔진에 맡긴다.
- R03에서 통과한 엔진이 없으면 대안 조사로 돌아간다. 자체 엔진 개발로 가지 않는다(R06-C4).
