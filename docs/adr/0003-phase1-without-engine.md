# ADR 0003: Phase 1은 제3자 지식 엔진 없이, 어댑터와 null 구현으로

- 날짜: 2026-11-21 / 상태: **잠정 — 배포처 검증 대기**
- 관련: 원 설계 2절·7절·19절, [ARCHITECTURE 3.2절·5.3절](../ARCHITECTURE.md), [OSS_EVALUATION 5.1절](../OSS_EVALUATION.md), [ADR 0002](0002-authority-in-product-records.md), 가정 A10

## 맥락

엔진 후보 3개(LightRAG, cognee, sage-wiki)는 모두 "보류"이고 실행 확인은 배포처에서만 할 수 있다(OSS_EVALUATION 5.1절, 7절). 한편 원 설계 19절은 Phase 1에서 "전체 기반 시스템을 먼저 구축하느라 핵심 제품 검증이 지연되지 않도록 한다"고 한다. 엔진 선정을 기다리면 Phase 1이 멈춘다.

## 결정

- Phase 1의 처리 경로에는 제3자 지식 엔진이 없다.
- 추출은 LLM Provider의 구조화 출력을 받아 제품의 정본 기록에 쓴다. 날짜, 상태, 의존 관계, 중복 검사는 결정론 코드가 한다(원 설계 10절).
- `KnowledgeEngine` 어댑터 규격과 계약 테스트, 아무것도 하지 않는 null 구현, 테스트용 메모리 구현을 V01에서 만든다.
- **파이프라인은 Phase 1부터 이 규격을 정해진 자리에서 부른다**(원본 저장 뒤, 추출 직전, 삭제·대체 뒤, 시작할 때. ARCHITECTURE 5.3절). null 구현이 묶여 있어 아무 일도 일어나지 않지만, 부르는 자리가 있어야 엔진을 꽂을 때 상위 코드를 고치지 않는다. V02가 이 호출과 그것을 확인하는 테스트를 만든다(V02-C5).

**범위 제한(이 선을 넘으면 멈추고 ADR을 다시 쓴다).** 각 줄은 테스트나 lint로 확인할 수 있는 형태다.

1. 원본 version 하나의 추출에서 Provider 호출은 1회, 응답이 스키마에 맞지 않을 때의 재시도는 1회까지다(테스트: 호출 횟수).
2. 문서를 chunk로 나누지 않는다. 한 번에 넣을 수 없는 크기의 원본은 "보류"로 남긴다.
3. 기존 항목과의 연결 후보는 그 항목의 이름·별칭이 원문에 **글자 그대로 들어 있는지**로만 찾는다. 별칭은 그 항목에 이미 기록된 이름과 사용자 교정에서만 온다. 비교 전의 가공은 유니코드 정규화, 대소문자 통일, 공백 정리뿐이다. 키워드 색인과 그 순위, 유사도 점수, 군집을 쓰지 않는다.
4. **같은 행인지는 값이 정확히 같을 때만 인정한다.** 두 사실은 항목 ID, 사실 종류, 정규화한 값이 모두 같을 때만, 두 관계는 주체 ID, 관계 유형, 대상 ID가 모두 같을 때만 같은 행이다. 값이 다르면 다른 행으로 둔다. 뜻이 비슷한 것을 합치거나 상충을 풀지 않는다(그것은 S02와 엔진의 일이다).
5. 대체와 삭제 전파는 **근거 개수를 세는 것**으로만 한다. 원본의 version은 바뀌지 않고 근거는 자기 version을 계속 가리킨다. 새 version이 오면 최신 version을 가리키는 근거가 없는 행을 superseded로 바꾼다(대체). 원본이 지워지면 그 원본의 모든 version을 가리키는 근거를 지우고, 근거가 하나도 남지 않은 행을 지운다(삭제). 내용을 비교해 무엇이 무엇을 대체했는지 추론하지 않는다.
6. 관계 조회는 규칙이 쓰는 정해진 질의의 **깊이 1 조인**까지다. 재귀 질의와 일반 그래프 탐색을 만들지 않는다.
7. Wiki 합성, 기억 통합, 벡터 색인 알고리즘을 만들지 않는다.

## 위험

이 방식은 **얇은 엔진을 직접 만드는 쪽으로 번질 수 있다.** 추출 품질이 모자랄 때 보충 추출을 한 번 더 넣고, 개체가 안 합쳐질 때 유사도 비교를 넣는 식으로 조금씩 넓어진다. 그러면 원 설계 2절("독자적으로 다시 구현하지 않는 것을 원칙")과 이슈 #15의 R06-C4("자체 엔진 재개발을 기본 대안으로 삼지 않는다")를 어긴다.

이미 선에 걸쳐 있는 것도 있다. 4번과 5번은 원 설계 7절이 Knowledge Graph의 필수 기능으로 든 "기존 사실의 변경 및 대체"와 "원본 삭제 시 파생 지식 갱신"의 가장 단순한 형태이고, 조사가 엔진을 평가한 바로 그 기능이다. 제품이 이것을 갖는 것이 옳은지는 [ADR 0002](0002-authority-in-product-records.md)의 사용자 확인 대상이었고, 위임받은 판단으로 유지하되 R07에서 다시 판단한다.

방지 장치는 둘이다. 위의 범위 제한을 V02 spec의 요구사항으로 옮겨 테스트와 리뷰가 대조하게 하고, R07에서 이 ADR을 실행 결과와 함께 다시 검토한다.

## 기각한 대안

| 대안 | 기각 이유 |
|---|---|
| 엔진 선정까지 Phase 1을 미룸 | 사용자가 실행 검증을 배포처로 옮기면서 개발을 잠정 ADR로 시작하기로 정했다(이슈 #1 진행 로그 2026-11-21) |
| 실행해 보지 않은 엔진을 지금 하나 골라 넣음 | Windows 실행, 라이선스 전체, 삭제 동작이 미검증이다. 틀리면 Phase 1 전체를 다시 한다 |
| 어댑터 없이 추출 코드를 파이프라인에 직접 엮음 | 엔진을 꽂을 때 상위 코드를 고쳐야 한다. V01-C7과 V02-C5에 어긋난다 |
| 규격만 만들고 부르는 자리는 엔진을 꽂을 때 만듦 | 위와 같은 문제다. 아무도 부르지 않는 규격은 구현을 바꿔 끼워도 달라지는 것이 없어, 교체가 된다는 시험이 공허하게 통과한다 |

## 결과

- Phase 1의 추출 품질은 Provider 모델과 지시문에만 달려 있다. 품질 수치는 R05 기준이 고정된 뒤에 잰다.
- R03에서 통과한 엔진이 나오면 어댑터에 꽂고, 위 범위 제한에 묶여 있던 기능(보충 추출, 개체 해소, 관련 문맥 검색)을 엔진에 맡긴다.
- R03에서 통과한 엔진이 없으면 대안 조사로 돌아간다. 자체 엔진 개발로 가지 않는다(R06-C4).
