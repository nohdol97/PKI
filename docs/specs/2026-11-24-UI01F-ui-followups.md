# 스펙: 화면 후속 묶음(UI01F) — 항목을 바꾼 뒤 남는 옛 상세, 다른 발견 밑에 뜨는 원본, 화면에 없는 항목 기준의 근거 읽기

- 날짜: 2026-11-24 / 상태: 확정(결정 D1~D6 포함)
- 관련: 이슈 #308(UI01 후속), #268·#283(탐색 후속), #197(I06F 후속). [UI01 spec](2026-11-24-UI01-ab-light-panes.md), [X02F spec](2026-11-24-X02F-explore-followups.md)(X02F-R4, X02F-R7, X02F-D5)
- 번호: 요구사항 `UI01F-R<n>`, 완료 기준 `UI01F-C<n>`, 결정 `UI01F-D<n>`, 작업 `UI01F-T<n>`. 고치는 곳은 `apps/web`뿐이다. 계약·백엔드·마이그레이션·새 경로는 없다.

## 배경

네 이슈에 남은 줄 가운데 `apps/web`에 있는 것을 코드와 한 줄씩 대조했다(기준: PR #307에 `origin/main` `f15aba81`을 합친 트리 `d3d3a4af`. 아래 줄 번호는 이 트리의 것이다). 정확성·보안·데이터 손실에 해당하는 결함은 **3건**이고, 셋 다 "화면이 지금 보고 있는 것과 다른 것의 내용을 보여 준다"는 같은 종류다. 나머지는 이미 고쳐졌거나, 안내 문구가 얼마나 오래 남는지의 문제이거나, 시험 보강·문구라서 이슈에 둔다("남김 표").

세 결함은 모두 코드를 따라가서 확인했고, 실행해서 관측한 것은 아니다.

### 결함 1 — 탐색에서 항목을 바꾸면 이전 항목의 상세 줄이 화면에 남는다 (#308 동작 1)

React는 같은 부모 밑의 자식을 `key`(이 자식이 누구인지 알려 주는 이름표)로 구분한다. 탐색의 상세 칸에서 항목 줄 상세(`RowDetail`)와 항목 정리(`EntityCuration`)는 형제인데 둘 다 `key={center.id}`를 쓴다(`apps/web/src/explore.tsx:317`, `:410`). 둘은 `DetailPane`의 `children` 배열 하나에 함께 들어간다(`apps/web/src/panes.tsx:104`).

실패하는 순서: 항목 5를 연 상태에서 항목 7을 연다.

1. React는 앞에서부터 자리를 맞추다가 `RowDetail`에서 이름표가 `5`에서 `7`로 바뀐 것을 보고 멈춘다.
2. 남은 옛 자식을 이름표로 찾는 표를 만든다. `RowDetail`(5)을 먼저 넣고 `EntityCuration`(5)이 **같은 이름표로 덮어쓴다**(`react-dom-client.development.js:6549-6555`).
3. 새 자식을 다 놓은 뒤 표에 남은 것만 지운다(`:7087-7090`). 옛 `RowDetail`은 표에 없으므로 지워지지 않는다.

결과: 항목 5의 "이력 보기" 줄(열어 둔 이력 포함)이 항목 7의 상세 칸에 그대로 남고, 항목을 바꿀 때마다 하나씩 쌓인다. React가 개발 빌드에서 내는 경고 "two children with the same key"(`:6968`)도 같은 원인이다. #283에 "출처 미추적"으로 적힌 E2E 로그의 경고(key `1`)가 이것일 가능성이 높다(미확인 — "미검증 범위").

### 결함 2 — 점검에서 느리게 온 원본이 다음 발견의 상세에 들어간다 (#308 동작 2)

`openEvidence`는 답이 오면 무조건 `setSource`를 부른다(`apps/web/src/lint.tsx:85-92`). 발견을 고르면 `setSource(undefined)`로 비우지만(`:129`), 이미 나간 읽기는 막지 않는다.

실패하는 순서: 발견 A에서 "근거 보기 1"을 누른다(응답이 느림) → 발견 B를 고른다(원본 칸이 비워짐) → A의 답이 도착한다 → B의 상세 밑 "원본 보기"에 A의 근거 원본이 보인다(`:225-232`). 같은 발견에서 근거 두 개를 잇달아 누르면 마지막에 누른 것이 아니라 마지막에 도착한 것이 보인다.

### 결함 3 — 탐색에서 B를 읽는 중에 A의 줄 근거를 열면 B 기준으로 읽는다 (#283 덧붙임)

항목을 열면 `current`가 **답이 오기 전에** 새 항목으로 바뀐다(`apps/web/src/explore.tsx:485`). 화면에는 아직 A가 보인다. 이때 A의 줄에서 "근거 보기"를 누르면 근거 읽기가 `current.id`, 곧 B를 쓴다(`:497`). 관계 줄의 근거는 가운데 항목의 추적에서 찾으므로(`:136-139`) B의 추적에 그 관계가 없으면 근거가 있는 줄에 "이 줄의 근거를 찾지 못했습니다"가 뜬다. 근거를 찾은 경우에도 그 답은 B를 연 **뒤에** 시작한 읽기라 버려지지 않고(`:486`, `:496`), B의 상세 밑에 A의 줄 근거가 그려진다. X02F-C4가 막은 것은 "B를 열기 전에 시작한 A의 근거 읽기"뿐이다.

## 목표

1. 탐색에서 항목을 바꾸면 이전 항목의 상세 줄이 남지 않는다.
2. 점검과 탐색의 근거·원본 칸에는 지금 화면에 보이는 발견·항목의 것만 그려진다.

## 비목표

- **안내 문구가 남는 시간**: 피드백 안내 덮어쓰기(#308 동작 4), 홈 첫 Insight 자동 열기의 실패 문구(#308 동작 3), 지식 검토·유형 정의의 거절 문구가 다음 요청에 지워지는 것(#283), API 키 저장 실패 문구가 호스트를 바꾼 뒤에 뜨는 것(#197 S3), 빠른 두 번째 "합치기 되돌리기"의 문구(#283). 모두 저장된 값은 맞고 문구만 어긋난다(D4).
- **같은 모양이 의심되는 다른 화면**(홈·알림의 Insight와 원본 열기, 위키의 근거 보기). 후보 줄에 없던 자리라 이 묶음에 넣지 않고 #308에 줄로 남긴다(D5).
- 접근성·모양·명암비·문구, Windows·배율·화면 낭독기 확인, 시험 보강만인 줄, #290의 새 기능, 백엔드·계약을 고쳐야 하는 줄.
- DOM 시험 환경 도입, 새 E2E(D6).

## 요구사항

- **UI01F-R1** 탐색 상세 칸의 형제 요소는 서로 다른 `key`를 가진다. 항목 줄 상세와 항목 정리는 항목이 바뀌면 각각 새로 만들어진다(지금처럼 항목별 상태를 비운다).
- **UI01F-R2** 점검의 원본 읽기는 **가장 나중에 낸 읽기**이고 **그 뒤로 다른 발견을 고르지 않았을 때만** 화면에 반영된다. 버려진 읽기는 원본도, 실패 문구도 남기지 않는다.
- **UI01F-R3** 탐색의 "근거 보기"는 누른 줄이 속한 화면의 항목이 지금 연 항목과 다르면 읽기를 내지 않는다.

## 인터페이스 / 설계 개요

웹 단위 시험에는 DOM이 없어, 규칙을 컴포넌트 밖의 함수에 둔다(X02F-D5와 같다).

- `explore.tsx`: 두 `key`에 서로 다른 접두어를 붙인다. `createExploreSession().evidence(row, label, forId)`가 `forId`(그 줄을 그린 화면의 `read.center.id`)를 받아 `current.id`와 다르면 아무것도 하지 않는다. 호출하는 자리는 `act`·`changed`가 이미 쓰는 방식과 같다(`:614-615`).
- `lint.tsx`: 질문 화면의 `sourceOpener`(`apps/web/src/ask.tsx:64-82`)와 같은 모양의 `evidenceOpener(api, show, fail)`를 내놓는다. `open(evidenceId)`는 읽기를 내고, `reset()`은 나가 있는 읽기를 버린다. 발견 줄을 누르는 자리(`:129`)가 `reset()`을 부른다. 기반은 `createLatest`(`apps/web/src/latest.ts:5`)다.

그림은 넣지 않는다(구성 요소 둘, 갈래 없는 짧은 순서).

## 잠정 결정

바꾸려면 적힌 자리 하나를 고치면 된다.

- **UI01F-D1 `key`를 없애지 않고 접두어로 나눈다.** 두 `key`는 항목이 바뀔 때 열어 둔 이력과 정리 입력을 비우는 구실을 한다. `Neighbourhood` 전체에 `key`를 주는 방법은 깊이·관계 종류 선택까지 새로 만들어져 바뀌는 범위가 넓다.
- **UI01F-D2 점검은 `ask.tsx`의 `sourceOpener`를 함께 쓰지 않고 같은 모양을 `lint.tsx`에 둔다.** 읽는 경로가 다르고(`evidenceSource` 대 `exploreSource`) 열 줄 남짓이다. 세 번째 쓰는 곳이 생기면 `latest.ts`로 올린다.
- **UI01F-D3 화면에 없는 항목의 줄에서 누른 "근거 보기"는 조용히 버린다.** 사용자는 이미 다른 항목을 열었고 그 화면이 곧 바뀐다. X02F-D6(버려진 요청에 알림 없음)과 같다. 읽기는 내되 답만 버리는 방법도 결과가 같지만 요청이 하나 더 나간다.
- **UI01F-D4 안내 문구의 수명은 결함으로 세지 않는다.** 기록·저장된 값이 맞고 화면에 틀린 내용이 뜨지 않는다. X02F가 같은 종류(#283의 거절 문구)를 남긴 것과 맞춘다. 결함으로 올리려면 문구를 대상별로 보관해야 하고(`feedback.tsx:37`, `App.tsx:871`) 화면마다 따로 고쳐야 한다.
- **UI01F-D5 후보 줄 밖에서 본 같은 모양은 넣지 않는다.** 홈에서 Insight A의 "원본 보기"가 B를 연 뒤 끝나면 B 밑에 A의 원본이 그려지고(`evidence-view.tsx:309-319`, `:562-576`), A·B를 잇달아 열면 늦게 온 쪽이 이긴다(`:541-545`). 알림 화면도 같은 리듀서를 쓴다(`notifications.tsx:79-87`). 위키(`wiki.tsx:346-353`)는 따라가 보지 않았다. 넣으려면 R2와 같은 요구사항을 화면마다 하나씩 더한다.
- **UI01F-D6 E2E는 더하지 않는다.** 세 결함 모두 응답 순서를 조작해야 드러나고 단위 시험이 규칙을 직접 본다. 화면의 호출 자리(`reset()`을 부르는 클릭, `forId`를 넘기는 자리)는 단위 시험이 닿지 못한다.

## 미검증 범위

- 세 결함은 코드 추적으로 확인했다. 브라우저에서 재현해 보지 않았다(결함 1의 "남는 줄"은 React 조정 코드의 읽기에 근거한다).
- `lint.tsx:129`의 `reset()` 호출과 `explore.tsx:613`의 `forId` 전달은 DOM 시험이 없어 직접 시험되지 않는다.
- E2E 로그의 "same key `1`" 경고가 결함 1에서 나온 것인지: 고친 뒤 전체 E2E 로그에서 사라졌는지로 확인한다.
- Windows·Electron.
