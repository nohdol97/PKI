# T181 — 시험용 DB 템플릿 (마이그레이션은 파일당 한 번)

- 상태: 확정
- 이슈: #181 (선행: #175, PR #178)
- 날짜: 2026-11-23

## 배경

시험 대부분은 경우마다 빈 DB를 열고 마이그레이션 29단계를 처음부터 돌린다. 마이그레이션은 "빈 DB를 현재 스키마까지 끌어올리는 작업"이고, 시험이 실제로 확인하려는 동작과는 무관한 준비 과정이다.

이슈 #181은 "파일 DB는 약 115 ms, 메모리 DB는 약 18 ms"라는 전제에서 파일 DB 시험만 대상으로 잡았다. 이번에 다시 재 보니 이 전제가 맞지 않았다.

| 여는 방식 | 한 번에 드는 시간(중앙값, 부하 30~80 상태) |
|---|---|
| 파일 DB 새로 열기 (`openCanonicalDb`) | 291~430 ms |
| 메모리 DB에 `migrate` | 280~312 ms |
| 템플릿 폴더 복사 후 `openCanonicalDb` | 9~22 ms |
| 템플릿 바이트로 메모리 DB 열기 | 4~5 ms |

즉 비용은 디스크 쓰기가 아니라 마이그레이션 자체이고, 메모리 DB 시험도 똑같이 느리다. 마이그레이션을 돌리는 시험 파일은 201개(`it(` 2,851개)이며 그중 메모리 DB 쪽이 더 많다. 같은 파일을 전후로 재면 `storage/src/jobs.test.ts`는 47.1 s → 5.4 s, `knowledge-engine/src/arrival.test.ts`는 13.0 s → 4.7 s, `backend/src/connector-sync-job.test.ts`는 32.9 s → 13.4 s였다(시험 수 동일, 전부 통과).

## 목표

- 시험 파일 하나가 마이그레이션을 한 번만 돌리고, 각 경우는 그 결과의 사본을 받는다.
- 시험의 단언·경우 수·제목은 그대로 둔다. 바뀌는 것은 준비 코드뿐이다.

## 비목표

- 제품 코드 변경. 환경 변수나 옵션으로 제품의 DB 열기 경로를 바꾸는 장치는 만들지 않는다.
- 마이그레이션 자체를 빠르게 하는 일(예: 가장 느린 v26 단계).
- 실행 전체에서 템플릿 하나를 공유하는 것(`globalSetup`). 파일마다 한 번이면 충분한지 먼저 본다.
- 디스크에 템플릿을 남겨 다음 실행에서 재사용하는 것. 마이그레이션이 바뀌면 낡은 템플릿이 조용히 쓰이기 때문이다.
- 마이그레이션·최초 설치·신원 키·장부 복구 자체를 확인하는 시험의 전환.
- 다른 세션이 지금 고치고 있는 시험 파일의 전환.

## 요구사항

- **R1** `@pki/testkit`에 `memoryDbTemplate(open, prepare)`를 둔다. 호출 시점(시험 파일이 로드될 때)에 `open`으로 임시 파일 DB를 열어 `prepare`를 한 번 돌리고, 그 파일의 바이트를 기억한 뒤 임시 파일을 지운다. 돌려주는 함수는 부를 때마다 그 바이트로 새 메모리 DB를 `open`해 돌려준다.
- **R2** `@pki/testkit`에 `dirTemplate(build)`를 둔다. 호출 시점에 임시 폴더를 만들어 `build`를 한 번 돌린다. 돌려주는 함수는 그 폴더를 지정한 경로로 복사한다. 템플릿 폴더는 그 시험 파일이 끝날 때 지운다.
- **R3** 두 helper는 열기·마이그레이션 함수를 인자로 받는다. testkit은 `@pki/storage`나 backend를 가져오지 않는다. 사본은 제품의 열기 함수(`openBetterSqlite3`, `openCanonicalDb`)를 그대로 지난다.
- **R4** 전환 대상은 "빈 DB를 열고 곧바로 마이그레이션하는 준비 코드"뿐이다. 메모리 쪽은 `openBetterSqlite3(":memory:")` 바로 다음 줄이 `migrate(db)`인 자리, 파일 쪽은 파일 안에서 `openCanonicalDb`를 한 번만 부르는 준비 코드다. 그 밖의 자리는 손대지 않는다.
- **R5** 전환한 뒤 그 파일의 시험이 실패하면 단언을 고치지 않고 그 파일을 원래대로 되돌린 다음 PR 본문에 파일과 이유를 적는다.
- **R6** `backend/src/import.test.ts`가 자체로 가진 템플릿 코드는 `dirTemplate`으로 바꾼다. 매 시험의 `beforeEach` DB는 지금처럼 새로 만든다.

## 완료 기준

- **C1** (R1, R2, R3) helper 시험: 사본 두 개를 받으면 둘 다 `prepare`/`build`가 만든 상태이고, 한쪽에 쓴 내용이 다른 쪽에 보이지 않으며, `prepare`/`build`는 한 번만 불린다. 메모리 쪽 시험은 실제 드라이버와 `migrate`로 `storage`에 두고, 폴더 쪽 시험은 testkit에 둔다.
- **C2** (R4, R5, R6) PR 직전 전체 실행(`pnpm lint`, `pnpm typecheck`, `pnpm test`)이 통과한다. 전환한 파일의 diff에는 import와 준비 코드 외의 변경이 없고 `it(`·`test(` 줄의 추가·삭제가 없다(시험 수 보존은 기준 전체 실행을 한 번 더 돌리는 대신 diff로 확인한다).
- **C3** (목표) 같은 장비에서 연달아 잰 단독 실행 시간이 `storage/src/jobs.test.ts`, `knowledge-engine/src/arrival.test.ts`, `backend/src/connector-sync-job.test.ts` 세 파일 모두 전환 전의 절반 이하다. 전체 실행의 벽시계 시간도 부하와 함께 PR에 적는다.

## 잠정 결정

| 결정 | 이유 | 바꾸려면 |
|---|---|---|
| 범위를 메모리 DB 시험까지 넓힌다(이슈 본문은 파일 DB만) | 실측으로 메모리 DB도 같은 비용임이 드러났고, 대상의 약 60%가 메모리 쪽이다 | T2를 빼고 T1·T3만 진행 |
| 메모리 사본은 "파일로 복사해 열기"가 아니라 템플릿 바이트로 메모리 DB를 연다 | 시험이 지금처럼 메모리 DB로 남고 더 빠르다(jobs 5.4 s 대 11.6 s) | helper 안에서 복사한 파일 경로를 `open`에 넘기도록 변경 |
| 위 방식은 `better-sqlite3`가 경로 자리에 바이트를 받는 동작에 기대며, helper 안에 형 변환 한 줄이 생긴다 | 제품의 `OpenSqlDriver` 형을 시험 때문에 넓히지 않기 위해서다. C1 시험이 이 동작을 지킨다 | 제품 형을 `string \| Buffer`로 넓히는 별도 결정 |
| 템플릿은 시험 파일마다 하나, 파일이 로드될 때 만든다 | 병렬 worker끼리 공유하지 않아 충돌이 없고, 매 실행 새로 만들어 낡지 않으며, 가짜 시계를 켜기 전에 만들어진다 | `globalSetup`으로 실행당 하나(미루는 항목) |
| 한 파일 안의 사본은 같은 신원 키(파일 DB는 옆의 삭제 장부까지)를 공유한다 | #178과 같은 성질이다. 서로 다른 키를 요구하는 시험은 R4 범위 밖이거나 R5로 되돌린다 | 해당 파일을 전환 목록에서 제외 |

## 미루는 항목

- 다른 세션이 고치는 중이거나 그 주제와 겹칠 시험 파일(insight·wiki·lint·reflection·analytical·local 계열, `api.contract`, `connector-sync-job`, `derivative-coverage` 등): 그 브랜치가 머지된 뒤 같은 방식으로 전환한다. #240 첫 묶음에서 이전에 미뤘던 파일 중 `dependency-delay`, `extraction-v3/v4`, `ontology-enforce`, `broker.claimed-scope/inputs/scope-classes`, `storage/ontology`, `cli-gate`, `knowledge-schema.api`, `ontology-api`를 전환했다.
- 준비 코드가 `beforeEach` 밖(`beforeAll`, 시험 본문, 헬퍼)에 있거나 `openCanonicalDb`를 두 번 이상 부르는 시험은 R4 범위 밖이라 전환하지 않는다.
- `openCanonicalDb`를 여러 번 부르는 backend 시험 14개(boot, composition, ledger 계열): 열기 자체가 시험 대상인 자리가 섞여 있어 파일마다 판단이 필요하다.
- 실행 전체에서 템플릿 하나 공유: 전환 뒤에도 파일당 한 번(약 0.2 s × 140여 파일)이 남는다.
- 마이그레이션 v26 단계의 비용 점검.
