# 스펙: 셸 수명주기 후속 묶음(SLF) — 제거 호출이 멈추지 않게, 나머지 항목 분류

- 날짜: 2026-11-24 / 상태: 확정(잠정 결정 D1~D7 포함)
- 관련: 이슈 #295(H02 공용 범위 후속), #304(백엔드 잠금 후속의 남은 줄), #198(N2), #291(`boot.ts` 색인 닫기 한 줄). [H02 공용 spec](2026-11-24-H02-common.md), [잠금 견고화 spec](2026-11-24-LKH-lock-hardening.md), [P7 후속 묶음 spec](2026-11-24-P7-followups.md)
- 번호: 요구사항 `SLF-R<n>`, 완료 기준 `SLF-C<n>`, 결정 `SLF-D<n>`, 작업 `SLF-T<n>`. 마이그레이션과 계약 변경은 없다.

| 말 | 뜻 |
|---|---|
| 제거 호출 | 설치 프로그램이 셸을 `--pki-uninstall-data=keep\|delete`로 부르는 것(H02A-R6). 창과 백엔드 없이 판정하고 종료 코드로 답한다 |
| 셸 잠금 | 셸이 데이터 폴더의 `instance.lock`에 쥐는 잠금(R04L). 한 폴더에 셸이 하나임을 보장한다 |
| 닫힌 쪽 | 확신이 없을 때 지우지 않고, 시작하지 않고, 설치하지 않는 쪽 |

## 배경

네 이슈에 남은 줄을 지금 코드(`origin/main` `f3ddb240`)와 하나씩 대조했다. 이미 고쳐져서 닫을 줄은 없다. 실제로 틀리게 동작하는 것은 넷이고 모두 작다. 가장 큰 것은 **제거 호출이 끝나지 않을 수 있다**는 것이다: 자동 시작 등록을 끄는 OS 호출이 예외를 내면 종료 코드를 내는 줄에 닿지 못해 제거 프로세스가 창 없이 남고, 그것을 기다리는 설치 프로그램도 멈춘다.

## 목표

1. 제거 호출은 어떤 실패에서도 한 줄과 종료 코드로 끝난다.
2. 지우기를 고르면 PKI 것이 아닌 이름 때문에 폴더가 반쯤 남지 않는다.
3. 자동 시작 항목의 표시는 누른 뒤에도 OS 상태와 같다.
4. `runUpdate`는 실패를 언제나 결과로 돌려준다.

## 비목표

- **A2의 틈을 닫는 것**(D1). 잠금을 얻는 쪽의 재확인과 Windows 실측이 필요하다.
- **종료 코드의 뜻을 나누는 것**(D3), 설치 프로그램, 업데이트 채널, 공개 키 형식 확인(A7).
- `backend/src/boot.ts`와 `backend/src/shell-main.ts`의 수정(F6, N2, 색인 닫기, #304 F2·F4·F6).
- SBOM 표시 규칙(F1~F3), 시험 보강만인 줄(A5, F7, F8), 두 잠금 모듈의 `SQLITE_BUSY` 비교.
- `apps/web`, 저장소 계층, 마이그레이션, Windows 실측.

## 요구사항

- **SLF-R1 제거 호출은 언제나 끝난다.** `removeUserData`는 던지지 않는다. ① `disableAutostart`가 던지면 아무것도 지우지 않고 `nothing was removed`가 든 한 줄과 종료 코드 1을 돌려준다(`keep`도 1이다: 등록이 남았다). ② 잠금의 `close()`가 던져도 남은 단계를 그대로 진행한다. ③ `main.ts`의 제거 갈래는 그 밖의 어떤 거절에도 표준 오류 한 줄을 쓰고 종료 코드 1로 끝난다.
- **SLF-R2 잠금 파일 이름으로 시작하는 폴더.** 데이터 폴더 안에서 이름이 `instance.lock`으로 시작해도 **폴더**이면 다른 내용과 함께 잠금을 쥔 동안 지운다. 잠금을 놓은 뒤로 미루는 것은 폴더가 아닌 것(파일과 링크)뿐이다. 링크는 따라가지 않는다.
- **SLF-R3 자동 시작 항목의 표시.** 패키지된 앱에서 항목을 누르면 `set`이 던져도 예외가 밖으로 나가지 않고(표준 오류 한 줄), 누른 뒤 그 항목의 체크는 `get()`을 다시 읽은 값이다.
- **SLF-R4 `runUpdate`는 거절되지 않는다.** 받은 파일을 지우다 실패해도 처음의 실패 이유를 결과(`{ ok: false, reason }`)로 돌려준다. 지우지 못한 것은 그대로 둔다.
- **SLF-R5 패키지 아닌 실행.** 제거 갈래는 패키지된 앱일 때만 OS의 자동 시작 등록을 건드린다(H02A-D8).
- **SLF-R6 문서.** ① H02 spec "미검증"의 틈 문장을 사실대로 고친다: macOS·Linux에서는 그 사이 시작한 PKI의 잠금 파일이 지워질 수 있다(변경 이력에 한 줄). ② `docs/site-setup.md` S46에 확인할 것 하나: Windows에서 열려 있는 `instance.lock`의 삭제가 거절되는지. ③ S48의 "종료 코드 1이면 지워지지 않은 것"을 "거절했거나 일부만 지운 것이고 표준 오류 한 줄이 어느 쪽인지 말한다"로. ④ S47에 한 문장: 해시 확인과 설치가 파일을 따로 열며 뒤따르는 Authenticode 확인이 있어 받아들인다. ⑤ `backend-lock.ts` 머리 주석에 쓰기 확인과 강한 참조(LKH-R2·R3).
- **SLF-R7 시험의 시간 한도.** `data-lock.test.ts`의 자식 프로세스 시험에 시간 한도 20초를 적는다.

## 인터페이스 / 설계 개요

- **R1**: `data-removal.ts`에서 `disableAutostart()`를 try로 감싸 거절 줄로 바꾸고, `finally`의 `held.close()`가 던지는 것을 삼킨다(프로세스가 곧 끝나고 OS가 잠금을 푼다). `main.ts`의 `whenReady().then(...)`에 `.catch`(한 줄 출력, `app.exit(1)`)를 붙인다.
- **R2**: 첫 번째 지우기의 건너뛰기 조건을 "이름이 잠금 파일로 시작하고 **폴더가 아님**"으로 바꾼다(`lstat`). 두 번째 지우기는 그대로다.
- **R3**: `click`이 Electron이 넘기는 항목을 선택 인자로 받는다(`click(item?: { checked: boolean })`). `set`을 try로 감싸고 끝에 `item.checked = get()`.
- **R4**: `failed()`의 `rmSync`를 try로 감싼다.
- **R5**: `main.ts`의 `disableAutostart`를 `app.isPackaged`일 때만 부르게 한다.

그림은 넣지 않는다(갈래가 늘지 않고 기존 호출을 감쌀 뿐이다).

## 잠정 결정

- **SLF-D1 A2는 이번에 닫지 않는다.** 잠금을 쥔 채 잠금 파일까지 지우면 Windows에서 열린 journal을 지울 수 없어 H02의 필수 지적 수정(`data-removal.test.ts`의 "while the lock is held no instance.lock\* file is removed")을 되돌리게 되고, macOS·Linux에서도 "잠금 파일을 먼저 열고 지워진 뒤에 잠근" 시작이 남아 틈의 크기가 같다. 실제로 닫으려면 잠금을 얻은 쪽이 "내가 잠근 파일이 아직 그 경로의 파일인가"를 다시 확인해야 하는데(예: 같은 경로에 두 번째 연결이 `SQLITE_BUSY`인지), 이것은 모든 시작이 지나는 셸 잠금을 바꾸는 일이고 Windows에서의 동작을 잴 수 없다. 틈은 연속한 동기 호출 둘 사이이고, 닿아도 기존 데이터는 잃지 않으며 정본 DB는 SQLite 자체 잠금이 지킨다. 다시 꺼낼 때의 출발점: 위 재확인 + POSIX에서는 잠금을 쥔 채 잠금 파일 삭제.
- **SLF-D2 자동 시작을 끄지 못하면 지우지 않는다.** 종료 코드 1의 지금 뜻("지워지지 않았다")과 같은 닫힌 쪽이고, 사용자는 다시 제거하거나 폴더를 직접 지울 수 있다. 끄지 못해도 지우게 하려면 `removeUserData`의 그 try에서 실패를 기억해 두고 끝에 1로 답하게 바꾼다.
- **SLF-D3 종료 코드는 나누지 않는다(A4).** 이 코드를 읽는 설치 프로그램이 아직 없어 나눌 값을 정할 근거가 없고, 표준 오류 한 줄이 이미 둘을 구분한다(`nothing was removed` / `may be partial`). 나누려면 `RemovalResult.code`에 값을 더하고 S48을 고친다(배포처가 설치 프로그램을 만들 때).
- **SLF-D4 `close()`의 실패는 삼킨다.** 제거 프로세스는 곧 끝나고 OS가 잠금을 푼다. 잠금이 정말 안 풀렸다면 뒤의 잠금 파일 삭제가 Windows에서 실패해 1로 끝난다.
- **SLF-D5 `failed()`는 지우지 못한 경로를 그대로 둔다.** "내려받기가 만든 파일만 지우기"는 채널이 무엇을 만드는지 정해져야 하므로 S47에 둔다. 지금은 결과를 돌려주는 약속(H02A-R4)만 지킨다.
- **SLF-D6 체크 표시는 누를 때 다시 읽는다.** OS 쪽에서 등록이 바뀐 경우까지 따라가려면 메뉴를 열 때마다 다시 만들어야 하는데 요구된 적이 없다.
- **SLF-D7 나머지 보류는 배경 표의 사유대로 이슈에 둔다.** LKH-D7(#304 F2·F4·F6, #198 N2)을 바꾸지 않는다.

## 미검증 범위

- **Windows**: 열려 있는 `instance.lock`의 삭제가 실제로 거절되는지(A2가 Windows에서 닫힌 쪽인지), `app.setLoginItemSettings`가 던지는 경우가 있는지. S46에서 확인한다.
- `main.ts`의 `.catch`와 `app.isPackaged` 가드는 단위 시험이 없다(코드 검토와 e2e의 기존 흐름만).
- A2의 재현은 개발 PC(macOS, Node 26)의 임시 폴더에서 한 프로세스의 연결 둘로 했다. 두 프로세스의 실제 경합은 재현하지 않았다.
- `node:sqlite`의 `errcode`가 확장 코드인지는 확인하지 않았다(어느 쪽이든 닫힌 쪽이다).
- RSA 공개 키를 넘겼을 때 `verify(null, …)`의 동작(A7)은 실행해 보지 않았다.
