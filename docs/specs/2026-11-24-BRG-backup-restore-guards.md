# 스펙: 백업·복원 가드 묶음(BRG) — scrypt 작업량 상한을 붙잡는 시험, 스키마 글 기준선

- 날짜: 2026-11-24 / 상태: 확정(잠정 결정 D1~D5 포함)
- 관련: 이슈 #270(착수 선언, 9번 줄), #298(F1·F2·F4), #304. [H01 spec](2026-11-23-H01-backup-restore.md)(H01-R9 ⑥), [H01F spec](2026-11-24-H01F-followups.md)(H01F-R2·R3·R6, C2·C3·C6), [RDF spec](2026-11-24-RDF-remaining-defects.md)
- 번호: 요구사항 `BRG-R<n>`, 완료 기준 `BRG-C<n>`, 결정 `BRG-D<n>`, 작업 `BRG-T<n>`. **제품 코드, 마이그레이션, 계약 변경은 없다. 시험만 더한다.**
- 기준 코드: `origin/main` `dfac802f`. 아래의 `파일:줄`은 그 커밋에서 열어 읽은 자리다.

| 말 | 뜻 |
|---|---|
| 머리말 | 백업 파일 앞의 평문 부분. 암호구 없이 읽히고 scrypt 비용 값(`N`·`r`·`p`)이 적혀 있다 |
| 작업량 상한 | 머리말의 scrypt 값 가운데 `N·r·p ≤ 2^22`(H01F-R3). 메모리 상한 `128·N·r ≤ 256MiB`와 따로 있는 조건이다 |
| 스키마 글 | SQLite가 DB 파일 안의 `sqlite_master` 표에 적어 두는, 표·색인·트리거를 만든 SQL 글 |
| 준비 검사 ⑥ | 복원을 준비할 때 사본의 스키마 글이 이 빌드가 만드는 것과 **글자까지** 같은지 보는 검사. 다르면 `foreign-schema`로 거절한다(H01-R9) |
| 기준선 | 지금 값을 저장소에 적어 두고, 값이 달라지면 빨개지는 시험. 고장을 고치는 것이 아니라 알리는 장치다 |

## 배경

#270의 9번 줄과 #298의 F1·F2·F4를 지금 코드와 한 줄씩 대조했다. **고칠 결함은 없다.** 남는 것은 시험 둘이다: 지워도 시험이 초록인 **보안 차단 가드 하나**(F1)와, 9번 줄이 걱정한 일이 실제로 생기는 순간을 알려 주는 **기준선 하나**. F2·F4의 가드는 이미 있는 시험이 붙잡고 있어(읽기로 확인) 변이 확인만 한다.

### 9번 줄: 무엇을 비교하고, 언제 어긋나는가

준비 검사 ⑥은 `sqlite_master`의 모든 행을 (종류, 이름, 표, **SQL 글 그대로**)로 읽어 정렬한 뒤(`backup.ts:429`~`:434`), 빈 메모리 DB에 이 빌드의 마이그레이션을 돌려 만든 것과 줄 단위로 똑같은지 본다(`:443`~`:453`, `:575`~`:579`). `user_version`은 ③에서 따로 보고, `application_id`는 보지 않는다. 글자 하나만 달라도 거절하는 것은 일부러다: 사본에 실려 온 트리거나 바뀐 표가 정본에서 돌지 않게 한다(검토 S1).

이 글 가운데 SQLite가 **스스로 지어 쓰는** 부분이 있다: FTS5가 만드는 그림자 표의 `CREATE` 글(`storage/src/migrations.ts:31`), `ALTER TABLE ... RENAME`이 고쳐 쓰는 글(`:158`·`:172`), `ADD COLUMN`이 덧붙이는 글. 백업은 `VACUUM INTO`라 이 글을 **만든 때의 판 그대로** 싣는다. 그래서 어긋나는 길은 둘뿐이다.

1. 번들 SQLite 판이 올라 위 세 가지 가운데 하나를 다르게 지어 쓰게 되면, 옛 판으로 만든 백업의 글과 새 판이 만든 기준이 달라진다.
2. 이미 main에 들어간 마이그레이션의 SQL 글을 누가 고치면(들여쓰기 하나도) 같은 일이 판 변경 없이 생긴다.

**지금은 둘 다 일어나지 않는다.** SQLite는 `better-sqlite3` `13.2.0`으로 고정돼 있고(`storage/package.json:12`, 실측 SQLite 3.54.1), 제품 코드에는 마이그레이션 밖에서 스키마를 바꾸는 문장이 없다(`ANALYZE`·`PRAGMA optimize`·`CREATE`·`DROP`·`ALTER`를 찾았고, 나온 것은 별도 파일인 벡터 색인과 시험용 표뿐이다). 같은 판에서 옛 스키마의 백업이 올려져 받아들여지는 것은 이미 시험이 있다(`backup.test.ts:395`). 판을 바꿔 끼우지 않고는 실패하는 시험을 쓸 수 없으므로 **결함으로 고치지 않는다.**

대신 그 일이 생기는 순간을 잡는다. 처음 33개 마이그레이션이 만드는 스키마 글은 다시는 바뀌지 않아야 하는 값이다(마이그레이션은 한 번 나가면 고치지 않는다). 그 값의 해시를 적어 두면, 위 1·2 가운데 어느 쪽이든 일어난 커밋에서 시험이 빨개진다. 사용자가 복원을 눌렀을 때가 아니라 판을 올리는 사람의 PR에서 드러난다.

## 목표

- scrypt 작업량 상한을 지우면 빨개지는 시험이 저장소에 있다.
- 사용자의 옛 백업이 `foreign-schema`로 거절되게 만드는 변경(SQLite 판 올림, 나간 마이그레이션 고침)이 그 커밋에서 시험으로 드러난다.
- F2·F4의 가드가 지금 시험으로 붙잡혀 있다는 것을 변이로 한 번 확인해 기록한다.

## 하지 않는 것

- **준비 검사 ⑥을 고치는 일.** 글자 비교를 느슨하게(정규화, 열 목록 비교) 바꾸지 않는다. 재현되는 고장이 없는데 보안 가드를 넓히는 일이다(D1).
- **제품 코드 변경.** `backup-file.ts`, `backup.ts`, `backup-api.ts`, `restore-boot.ts`는 건드리지 않는다. 변이 확인 때 잠깐 고쳤다가 백업 복사본으로 되돌릴 뿐이다.
- 복원 표식 상태의 재설계(#298·#304, 사용자 결정 대기), 잠금 없이 뜬 백엔드(#304 F2·F6), Windows·배포처 항목, 문구만인 줄(F3·F7), F5·F6, 2GiB 실측.
- `apps/web`, `README.md`.
- 경계값·조합의 전수 시험(작업량이 정확히 상한인 값, `p`의 다른 값들, 마이그레이션 단계별 해시).

## 요구사항

- **BRG-R1 작업량 상한을 시험이 붙잡는다.** *(변이 확인 대상)* 메모리 상한과 다른 모든 조건은 지나고 **작업량 상한에서만** 걸리는 머리말 하나(`{N: 2^17, r: 8, p: 16}`: 메모리 128MiB, 작업량 2^24)를 H01F-C3 시험의 조작 파일에 더한다. `backup-file.ts:83`의 작업량 조건을 지운 변이에서 그 시험이 빨개져야 한다.
- **BRG-R2 스키마 글의 기준선을 둔다.** 빈 메모리 DB에 마이그레이션의 **처음 33개**를 적용한 뒤 `sqlite_master`의 (`type`, `name`, `tbl_name`, `sql`)을 준비 검사 ⑥과 같은 방식으로 줄로 만들어 정렬하고, 그 글의 SHA-256이 시험에 적힌 값과 같은지 본다. 시험 위 주석에 **빨개졌을 때 할 일**을 적는다: "값을 고쳐 쓰지 말 것. 이 값이 달라졌다는 것은 이전 빌드로 만든 백업이 `foreign-schema`로 거절된다는 뜻이다. 준비 검사 ⑥을 먼저 다룬 뒤(이 spec의 D1) 값을 바꾼다."
- **BRG-R3 F2·F4의 가드는 변이 확인만 한다.** 새 시험을 쓰지 않는다. 아래 "변이 확인"의 둘째·셋째 줄이 빨개지는 것을 보고 PR에 적는다. 초록이면(읽기가 틀렸다는 뜻) 그 가드에 대표 단언 하나를 더하고 그 사실을 보고한다.

### 변이 확인

데이터 보호·보안의 허용·차단 가드 셋에만 한다. 한 번에 하나씩 고치고, 빨간 출력을 본 뒤 **백업 복사본으로** 되돌린다(`git checkout`으로 되돌리지 않는다).

| 가드 | 변이 | 빨개져야 하는 시험 | 빨개지는 단언 |
|---|---|---|---|
| 작업량 상한(R1) | `backup-file.ts:83`에서 `&& N * r * p <= MAX_SCRYPT_WORK`를 지운다 | C1 | `readBackupHeader`의 `damaged` 기대(답이 오류 없음이 된다). 이 단언이 `openBackup`보다 **먼저** 있어야 한다: 뒤의 것이 먼저 돌면 변이 상태에서 16배 scrypt가 실제로 돈다 |
| 이전 사본이 있을 때 새 준비 거절(F2) | `backup-api.ts:253` 한 줄을 지운다 | 기존 `backup-api.test.ts:331`(H01F-C2) | `:351`의 `already-pending` 기대(답이 `staged`가 된다). 그 뒤의 "표식이 있다"·"사본이 그대로다" 단언은 변이에서도 참이라 가드가 아니다 |

## 잠정 결정

바꾸려면 적힌 자리 하나를 고치면 된다.

- **BRG-D1 9번 줄은 고치지 않고 기준선으로 닫는다.** 고정된 판에서는 앱이 만든 백업의 스키마 글이 기준과 달라질 길이 없다(위 "9번 줄"). 비교를 느슨하게 하는 쪽은 트리거·바뀐 표를 막는 가드(S1)를 넓히는 일이라, 어긋남이 실제로 무엇인지 보기 전에는 정할 수 없다. 기준선이 빨개지면 그때 달라진 줄을 보고 ⑥의 spec을 쓴다(예: 표·색인은 `PRAGMA table_xinfo`·`index_list`로 견주고 트리거·뷰는 글자 그대로). 기준선도 빼려면 C2 시험 하나를 지운다(그러면 이 줄은 #270에 "시험 없음"으로 남는다).
- **BRG-D2 기준선은 처음 33개에 고정한다.** 뒤에 더해지는 마이그레이션은 값에 들지 않아, 새 마이그레이션을 넣는 PR이 이 시험을 고칠 일이 없다. SQLite가 지어 쓰는 세 가지(FTS5 그림자 표, `RENAME`, `ADD COLUMN`)는 모두 33개 안에 있다. 범위를 넓히려면 개수와 값을 함께 새로 적은 시험을 **하나 더** 둔다(이 값은 고치지 않는다).
- **BRG-D3 F2·F4에는 시험을 더하지 않는다.** 이미 빨개질 시험이 있는 가드에 같은 동작을 또 확인하는 시험을 쓰지 않는다(테스트 간략화 규칙). F4를 저장 계층에서도 붙잡으려면 C6 시험에 "사본에만 있는 `providers.openaiCompatible.model`이 준비 파일에 없다" 두 줄을 더한다.
- **BRG-D4 F1은 사례 하나다.** 상한과 정확히 같은 값, `r`·`p`의 다른 조합은 넣지 않는다. 받아들이는 쪽은 같은 시험의 제품 기본값 파일이 이미 본다(`backup-file.test.ts:175`~`:185`).
- **BRG-D5 기준선 시험은 `sqlite_master`를 직접 읽는다.** `backup.ts`의 `schemaLines`를 내보내지 않는다(제품 코드 변경 없음). 대가는 ⑥이 견주는 열이 바뀌면 시험의 `SELECT`도 손으로 맞춰야 한다는 것이다. 묶으려면 `schemaLines`를 내보내 시험이 그것을 부르게 한다.

## 미검증 범위

- **F2·F4가 빨개진다는 것은 코드 읽기로 내린 판단이다.** 변이를 실제로 돌리는 것은 T1의 일이다(R3의 "초록이면" 갈래가 그 대비다).
- **SQLite 판을 올렸을 때 글이 실제로 달라지는지.** 다른 판으로 만든 파일이 없어 보지 못했다. 기준선은 "달라지면 알린다"까지만 한다.
- **기준선 값.** 설계 때 저장소 밖의 임시 스크립트로 한 번 쟀다(212줄, SQLite 3.54.1, 두 번 실행 같은 값). 시험에 적는 값은 구현 때 시험이 먼저 빨개진 출력에서 얻고, 잰 값과 같은지 견준다.
- **운영체제에 따른 차이.** 스키마 글은 SQLite가 만들어 운영체제와 무관하다고 보지만 Windows에서 돌려 보지 않았다.
- **변이 상태의 scrypt 시간**(16배)과 Electron·배포처 동작.
- 동료 브랜치 `feat/cuf-curation-ui`는 원격에 없어 로컬 작업 폴더로만 봤다: 겹치는 파일은 `docs/README.md` 하나다(색인 줄 덧붙임, 뒤에 머지하는 쪽이 rebase). `storage`·`backend`는 건드리지 않는다.
