# 스펙: 분석 읽기(`GET /api/analytical`) 속도 — 문장 재사용과 한 읽기 안의 기억

- 날짜: 2026-11-23 / 상태: 초안
- 관련: 이슈 #233, #227(R1), [S03 spec](2026-11-22-S03-analytical-semantic.md) 잠정 결정 35 ⑥. 그 spec은 고치지 않고 이 문서가 잇는다. 번호는 `AR-…`이다.

| 말 | 뜻 |
|---|---|
| 문장 준비 | SQL 글을 SQLite가 실행할 수 있는 모양으로 바꾸는 일(`prepare`). 같은 글이면 한 번 만든 것을 다시 쓸 수 있다 |
| 질의 수 | 한 번의 읽기가 드라이버의 `all`을 부른 횟수. 시계와 달리 기계 부하에 흔들리지 않는다 |
| 세 목록 한 묶음 | 측정 세계의 Dataset 1개 + Metric 1개 + Join 1개(`tooling/poc/s03/analytical-read-latency.ts`의 `seed`) |

## 배경

Dataset·Metric·Join 각 200개에서 `GET /api/analytical`의 중앙값이 약 30초다(#233). 읽어서 다시 재 보니 원인은 셋이고, 모두 항목 수에 비례한다(제곱으로 늘지 않는다).

| 원인 | 실측(200개, 한 번의 읽기) |
|---|---|
| ① 드라이버가 `run`·`all`마다 문장을 새로 준비한다 | 질의 156,404번에 준비도 156,404번. SQL 글은 42가지뿐이다 |
| ② 같은 행의 보임 여부를 여러 번 묻는다 | `shown` 23,600번 가운데 서로 다른 물음은 5,600개. 물음 하나가 등록부에서 질의 약 3.7번이다 |
| ③ Metric이 `grain` 하나를 얻으려고 Dataset의 사실 행 전부를 다시 만든다 | ②를 없앤 뒤 남는 질의 91,004번 가운데 약 13,000번 |

같은 프로세스에서 번갈아 5회씩 잰 값(Apple M1, Node v26.5.0, 부하 평균 43~86으로 매우 높음. 시계 값은 회차마다 3배까지 흔들린다):

| 구성 | 질의 수 | CPU 중앙값 | 시계 중앙값 |
|---|---|---|---|
| 지금 | 156,404 | 17.3초 | 30.9초 |
| ①만 | 156,404 | 7.4초 | 12.9초 |
| ②③만 | 77,810 | 8.2초 | 12.8초 |
| ①+②③ | 77,810 | 4.5초 | 8.4초 |

비유하자면 같은 서류 양식을 물을 때마다 새로 인쇄하고(①), 같은 사람에게 같은 질문을 네 번씩 하는(②) 셈이다. 다만 질문의 가짓수 자체(묶음마다 약 390번)는 이 작업으로 줄지 않는다.

## 목표

- 같은 측정 스크립트의 중앙값을 같은 세션에서 잰 변경 전 값의 **3분의 1 이하**로 낮춘다(실측 예상 약 3.7배).
- 응답 내용은 #227 R1이 고치는 중복을 빼고 한 글자도 달라지지 않는다.

## 비목표

- **1초 기준(결정 35 ⑥)은 이 작업으로 채우지 않는다.** 열 배 이상 줄이려면 사실 행마다 도는 읽기(근거, 검사 줄, 유효 판정, 경쟁 값, `unmet`)를 묶음 질의로 바꾸고 보임 판정을 한 번에 물어야 한다. 앞의 것은 `storage`의 모듈 여섯을, 뒤의 것은 다른 세션이 잡고 있는 `backend/src/server.ts`를 고쳐야 해서 후속 이슈로 넘긴다.
- 읽기 사이에 걸친 캐시(프로세스 수명의 결과 캐시)는 만들지 않는다. 기억은 읽기 한 번 안에서만 산다.
- `SqlDriver` 포트(`sql-driver.ts`)의 모양, HTTP 계약, 스키마는 바꾸지 않는다.

## 요구사항

- **AR-R1** better-sqlite3 드라이버는 연결마다 SQL 글을 열쇠로 준비한 문장을 보관하고, `run`과 `all`은 같은 글이면 그것을 다시 쓴다. `exec`와 `transaction`은 그대로다.
- **AR-R2** 보관하는 문장 수에는 상한(256)이 있고, 넘으면 가장 먼저 들어온 것부터 버린다. 자리 표시 개수가 바뀌는 SQL(`IN (?, ?, …)`)이 보관소를 끝없이 키우지 못하게 하기 위해서다. `close`는 보관소를 비운다.
- **AR-R3** 문장을 다시 써도 결과는 같다: 보관된 뒤 표의 열이 바뀌거나 표가 다시 만들어져도 새 모양으로 답하고, 닫힌 뒤의 사용은 지금처럼 거부된다.
- **AR-R4** `listAnalytical`과 `listMetricViews`는 읽기 한 번 안에서 같은 `(kind, id)`의 보임을 `Visibility.shown`에 한 번만 묻는다. `unmet` 판정(`dataChecksUnmet`)에 넘기는 보임도 같은 기억을 쓴다.
- **AR-R5** 읽기 한 번 안에서 한 항목의 사실 행 목록, 한 Dataset의 실제 표 목록, 한 종류의 검사 필요 여부는 한 번만 만든다.
- **AR-R6** (#227 R1) 묶음의 구성원은 **대표 아래에만** 붙는다. 대표가 숨어서 최상위에 선 구성원은 `members`가 빈 목록이다.

| 번호 | 요구사항 | 시험 | 기준 |

| AR-C6 | 목표 | `tooling/poc/s03/analytical-read-latency.ts`(200개, 5회) | 변경 전(`origin/main`)과 변경 후를 같은 세션에서 연달아 재서 중앙값이 3분의 1 이하. 두 값과 표본, 잴 때의 부하 평균을 PR 본문과 #233에 적는다. 수동 측정이며 시험 묶음에 넣지 않는다 |

## 위험

- **드라이버 변경은 모든 DB 호출에 닿는다.** 문장은 `all`·`run`이 끝나면 초기화되므로 잠금을 쥔 채 남지 않고, 스키마가 바뀌면 SQLite가 스스로 다시 준비한다(better-sqlite3 13.2.0에서 열 추가·표 재생성 뒤 새 모양으로 답하는 것을 확인). PR 직전 전체 시험이 이 변경의 주된 확인이다.
- **기억한 사실 행은 응답 안에서 같은 객체를 두 곳이 가리킨다**(Dataset의 `grain`과 그 Dataset을 재는 Metric의 `grain`). 읽기 결과를 받은 쪽이 고쳐 쓰지 않는다는 전제이며, 지금 호출자(API 직렬화, K01 페이지)는 읽기만 한다.
