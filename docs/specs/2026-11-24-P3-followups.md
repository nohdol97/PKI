### #233 실측 (2026-11-24, Apple M1, Node v24.22.3, 부하 평균 1.7)

- `node tooling/poc/s03/analytical-read-latency.ts 200 5`: 표본 1737, 1741, 1724, 1733, 1740ms, **중앙값 1,737ms**, 응답 967,453바이트. #245 뒤에도 1초 기준(S03 결정 35 ⑥)을 넘는다.
- 같은 실행의 CPU 프로파일: 시간의 89%가 `listAnalytical`, 79%가 드라이버의 `all`이다. 등록부 보임 판정(`registry.visible`)은 12%다.
- 세 목록 200묶음의 읽기 한 번에서 읽기 함수가 내는 질의는 57,010번인데 **서로 다른 질의는 23,612개**다(59%가 되풀이). 큰 것은 근거 목록(사실 하나에 네댓 번), 온톨로지 전체(4,600번, 해석 비용 포함), 사실 한 줄 읽기다. `valid-row`·`assertion-links`·`analytical-gate`·`knowledge`가 저마다 같은 줄을 다시 읽기 때문이다.
- 되풀이를 없앤 시험 삼아 만든 읽기(메모리 DB, 서버 없이)는 5회 기준 약 1,000ms → 약 570ms였고 응답의 JSON 글은 같았다.

비유하자면 한 회의 안에서 같은 서류를 부서마다 다시 떼어 오는 셈이다. 회의가 끝날 때까지 서류가 바뀌지 않으니 한 번 뗀 것을 돌려 보면 된다.

## 목표

1. `GET /api/analytical`의 읽기 한 번이 같은 질의를 드라이버에 두 번 내지 않는다.
2. 응답 내용은 한 글자도 달라지지 않는다.

## 비목표

- **1초 기준을 완료 기준으로 삼는 것.** 시계 값은 PR 본문과 #233에 적는 근거일 뿐이다. 예상은 약 1.0~1.2초이고 재 보기 전에는 모른다.
- **읽기 사이에 걸친 캐시.** 기억은 읽기 한 번 안에서만 산다.
- **저장 모듈의 사실별 읽기를 묶음 질의로 바꾸기, 등록부 보임 판정의 묶음 조회.** `backend/src/server.ts`와 `SqlDriver` 포트의 모양은 건드리지 않는다.
- **위 표의 "이슈에 둠"·"미룸" 항목 전부.** 시험 보강·문구·구조 항목은 구현하지 않는다(테스트 간략화 규칙 6항).
- **새 테이블·마이그레이션.** 없다.

## 요구사항

- **P3F-R1 읽기 한 번 안에서 같은 질의는 한 번만 드라이버에 간다(#233).** `listAnalytical`과 `listMetricViews`는 받은 드라이버를 읽기 기억으로 감싸 쓴다. 감싼 드라이버의 `all`은 같은 질의면 처음 받은 행을 그대로 돌려준다. `run`·`exec`·`transaction`이 불리면 기억을 비우고 넘긴다(읽기 도중 쓰기가 끼어도 옛 값을 돌려주지 않게). 돌려주는 행과 목록은 얼려서, 받은 쪽이 고쳐 쓰면 바로 실패한다. 값에 `bigint`나 바이트 배열이 든 질의는 기억하지 않고 그대로 넘긴다.
- **P3F-R2 응답 불변.** 같은 저장 상태와 같은 보임 판정에서 두 읽기 함수의 반환 값은 변경 전과 같다. `Visibility.shown`을 묻는 횟수와 순서도 그대로다.

## 인터페이스 / 설계 개요

- 새 파일 `storage/src/read-memo.ts`: `memoReads(db: SqlDriver): SqlDriver`. 열쇠는 SQL 글과 값 목록의 JSON. `storage/src/index.ts`로 내보내지 않는다(쓰는 곳이 하나다).
- `storage/src/analytical-views.ts`의 `Reader` 생성자 한 줄: `this.db = memoReads(db)`. 읽기 함수가 `Reader`를 읽기마다 새로 만들므로 기억의 수명이 곧 읽기 한 번이다. 기존의 `seen`·`once`는 그대로 둔다(SQL 위의 계산을 아낀다).
- 그 밖의 제품 파일은 고치지 않는다.

그림은 넣지 않는다(파일 둘의 작은 변경이라 순서 있는 교환·상태 전이·네 개 이상 부품의 구조가 없다).

## 잠정 결정

바꾸려면 적힌 자리 하나를 고치면 된다.

- **P3F-D1 되풀이는 SQL 읽기 층에서 한 번에 없앤다.** 저장 모듈 여섯을 묶음 질의로 고치는 것보다 자리가 하나이고, 읽기 도중 쓰기가 없으면 답이 같다는 것이 구조로 보장된다. 되돌리려면 `Reader` 생성자의 한 줄을 지운다.
- **P3F-D2 돌려주는 행은 복사하지 않고 얼린다.** 복사 비용이 없고, 받은 쪽이 고쳐 쓰는 일이 생기면 조용히 틀리는 대신 시험에서 예외로 드러난다(측정 세계에서는 얼린 채로 통과했다). 고쳐 쓰는 호출자가 정당하게 있으면 `read-memo.ts`에서 얼리는 대신 돌려줄 때마다 얕은 복사를 한다.
- **P3F-D3 등록부 보임 판정에는 기억을 붙이지 않는다.** 읽기 시간의 12%이고, 붙이려면 다른 작업과 겹치기 쉬운 `backend/src/server.ts`의 `shown` 줄을 고쳐야 한다. 시험 삼아 붙여 봐도 3% 안팎만 더 줄었다. 붙이려면 `backend/src/analytical-api.ts`의 `list`가 같은 감싼 드라이버를 `shown`에도 넘기게 한다.
- **P3F-D4 #233은 이 묶음 뒤에도 1초를 넘으면 열어 둔다.** 닫는 조건은 한가한 기계에서 잰 중앙값 1초 이하다. 남는 일은 사실별 읽기의 묶음 질의다.
- **P3F-D5 #218의 두 항목은 이번에 넣지 않는다.** 첫째는 판정 규칙을 정해야 하고, 셋째는 응답 크기 상한이 이미 막는다. 셋째를 넣으려면 `storage/src/analytical-types.ts`의 `columnSet`·`keyPairs`에 원소 수 상한(사용자 입력 경로의 50, `packages/contracts/src/analytical-types.ts:183`과 같게)을 더하고 시험 한 건을 둔다.
- **P3F-D6 마이그레이션은 없다.** 합칠 때 다른 작업이 번호를 올렸어도 이 묶음은 영향이 없다.
