# 스펙: R04 후속 — 단일 실행의 기준을 데이터 폴더의 잠금으로

- 날짜: 2026-11-23 / 상태: 확정(잠정 결정 포함)
- 관련: 이슈 #13(R04)의 위험 기록(V01-T15 독립 검토 F4), [V01 spec](2026-11-21-V01-vertical-skeleton.md) "T15가 넘기는 것" 6항. 그 spec은 고치지 않고 이 문서가 잇는다. 번호는 `R04L-…`이다.

| 말 | 뜻 |
|---|---|
| 데이터 폴더 | 정본 DB(`pki.sqlite`)와 비밀 저장 파일이 있는 OS 사용자별 폴더. 셸이 `dataDir ?? dataDirectory()`로 정한다 |
| userData | Electron(Chromium)이 자기 프로필을 두는 폴더. 데이터 폴더와 다른 곳이며, Chromium 스위치 `--user-data-dir`로 옮길 수 있다 |
| 데이터 잠금 | 이 spec이 더하는 것. 데이터 폴더 안의 잠금 파일을 셸 프로세스가 살아 있는 동안 쥐고 있는 것 |

## 배경

지금 단일 실행은 Electron의 `app.requestSingleInstanceLock()` 하나에 기대고, 이 잠금은 userData에 잡힌다(`apps/desktop/src/main.ts`). 그래서 빌드한 앱을 `--user-data-dir=<다른 폴더>`로 다시 띄우면 잠금이 서로 다른 폴더에 잡혀, 두 번째 셸과 두 번째 백엔드가 **같은 데이터 폴더·같은 DB**로 뜬다(검토자가 macOS에서 재현). 이 스위치는 배포 빌드에서도 없앨 수 없다. 비유하자면 현관문(userData)에만 자물쇠를 달아 두었는데, 금고(데이터 폴더)로 가는 옆문이 하나 더 있는 셈이다. 그래서 자물쇠를 금고 자체에 단다.

## 목표

- 같은 데이터 폴더를 쓰는 셸은 userData가 어디든 **한 번에 하나만** 백엔드를 띄운다.
- 비정상 종료가 남긴 흔적이 다음 시작을 막지 않는다.
- 스위치 없이 띄우는 보통의 경우(두 번째 실행이 0으로 끝나고 첫 창이 앞으로 온다)는 그대로다.

## 비목표

- **`--user-data-dir` 스위치를 거부하지 않는다.** E2E와 산출물 시험이 이 스위치로 프로필을 격리하고, userData를 옮기는 길이 이 스위치만도 아니다(잠정 결정 D1).
- **셸 없이 띄운 백엔드는 다루지 않는다.** 브라우저 개발용 백엔드(`pnpm dev`)가 앱과 같은 데이터 폴더를 여는 경우는 범위 밖이다. 잠금은 셸이 쥔다(D2).
- **다른 userData로 띄운 두 번째 실행이 첫 창을 앞으로 가져오지 않는다.** 두 프로세스 사이에 새 통로를 만들지 않는다(D3).
- 네트워크 드라이브나 동기화 폴더에 둔 데이터 폴더에서 파일 잠금이 믿을 만한지는 다루지 않는다.
- `backend/` 코드, HTTP 계약(`packages/contracts`), 화면은 고치지 않는다.

## 요구사항

- **R04L-R1** 셸은 창과 백엔드를 만들기 전에(`run()` 전에) 데이터 폴더의 데이터 잠금을 얻는다. 데이터 폴더가 아직 없으면 기존 규칙(`ensureDataDirectory`, 소유자 전용)으로 만든 뒤 얻는다. 순서는 디버깅 스위치 거부 → Electron 단일 실행 잠금 → 데이터 잠금이다.
- **R04L-R2** 데이터 잠금을 다른 살아 있는 프로세스가 쥐고 있으면 셸은 창, 백엔드, 비밀 저장소를 만들지 않고, 표준 오류에 정해진 한 줄(`PKI: this data folder is already in use by another running PKI`)을 쓰고 종료 코드 1로 끝난다. 데이터 폴더의 다른 파일은 건드리지 않는다.
- **R04L-R3** 데이터 잠금은 쥔 프로세스가 끝나면(정상 종료, 강제 종료, 충돌 모두) OS가 풀어 준다. 남은 잠금 파일은 그 자체로 "쥐고 있음"을 뜻하지 않으며, 다음 시작은 지우기나 사용자 조치 없이 잠금을 얻는다. PID 기록이나 시간 초과로 낡은 잠금을 추정하지 않는다.
- **R04L-R4** 셸은 데이터 잠금을 스스로 풀지 않고 프로세스가 끝날 때까지 쥔다. 그래서 종료 중 백엔드가 멈추기를 기다리는 동안(`will-quit`)에도 다른 셸이 같은 폴더로 시작하지 못한다.
- **R04L-R5** "쥐고 있음" 말고 다른 이유로 잠금을 얻지 못하면(폴더를 만들 수 없음, 쓰기 권한 없음 등) 셸은 닫힌 쪽으로 끝난다: 표준 오류 한 줄과 종료 코드 1, 백엔드 없음.
- **R04L-R6** 같은 userData로 띄운 두 번째 실행은 지금과 같다: Electron 잠금에서 걸려 종료 코드 0으로 끝나고, 첫 실행이 `second-instance`를 받아 창을 앞으로 가져온다.

## 인터페이스 / 설계 개요

새 모듈 하나(`apps/desktop/src/data-lock.ts`)와 `main.ts`의 분기 하나가 전부다.

- **잠금의 수단**: 데이터 폴더 안의 파일 `instance.lock`을 Node 내장 `node:sqlite`로 열어 `BEGIN EXCLUSIVE`로 배타 잠금을 얻고, 그 연결을 프로세스가 끝날 때까지 닫지 않는다. SQLite의 파일 잠금은 OS의 잠금이라 프로세스가 죽으면 OS가 푼다. 이미 쥐어져 있으면 기다리지 않고 바로 `SQLITE_BUSY`(오류 번호 5)가 나오며, 이것만 "쥐고 있음"으로 읽는다. 옆에 `instance.lock-journal`이 생길 수 있고 둘 다 내용이 없는 파일이다.
- **모듈의 겉면**: `lockDataDirectory(dir)` 하나. 얻으면 연결을 쥔 값을, 다른 프로세스가 쥐고 있으면 `undefined`를 돌려주고, 그 밖의 실패는 던진다. `main.ts`는 값을 모듈 변수에 붙들어 둔다(가비지 수집으로 닫히면 잠금이 풀린다).
- **시작할 때의 세 갈래**

| 상황 | 걸리는 곳 | 결과 |
|---|---|---|
| 같은 userData로 두 번째 실행 | Electron 잠금 | 종료 코드 0, 첫 창이 앞으로(지금과 같음) |
| 다른 userData, 같은 데이터 폴더 | 데이터 잠금 | 표준 오류 한 줄, 종료 코드 1, 백엔드 없음 |
| 다른 userData, 다른 데이터 폴더(시험) | 없음 | 각자 시작(지금과 같음) |

### 대안과 기각 사유

- **스위치가 있으면 끝내기**: 시험이 쓰는 격리 수단을 잃고, userData를 옮기는 다른 길(Linux의 `XDG_CONFIG_HOME` 등)은 그대로 남는다.
- **PID를 적은 잠금 파일**: 죽은 프로세스의 PID를 다른 프로그램이 다시 쓰면 낡은 잠금을 산 것으로 읽어 시작을 막는다. 낡음을 추정하는 코드가 따로 필요하다.
- **이름 붙은 파이프·소켓**: 두 번째 실행이 첫 창을 깨울 수 있지만, Windows 파이프 이름은 PC 전체가 공유해 다른 사용자가 선점할 수 있고, 소켓 경로 길이 제한과 낡은 소켓 파일 처리가 따라온다.
- **백엔드가 잠금을 쥐기**: 셸의 비밀 저장소도 데이터 폴더에 쓰므로 셸보다 늦고, 백엔드 재시작 때마다 잠금이 잠깐 풀린다.

## 완료 기준 (테스트 가능한 형태)

- **R04L-C1** (R1·R2·R3, 단위) 한 폴더의 데이터 잠금을 쥔 동안 같은 폴더에 `lockDataDirectory`를 다시 부르면 `undefined`가 나오고, 없던 폴더는 만들어진다. → `apps/desktop/src/data-lock.test.ts`
- **R04L-C2** (R3, 단위) 잠금을 쥔 자식 프로세스를 SIGKILL로 죽인 뒤, 잠금 파일이 남아 있는 그 폴더에 `lockDataDirectory`를 부르면 잠금을 얻는다. → 같은 파일
- **R04L-C3** (R2·R4·R6, Electron E2E) 셸이 떠 있을 때 **다른 `--user-data-dir`, 같은 데이터 폴더**로 두 번째 셸을 띄우면 종료 코드 1로 끝나고 표준 오류에 정해진 줄이 있으며, 첫 셸의 백엔드 PID 목록이 그대로다. 같은 시험 안에서 같은 userData의 두 번째 실행은 여전히 0으로 끝난다. → `apps/desktop/e2e/lifecycle.e2e.ts`의 기존 단일 실행 시험에 더한다. 변이 확인 1건: `main.ts`의 데이터 잠금 분기를 지우면 이 시험이 빨개져야 한다(데이터 보호 가드).

R5는 따로 시험을 두지 않는다(던진 오류가 닫힌 쪽으로 끝나는 `main.ts`의 한 갈래이고, 검토에서 코드로 확인한다).

## 미해결 질문 / 검증하지 않은 범위

- **Windows 실행은 확인하지 않았다.** SQLite는 Windows에서 `LockFileEx`를 쓰고 프로세스가 끝나면 풀리는 것이 문서상의 동작이지만, 설치한 앱으로 C3를 Windows 11에서 돌려 본 적이 없다. R04(#13)·H02(#33)의 Windows 확인 항목으로 남긴다.
- 산출물(배포 빌드)에서의 C3는 따로 두지 않았다. `main.ts`의 이 갈래는 원본 실행과 산출물이 같은 코드이고, `node:` 내장 모듈은 번들에서 밖에 둔다(`apps/desktop/build/bundle.ts`).
- 설계 전에 확인한 사실: 이 저장소의 Electron 45.4.1(Node 24.22.3)에서 `node:sqlite`의 `BEGIN EXCLUSIVE`가 두 프로세스 사이에 `SQLITE_BUSY`를 내고, 쥔 쪽을 SIGKILL로 죽이면 바로 다시 얻어진다(macOS, `ELECTRON_RUN_AS_NODE`로 실행). Electron 주 프로세스 안에서의 동작은 C3가 처음 확인한다.

## 잠정 결정과 가정

| 번호 | 결정 | 이유 | 바꾸려면 |
|---|---|---|---|
| D1 | 스위치 거부가 아니라 데이터 폴더의 잠금 | 지키려는 것이 데이터 폴더이므로 거기에 잠근다. userData를 옮기는 모든 길을 한 번에 막고 시험의 격리 수단을 유지한다 | `debugging.ts`처럼 산출물에서 `user-data-dir` 스위치를 거부하는 검사를 더한다(잠금과 함께 둘 수 있다) |
| D2 | 잠금은 셸(`main.ts`)이 쥔다 | 셸이 백엔드보다 먼저 데이터 폴더에 쓰고(비밀 저장소), 백엔드 재시작 사이에도 잠금이 이어진다. `backend/`를 고치지 않는다 | `lockDataDirectory`를 `@pki/storage`로 옮겨 `bootBackend`도 부르게 한다(셸 없는 백엔드까지 막힌다) |
| D3 | 데이터 잠금에 걸린 두 번째 실행은 창을 깨우지 않고, 대화 상자 없이 표준 오류 한 줄과 종료 코드 1로 끝난다 | 스위치를 일부러 준 드문 실행이고, 프로세스 사이 통로를 새로 만들지 않는다. 코드 0이 아닌 것은 "첫 실행에 넘겨졌다"가 아니기 때문이다 | `main.ts`의 그 갈래에서 `dialog.showErrorBox`를 부르거나, 잠금 모듈에 통로를 더한다 |
| D4 | 수단은 `node:sqlite`의 배타 잠금, 파일 이름은 `instance.lock` | Node 표준 라이브러리에는 OS 파일 잠금이 없고, 내장 SQLite가 세 OS의 잠금을 이미 감싸고 있다. 새 의존성이 없고 낡은 잠금을 추정할 코드가 없다 | `data-lock.ts` 안만 바꾼다(겉면은 `lockDataDirectory` 하나) |

가정: 데이터 폴더는 로컬 디스크에 있다. 한 OS 사용자의 두 실행이 같은 경로 문자열이 아닌 다른 이름(심볼릭 링크)으로 같은 폴더를 열어도 잠금 파일은 같은 파일이라 걸린다.
