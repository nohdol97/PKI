# 스펙: I04 후속 — 삭제 장부 재적용이 줄마다 원본을 훑는 비용

- 날짜: 2026-11-23 / 상태: 확정(잠정 결정 포함)
- 관련: 이슈 #123. [I04 spec](2026-11-21-I04-invalidation.md)의 I04-R17(재적용)·I04-R20(보류)·I04-R7(키 있는 해시)과 [I02-B spec](2026-11-22-I02-local-file-import.md)의 후속 F2·남는 위험 8을 잇는다. 두 spec은 고치지 않고 이 문서가 인용한다. 번호는 `F123-…`이다.

| 말 | 뜻 |
|---|---|
| 장부 줄 | 삭제 장부 파일의 한 줄. 인스턴스 ID와 원본 정체의 **키 있는 해시**(I04-R7)로 원본을 가리킨다 |
| 평문 원본 | `sources` 행 가운데 `namespace`·`external_id`가 원래 값인 행(`identity_hashed = 0`) |
| 해시된 행 | 소거된 원본의 행. `namespace`·`external_id` 자리에 해시가 들어 있다(`identity_hashed = 1`) |
| 실행 | 재적용 함수를 한 번 부른 것(시작 한 번, 복원 한 번) |
| 실행 색인 | 이 spec이 더하는 것. 한 실행 동안만 메모리에 두는 "인스턴스 → (해시 → 평문 원본 ID)" 표 |

## 배경

재적용은 장부 줄마다 `ensureSourceByHash`(`storage/src/identity.ts`)로 그 줄의 원본을 찾는다. 해시된 행이 없으면 그 인스턴스의 평문 원본을 **전부** 읽어 하나씩 해시해 견준다. 해시는 한쪽 방향이라 장부 줄에서 평문 정체를 되살릴 수 없기 때문이다. 그래서 시간이 "줄 수 × 원본 수"로 늘고, 모든 위치의 원본을 한 인스턴스에 두는 `local-files`에서 가장 크다. 이 일은 API가 열리기 전에 끝나야 하므로(I04-R17) 그만큼 시작이 늦는다. 전화번호부를 사람 찾을 때마다 첫 장부터 넘기는 것과 같아서, 한 번 넘기며 찾아보기 표를 만들어 두면 된다.

## 목표

- 한 실행에서 평문 원본을 읽고 해시하는 일이 **인스턴스마다 많아야 한 번**이다(줄 수와 무관).
- 줄이 가리키는 원본, 만들어지는 행, 순번·보류·실패 동작은 지금과 한 치도 다르지 않다.

## 비목표

- **스키마와 저장 데이터를 바꾸지 않는다.** 평문 원본의 해시를 열이나 색인으로 저장하지 않는다(마이그레이션 없음, D1).
- 실행 색인을 실행과 실행 사이에 남기지 않는다(파일, 설정 행, 모듈 변수 모두 아님).
- `identityKey`를 한 번만 부르는 다른 자리(`findHashedSourceId`, `ensureTombstoneSource`, `sourceLedgerName`, `tombstone-entry.ts`)는 고치지 않는다. 줄 수에 곱해지는 훑기가 없다.
- 원본이 수백만인 인스턴스의 메모리 상한은 다루지 않는다(남는 위험 1).
- 시간을 재서 통과·실패를 가르는 시험을 두지 않는다. 시간은 PR에 적는 측정이다(F123-R6).
- `storage/src/index.ts`의 내보내기, HTTP 계약, 화면은 고치지 않는다.

## 요구사항

- **F123-R1** `ensureSourceByHash`는 해시된 행이 없을 때 평문 원본을 직접 훑지 않고 실행 색인에서 찾는다. 색인의 한 인스턴스 분량은 그 인스턴스에서 **처음 못 찾았을 때** 한 번 만든다(평문 원본을 한 번 읽고, 키를 한 번 읽어 각각 해시). 해시된 행으로 바로 찾은 줄은 색인을 만들지 않는다.
- **F123-R2** 재적용은 실행마다 빈 실행 색인 하나를 만들어 그 실행의 모든 줄(보류 줄의 재시도 포함)에 넘긴다. 색인은 실행이 끝나거나 줄 하나가 실패해 실행이 멈추면 버린다.
- **F123-R3 (같은 답)** 색인의 해시는 `identityKey(인스턴스, namespace, external_id)`와 **같은 바이트**다(같은 키, 같은 길이 접두 방식, 인스턴스 ID 포함). 찾는 순서도 그대로다: ① 해시된 행 ② 평문 원본 ③ 둘 다 없으면 해시된 자리표시 행을 새로 넣는다(`namespace = external_id = 해시`, `identity_hashed = 1`). 다른 인스턴스의 같은 `namespace`·`external_id`는 맞지 않는다.
- **F123-R4 (실행 중의 변화)** 실행 중에 평문 원본이 해시된 행으로 바뀌거나(삭제 줄의 소거) 자리표시 행이 새로 생겨도, 그 뒤의 줄은 ①에서 같은 원본 ID를 얻는다. 해제 줄만 받은 원본은 평문으로 남고 색인의 항목이 계속 맞다. 색인에 남은 낡은 항목이 ①보다 먼저 쓰이는 일은 없다.
- **F123-R5 (그대로인 것)** 줄 하나가 한 트랜잭션인 것, 순번을 같은 트랜잭션에 적는 것, 보류 목록, 실패한 줄에서 시작이 멈추는 것(I04-R17·R20)은 바뀌지 않는다. 평문 원본이 하나도 없으면 키를 읽지 않는다(지금처럼 키 없는 데이터베이스에서 던지지 않는다). 평문 원본이 있는데 키가 없으면 지금처럼 `IdentityKeyMissingError`다.
- **F123-R6 (측정)** 합성 규모(한 인스턴스의 평문 원본 5만, 장부 줄 1천)로 고치기 전과 뒤의 재적용 시간을 재서 PR 본문에 적는다. 측정 코드는 저장소에 넣지 않는다.

## 인터페이스 / 설계 개요

- `ensureSourceByHash(db, connectorInstanceId, hash, plainIndex?)`: 넷째 인자가 실행 색인(`Map<인스턴스 ID, Map<해시, 원본 ID>>`)이다. 주지 않으면 그 호출만 쓰는 빈 색인으로 같은 길을 탄다(길은 하나, 옛 훑기 코드는 지운다).
- `ledger-reapply.ts`: 실행을 여는 자리(`return (db) => { … }` 안)에서 `new Map()`을 만들어 `applyLine`을 거쳐 넘긴다. 공장 함수(`createLedgerReapply`)나 모듈 수준에 두지 않는다(`reapplyLedger`는 프로세스가 사는 동안 하나다).
- 고치는 파일은 `storage/src/identity.ts`, `knowledge-engine/src/ledger-reapply.ts`와 그 시험 둘이다.

## 완료 기준 (테스트 가능한 형태)

- **F123-C1** (R1·R2, 재적용) 평문 원본 M개인 인스턴스에, 데이터베이스가 모르는 정체를 가리키는 줄 N개가 있는 장부를 재적용할 때, 실행 동안 드라이버가 돌려준 행 수의 합이 줄 수에 곱해지지 않는다(M=300, N=20에서 `3 × M` 미만. 고치기 전은 `M × N` 이상). 시간은 재지 않는다. → `knowledge-engine/src/ledger-reapply.test.ts`. 변이 확인 1건: `ledger-reapply.ts`가 색인을 넘기지 않으면 이 시험이 빨개져야 한다.
- **F123-C2** (R3·R5, 단위) 같은 실행 색인으로 `ensureSourceByHash`를 부를 때: 평문 원본의 `identityKey` 값을 주면 그 원본 ID가, 해시된 행이 있으면 그 ID가, 아무도 아니면 새 자리표시 행의 ID가 나오고 같은 해시를 다시 주면 행이 늘지 않고 같은 ID다. 다른 인스턴스의 같은 정체는 맞지 않는다. 평문 원본이 없는 인스턴스는 키가 없어도 던지지 않는다. → `storage/src/identity.test.ts`
- **F123-C3** (R4, 단위) 색인이 만들어진 뒤 평문 원본이 `hashSourceIdentity`로 해시되면, 같은 색인으로 같은 해시를 찾을 때 같은 원본 ID가 나오고 행이 새로 생기지 않는다. → `storage/src/identity.test.ts`

R5의 나머지(트랜잭션·순번·보류·실패)는 새 시험을 두지 않는다. `ledger-reapply.test.ts`의 기존 시험(순서, 같은 원본의 해제와 삭제, 실패한 줄, I04-R20의 C5~C10)이 고치지 않은 채 통과하는 것이 기준이다.

## 잠정 결정과 가정

| 번호 | 결정 | 이유 | 바꾸려면 |
|---|---|---|---|
| D1 | 메모리의 실행 색인. 스키마는 그대로 | 해시 열을 저장하면 사용자 데이터 마이그레이션이 생기고, 원본을 넣고 고치는 모든 길이 그 열을 맞춰야 한다. 재적용은 시작에 한 번이다 | 측정에서 색인을 만드는 한 번의 훑기 자체가 문제면 `sources`에 해시 열과 색인을 더하는 별도 spec(마이그레이션, 사용자 확인 대상) |
| D2 | 색인을 `ensureSourceByHash`의 선택 인자로, 형은 이름 없는 `Map` | 새 내보내기가 없어 다른 작업이 고치는 `storage/src/index.ts`와 부딪치지 않는다 | 형에 이름을 붙여 내보내거나, 색인을 쥔 함수를 만드는 공장으로 바꾼다(동작 같음) |
| D3 | 색인은 처음 못 찾았을 때 만든다 | 흔한 시작(줄이 없거나 모두 해시된 행을 가리킴)은 지금처럼 훑기도 키 읽기도 없다 | 실행 처음에 미리 만들도록 옮긴다 |
| D4 | 완료 기준은 시간 대신 읽은 행 수 | 부하에 따라 흔들리지 않고, 드라이버의 SQL 문장에 묶이지 않는다 | 상한(`3 × M`)은 시험 상수다 |

가정: 재적용 실행 중에 평문 원본을 새로 넣거나 `sources` 행을 지우는 길은 없다(제품 코드에 `DELETE FROM sources`가 없고, 실행 중의 `sources` 쓰기는 자리표시 행 넣기와 소거의 해시뿐이다. 2026-11-23 코드로 확인).

## 남는 위험 / 검증하지 않은 범위

1. **메모리.** 색인은 못 찾은 줄이 있는 인스턴스의 평문 원본 수만큼 항목을 쥔다(항목 하나에 64자 해시와 숫자, 5만에 10 MB 안팎으로 추정, 재지 않음). 원본이 수백만이면 수백 MB가 될 수 있다. 측정(R6) 때 메모리도 함께 적는다.
2. **한 번의 훑기는 남는다.** 못 찾은 줄이 하나라도 있으면 그 인스턴스의 평문 원본 전부를 한 번 해시한다. 원본 수에 비례하는 이 시간이 얼마인지는 R6의 측정으로만 안다.
3. **Windows와 실제 복원본으로는 재지 않는다.** 측정은 합성 데이터와 개발 PC다. 실제 백업으로 하는 검증은 H01-C2의 몫이다.
