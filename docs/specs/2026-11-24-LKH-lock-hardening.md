# 스펙: 잠금 견고화 묶음(LKH) — 읽기 전용 잠금 파일에서도 잠금이 진짜이게

- 날짜: 2026-11-24 / 상태: 확정(잠정 결정 D1~D7 포함)
- 관련: 이슈 #304(백엔드 잠금 검토의 남은 지적), #198(데이터 폴더 잠금 검토의 남은 지적). [R04 잠금 spec](2026-11-23-R04-data-dir-lock.md), [P7 후속 묶음 spec](2026-11-24-P7-followups.md), [H02 공용 spec](2026-11-24-H02-common.md)(H02A-R7)
- 번호: 요구사항 `LKH-R<n>`, 완료 기준 `LKH-C<n>`, 결정 `LKH-D<n>`, 작업 `LKH-T<n>`

| 말 | 뜻 |
|---|---|
| 셸 잠금 | 셸(Electron 쪽)이 데이터 폴더의 `instance.lock`에 쥐는 잠금(R04L). 한 폴더에 셸이 하나임을 보장하고, 데이터 지우기(H02A-R7)도 이 잠금을 얻어야만 지운다 |
| 백엔드 잠금 | 백엔드가 `backend.lock`에 쥐는 잠금(P7F-R1). 이것을 쥔 시작만 남은 `running` 작업을 바로 회수한다 |
| 쓰기 시도 | 이 spec이 더하는 것. 잠금을 얻었다고 답하기 전에 잠금 파일에 실제로 한 번 써 보는 것 |

## 배경

두 잠금은 같은 수단을 쓴다: 잠금 파일을 `node:sqlite`로 열고 `BEGIN EXCLUSIVE`가 성공하면 "얻었다"고 답한다. 그런데 **잠금 파일이 읽기 전용이면** SQLite는 파일을 조용히 읽기 전용으로 열고, 이때 `BEGIN EXCLUSIVE`는 배타 잠금 없이 성공한다. 그래서 몇 번을 불러도 모두 "얻었다"가 된다. 임시 폴더에서 다시 확인했다(권한 0444인 파일에 연결 둘이 모두 성공, 그 안에서 쓰기를 하면 `SQLITE_READONLY`(오류 번호 8)로 실패. 쓸 수 있는 파일에서는 쓰기 뒤에도 두 번째 연결이 `SQLITE_BUSY`(5)이고, 쥔 프로세스를 강제 종료한 뒤 다음 시도가 다시 얻는다).

코드에서 닿는 결과:

- **셸**(`apps/desktop/src/data-lock.ts:23`): `instance.lock`이 읽기 전용이면 다른 userData로 띄운 두 번째 셸이 잠금을 "얻어" 한 폴더에 셸과 백엔드가 둘 뜬다(R04L-R2 위반). 더 크게는 데이터 지우기가 `input.lock(dir)`의 답만 믿고 폴더를 지우므로(`apps/desktop/src/data-removal.ts:59-72`), **PKI가 켜져 있는 동안 데이터 폴더가 지워진다**(H02A-R7 ③ 위반).
- **백엔드**(`backend/src/backend-lock.ts:25`): `backend.lock`이 읽기 전용이면 살아 있는 다른 백엔드가 있어도 시작이 잠금을 "얻어" 그 백엔드의 실행 중 작업을 회수한다. 작업 한 건이 두 번 실행된다(임대 토큰이 옛 실행의 쓰기를 거절하므로 결과가 두 번 쓰이지는 않는다).

## 목표

1. 잠금 파일에 쓸 수 없으면 두 잠금 모두 "얻지 못함"이다. 셸은 닫힌 쪽으로 끝나고, 데이터 지우기는 아무것도 지우지 않고, 백엔드는 회수하지 않는다.
2. 잠금은 호출한 쪽이 값을 붙들고 있는지와 상관없이 닫을 때나 프로세스가 끝날 때까지 유지된다.
3. 데이터 폴더 위치를 정하지 못하면 셸의 시작과 제거 호출이 정해진 한 줄과 종료 코드 1로 끝난다.

## 비목표

- **읽기 전용 잠금 파일을 제품이 고치지 않는다.** 속성을 바꾸거나 파일을 지우고 다시 만들지 않는다(D2).
- **F2·F6·N2·F4, 복원 표식 재설계.** 위 표의 사유대로 이슈에 둔다.
- **잠금 없이도 백엔드가 시작하는 동작(P7F-D2), 잠금 파일 이름, 사용자 데이터의 이동·마이그레이션**을 바꾸지 않는다.
- **두 잠금 모듈을 하나로 합치지 않는다**(D4). `backend/src/boot.ts`는 고치지 않는다(D5).
- **Windows 실측**, 시험 보강만인 항목(F5·N4), `apps/web`, Wiki·Reflection·Lint, 느린 정규화기 시험.

## 요구사항

- **LKH-R1 셸 잠금은 써 봐야 얻은 것이다.** `lockDataDirectory`는 배타 트랜잭션 안에서 잠금 파일에 쓰기를 한 번 시도한다. 쓰기가 실패하면 연결을 닫고 **던진다**(얻은 값도 `undefined`도 아니다). 그러면 지금 있는 호출부가 닫힌 쪽으로 간다: 셸의 시작은 표준 오류 한 줄과 종료 코드 1(R04L-R5), 데이터 지우기는 `nothing was removed`와 종료 코드 1(H02A-R7). 쓸 수 있는 파일에서의 동작(얻음, 다른 프로세스가 쥐면 `undefined`, 강제 종료 뒤 다시 얻음)은 그대로다.
- **LKH-R2 백엔드 잠금도 같다.** `takeBackendLock`은 같은 쓰기 시도를 하고, 실패하면 `undefined`를 돌려주며 지금의 고정 로그 한 줄(`backend-lock-unavailable`)을 남긴다. 시작은 계속하고 회수만 하지 않는다(P7F-R1 그대로).
- **LKH-R3 잠금의 수명.** 두 잠금 모듈은 얻은 연결을 모듈 안에서 강하게 붙든다. 돌려준 값을 호출부가 버리거나 가비지 수집이 돌아도 잠금은 `close()`나 프로세스 종료 전에는 풀리지 않는다. `close()`는 붙든 것을 놓는다.
- **LKH-R4 데이터 폴더 위치를 못 정할 때.** 위치 계산(`dataDir ?? dataDirectory()`)이 던지면 ① 셸의 시작은 잠금을 시도하지 않고 표준 오류 한 줄과 종료 코드 1로 끝난다(창·백엔드·비밀 저장소 없음). ② 제거 호출은 `delete`이면 `nothing was removed`가 든 한 줄과 종료 코드 1, `keep`이면 지금처럼 자동 시작만 끄고 0이다. 어느 쪽도 잡히지 않은 오류로 끝나지 않는다.
- **LKH-R5 문서.** `docs/site-setup.md` S46의 "데이터 잠금의 Windows 동작"에 확인할 것 둘을 더한다: 읽기 전용 속성이 붙은 잠금 파일에서 시작과 지우기가 거절되는지, 충돌 직후 다시 띄울 때 잠금이 늦게 풀리는지(N3). 두 잠금 모듈의 머리 주석을 R1~R3에 맞춘다.

## 인터페이스 / 설계 개요

- **R1·R2 쓰기 시도**: `BEGIN EXCLUSIVE` 바로 뒤, 같은 연결에서 `PRAGMA user_version = 1`. 커밋하지 않으므로 닫히거나 프로세스가 죽으면 되돌려지고 잠금 파일은 빈 파일로 남는다(확인함: 닫은 뒤 크기 0, 강제 종료 뒤 `-journal`이 남아도 다음 시도가 얻는다). `SQLITE_BUSY`(5)만 "다른 프로세스가 쥠"으로 읽는 규칙은 그대로이고, 쓰기 실패(8 등)는 "그 밖의 실패" 갈래로 간다.
- **R3**: 각 모듈에 모듈 수준 `Set` 하나. 얻을 때 넣고 `close()`에서 뺀다. `boot.ts`의 WeakMap은 "이 시작의 잠금을 찾는" 용도로 그대로 둔다.
- **R4**: 판단을 Electron 없이 시험할 수 있는 자리로 옮긴다. `data-lock.ts`에 위치 계산과 잠금을 한 번에 하는 함수(`openDataFolder(resolve)`: 얻으면 `{ dir, lock }`, 아니면 표준 오류에 쓸 한 줄)를 두고 `main.ts`의 `takeDataLock`과 모듈 맨 위의 `dataPath` 계산이 이것을 쓴다. `removeUserData`의 `dir`은 값이 아니라 `() => string`으로 받아 `keep` 판정 뒤에 try 안에서 부른다.

| 상황 | 셸의 시작 | 데이터 지우기(`delete`) | 백엔드의 시작 |
|---|---|---|---|
| 잠금 파일에 쓸 수 있고 아무도 안 쥠 | 얻음 | 얻고 지움 | 얻고 회수 |
| 다른 살아 있는 프로세스가 쥠 | `undefined` → 종료 코드 1(지금과 같음) | 거절(지금과 같음) | `undefined` → 회수 안 함(지금과 같음) |
| **잠금 파일에 쓸 수 없음** | **던짐 → 한 줄, 종료 코드 1** | **거절, 아무것도 안 지움** | **`undefined` + 로그 → 회수 안 함** |

그림은 넣지 않는다(잠금 함수 안에 갈래 하나가 더해질 뿐이고 위 표가 그 전부다).

## 잠정 결정

바꾸려면 적힌 자리 하나를 고치면 된다.

- **LKH-D1 쓰기 시도는 `PRAGMA user_version = 1`이고 커밋하지 않는다.** 쓰기 권한을 미리 묻는 방법(`access`)은 묻는 때와 잠그는 때 사이가 비고 Windows의 속성을 믿을 수 없어 쓰지 않는다. 다른 쓰기로 바꾸려면 두 모듈의 그 한 줄을 고친다.
- **LKH-D2 읽기 전용 잠금 파일이면 셸은 시작하지 않고, 제품이 파일을 고치지 않는다.** 쓰기 권한 없음은 R04L-R5가 이미 닫힌 쪽으로 정한 경우이고, 남의 파일 속성을 바꾸거나 지우는 것은 잠금보다 위험하다. 사용자는 파일 속성을 풀거나 잠금 파일을 지우면 된다(둘 다 빈 파일이다). 제품이 스스로 풀게 하려면 `lockDataDirectory`의 실패 갈래에 그 시도를 넣는다.
- **LKH-D3 백엔드는 읽기 전용이어도 시작한다.** P7F-D2를 바꾸지 않는다. 회수만 임대 만료로 미뤄진다.
- **LKH-D4 두 잠금 모듈은 합치지 않는다(P7F-D6 유지).** `node:sqlite`를 직접 여는 파일은 저장소에서 이 둘뿐이고 `@pki/storage`는 드라이버를 직접 열지 않는다. 합치려면 공용 자리를 정하는 일이 먼저다(후속).
- **LKH-D5 강한 참조는 잠금 모듈 안에 둔다.** 호출부(`boot.ts`, `main.ts`)가 붙들게 하는 약속은 문서로만 지켜졌다(N5). 그래서 `boot.ts`는 한 줄도 고치지 않는다.
- **LKH-D6 N1은 판단을 `data-lock.ts`와 `removeUserData`로 옮겨 고친다.** `main.ts`는 Electron 없이 시험할 수 없어 그 안에서 try만 넓히면 지키는 시험이 없다. `keep`은 폴더 위치가 필요 없으므로 위치를 못 정해도 0이다. `main.ts`만 고치는 쪽으로 가려면 C5를 지우고 e2e를 Windows에서 돌려야 한다.
- **LKH-D7 F2·F6·N2·F4는 이번에 고치지 않는다.** 사유는 배경의 표. 다시 꺼낼 때의 출발점: F2는 "모든 백엔드가 공유 잠금을 쥐고, 시작 때 배타로 바꿔 보는 것이 되면 회수"하는 모델, N2는 utility process의 부모 끊김 실측.

## 미검증 범위

- **Windows**: 읽기 전용 속성이 붙은 잠금 파일에서 SQLite가 같은 식으로 여는지, 죽은 프로세스의 잠금이 늦게 풀리는지(N3), 강제 종료. S46·S19에서 확인한다. 이 묶음의 시험은 POSIX 권한(0444)으로만 본다.
- 배경의 재확인은 개발 PC의 Node(v26)로 직접 실행한 것이다. 저장소가 고정한 Node 24에서는 C1~C3의 시험이 처음으로 확인한다.
- 쥔 프로세스가 **쓸 수 있을 때** 잠금을 얻은 뒤에 파일이 읽기 전용으로 바뀐 경우는 재현하지 않았다(R1·R2 뒤에는 새로 오는 쪽이 쓰기 시도에서 걸리므로 결과는 같아야 한다).
- 셸만 죽었을 때 Electron이 백엔드를 함께 끝내는지(N2), 네트워크·동기화 폴더에서의 파일 잠금(R04L 비목표 그대로).
- 제품 기본 임대(2분)에서의 재개 시간 재측정(#304 미측정).
