# 평가 기준: 지식 품질 측정 방법과 통과 기준

- 작성일: 2026-11-21 / 상태: **잠정** (수치는 측정 전에 고정한 제품 결정이며, 변경은 측정 전 PR로만 한다)
- 근거: [원 설계](design/original-design.md) §18, [R05 spec](specs/2026-11-21-R05-golden-dataset.md) (R05-R9, 완료 기준 R05-C3), 데이터셋 [eval/golden/README.md](../eval/golden/README.md)

## 0. 먼저 밝혀 둘 것

- **이 문서의 어떤 수치도 측정값이 아니다.** 제품, 엔진, 임베딩 모델, LLM은 한 번도 실행되지 않았다. 아래 숫자는 "이 정도면 쓸 만하다"고 **미리** 정한 통과선이다.
- 측정은 **배포처 환경**(Windows 11 실기, 실제 CLI Provider와 임베딩 모델이 있는 곳)에서 한다. 이 저장소의 CI나 macOS 개발 기기에서 나온 숫자는 기준표를 채우는 근거로 쓰지 않는다.
- 통과선을 **결과를 본 뒤에** 바꾸면 기준이 결과에 맞춰진다. 그래서 변경은 측정 전에 PR로 올려 사람이 승인한 것만 인정한다. 결과를 본 뒤 바꾸고 싶다면 바꾼 이유와 "측정 후 변경"이라는 표시를 결과 보고에 함께 적는다.
- 지금 `eval/scorer/score.py`가 계산하는 것은 6개(Recall@K, Precision@K, MRR, 관계 precision/recall, 엔티티 해소 pairwise F1, citation accuracy)뿐이다. 나머지 지표는 정의만 있고 계산 코드가 없다. 표에 **자동(scorer)**, **자동(미구현)**, **사람 평가**로 구분해 두었다.

## 1. 평가에 쓰는 데이터

| 구분 | 인스턴스 | 레코드 id | 답변 가능 질문 | 용도 |
|---|---|---|---|---|
| dev | 22 | 82 | 23 | 개발·튜닝·**ablation 단계 선택**·원인 분석 |
| eval(봉인) | 18 | 65 | 17 | C5 최종 판정에 **한 번만** 사용 |

eval 안의 판정 분모는 작다. 답변 가능 질문 17개, 엔티티 쌍 22개(같음 14, 다름 8), 관계 20개(연결해야 함 14, 연결하면 안 됨 6), 상충 쌍 3개, 중복 묶음 2개, 기대 Insight 5개(추론 3, 명시 2)와 만들면 안 되는 Insight 3개, 삭제로 사라져야 할 사실 2개와 권한 철회로 제한될 사실 1개이다. 그래서 **비율 통과선은 §4에서 eval 위의 개수("0 of 8")로 다시 적었다.** 시나리오별 하위 집합은 eval에서 질문이 1~2개뿐이라 판정에 쓰지 않고 dev에서 원인 분석용으로만 쓴다. 봉인은 공개 저장소이므로 관례일 뿐 비밀이 아니다. 정답은 생성자가 만들었고 독립 검토 전이다(§6).

## 2. 지표 정의

기호: `G`는 정답(gold) 집합, `P`는 예측(prediction) 집합, `Q`는 평가할 질문 집합, `rel(q)`는 질문 q의 정답 근거 레코드 집합(`labels/qa.jsonl`의 `evidence`의 `record_id`), `rank_q`는 q에 대한 순위 목록(같은 레코드가 여러 번 나오면 첫 번째만 센다).

### 2.0 모든 지표에 공통인 규칙

1. **정답은 시나리오가 드러내려는 항목만 담은 것이지 전수가 아니다.** 예컨대 eval 엔티티는 46개이고 사람·팀·부수 프로젝트의 상당수는 라벨이 없다. 그래서 정밀도(precision) 계열 지표(엔티티, 관계, Insight, Source Attribution)는 **라벨이 붙은 항목에 닿는 예측만** 센다. 예측이 "닿는다"는 것은 그 예측의 엔티티가 라벨이 있는 엔티티에 정렬되거나(§6), 인용한 레코드가 해당 인스턴스 정답의 evidence 레코드에 속한다는 뜻이다. 닿지 않는 예측은 정밀도에 넣지 않고 **`unjudged`로 개수를 따로 보고**한다(판정 어댑터가 `judged: false`로 표시하며 `score.py`는 관계 예측에서 이를 따로 센다). unjudged가 전체 예측의 대부분이면 정밀도 숫자만으로 결론 내리지 않고 표본 검토를 붙인다. 재현율(recall) 계열은 영향이 없다.
2. **인용은 `(질문, record_id, version)` 단위로 한 번만 센다.** 같은 질문에서 같은 인용을 여러 번 내도 분자와 분모에 한 번씩이다(점수 부풀리기 방지).
3. **대칭 관계**(`CONTRADICTS`, `RELATED_TO`)는 방향을 구분하지 않는다. 나머지 관계는 방향과 타입이 모두 맞아야 일치한다.
4. **엔티티 일치는 일대일이다.** 예측 엔티티 하나는 정답 엔티티 하나에만, 정답 엔티티 하나는 예측 엔티티 하나에만 대응한다(IoU가 큰 쌍부터 탐욕적으로 배정). 한 정답 엔티티가 여러 span으로 나오면 그중 하나만 겹쳐도 후보이다.
5. **시간 사실 표기.** `attribute`는 `eval/scorer/validate.py`의 통제 어휘(`FACT_ATTRIBUTES`)만 쓴다. `start_instant`, `due_instant`, `submit_instant`의 값은 UTC(`...Z`)이고, 날짜만 있는 값은 일 단위로 비교한다. `valid_from`은 "원문이 시작을 말하면 그 시점, 말하지 않으면 근거 레코드의 `created_at`을 UTC로 바꾼 날", `valid_until`은 "원문이 끝을 말하거나 원문이 삭제된 날, 없으면 null"이다. `valid_from`이 null인 것은 "끝만 알려진 사실"에 한한다.

### 2.1 Knowledge Evaluation

| 지표 | 정확한 식 | 방식 |
|---|---|---|
| Entity Extraction Accuracy | 예측 엔티티가 정답 엔티티와 일치 = 타입이 같고, 예측 span과 해당 정답 엔티티의 evidence span 중 하나가 같은 `(record_id, version)`에서 겹침 비율(IoU) ≥ 0.5. `P = TP/\|P_judged\|`, `R = TP/\|G\|`, `F1 = 2PR/(P+R)` (§2.0의 1·4) | 자동(미구현) |
| Entity Resolution Accuracy | `labels/resolution_pairs.jsonl`의 각 쌍을 "같은 엔티티인가"로 이진 판정. 양성 = 같음. `P = TP/(TP+FP)`, `R = TP/(TP+FN)`, `F1 = 2PR/(P+R)`. 예측이 없는 쌍은 "같지 않음". 별도 보고: `false_merge_rate = FP / (정답이 "다름"인 쌍 수)` | 자동(scorer) |
| Relationship Precision / Recall | 정답 삼중항 `(subject, relation, object)`은 `relations.jsonl`에서 `expected: true`. 예측 삼중항의 엔티티는 정답 엔티티 id로 표기한다(정렬은 §6). `P = \|P∩G\|/\|P_judged\|`, `R = \|P∩G\|/\|G\|`. 타입이 다르면 불일치(§2.0의 3). 별도 보고: `forbidden_rate = \|P∩F\| / \|F\|` (`F` = `expected: false` 삼중항, 즉 연결하면 안 되는 방해 쌍) | 자동(scorer) |
| Semantic Definition Accuracy | 약어·개념 항목(`Concept`)에 제품이 낸 정의를 사람 2명이 원문과 대조해 정확/부정확로 판정. `정확한 정의 수 / 평가한 정의 수` | 사람 평가 |
| Temporal Fact Accuracy | `temporal_facts.jsonl`의 각 사실에서 `(subject, attribute, value, valid_from, valid_until, expected_status)`가 모두 일치하면 1(표기 규칙은 §2.0의 5). `일치한 사실 수 / 정답 사실 수` | 자동(미구현) |
| Source Attribution | 제품이 주장(관계, 사실, Insight)에 붙인 근거 span이 정답 evidence span과 같은 `(record_id, version)`에서 정답 span 길이의 50% 이상 겹치면 맞음. `precision = 맞은 근거 수 / 낸 근거 수`, `recall = 덮은 정답 근거 수 / 정답 근거 수` | 자동(미구현) |
| Contradiction Detection | 정답 = `CONTRADICTS` 관계와 `expected_status: disputed`인 사실 쌍. 제품이 "상충"으로 표시한 쌍의 `P`, `R`, `F1` | 자동(미구현) |
| Knowledge Consolidation Quality | `duplicate_threads` 시나리오에서 중복 묶음 하나가 지식 항목 정확히 1개로 합쳐진 비율 = `합쳐진 묶음 수 / 묶음 수`. 동시에 `false_merge_rate`(근접 중복인데 다른 값을 합친 경우)를 본다 | 자동(미구현) |
| Knowledge Lint Accuracy | lint가 보고한 문제(상충, 오래된 사실, 중복)를 정답(상충 사실, `superseded`로 남아야 할 사실, 중복 묶음)과 비교한 `P`, `R` | 자동(미구현) |
| Deletion Propagation | `expected_status: removed`인 사실 중 삭제 후 제품 상태에서 사라진 비율. 다른 출처가 지지하는 사실(`S06-I2`)이 **남아 있는지**도 함께 확인(과삭제 검사) | 자동(미구현) |
| Access Leak | `expected_status: restricted`이거나 `answerable: false`이고 `viewer`가 있는 질문에서, 해당 viewer에게 답이나 인용으로 나온 금지 근거의 개수. 0이어야 한다 | 자동(미구현) |

### 2.2 Insight Evaluation

정답 Insight와의 일치 = 같은 `insight_type`이고, 정답 evidence의 `record_id`를 1개 이상 인용하며, `affected_entities`가 하나 이상 겹침. `expected: false`인 정답(만들어지면 안 되는 Insight)에 일치하면 오탐이다.

| 지표 | 정확한 식 | 방식 |
|---|---|---|
| Insight Recall | `일치한 정답(expected: true) / 정답(expected: true) 수` | 자동(미구현) |
| False Positive Rate | `(정답에 일치하지 않는 예측 + expected:false에 일치한 예측) / 판정 대상 예측 Insight 수`. 판정 대상은 라벨이 있는 인스턴스의 레코드를 인용한 예측이고 나머지는 `unjudged`로 따로 센다(§2.0의 1) | 자동(미구현) |
| Faithfulness | 예측 Insight 중 ① 모든 `evidence_refs`가 실제 span으로 풀리고 ② 요약이 그 span들이 말하는 범위를 넘지 않으며 ③ `is_inference`가 정답과 같은 것의 비율 | ①③ 자동(미구현), ② 사람 평가 |
| Relevance | 사람 평가자 2명이 "이 사용자의 업무에 관련 있는가"를 1~5점으로 채점한 평균 | 사람 평가 |
| Novelty | "원본 하나만 읽어서는 알기 어려운가"를 1~5점으로 채점한 평균 | 사람 평가 |
| Actionability | "무엇을 해야 하는지 알 수 있는가"를 1~5점으로 채점한 평균 | 사람 평가 |
| Importance Ranking | 사람이 매긴 중요도(0~3)를 정답으로 상위 3개의 `nDCG@3 = DCG@3 / IDCG@3`, `DCG@3 = Σ(2^rel_i − 1)/log2(i+1)` | 사람 평가 + 자동 |
| Duplicate Notification Rate | 같은 근거로 이미 알린 Insight를 새 근거 없이 다시 알린 알림 수 / 전체 알림 수. 같은 입력을 재수집(`duplicate_threads`)시킨 재생 실험으로 측정 | 자동(미구현) |

사람 평가는 평가자 2명이 독립으로 채점하고, 일치도(Cohen's κ, 점수를 높음/낮음으로 이진화해 계산)가 0.6 미만이면 평가표를 고쳐 다시 채점한다. 그 상태의 평균은 통과 판정에 쓰지 않는다.

### 2.3 Retrieval Evaluation

`K`의 기본값은 5이고 10도 함께 보고한다. 지표는 질문별로 계산해 **질문 평균**을 낸다. 대상은 `answerable: true`인 질문이다.

| 지표 | 정확한 식 |
|---|---|
| Recall@K | `\|rel(q) ∩ top_K(rank_q)\| / \|rel(q)\|` |
| Precision@K | `\|rel(q) ∩ top_K(rank_q)\| / K` (결과가 K개보다 적어도 K로 나눈다. 짧은 목록에 보상하지 않는다) |
| MRR | `1 / (rel(q)에 속하는 첫 레코드의 순위)`. 없으면 0 |
| Answer Groundedness | 제품 답변을 원자적 주장으로 쪼갠 뒤, 인용한 span이 그 주장을 뒷받침하는 비율. `뒷받침된 주장 수 / 전체 주장 수` (사람 2명이 판정, 이후 자동 판정기를 쓰려면 사람 판정과의 일치도를 먼저 보고) |
| Citation Accuracy | `맞는 인용 수 / 제품이 낸 인용 수`(질문별로 중복 제거, §2.0의 2). 인용은 `(record_id, version)` 쌍이고, 그 질문의 정답 evidence 쌍과 같으면 맞다. 답할 수 없는 질문(`answerable: false`)에 낸 인용은 전부 틀린 인용이다. 별도 보고: `citation_recall = 덮은 정답 쌍 수 / 정답 쌍 수`, `forbidden_citations`(금지 근거를 인용한 횟수) |

Recall@K는 정답 근거가 1~3개인 이 데이터에서 "필요한 원문을 찾았는가"를, Precision@K는 "찾은 것 중 쓸모 있는 비율"을, MRR은 "첫 번째 정답이 얼마나 위에 있는가"를 본다. 정답 근거가 평균 1.8개이므로 eval의 Precision@5 상한은 약 0.36이다.

| 장시간 실행 안정성 | 72시간 연속 가동에서 충돌 횟수와 RSS 증가율(1시간째 대비 72시간째) |

## 3. Ablation: 구성 5개와 유지 조건

설계 §18은 다음 5개 구성을 비교해 Semantic과 Graph가 **실제로** 품질을 올리는지 보라고 한다. 올리지 못하면 제거하거나 단순화한다.

| 구성 | 이름 | 추가되는 것 | 이 단계가 하는 일 |
|---|---|---|---|
| C1 | Keyword | 어휘 검색 | 기준선. 검색 지표(Recall@K, Precision@K, MRR, citation)만 낸다. 관계·엔티티 해소·시간 사실 지표는 이 구성이 만들지 않으므로 "없음"이다 |
| C2 | Keyword + Vector | 임베딩 검색 | 어휘가 다르게 표현된 같은 개념(`mixed_ko_en_same_concept`, `abbreviation_two_meanings`)에서 C1이 놓친 근거를 찾는다 |
| C3 | + Graph | 엔티티·관계 그래프 | 여러 문서를 거치는 질의(`schedule_dependency_delay`)와 동명이인·방해 쌍을 다루고, 관계 지표와 엔티티 해소 지표를 처음 낸다 |
| C4 | + Semantic | 용어·개념·약어·사실 유효기간 층 | 약어 다의성, 정정·대체 질의를 다루고, 시간 사실 지표를 처음 낸다 |
| C5 | + Wiki | Knowledge Wiki를 포함한 종합 검색 | 답변 groundedness와 citation recall을 올리되 **Wiki 페이지가 아닌 원문 span을 인용**해야 한다(Wiki는 재생성 가능한 투영이다) |

### 3.1 단계 선택은 dev에서, eval은 C5 최종 판정에 한 번만

C2~C4를 남길지 버릴지는 **dev 분할에서만** 정한다. 봉인된 eval은 선택이 끝난 뒤 최종 구성(C5 또는 단순화된 구성)에 대해 **한 번만** 돌려 §4로 판정한다. eval 결과를 보고 단계를 다시 고르거나 통과선을 바꾸면 그것은 "eval을 튜닝에 썼다"는 뜻이므로 결과 보고에 그 횟수를 밝히고 판정은 무효로 본다. 단계 선택은 검색 지연과 방해 문서의 영향이 보이도록 코퍼스 단계 **T1**(§5)에서 한다. T0 결과는 함께 보고한다.

### 3.2 단계별 유지 규칙 (dev, 직전 단계와 같은 질문으로 비교)

C(k)를 C(k−1)와 비교한다. 아래 A, B, C를 모두 만족해야 유지한다.

- **A. 이득.** 아래 둘 중 하나.
  1. *검색 이득*: dev 답변 가능 질문 23개에서 Recall@5 평균 또는 MRR 평균이 **+0.02 이상** 높고, 더 나아진 질문 수에서 나빠진 질문 수를 뺀 값이 **+1 이상**.
  2. *자기 층 이득*(C3, C4만): 이 단계가 처음 내는 지표가 §4의 해당 통과선을 **dev 분모로** 충족하고(C3: 관계 precision·recall, 엔티티 해소 F1·false merge. C4: 시간 사실 정확도), 검색 지표(Recall@5, MRR)가 직전 단계보다 **0.02를 넘어 나빠지지 않는다**.
- **B. 무회귀.** citation accuracy가 직전 단계보다 −0.02보다 더 떨어지지 않고, `forbidden_citations`는 0을 유지하며, 직전에 같은 지표를 낸 단계가 있으면 그 단계보다 `false_merge_rate`가 오르지 않는다(처음 내는 단계는 §4 통과선과 비교).
- **C. 비용 상한.** 검색 p95가 직전 단계의 2배 이하이고 §4.4의 절대 상한 이하이며, 파생 저장 공간과 LLM 호출 횟수가 §4.4 예산 안에 있다.

**여러 단계가 함께 남을 수 있는 산술.** 질문 하나가 0에서 1로 바뀌면 평균은 `1/23 = 0.043` 오르므로 "+0.02, 순증 +1" 조건은 질문 하나의 순이득이면 충족된다. 아무 튜닝 없는 문자 bigram TF-IDF 순위기를 리뷰어가 dev에 돌려 본 점검(제품 측정이 아니라 데이터의 변별력 점검이다)에서 dev 23개 중 6개가 전체 재현을 못 했다. 즉 어휘 기준선에도 개선 여지가 질문 6개 분량 있어 세 단계가 각각 순이득 +1 이상을 내는 것(합 +3 ≤ 6)이 산술적으로 가능하다. 실제 키워드 엔진은 이 숫자와 다를 수 있다. 직전의 "eval 11개에서 단계마다 +2"는 질문 11개 중 개선 여지가 3개뿐이라 세 단계 중 하나만 남도록 구조적으로 정해져 있어 폐기했다.

하나라도 어기면 그 단계는 **제거하거나 단순화**하고, 단순화한 구성에 같은 규칙을 한 번 더 적용한다. 단계별 시나리오 하위 집합(예: 그래프는 `schedule_dependency_delay`)은 dev에서 이득의 원인을 설명하는 진단 자료로만 쓰고 유지 여부 판정에는 쓰지 않는다. 데이터가 커지면 질문 단위 부트스트랩 신뢰구간 하한 > 0 규칙으로 바꾼다(측정 전 PR로).

## 4. 통과선 (잠정 — 변경은 측정 전 PR로만)

판정은 **최종 구성, eval 분할, 한 번**에 적용한다. dev 결과는 보고하되 판정하지 않는다. "하드"는 한 번이라도 어기면 다른 지표와 무관하게 불합격인 항목이다. 분모가 작은 비율은 **eval 위의 개수**로 적고 분모를 보인다. "판정 보류"는 정답 라벨이나 채점표가 아직 없어 측정해도 통과를 가를 수 없는 항목이며, 보류가 풀리기 전에는 통과 판정에서 제외하되 결과 보고에 "판정 못 함"으로 남긴다.

### 4.1 Retrieval

검색 통과선은 **코퍼스 T1과 T2**(방해 문서가 있는 단계, §5)에서 판정한다. T0는 변별력이 낮다. 아무 튜닝 없는 문자 bigram TF-IDF 순위기를 리뷰어가 (개정 전 eval 11개 질문에) 돌려 본 점검에서 Recall@5 0.864, MRR 0.909로, 아래 절대 통과선(0.80, 0.70)을 이미 넘었다. 제품 측정이 아니라 데이터의 변별력 점검이며, 그래서 통과선을 T0에서 판정하지 않고 같은 실행의 C1 기준선보다 더 나아야 한다는 조건을 붙였다.

| 지표 | 통과선 (eval 17개 질문) | 한 줄 근거 |
|---|---|---|
| Recall@5 | ≥ 0.80 이고 같은 실행·같은 코퍼스 단계의 C1보다 **+0.05 이상** | 필요한 원문 5건 중 4건은 상위 5개에 있어야 한다. 기준선과의 격차는 "단순 어휘 검색으로도 되는 것"을 성과로 세지 않기 위해 |
| MRR | ≥ 0.70 이고 C1보다 **+0.05 이상** | 첫 정답이 평균 1~2위에 있어야 한다 |
| Precision@5 | ≥ 0.24 | 정답이 평균 1.7개라 상한이 0.34이다. 상한의 약 70% |
| Citation accuracy | ≥ 0.90 | 틀린 인용은 신뢰를 깨는 오류다 |
| Citation recall | ≥ 0.80 | 필요한 근거 5건 중 4건은 답변에 달려야 확인 가능하다 |
| Forbidden citations | **0 of 3** 금지 질문(하드) | 삭제·권한 철회된 원문 인용은 데이터 유출이다. eval에는 `answerable: false` 질문이 3개이다 |
| Answer Groundedness | ≥ 0.90 — **판정 보류** | 채점표(원자적 주장 분해, 판정 기준)가 아직 없다 |

  배경 문서에는 골든 질문의 정답이 들어 있지 않아야 한다(정답 근거가 늘면 Recall이 의미를 잃는다). 배경 문서는 배포처가 합성으로 만들고 만든 방법을 결과에 적는다.
- **지연 분포**: 모든 지연은 p50과 p95를 함께 적는다(평균만 적지 않는다). 질의 수, 워밍업 제외 방식, 반복 횟수를 적는다.
- **LLM 호출 예산**: 호출 횟수(문서당·질문당·일일), Provider 이름과 모델 식별자, 호출 한도 설정, 실패·재시도 횟수. 모델 이름은 결과 보고에만 적고 이 기준표에는 박지 않는다.
- **임베딩 모델과 그 버전**, 엔진·저장소의 고정 버전, 구성 번호(C1~C5), 실행 일시, 사용한 데이터 분할(dev/eval), 데이터셋 commit.
- **미실행·미검증 표시**: 측정하지 못한 칸은 비우지 말고 "미측정"으로 적는다.

## 6. 알려진 한계

- eval이 작다(답변 가능 질문 17개, 연결해야 할 관계 14개, 엔티티 쌍 22개). 그래서 §4의 비율을 개수로 적었고, 소수점 단위 차이는 해석하지 않는다.
- 정답은 생성자(LLM)가 만들었고 **사람의 독립 검토를 받지 않았다.** 원래 eval 12개 인스턴스의 쌍·관계·시간 사실·Insight는 라벨을 보지 않은 두 번째 기계 검토를 한 번 받았지만(`eval/golden/labels/REVIEW_STATUS.md`), 새로 더한 eval 인스턴스 6개와 dev, QA, 엔티티는 받지 않았다. 점수는 "잠정 라벨 기준"이라고 표시한다.
- 제품이 낸 엔티티를 정답 엔티티 id에 대응시키는 정렬(예: 이름·별칭·mention span 비교)은 평가 어댑터가 하며 이 저장소에는 아직 없다. 정렬 규칙과 "라벨에 닿는 예측" 판정(§2.0의 1)은 측정 전에 따로 고정해야 한다.
- 정답은 전수가 아니라 시나리오가 드러내려는 항목만이다. 정밀도 계열 숫자는 라벨에 닿는 예측에 대해서만 말하며, 나머지는 `unjudged` 개수로만 남는다.
- 합성 데이터의 문체는 실제 사내 문서와 다르다. 실제 문서에서의 성능은 배포처 환경에서 별도로 확인한다.
- 사람 평가 지표(§2.2)와 Answer Groundedness는 채점표를 아직 만들지 않았다. 측정 전에 채점표 PR이 필요하며, 그때까지 해당 통과선은 "판정 보류"이다.
- `score.py`가 계산하는 것은 Recall@K, Precision@K, MRR, 관계 precision/recall(`unjudged` 개수 포함), 엔티티 해소 pairwise F1, citation accuracy뿐이다.
